## Symptom
A regular Hermes Desktop chat (any session whose title is NOT the canonical
"Bot Chat") cannot hand work off with an @mention. The user types
`@researcher please review this`; the Desktop composer middleware correctly
identifies the target and tells the agent to "send it with your message_agent
tool … If this session has no message_agent tool, agent messaging is
unavailable here — say so." But a regular session had no message_agent tool
(the backend injected it only into sessions titled "Bot Chat"), so the handoff
failed silently. (See parent DIAGNOSIS_94018.md for the full two-PR root-cause
analysis: #91802 Bot-Chat-only gate + #91915 identification-only middleware.)

## Fix (narrow capability — no global gate removal, no weakened validation)
A session now qualifies for message_agent injection AND dispatch when either:

  (A) it is the canonical "Bot Chat" session on a Bot-Mode-managed install
      (unchanged, as before), OR

  (B) it is a trusted Desktop chat-panel session
      (`agent.platform == "desktop"`) on a Bot-Mode-managed install.

## Why `platform == "desktop"` is the right, narrow signal
The Desktop gateway stamps its chat-panel sessions with platform "desktop"
(tui_gateway._resolve_session_platform: HERMES_DESKTOP=1 without
HERMES_DESKTOP_TERMINAL). Every other source is excluded by construction:
- embedded terminal pane / standalone TUI  -> "tui"
- CLI                                      -> "cli"
- gateway group-room member sessions       -> their platform (e.g. "telegram")
- cron                                     -> "cron"
- kanban workers                           -> "kanban"
- subagents                                -> "subagent"
None equals "desktop", so the capability opens ONLY the trusted Desktop
chat-panel surface the @mention middleware actually drives — the exact surface
described by the issue ("hand work off from any chat"). CLI, TUI, gateway,
group-room, cron, kanban and subagent sessions remain title-gated/fail-closed
identically to before.

## Security properties preserved (unchanged)
- message_agent is still NOT in the global tool registry nor any toolset
  (test_schema_never_in_global_registry).
- Dispatch is still re-gated at execution time (defense in depth).
- Agent still COMPOSES its own message; user text is never forwarded verbatim;
  no renderer/shellout transport is restored.
- Managed-install check and the _bot_mode_protocol config toggle still apply
  to Desktop sessions too.
