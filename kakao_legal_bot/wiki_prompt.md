# RAW → WIKI 작성 규칙

원문(`raw/`) 하나를 읽고 위키 노트(`wiki/`) 하나를 쓴다.
**요약이 아니라 색인 가능한 구조로 다시 쓰는 일**이다. 이 노트가 나중에
검색·인용의 근거가 되므로, 원문에 없는 것을 쓰면 그대로 답변에 섞인다.

## 절대 규칙

1. **원문에 없는 사실을 쓰지 않는다.** 모르면 비워 두고 `[미확인]` 이라고 적는다.
2. **조문 번호와 사건번호는 원문에 적힌 그대로 옮긴다.** 기억으로 고치지 않는다.
3. **날짜는 반드시 적는다.** 없으면 `[미확인]`. 날짜가 없는 노트는 개정 전후를
   가릴 수 없어 검색에서 뒤로 밀린다.
4. 원문의 `[[중요키워드]]` 표시는 **그대로 살린다.** 지우지 않는다.

## frontmatter (반드시 이 형식)

```
---
title: 노트 제목 (그 문서가 무엇에 관한 것인지 한 줄)
kind: 판례 | 법령 | 주석서 | 서적 | 실무편람 | 서식 | 기타
source: raw/…/원문파일.md
collection: cases | commentary | books | practice | forms
written_on: YYYY-MM-DD      # 자료의 작성·발행일 (책·주석서·편람)
effective_on: YYYY-MM-DD    # 법령 시행일 (kind: 법령)
promulgated_on: YYYY-MM-DD  # 공포일
decided_on: YYYY-MM-DD      # 선고일 (kind: 판례)
court: 대법원
case_no: 2017다12345
case_name: 임대차보증금반환
statutes: [민법 제618조, 주택임대차보호법 제3조 제1항]
cases: [2016다212524]
keywords: [임대차보증금, 대항력]
---
```

`statutes` · `cases` · `keywords` 는 비워 두어도 된다 — 빌드가 본문에서
자동으로 뽑아 채운다. 다만 **본문에 없지만 중요한 것**은 직접 적어라.

## 판례를 쓸 때

```markdown
# 대법원 2018. 3. 15. 선고 2017다12345 판결 [[임대차보증금반환]]

## 사건의 개요
당사자를 기준으로 6하원칙으로 적는다. 누가(원고·피고가 누구인지),
언제, 어디서, 무엇을, 어떻게, 왜. 원심까지의 경과도 한 줄.

## 판시사항 (쟁점)
1. 쟁점을 한 문장의 물음으로 적고 **(긍정)** 또는 **(부정)** 으로 법원의
   결론을 붙인다. 예: "임차인의 보증금반환채권과 임대인의 목적물인도청구권이
   동시이행관계에 있는지 (긍정)"
2. 쟁점이 여럿이면 번호를 매겨 각각 (긍정)/(부정) 을 붙인다.
   판단하지 않은 쟁점은 **(판단 없음)** 이라고 적는다.

## 판결 이유 중 중요한 문장
- 원문에서 밑줄이 그어진 문장
- 다른 대법원 판례를 인용하는 문장 (인용된 사건번호를 그대로 옮긴다)
- 법리를 선언하는 문장
> 인용은 원문 그대로. 줄여 쓰지 말고, 줄일 때는 …로 생략을 표시한다.

## 관련 조문
민법 제618조, 같은 법 제536조
```

전원합의체 판결이면 제목에 반드시 **전원합의체**를 적는다.
반대의견·별개의견이 있으면 그 취지를 한 줄로 남긴다.

## 법령을 쓸 때

```markdown
# 민법 제618조 (임대차의 의의)

- 공포: 2022-12-27 / **시행: 2023-06-01**
- 개정 전 조문은 `구 민법 제618조` 로 적고 별도 노트로 둔다.

## 조문
(원문 그대로)

## 하위 조항
- 제1항 …
- 제2항 …

## 관련 조문·판례
```

**조항 번호를 반드시 적는다.** 조·항·호·목까지 원문대로.
개정된 법령이라면 시행일이 언제부터인지가 이 노트의 핵심이다.

## 책·주석서·실무편람을 쓸 때

```markdown
# (소제목) [[핵심키워드]]

## 요지
서너 문장. 이 대목이 무엇을 말하는지.

## 내용
원문의 논리 흐름을 유지하되 압축한다. 인용된 조문·판례는 빠짐없이 옮긴다.

## 인용된 조문·판례
민법 제618조 / 대법원 2017다12345
```

## 서식(서면)을 쓸 때

문서의 **뼈대**(제목 · 당사자 표시 · 청구취지 · 청구원인 · 입증방법 · 첨부)를
항목으로 남기고, 각 항목에 들어가는 내용을 한 줄로 설명한다.
기재례가 있으면 그대로 옮긴다. 기재방식이 바뀐 서식이면 `written_on` 을
반드시 적는다 — 옛 기재례가 새 것 행세를 하면 안 된다.

## 쓰고 나서

```bash
python -m kakao_legal_bot.app.wiki.build index --wiki ./vault/wiki
python -m kakao_legal_bot.app.wiki.build lint  --wiki ./vault/wiki
```

`lint` 가 잡은 것 중 **개정 이후 확인 필요** 와 **내용 대조 필요** 는
사람이 읽어야 판정된다. 그 목록을 받아 두 자료를 대조하고, 다르면
**최신(시행일·발행일) 자료를 기준으로** 오래된 노트에 다음 줄을 남긴다.

```
> ⚠ 이 서술은 YYYY-MM-DD 시행 개정 전 기준이다. 현행은 [[…]] 참조.
```

## 동기화 작업지시서를 받았을 때

`_sync-worklist.jsonl` 은 국가법령 API가 찾아낸 변동과 그로 인해 낡았을 수
있는 자료의 목록이다. 줄마다 `job` 이 둘 중 하나다.

**`job: "wiki"`** — 새로 받아온 법령·판례(`raw`)를 위 규칙대로 위키 노트로 쓴다.
법령이면 `effective_on` 을, 판례면 `decided_on` 을 반드시 적는다.

**`job: "revise"`** — `path` 의 기존 노트가 `statute` 를 다루는데 그 조문이
`effective_on` 에 개정되었고, 이 노트는 `as_of` 자료다. 할 일:

1. 새 조문(`raw/법령/…`)과 그 노트의 서술을 **대조**한다.
2. 달라진 것이 없으면 노트에 `verified: true` 만 남기고 넘어간다.
   **달라지지 않은 것을 고치지 않는다.**
3. 달라졌으면 낡은 서술 바로 위에 다음 줄을 넣는다.

   ```
   > ⚠ YYYY-MM-DD 시행 개정 전 기준이다. 현행: (바뀐 내용 한 줄) — [[새 법령 노트]]
   ```

4. **원래 서술을 지우지 않는다.** 연혁은 "그때는 어땠는가"를 묻는 사건에서
   필요하다. 지우면 그 사건을 못 맡는다.
5. 판단이 서지 않으면 고치지 말고 노트 맨 위에 `> ⚠ 변호사 확인 필요:` 로
   무엇이 걸리는지 한 줄 남긴다. 지어낸 정정이 낡은 서술보다 나쁘다.
