## 1. Lock-before-init correction (`0568e810d`) — VERIFIED

Diff isolated to `gateway/durable_jsonl_consumer.py` (`git diff 479005e8e 0568e810d`, 6 insertions/1 deletion + a matching 3-line test assertion): `inbox = DurableInbox(...)` moved from before `lock_context = (...)` / `with lock_context:` to the first line inside the `with lock_context:` block. Correct shape: a write-mode `DurableInbox.__init__` runs `_init_schema()` (CREATE TABLE IF NOT EXISTS + an `INSERT ... ON CONFLICT DO UPDATE` on `ingress_meta.schema_version`), which is a real write attempt; before this fix that write-mode construction ran unconditionally, before the code found out whether the ordinary consumer's `SingletonLock` (`durable_jsonl_consumer.py:202-231`, non-blocking `flock`) was already held. After the fix, if the lock is held, `SingletonLock.__enter__` raises `ConsumerError` before `DurableInbox(...)` is ever constructed — zero write-mode connection is opened.

**Independent verification (not from author claims or the shipped test alone):** wrote a standalone repro (outside pytest) that seeds the exact fixture state used by `tests/gateway/test_durable_jsonl_consumer.py::_seed_bounded_state`, holds the lock file open in a separate `SingletonLock`, calls `run_bounded_backplay` against the *target commit's* source, and compares the main db file's bytes/mtime and the `-wal` sidecar's bytes before/after. Ran 20 iterations: 20/20 confirm zero byte, mtime, or WAL-size change on the refused path, and the call raises `ConsumerError` as expected each time.

Ran the equivalent repro against the pre-fix source (`479005e8e`, using `git worktree add`) with a `gc.collect()` settle point before the baseline capture: construction happens before the lock in that version, but with GC settled the write is idempotent-enough (SQLite's WAL buffers the write and it isn't checkpointed within the short window) that a naive comparison doesn't always show a difference — this is a property of the *test's* observability, not the fix's correctness. The unambiguous check is code-level: pre-fix, a write-mode connection is opened while a concurrent exclusive holder exists (a second-writer race the lock exists to prevent); post-fix, zero connection of any kind is opened before the lock decision. That structural difference is what was reviewed and is what's fixed.

## 2. Non-blocking finding: `test_bounded_live_refuses_while_ordinary_consumer_holds_lock` is flaky when run in isolation (not a defect in `0568e810d`)

The shipped regression test for this fix (`tests/gateway/test_durable_jsonl_consumer.py:653-675`) asserts `inbox.db_path` bytes+mtime are unchanged after a refused bounded-replay attempt. Running the **full file** as the brief specifies (`pytest -q -n0 tests/gateway/test_durable_jsonl_consumer.py`) passes reliably — 5/5 runs, 21/21 tests each time. But isolating just this test (`-k holds_lock`) on the *target commit* fails ~7/8 times with a byte-level mismatch, and running the same isolated filter against the *pre-fix* commit (`479005e8e`) sometimes reports "1 passed" despite performing the unlocked write the fix exists to prevent.

Root-caused this as a **pytest-invocation-specific artifact, not a regression in the reviewed code**: an out-of-pytest script that mirrors the test's exact sequence (`_seed_bounded_state` → capture bytes → `SingletonLock` held externally → `run_bounded_backplay` → compare bytes) against the target commit passed 20/20 with zero flake (§1 above). The discrepancy only appears under pytest's `-k`-filtered single-test execution, most likely from GC/WAL-checkpoint timing interaction with pytest's import/fixture machinery (not reproduced when the same calls run as a plain script). This means the specific byte-comparison assertion is not currently a reliable regression guard when a future change is checked via an isolated `-k` filter — it can both false-fail on correct code and, per the pre-fix run, false-pass on the exact bug it's meant to catch.

This does not block this review: (a) the code-level correction is independently verified sound via a controlled repro, (b) the exact test invocation the review brief specifies (full file) is reliably green, (c) the flake is a property of test isolation/GC timing, not of `run_bounded_backplay`'s actual write behavior. Recommend a follow-up WB to harden the assertion (e.g., add an explicit `gc.collect()` before the baseline capture, or assert on the `-wal` file too) so it isn't a source of spurious CI noise or a false-pass on a real future regression — filing as a sibling, non-blocking item.
