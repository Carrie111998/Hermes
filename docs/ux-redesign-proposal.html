The diagnosis

The product already knows what it should be

Daily operation runs without per-day approval, but the operator gets a daily plan notification each morning and a results report each evening. […] Supervisors get clean business reports — never technical logs, error dumps, or workflow mechanics. company-packs/silverline/business-rules.md:17–21

That is the right product, written down in your own repo. What shipped is the opposite: a customer-facing run-log viewer, a raw Hermes command unavailable string on the Integrations page, and database enums printed straight into the interface.

The gap isn't craft — the CSS is careful, the accessibility work is real, the component kit is clean. The gap is that the human was made the orchestrator of a seven-stage pipeline nobody showed them. To get one reply today you must know to go: Lead Map → Research → Leads → research each lead → Contacts → Campaigns → Message queue → approve → send.

Verified in code

What's costing you trust right now

01

Every status enum is printed to the user by default. badge() falls back to String(status).replace(/_/g,' '), so the interface says “draft generated”, “draft created”, “do not contact”. This one function is the mechanical root of the system-language problem — and the one-function fix.

server/webui/js/ui.js:105
02

The biggest thing on the dashboard can't do anything. The chat box is read-only by design — its system prompt forbids it from claiming it sent, changed, or ran anything. It looks like an agent you can command. It's a FAQ bot.

server/chat_bridge.py:152–160
03

“Onboarding step 5 of 8” is wrong. Only five of the eight steps are required. You're telling users who have finished that they're 62% done, forever.

server/routes/onboarding.py:22–24 — REQUIRED_STEPS has 5 entries
04

Messages that failed quality checks are invisible. The approval queue's filter chips list five statuses and omit qa_failed — so a message the agent itself doesn't trust appears under no filter but “All”, in neutral grey, looking exactly as calm as a good one.

server/webui/js/pages/outreach.js:119 · STATUS_KIND has no qa_failed entry
05

Six buttons, no primary path. The review modal offers Save, Regenerate, Approve, Create draft, Send now, and Mark replied at equal weight. “Send now” then toasts “Message marked sent.” A user cannot tell what any of them will do.

server/webui/js/pages/_page-utils.js:143–159
06

Every score reads 0. The band maths treats an unscored lead as a low-scoring one, so twenty-five companies are presented as uniformly worthless.

server/webui/js/ui.js:110–114 · pages/leads.js:122
07

Two scoring systems argue on one card. Lead detail shows evidence-based fit_score and evidence_confidence directly beside the legacy score, band, and factor bars. Two parallel discovery systems are both in the nav — Research sits empty while Leads holds 25 — with nothing explaining the relationship.

server/webui/js/pages/leads.js:210–240
08

The pipeline is exposed as buttons. Lead detail's action row is Research → Find contacts → Generate email, to be clicked by hand, per company, twenty-five times. Starting any of them offers a “Watch” toast that navigates the customer into the run-log viewer.

server/webui/js/pages/leads.js:185, 311
09

The daily job is three clicks deep. Approving six emails — the entire reason to open the app — lives behind Campaigns → Message queue tab → row → modal.

server/webui/js/pages/outreach.js:39–47
The four screens

What replaces them

Same stack — vanilla ES modules, no build step, no React. These reuse the existing component kit in ui.js rather than introducing a parallel layer.

  • Approve never means send. The button states its outcome — “saves a draft in your mailbox” or “Approve and send” — because the default mode is draft.
  • Editing nulls the approval server-side, so Edit is inline and its save button reads “Save and approve”. One action, no trap.
  • QA-failed messages join the queue and explain themselves: “I wrote this one but I don't trust it — the subject line doesn't match your standard subject.”
  • The send gate fails closed outside working hours. That becomes a sentence, not an error: “Approved. I'll send this at 09:00 Dubai time — it's outside their hours now.”
  • Keyboard: A approve, E edit, S skip. Six in ninety seconds.

Build order

Every phase ships on its own

Phases 0–5 are frontend-only and run on today's backend. The scheduler is a parallel track — nothing waits on it.

Parallel

Scheduler — backend

A per-tenant daily job, a digest table, a since filter on the activity feed, and an emailed report. Until it ships, “the agent worked overnight” is not true and the UI must not say it — Phase 2's degraded state is the honest one.

~1 week
Scope

What this is not

  • No React, no build step, no touching web/src
  • No i18n — the interface stays English
  • No change to the 216-route API contract; the frontend adapts
  • No design-token overhaul — tokens.css stays exactly as it is
  • Not deleting the evidence-first research subsystem — it moves behind admin
  • No WhatsApp or LinkedIn feature work
  • No admin redesign beyond receiving the three demoted pages

Roughly 1,700 lines of page code get deleted, and nothing a user can do today becomes impossible.

Simplicity here isn't hiding features behind menus. It's that the deep structure of this product is one sentence — the agent finds buyers and writes to them; the human decides — and the interface should be shaped like that sentence.
