Service Mesh / Internal mTLS / Egress

在内部服务之间提供 mTLS、服务身份、授权策略和受控 egress gateway，支撑 TokenRouter/Job Manager/worker 的零信任通信。

结论
Istio 是该模块的主选型。Hermes 需要明确区分服务身份、用户身份和 sandbox token。Istio 的 mTLS、AuthorizationPolicy、egress gateway 能把服务到服务通信也纳入策略边界。

为什么选它

  • Hermes 需要明确区分服务身份、用户身份和 sandbox token。Istio 的 mTLS、AuthorizationPolicy、egress gateway 能把服务到服务通信也纳入策略边界。
  • Envoy Gateway 已经在入口使用 Envoy，Istio 数据面同样基于 Envoy，便于统一观测和策略思路。
  • Linkerd 更轻，但复杂 egress、ext_authz 和细粒度授权场景不如 Istio 完整。

候选方案对比

候选优势为什么不是主选
Linkerd简单、轻量、mTLS 易用复杂 egress gateway、Envoy 过滤器生态和策略扩展性较弱

no mesh / library mTLS少一层复杂度服务身份、默认拒绝、egress 统一治理会散落在应用里

Hermes 落地设计

  1. 控制面 namespace 启用 strict mTLS；TokenRouter、Job Manager、Volume Mounter、Asset Service 只接受 mesh identity。
  2. 所有外部 provider/API 流量必须经 egress gateway 或 TokenRouter；sandbox namespace 默认无直接 internet egress。
  3. AuthorizationPolicy 限制服务调用方向，例如 GPU worker 可以回调 Job Manager，但不能调用 OpenBao。
  4. Service mesh 不承载用户授权最终决策；用户/tenant/tool 决策仍由 OPA/TokenRouter 完成。

实施规划

  1. MVP：仅控制面服务启用 Istio mTLS，不把 sandbox 先放进 mesh。
  2. 第二阶段：egress gateway + allowlist + provider endpoint audit。
  3. 第三阶段：namespace default-deny、workload identity policy、mesh chaos tests。

验收标准

  • 未注入 mesh identity 的服务不能调用 TokenRouter。
  • Worker 不能直接访问 OpenBao 或数据库。
  • 外部 egress 目标不在 allowlist 时被网格拒绝并记录。
