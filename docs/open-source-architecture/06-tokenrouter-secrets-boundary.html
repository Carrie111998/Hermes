结论
Custom TokenRouter backed by OpenBao 是该模块的主选型。Hermes 的 TokenRouter 不只是 secrets lookup，它要执行 plan、scope、asset ACL、model allowlist、concurrency、redaction 和 audit。这个业务逻辑必须自研。

为什么选它

  • Hermes 的 TokenRouter 不只是 secrets lookup，它要执行 plan、scope、asset ACL、model allowlist、concurrency、redaction 和 audit。这个业务逻辑必须自研。
  • OpenBao 适合作为开源 secrets 基座：支持 auth methods、secrets engines、Kubernetes/JWT auth、审计设备和 transit 加密。
  • 相比直接用 Kubernetes Secret 或云 Secret Manager，OpenBao 更容易保持云无关和统一审计；相比 HashiCorp Vault，OpenBao 的开源治理/许可证风险更可控。

候选方案对比

候选优势为什么不是主选
HashiCorp Vault成熟度高、生态大许可证和开源治理不符合“纯开源优先”的目标
Kubernetes Secrets only简单，内建不能承担 provider key 池、动态凭证、审计和细粒度访问边界
Cloud Secret Manager云厂商托管，运维少不满足开源/云无关要求；多云迁移和本地测试割裂

Hermes 落地设计

  1. OpenBao 存 provider key、KMS/transit key、connector secrets；TokenRouter 通过 Kubernetes/JWT auth 拿最小权限 token。
  2. Sandbox 只持有 `HF_JWT_TOKEN`，TokenRouter 验签和 OPA 决策后，用 OpenBao 取真实上游凭证或生成短期凭证。
  3. TokenRouter 永不把真实 key 返回 sandbox；只执行上游调用、创建 job，或返回一次性 scoped URL。
  4. 所有 key read、token exchange、deny、upstream call result 都写 audit_events；敏感值只存 HMAC/摘要。

实施规划

  1. MVP：静态 provider key 存 OpenBao KV，TokenRouter scope+plan 校验。
  2. 第二阶段：provider key pool、region fallback、circuit breaker、per-tenant budget。
  3. 第三阶段：动态凭证、transit 加密、break-glass 审计流程。

验收标准

  • Sandbox 环境变量和文件系统中不存在真实 provider key。
  • 过期 `HF_JWT_TOKEN` 被 TokenRouter 拒绝。
  • OpenBao audit 中能查到每次 TokenRouter secrets access。
