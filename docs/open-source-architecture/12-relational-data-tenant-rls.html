结论
PostgreSQL with Row Level Security 是该模块的主选型。Hermes 控制面是典型关系模型：租户、成员、项目、会话、工具调用、用量、审计都需要事务和约束。PostgreSQL 是最稳妥的开源选择。

为什么选它

  • Hermes 控制面是典型关系模型：租户、成员、项目、会话、工具调用、用量、审计都需要事务和约束。PostgreSQL 是最稳妥的开源选择。
  • Row Level Security 可以把 tenant isolation 下沉到数据库层，作为应用层过滤之外的第二道防线。
  • JSONB 可承载 payload/result/acl 等半结构化字段，但主授权字段必须结构化列化，便于索引和 RLS 策略。

候选方案对比

候选优势为什么不是主选
MySQL成熟，团队常见缺少 PostgreSQL RLS 这种强内建租户隔离机制
CockroachDB分布式 SQL，多区域强复杂度和成本更高；早期不应先承担分布式数据库语义
MongoDB/DynamoDB文档/高扩展方便复杂事务、审计查询、RLS 类隔离需要更多应用层自研

Hermes 落地设计

  1. 所有 tenant-scoped 表必须有 tenant_id；workspace/project/session 相关表还要有 workspace_id/project_id/session_id。
  2. 每个请求进入 DB transaction 前设置 `app.current_tenant_id`、`app.current_workspace_id` 等 session variables；RLS policy 引用这些值。
  3. DB owner/superuser 连接只用于迁移；应用 runtime 使用受限 role，强制 RLS。
  4. Audit 表 append-only；删除用户数据走 tombstone/anonymization，不直接破坏审计链。

实施规划

  1. MVP：核心表 + tenant_id composite index + app-level filters。
  2. 第二阶段：启用 RLS policy 和 CI isolation tests。
  3. 第三阶段：审计归档分区、只读 replica、data residency 分库策略。

验收标准

  • 没有设置 tenant session variable 时查询返回 0 行或报错。
  • Tenant A 的 DB role 无法 select Tenant B 行。
  • 所有新增表 CI 检查必须包含 tenant_id 或显式标记 global table。
