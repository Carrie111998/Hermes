结论
NATS JetStream 是该模块的主选型。Hermes 需要低延迟事件推送和短期持久化回放，而不是只要一个重型日志管道。NATS JetStream 同时提供 pub/sub、stream、durable consumer 和 at-least-once delivery。

为什么选它

  • Hermes 需要低延迟事件推送和短期持久化回放，而不是只要一个重型日志管道。NATS JetStream 同时提供 pub/sub、stream、durable consumer 和 at-least-once delivery。
  • 相比 Kafka，NATS 运维轻、延迟低，更适合 session fanout 和控制面事件；相比 Redis Streams，NATS 的 subject/ACL/cluster 模型更适合多服务消息总线。
  • 它和 Temporal 分工清楚：Temporal 负责 durable workflow truth，NATS 负责事件广播和可短期回放的用户体验流。

候选方案对比

候选优势为什么不是主选
Kafka/Redpanda吞吐极高，生态强对 session fanout 和控制消息偏重；运维与容量规划成本更高
RabbitMQ传统队列成熟stream replay、subject routing 和轻量 request/reply 不如 NATS 贴合
Redis Streams/PubSub部署简单多租户 ACL、持久化语义和大规模 stream 运维边界较弱

Hermes 落地设计

  1. Subject 命名必须包含作用域：`tenant.<tid>.workspace.<wid>.session.<sid>.events`，内部服务使用 service account ACL。
  2. 前端不能直接连接 NATS；Edge/Realtime Fanout Service 订阅授权 subject 后转 SSE/WebSocket。
  3. Job worker 发布 progress event，Job Manager/Temporal 仍负责最终状态写入。
  4. JetStream retention 按事件类型配置：session events 短保留，audit 不走 NATS 作为唯一存储。

实施规划

  1. MVP：session events stream + fanout service。
  2. 第二阶段：worker heartbeat、job progress、dead-letter stream。
  3. 第三阶段：per-tenant event quotas、backpressure、consumer lag alerts。

验收标准

  • 无授权 fanout 服务不能订阅跨 tenant wildcard。
  • SSE reconnect 能从 last_event_id 后补短期事件。
  • JetStream consumer lag 会触发告警而不是静默丢状态。
