总览下一项
结论
Envoy Gateway + Envoy Proxy 是该模块的主选型。Hermes 的入口层需要同时处理普通 HTTP、SSE、WebSocket、长连接空闲超时、租户级限流和策略外调，Envoy 的过滤器模型和 Envoy Gateway 的 Gateway API 扩展正好覆盖这些边界。

为什么选它

  • Hermes 的入口层需要同时处理普通 HTTP、SSE、WebSocket、长连接空闲超时、租户级限流和策略外调，Envoy 的过滤器模型和 Envoy Gateway 的 Gateway API 扩展正好覆盖这些边界。
  • Envoy Gateway 原生支持 SecurityPolicy、external authorization 和本地/全局限流，便于把 JWT claim、tenant_id、workspace_id 和 plan 转成统一的控制面决策输入。
  • 相比功能型 API 网关，Envoy 更适合做后续 service mesh、OPA ext_authz、TokenRouter、egress gateway 的共同代理基础。

Hermes 落地设计

  1. 部署两个入口 GatewayClass：`public-hermes` 处理用户流量，`internal-hermes` 处理控制面内部入口。
  2. 所有用户请求先通过 JWT SecurityPolicy；JWT 的 `sub`、`tenant_id`、`workspace_id`、`plan` 通过受信 header 传给 Session Service，外部请求不得直接提交这些 header。
  3. 对 `/sessions/:id/events` 使用 SSE 长连接配置，按 `session_id` 做一致性哈希或 sticky routing，避免事件流在扩缩容时抖动。
  4. 把 `ext_authz` 指向 OPA/Policy Adapter，由它判断 session stream 订阅、workspace membership、plan rate limit 和工具入口权限。
  5. Edge 只做身份和路由，不读取用户文件，不持有 provider key，不直接创建 GPU job。

实施规划

  1. 先接入 JWT 校验、请求体大小限制、SSE idle timeout 和 `/healthz`。
  2. 第二步启用 per-route local rate limit；接入 Redis-backed global rate limit。
  3. 第三步启用 ext_authz，把 session subscribe、tool preflight 和 tenant plan 都统一到 OPA 决策。

验收标准

  • Tenant A 的 stream token 不能订阅 Tenant B 的 SSE。
  • JWT 缺少 tenant/workspace claim 时返回 401/403。
  • 超过 plan 的请求被限流而不是进入后端队列。
  • WebSocket/SSE 断线重连不会跨 session 泄露事件。
