结论
Kueue + NVIDIA GPU Operator 是该模块的主选型。Hermes 的 supercomputer 本质是多租户 GPU batch fabric：要按 plan/tenant 控制 queue、quota、priority、concurrency 和抢占。Kueue 是 Kubernetes-native 的 job queueing 方案，贴合这个模型。

为什么选它

  • Hermes 的 supercomputer 本质是多租户 GPU batch fabric：要按 plan/tenant 控制 queue、quota、priority、concurrency 和抢占。Kueue 是 Kubernetes-native 的 job queueing 方案，贴合这个模型。
  • NVIDIA GPU Operator 把 driver、container toolkit、device plugin、DCGM exporter 等 GPU 节点基础设施自动化，减少手工节点漂移。
  • 相比 Slurm，Kueue 更适合和现有 K8s control plane、namespace、quota、GitOps、GPU worker deployment 整合。

候选方案对比

候选优势为什么不是主选
SlurmHPC 调度成熟，GPU 集群经验丰富和 K8s SaaS 控制面、per-tenant web workload、GitOps 的集成成本高
Volcano批调度能力强生态和 SIG Scheduling/Kueue 的 K8s 原生 Job API 方向需要权衡
Ray/KubeRay分布式 Python/ML 任务强更像计算框架；不应替代租户 quota/admission 的底层调度层

Hermes 落地设计

  1. 每个 plan 或 tenant tier 映射到 LocalQueue；ClusterQueue 定义 GPU/CPU/memory quota、cohort borrowing 和 preemption 策略。
  2. Job Manager 只创建受控 Job/Workload，不让 sandbox 直接提交 Kubernetes Job。
  3. GPU worker 启动后从 Job Manager 获取 lease 和 input manifest，只能写 assigned output_prefix。
  4. GPU Operator 管理节点 GPU 栈，DCGM metrics 进入 OpenTelemetry/Grafana。

实施规划

  1. MVP：单 GPU node pool + Kueue LocalQueue + one model worker。
  2. 第二阶段：按 model/profile 分队列，MIG/whole GPU 策略，spot/on-demand 分层。
  3. 第三阶段：tenant fairness、preemption、multi-region queue admission。

验收标准

  • 超过 tenant GPU quota 的 job 等待而不是直接创建 pod。
  • Worker 无法写 assigned output_prefix 之外的对象。
  • GPU node 驱动/device plugin 版本漂移能被 operator/observability 捕获。
