结论
Open Policy Agent (OPA) 是该模块的主选型。Hermes 的安全边界很多，不能把权限判断散落在每个服务里。OPA 可以用同一种 policy bundle 驱动 Envoy ext_authz、Kubernetes admission 和业务服务 sidecar/SDK。

为什么选它

  • Hermes 的安全边界很多，不能把权限判断散落在每个服务里。OPA 可以用同一种 policy bundle 驱动 Envoy ext_authz、Kubernetes admission 和业务服务 sidecar/SDK。
  • OPA 的 Rego 适合表达 asset ACL、tool scope、mount policy、tenant plan、egress allowlist 这类结构化策略。
  • 相比只在应用里写 if/else，OPA policy 可以版本化、审计、回放测试，并在 CI 中做策略单元测试。

候选方案对比

候选优势为什么不是主选
Cedar权限语言清晰，适合应用授权Envoy/K8s/sidecar 生态没有 OPA 广；需要更多自研集成
Casbin轻量，嵌入应用简单跨网关、K8s admission、bundle 分发和决策审计不如 OPA
OpenFGA关系授权强适合 Zanzibar 风格关系图，不适合作为所有 tool/egress/mount 的通用 PDP

Hermes 落地设计

  1. 建立 `policy-bundles/hermes` 仓库，按 `edge.rego`、`tokenrouter.rego`、`mount.rego`、`egress.rego`、`skill_exfil.rego` 拆分。
  2. 所有策略输入必须包含 identity tuple：tenant_id、workspace_id、project_id、session_id、user_id、run_id、tool_call_id。
  3. OPA 返回 `{allow, reason, redactions, limits}`，业务服务只能执行明确 allow；缺字段、未知工具、未知模型全部默认 deny。
  4. 策略发布走 GitOps，生产 OPA 只拉签名 bundle，不从运行时写入策略。

实施规划

  1. 先做 TokenRouter 和 Volume Mounter 的库内 OPA evaluate。
  2. 再接 Edge ext_authz，把会话订阅、API route 和 plan 限流的决策统一。
  3. 最后加 Kubernetes admission，阻止未声明 RuntimeClass、hostPath、privileged、metadata egress 的 sandbox pod。

验收标准

  • 策略 bundle 缺失时所有敏感操作默认拒绝。
  • 每个 deny 都有短 reason，但不暴露内部规则细节。
  • OPA 单测覆盖所有 acceptance criteria 的 allow/deny 路径。
