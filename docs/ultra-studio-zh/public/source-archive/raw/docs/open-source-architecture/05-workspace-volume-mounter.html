Workspace Volume Mounter / POSIX Data Isolation

把 tenant/workspace/project/session 的文件、memory、outputs 以 POSIX 文件系统形式挂进 sandbox，同时让底层容量和生命周期走对象存储。

结论
JuiceFS CSI backed by object storage 是该模块的主选型。Agent 和工具天然按文件系统工作，需要 POSIX 语义、目录遍历、临时输出和原子文件写入；直接 S3 API 会让工具改造成本高。

为什么选它

  • Agent 和工具天然按文件系统工作，需要 POSIX 语义、目录遍历、临时输出和原子文件写入；直接 S3 API 会让工具改造成本高。
  • JuiceFS 把元数据和对象数据分离，适合用对象存储承载大规模媒体/文件，同时通过 CSI 给 sandbox pod 挂载。
  • 相比共享 NFS，JuiceFS 更适合弹性容量和云对象存储；相比直接 CephFS，后续迁移到云 S3/R2/GCS 更灵活。

候选方案对比

候选优势为什么不是主选
CephFS CSI强 POSIX，一体化存储，适合自建 Rook-Ceph和底层 Ceph 强绑定；跨云对象存储迁移没有 JuiceFS 灵活
NFS/EFS成熟简单租户隔离、审计、弹性缓存和大规模小文件/媒体混合负载要额外治理
direct object storage only权限边界清晰，成本低不适配大部分 agent/tool 的文件工作流，需要大量工具重写

Hermes 落地设计

  1. Volume Mounter 是控制面服务，不让 agent 直接指定挂载源；agent 只能请求抽象 path set：`.memories`、`files`、`outputs`、`AGENTS.md`、`project.md`。
  2. Mounter 调 OPA 判断 requested_paths，再创建/绑定 CSI volume 或 subPath，挂载到 `/workspace`。
  3. 每个 project 有独立 namespace/prefix；session outputs 可以写，AGENTS.md/project.md 默认只读，skill internals 永不挂进 sandbox。
  4. 对 bulk read/export 走 egress filter，不靠文件系统权限单独兜底。

实施规划

  1. MVP：project 级 JuiceFS volume，session 输出目录隔离。
  2. 第二阶段：per-session snapshot/restore，失败 job 输出自动归档。
  3. 第三阶段：冷热缓存、文件 lineage、对象生命周期策略和租户加密上下文。

验收标准

  • 请求未授权路径时 mount policy 返回 deny。
  • Sandbox 内没有 skill `references/*` 和 provider credentials。
  • Tenant A project volume 无法由 Tenant B session mount。
