结论
Rook-Ceph RGW for production; MinIO only for dev/small private deployments 是该模块的主选型。生产级开源存储需要对象、块、文件多模式能力和 Kubernetes operator 治理；Rook-Ceph 同时提供 CephFS、RBD 和 RGW/S3，适合 Hermes 的 mixed storage plane。

为什么选它

  • 生产级开源存储需要对象、块、文件多模式能力和 Kubernetes operator 治理；Rook-Ceph 同时提供 CephFS、RBD 和 RGW/S3，适合 Hermes 的 mixed storage plane。
  • Ceph RGW 有 S3/Swift 接口、用户/桶/tenant 概念，和多租户媒体资产模型更贴近。
  • MinIO 非常适合开发和简单私有云，但当前许可证与商业云产品的合规边界要谨慎；因此不作为默认生产基座。

候选方案对比

候选优势为什么不是主选
MinIO简单、高性能、S3 兼容，AI 场景常见AGPL/商业许可边界需要法务确认；只做对象存储，不覆盖块/文件一体化

Hermes 落地设计

  1. 对象 key 统一前缀：`tenant/<tid>/workspace/<wid>/project/<pid>/{uploads,generated,jobs,thumbnails,manifests}`。
  2. Job Manager 生成 output_prefix，worker 只拿 scoped write credential 或代理写入，不接受 worker 自报目标路径。
  3. Asset ID 是授权对象，object key 只是存储定位；任何下载/预览都要通过 Asset Service 签发短期 URL。
  4. Rook-Ceph 提供 RGW；JuiceFS 可把 RGW 或云对象存储作为数据 backend。

实施规划

  1. MVP：dev 用 MinIO 或云 S3；接口按 S3-compatible 设计。
  2. 生产自托管：部署 Rook-Ceph RGW，开启 bucket lifecycle、versioning/retention 策略。
  3. 高级阶段：per-tenant encryption context、多区域复制、asset lineage manifest。

验收标准

  • Tenant A 的 scoped credential 不能列出 Tenant B prefix。
  • Worker 传入任意 output_prefix 会被 Job Manager 覆盖或拒绝。
  • 删除 asset 不破坏审计 manifest 和 usage record。
