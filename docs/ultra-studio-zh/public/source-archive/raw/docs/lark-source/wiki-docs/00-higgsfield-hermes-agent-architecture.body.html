1. 一页结论

Higgsfield Supercomputer 可以拆成四层来看：基础前后端设计、基础设施、Agent 层、高级设施。

这套系统的核心不是“一个 Agent 进程”，而是一个多租户实时会话系统：前端建立流式会话，边缘网关完成身份和套餐鉴权，后端按需挂接 Sandbox，Agent 在隔离环境中调用工具，TokenRouter 负责凭证交换和配额控制，GPU 生成任务进入异步队列，由后端渲染集群消费。

当前材料里已经明确的主链路是：

  1. Web 通过 Vercel AI SDK 建立 SSE 或 WebSocket 会话。
  2. Edge Gateway 用 JWT 解析用户、Workspace 和订阅计划。
  3. Sandbox VM 按需冷启动或热挂接。
  4. Volume Mounter 挂载用户数据、.memories/、AGENTS.md、project.md。
  5. Hermes 注入短生命周期 HF_JWT_TOKEN。
  6. Hermes Agent 通过默认工具、Skill 和 Higgsfield 工具完成任务。
  7. TokenRouter 负责 token 交换、鉴权、审计、并发槽和上游 API 路由。
  8. 视频、图像、音频等重任务通过异步队列交给 GPU Render Workers。

本期不建设或的能力是：

  • CometAPI 媒体专用网关。❌
  • 多路异步生成核心与异构算力调度链。❌
  • Boost Speed 并发提升。❌
  • Reusable Media & Zero-Upload caching。❌
  • higgsfield_soul_id。❌

4. 核心组件分析

4.1 Web & Backend Gateway

前端通过 Vercel AI SDK 建立基于 Data Stream Protocol 的 SSE（Server-Sent Events）或 WebSocket 连接。

边缘网关截获该连接，通过 JWT 解密出用户的身份权限、Workspace 权限以及当前的订阅计划（Pluses / Pro 限制）。

Web 层负责：

  • 建立实时会话连接。
  • 承载 Agent 的流式输出。
  • 展示工具调用、生成任务、媒体结果和错误状态。
  • 把用户身份、Workspace、项目和订阅计划传递给后端网关。

后端入口负责：

  • 验证 JWT。
  • 判断 Workspace 权限。
  • 判断订阅计划限制。
  • 决定是否启动或挂接 Sandbox。
  • 向 Agent 运行时传递当前会话上下文。

4.2 Sandbox VM & Volume Mounter

系统不会为所有用户维持一个常驻的重量级虚拟机，而是采用即时冷启动 / 热挂接（On-Demand Provisioning）的轻量级 Linux 隔离沙箱。

每个沙箱拥有自己独立的临时文件系统（RootFS）。

启动时，存储卷挂载服务（Volume Mounter）会将该用户专属的持久化数据、历史记忆（.memories/）以及项目配置文件（AGENTS.md、project.md）挂载到沙箱的特定工作目录下。

在容器跑起来的同时，编排层会把临时的、具有生命周期约束的 HF_JWT_TOKEN 写入该沙箱的环境变量中。

4.3 多用户隔离与零信任安全边界

为了保障多用户并发时的绝对安全，系统在架构设计上实行物理与逻辑解耦。

每个用户的 Sandbox 运行在相互隔离的运行时：

  • 不同的用户属于不同的 Linux 命名空间（Namespaces）与控制组（Cgroups）。
  • 在沙箱中执行的任何终端命令（terminal，如编译、运行 Python 进程），其计算和内存消耗都被严格限制在当前 Cgroup 中，绝无可能越界访问或探知其他用户的内存。

Agent 即使被注入了解析工具，运行时也对任何云服务商的 Master Key 完全脱敏。

Agent 与底层基础设施（如 GPU 集群、存储桶、Gemini 官方 API）的每一次交互，都必须携带沙箱特有的 JWT 穿透 TokenRouter。

TokenRouter 会在边缘进行权限鉴别、审计并动态替换为真实密钥。

4.4 TokenRouter ✅

TokenRouter 用来交换 token，保证 token 不被盗。

Agent 通过 token 和本地服务交互，即使 Agent 的 token 被盗，也不会出现真实密钥泄露问题，外界也无法直接访问本地服务器。

4.5 Hermes Agent Runtime

Agent 的大脑，即 LLM 的推理步骤，是无状态的。

Agent 本身不需要消耗高昂的 GPU 硬件进行持续计算，它只是一个“推理-工具调用”的事件循环。

当 Agent 等待工具反馈（如等待一分钟的视频渲染或复杂的网页抓取）时，沙箱进程会进入非阻塞的挂起状态，甚至在特定的冷闲置期允许快照置换，释放 CPU 及内存。

这意味着大量 Agent 推理进程可以在高密宿主机上被调度。

Agent Runtime 主要依赖三类能力：

4.6 Generation Fabric

最消耗资源的是视频与图像生成，例如运行 seedance_2_0 或 veo-3-1。

当 Agent 调用 higgsfield_generate 提交批量渲染请求时，接口以非阻塞异步（async=true）方式提交。

任务会被瞬间压入底层的分布式消息队列，例如 Redis Streams / Kafka 架构。

真正的耗能大户 GPU 渲染集群（或者第三方API）作为消费者，从队列中按优先级拉取任务进行多节点分布式渲染。

这种控制流与数据流的彻底分离，确保不管有多少用户同时生成视频，Agent 自身的交互界面不会卡死。

6. 高级设施分析

6.1 动态并发削峰与限制（Concurrency Clamping Layer）

为了防止少数用户恶意刷单导致集群瘫痪，TokenRouter 在网关层实现严格的令牌桶限流和基于套餐的并发槽控制（Concurrency Slots）。

系统会向下游 Agent 传递当前的并发限制，例如：

  • text2image_concurrent_jobs: 8

如果用户突然发起 100 张图片的批量生成，Agent 的运行时检测到并发槽已满，会自动在内部将任务切分为符合限额的微批次（Batch Chunking）。

这些任务会以流水线串行 / 小并发方式自动分发并轮询，而不会盲目向后端倾泻流量，从而在协议端实现平噪。

6.2 上游 API 负载均衡（Multimodal Gateway Balancing）

Gemini、Claude 等模型有严格的上游 Rate Limit 限制。

TokenRouter 后台会动态维护一组极大的 API Key 资源池。

在调用 Gemini API 时，网关会自动在多个企业级 Vertex 接口、不同可用区之间进行毫秒级的轮询（Round-Robin）与熔断降级。

即使某一个云服务商的可用区发生网络抖动，TokenRouter 也能实现无感知的热切换，确保高并发下的整体可用性。

6.3 CometAPI：媒体 API 网关 ❌

CometAPI 是专为多模态 / 大二进制流设计的媒体 API 网关。

标准 API 网关在面对动辄几十甚至数百兆的视频、音频二进制数据时，容易遇到序列化瓶颈、吞吐量受限和连接超时等问题。

因此，CometAPI 被设计为媒体专用网关。

6.5 重复媒体解耦与特征重用缓存 ❌

Reusable Media & Zero-Upload caching 用于解决多阶段、批量视频生成中的重复上传问题。

在 12-Shot Storyboard 到 Clip 的串联场景中，频繁上传几十兆的输入图像或过渡片段会引发严重吞吐延迟。

该能力目标是：

  • 降低重复上传。
  • 重用媒体特征。
  • 降低多阶段生成延迟。
  • 支持批量视频生产链路。
