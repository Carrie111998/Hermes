# kanban-cleanup-operator — Destructive DB Operator with Operator-in-the-Loop

This skill is a **companion to `kanban-worker`** and is bound to the
`cleanup-operator` profile. It defines the worker-side sequence for
destructive DB operations on the live trading system:

```
  builder (implements)  ->  tester (verifies)  ->  cleanup-operator (operates)  ->  release-ci
                                                  |
                                                  +-- Telegram-confirm, then --apply-confirm
```

The skill exists because the trading-bot has an **Iron-Law DB-Write-vor-Review
verboten** rule: no production DB write may happen before a human
reviewer has approved it. Builders can implement, code-review, and dry-run
the change, but they may **NOT** run the actual `apply` step. That step
belongs to this profile, with a mandatory operator confirmation gate.

## Why this profile exists (architecture)

The issue #139 fix has three parts:

- **#139-A** (PR #140, merged) — added the `--apply-confirm=<token>`
  mechanism in the cleanup scripts. The token is generated by the
  operator, written to a short-lived file, and required as the literal
  argument. Without the token the script exits non-zero with a clear
  "missing token" error.
- **#139-B** (this skill + the dispatcher gate) — adds the worker profile
  and the workflow constraint that only `cleanup-operator` can run
  `--apply` / `--apply-confirm`. The dispatcher refuses to spawn a
  `cleanup-operator` task whose body lacks an
  `apply_confirm_token_prefix:` field (see
  `tests/hermes_cli/test_kanban_cleanup_operator.py`).
- **#139-C** (future) — hardens builder/tester profiles to refuse
  `--apply` flags entirely. Out of scope here; this skill is the
  matching "the right way" half of the split.

## Iron Laws (NEVER violate)

1. **Never run `--apply` or `--apply-confirm` without first showing the
   operator the dry-run output and getting a Telegram / kanban-comment
   confirmation reply.** The Telegram confirm must include the token
   prefix (first 8 chars) and a short recon-snapshot (row counts,
   table list). The operator replies `<prefix> confirm` to authorise
   the apply, `<prefix> cancel` to abort.
2. **Never read or echo the full token.** The token is short-lived
   (default 1h) and meant to be passed exactly once. The operator pastes
   the token into the confirmation message; you echo the prefix only.
3. **Never run `--apply` on the live trading DB without a fresh
   recon-snapshot taken less than 60 seconds before the apply.** If the
   snapshot is older, re-run the recon step — the snapshot is the
   "before" half of the verify-after-apply loop, and an old snapshot
   defeats the audit trail.
4. **If the verify-after-apply step fails, immediately roll back to the
   pre-apply snapshot and exit 1.** Do not retry the apply. A second
   apply on a half-modified DB is the canonical way to corrupt the
   trading state.
5. **This profile may NOT use the gateway auto-dispatch path for
   destructive steps.** Use the standard spawn from the dispatcher
   (the `apply_confirm_token_prefix` field in the body is the
   dispatcher-side gate), but the `apply` step itself is always
   manual-invocation by the operator after the Telegram reply lands.

## Workflow — the canonical 4-step sequence

This is the sequence the skill MUST run. Each step is mandatory; the
failure modes below name the exit code and recovery path.

### Step 1 — Dry-Run (READ-ONLY, always safe)

The dry-run produces a `recon-snapshot` and a `apply-preview`. The
output goes into the task body and into the operator's Telegram
channel.

```bash
# Find the cleanup script the builder produced. Common locations:
SCRIPT=$(ls scripts/cleanup_*.py | head -1)
[ -z "$SCRIPT" ] && { echo "no cleanup script found"; exit 70; }

# Run the dry-run. Most cleanup scripts accept --dry-run as the only
# flag; some also accept --recon-snapshot=/path/to/snapshot.json.
python3 "$SCRIPT" --dry-run --recon-snapshot=/tmp/recon-snapshot.json

# Capture the apply-token (first 32 hex chars on a line by itself):
TOKEN=$(python3 "$SCRIPT" --dry-run 2>&1 | grep -E '^apply-token:' | awk '{print $2}')
[ -z "$TOKEN" ] && { echo "dry-run produced no token"; exit 71; }
TOKEN_PREFIX=$(echo -n "$TOKEN" | cut -c1-8)
```

Then embed the snapshot + the prefix in the task body via the
`kanban_comment` tool, so the operator can verify the recon snapshot
without leaving the board:

```python
kanban_comment(
    task_id=TASK_ID,
    body=(
        "Dry-run summary (step 1 of 4):\n\n"
        "<include the dry-run stdout here, with row counts and the "
        "table list>\n\n"
        f"apply-token-prefix: {TOKEN_PREFIX}\n"
        "Waiting for operator Telegram reply: '<prefix> confirm' OR "
        "'<prefix> cancel'."
    ),
)
```

### Step 2 — Operator Telegram / kanban-comment confirmation

Post the snapshot to the operator's Telegram chat AND wait for the
reply. The reply must be one of:

- `<prefix> confirm` — authorise the apply
- `<prefix> cancel` — abort (exit 130, task -> blocked, reason "operator cancelled")

Free-form chat is NEVER interpreted as a confirmation. If the operator
types something else, log the message and keep waiting.

**Default timeout:** 5 minutes (overridable via
`APPLY_CONFIRM_TIMEOUT_SECONDS`). On timeout: exit 77, task -> blocked,
reason "no operator reply within timeout window".

### Step 3 -- --apply-confirm=<token>

ONLY after a `<prefix> confirm` reply has landed, run the apply step
with the full token:

```bash
python3 "$SCRIPT" --apply-confirm="$TOKEN" \
    --recon-snapshot=/tmp/recon-snapshot.json
```

The script validates the token against the file before touching the DB
(see Iron-Law #1 in `scripts/cleanup_999010_999011.py` from PR #140).
On token mismatch / missing file: exit 77, no DB write, no APPLIED
audit row. On success: APPLIED row in the audit log with
`token_prefix` (first 8 chars) + `confirm_ts` in `details_json`.

### Step 4 -- Verify (with rollback on fail)

After the apply, re-run the recon step (read-only) and compare against
the pre-apply snapshot. The differences should match the script's
intended effect exactly (e.g. "row updated from status=X to status=Y"
for exactly N rows, no other rows touched, no schema changes).

```bash
python3 "$SCRIPT" --recon-snapshot=/tmp/recon-snapshot-after.json

# diff -u /tmp/recon-snapshot.json /tmp/recon-snapshot-after.json
# (must show only the expected changes)
```

If the diff shows unexpected changes (extra rows touched, schema drift,
unintended UPDATEs), immediately roll back to the pre-apply snapshot
and exit 1. A second apply on a half-modified DB is the canonical way
to corrupt the trading state (Iron-Law #4).

## Failure modes (exit codes)

| Exit | Meaning | Recovery |
|------|---------|----------|
| 0 | Success | Task -> done; kanban_comment with summary |
| 1 | Verify-after-apply failed (rollback executed) | Task -> blocked, reason "verify-after-apply failed; rolled back"; operator must inspect before re-running |
| 70 | No cleanup script found | Task -> blocked, reason "no scripts/cleanup_*.py in workspace"; operator must attach the script or reparent the task to the builder |
| 71 | Dry-run produced no token | Task -> blocked, reason "dry-run output missing apply-token:"; builder needs to fix the script |
| 77 | Token file missing / mismatch / no operator reply within timeout | Task -> blocked, reason "operator gate tripped: <specific reason>"; operator must re-create the dry-run or extend the timeout |
| 78 | Stale snapshot (older than 60s before apply) | Re-run step 1; do NOT apply |
| 130 | Operator cancelled (Telegram reply `<prefix> cancel`) | Task -> blocked, reason "operator cancelled apply"; operator must re-create the task to retry |

## Profile setup (live config — not a repo change)

The `cleanup-operator` profile is **not** versioned in this repo. It is
live configuration under `~/.hermes/profiles/cleanup-operator/`. The
profile must exist BEFORE the dispatcher will spawn a worker for a
`cleanup-operator` task; the dispatcher refuses to spawn for an
unknown assignee (existing behaviour, see
`_dispatch_once_locked` -> `skipped_nonspawnable`).

The minimal live config:

```bash
mkdir -p ~/.hermes/profiles/cleanup-operator/{logs,skills}
```

`~/.hermes/profiles/cleanup-operator/config.yaml`:

```yaml
profile:
  name: cleanup-operator
  description: Destructive DB operator with operator-in-the-loop confirmation
  primary_model: anthropic/claude-sonnet-4-5
  fallback_models:
    - openai/gpt-4o
  enabled_toolsets:
    - terminal
    - file
    - web
    - session_search

# Telegram route: the operator's chat_id for confirmation messages.
gateway:
  notifier:
    routes:
      cleanup_operator_confirm:
        platform: telegram
        chat_id: "REPLACE_WITH_OPERATOR_CHAT_ID"
        kind: cleanup_operator_confirm

# Operator-in-the-loop env (read by the skill on worker startup):
cleanup_operator:
  telegram_confirm_timeout_seconds: 300      # default 5 min
  recon_snapshot_max_age_seconds: 60          # default 60s
  apply_token_file: /tmp/cleanup-operator.token
```

Optional: adopt this skill into the profile with
`hermes curator adopt kanban-cleanup-operator` (only if the operator
wants it force-loaded by default; usually the dispatcher-driven
load via task body is enough).

## Workflow constraint at the dispatcher (the gate)

A `cleanup-operator` task whose body lacks an
`apply_confirm_token_prefix:` field is **refused by the dispatcher
before any worker is spawned**. See
`hermes_cli/kanban_db.py::dispatch_once` (around the
`_dispatch_once_locked` body) and the gate function
`_validate_cleanup_operator_task`. The gate is intentionally placed
BEFORE the `profile_exists` check so a missing/short token trips even
on systems where the `cleanup-operator` profile isn't installed yet —
the rejected task lands in `blocked` with a `dispatch_rejected` event.

**Why the dispatcher-side gate:** the worker-side gate (the skill
above) is the primary defence, but the dispatcher-side gate is the
fail-safe. If a builder somehow produces a `cleanup-operator` task
without the body field — for example by automating the task creation
without going through the operator-recipe — the dispatcher catches it
before any subprocess is launched, instead of relying on the worker
process to refuse.
