# Godfile Kill Campaigns (5×2×3 blind-witness decomposition)

Orchestrate decomposing multi-thousand-line godfiles into mixin modules via a double-blind multi-wave pipeline, ending in native-interlocked PRs with exact kill-line math. Proven across nine godfiles of NousResearch/hermes-agent (adapter, run.py, run_agent, base, kanban_db, main, tui_server, cli, web_server).

## Pipeline stages
1. **Sharding**: split the godfile into 5 equal regions; build per-region def bundles.
2. **Wave 1** (blind witnesses ×2 per shard): independent cluster maps → JSON catalogs (names+lines+spans, move/stay/shared, proposed mixin names, slice order, cross-region edges).
3. **Wave 2** (blind ×2 per shard): independent re-maps — the cross-check (witnesses must NOT see wave-1 outputs).
4. **Wave 3** (blind ×2 per shard): validate every (method, line) claim vs live source via tokenize/AST → VERIFIED/CONTRADICTED verdicts. Classes/string-text are NOT defs; kind-mismatch (NamedTuple class) is benign; decorator-line off-by-ones are real catches.
5. **Agreement merge**: canonical clusters = connected components of the co-membership graph (edge if ≥3/4 witnesses co-located); classification = majority vote; slice order by average witness position; CONTRADICTED methods excluded unless the def exists live. Output: per-shard agreement + `shard-plan.json`.
6. **Extraction w1** (blind implementers ×2 per shard): verbatim extraction into mixin modules; each sandbox = patch + MANIFEST.json + minimal orig/new trees + regression tests.
7. **Extraction w2** (blind adjudicators): cross-check both patches (byte-fidelity, plan fidelity, module conventions, tests, apply, freshness); canonical per cluster → verdict JSONs.
8. **Extraction w3** (validators): apply canonical to a fresh deduplicated worktree; py_compile + shipped tests; VERIFIED verdicts. Canonical may be a COMBINED pair of disjoint w2-accepted patches — apply both sequentially (w1a-then-w1b) in one worktree. Full empirical procedure, pristine-source tricks, and cleanup traps in `references/wave3-witness-validation.md`; combined-canonical recipe in `references/wave3-combined-canonical-validation.md`.
9. **Extraction merger** (local env-parameterized script): pick canonical per region (w3 VERIFIED + w2 not-CONTRADICTED), apply to worktrees, verify, emit manifest.
10. **PR phase**: commit + push to fork, REST PRs with plain-text Related interlock blocks, issue-side edges patched, epic kill-ledger with exact line math.

## Doctrines (non-negotiable)
- **KILL SEQUENCE IS ONE-GOD-AT-A-TIME (Axl, 2026-08-05)**: sharding/mapping
  (waves 1-3, agreements, plans) may run wide across many godfiles; the KILL
  does not. The extraction→merger→PRs→CI-watch sequence serializes per godfile:
  one god's kill runs start to finish (its extraction waves, merger, PRs, CI
  watched to zero failures/pending) before the NEXT god's extraction begins.
  Completed verification material for other gods is STAGED (verified on disk),
  never started. The active kill's CI watch is the gate. A four-wide
  celebration of parallel extraction waves is the anti-pattern.
- **Persist-early**: write the JSON/patch to disk the moment the analysis is done. Lanes die on 429/503 storms; "deaths cost retries, never work" — a lane that persisted before dying delivered (the web_server s5-w1a lane landed after 14 deaths because it wrote first).
- **Reduced-scope ordering**: extract the 1-2 highest-agreement clusters FIRST and write the patch immediately, then extend if the API survives.
- **EXTRACT ALWAYS**: overlap goes in MANIFEST `interlocked_with`, never skipped. A dedup-reading CONTRADICTED verdict is superseded by extract-always (canonical-with-interlock).
- **Space discipline**: minimal orig/new trees only; NEVER full-repo tar copies (one filled the disk to 99% → ENOSPC); deduplicated git worktrees for validation; validate trees are replicas and removable.
- **Baseline-verify every suite failure**: a failing test must be checked against the LIVE repo before believing it. Identical failure set = env-dependent (compression hooks, nous-token presence, Anthropic client mocks, real-threading timing). Once-pass-once-fail under load = flake, not regression. Fails only in the patched tree = real finding.
- **Byte-fidelity**: moved bodies verbatim (difflib 0); reconstruction = orig minus slices + import block; class attrs stay; module-level constants used by tests stay.
- **Cross-tree validation**: run witness A's tests against witness B's tree AND vice versa — isolation passes miss seam-strategy divergences (e.g. main-namespace routing vs module-scoped binding; the patching contract is the live behavior).

## Pitfalls (each cost real debugging time)
- **Merger `patch_path` must prefer `*-repo.patch`** — the raw `*-impl-w{N}.patch` may be a full-tree CONTRADICTED diff that DELETES the godfile wholesale (a 1.3MB variant did; the 16KB canonical applied clean). Candidate ORDER is the bug. Verify with: apply patch to an orig copy, `diff -rq` vs new.
- **Branch-name collisions**: the first campaign's shipped PR branches own `gfg/extract-*`; later godfiles need campaign-scoped prefixes (EX_BRANCH_PREFIX env).
- **Stale worktree registrations** crash `cwd=wt` subprocesses (WinError 267) — `git worktree prune`; git on Windows needs native `C:/` paths (rejects MSYS `/c/`).
- **Windows 32K cmdline** (WinError 206): don't pass every test file as pytest args — scope to the region's shipped tests (`test_s{region}_*`).
- **Store python breaks on long paths** for py_compile — use the repo venv python.
- **Verdict schemas vary (four proven shapes)**: (1) `patch_verdicts[{patch, verdict}]` lists; (2) per-cluster `canonical`/`winner`/`source` fields; (3) top-level `verdict`+`canonical`/`canonical_patch`/`recommendation`; (4) `adjudication` dicts (w2b) and `canonical_merged_patch` keys (w2a). The merger's rec parser must handle all four. Verdict strings are NOT always the literal `"VERIFIED"` — accept the PASS family (`PASS`, `PASS_WITH_NOTES`, `PASS_WITH_GAPS`, `PASS_WITH_DISCREPANCY`, and anything starting `CANONICAL PATCH`) or the region stays BLOCKED with "no admissible patch" (run_agent s2 was blocked until the parser accepted `"CANONICAL PATCH (s2-w1a) PASSES ALL HARD..."`).
- **Idempotent apply**: check `git status --porcelain` first; skip already-applied worktrees; never re-apply over dirty state (repeated applies corrupt — staged `D` deletions appeared).
- **Test-authoring bugs in shipped regression tests** (baseline-reproducible, fix the TEST not the code): `object()` can't take attributes; the stub must match the method's real accessor (`_session_state` vs `_peek_session_state`); class-level descriptors (SessionFieldView) can't be stubbed via setattr; assertions must match LIVE-verified verbatim semantics — probe the live method before aligning the test.
- **Overlay collection crash**: a PYTHONPATH overlay whose tree contains a `tests/` dir shadows the repo's tests package → collection crash at startup (anyio import failure) — an INVALID reproduction, not evidence.
- **Patch-freshness drift**: lanes' final edits outrun their patch writes; the w2 freshness check (regenerate `diff -ruN orig new`, compare) catches it; regenerate to align. Fastest decisive check for git-format patches: `git hash-object sandbox/orig/<file>` vs the live blob, matched against the patch's `index <old>..<new>` line — byte-identical orig + matching index = fresh. For `diff -ruN` patches, `git apply -p1` strips the `orig/`/`new/` first component (works), but the patch is only as fresh as its orig tree: if live moved even a few lines OUTSIDE the moved regions, whole-file hunks die with `error: while searching for` (cli s1-w1a: 4-line drift at an unrelated class method killed a whole-file hunk). A stale-but-content-correct patch still needs regeneration; verify its content against current live independently (see the w2 checklist: PYTHONPATH shadow run).
- **Apply-mode for `orig/`/`new/`-prefixed raw patches: plain `git apply` WORKS, `-p2` FAILS** (cli s2-w1a, verified): git's a/b-prefix heuristic maps the differing first components to repo-relative paths, so `git apply <raw patch>` resolves `orig/cli.py`→`cli.py`, `new/hermes_cli/x.py`→`hermes_cli/x.py`; `-p1` also works; `-p2` strips both components and dies with `unable to find filename in patch at line 3`. The embedded `Binary files ... differ` (__pycache__) header lines are inert. Confirm resolved targets with `git apply --stat` (must show repo-relative paths), and record the apply mode in the w2 verdict so the merger doesn't guess.
- **Stale witness orig is tolerable when the shard region is intact** (cli s2-w1b): witness orig blob ≠ HEAD blob (4-line drift at line 10252, OUTSIDE shard region 3697-7392). Rules: (1) diff only the shard's line region — must be byte-identical; (2) the patch's `index <old>..<new>` line must equal `git hash-object <witness orig>` (internal consistency); (3) context lines all lie in the unchanged region, so `git apply --check` against live passes. Note it in the verdict as a minor finding, not a rejection.
- **Minimal validation replicas MUST include conftest.py files** (cli s2-w2b): copying only cli.py + package dir + selected test files into a replica tree omits `tests/conftest.py` and each touched dir's `conftest.py`, whose autouse fixtures reset module caches and sandbox env state. Without them tests fail spuriously — produced TWO fake "regressions" (stale skill-scan cache → `resolve_skill_command_key` returned None; leaked gateway session vars → secret-capture callback fired) that cost a full root-cause cycle; the replica was the bug, not the patch. Copy `tests/conftest.py` + `tests/<dir>/conftest.py` for every dir you touch, then baseline-verify the same suites on the live repo: failure sets must match exactly.
- **Byte-fidelity via AST line-slicing, not `ast.get_source_segment`** (cli s2-w2b): on 10K+-line godfiles, `get_source_segment` per def is O(n²)-ish and times out (>300s); slice `"\n".join(src.split("\n")[node.lineno-1:node.end_lineno])` instead — instant. When allowing lazy-import shim lines, strip shims ANYWHERE in the body (they're often inserted mid-body, e.g. after the first statement, or followed by an added blank line), not just at the top — top-only stripping falsely flags otherwise-verbatim methods.
- **CRLF patch corruption looks like a whole-file rewrite**: if the patch's first hunk is `@@ -1,N +1,M @@` and the patch is 10-100x bigger than the expected minimal diff, check EOLs (`file orig/x.py new/x.py`) — one tree CRLF, the other LF → GNU diff rewrites every line (cli s1-w1a: a 6-method move produced a 1.7MB patch). `git apply --check` can still PASS whole-file hunks (no context matching needed), and the applied worktree then shows the ENTIRE godfile as modified. Verify the true content delta with `git diff --no-index --ignore-cr-at-eol --stat orig new`. The committed patch may also be post-hoc LF-normalized (≠ raw `diff -ruN` output; size gap ≈ #added-lines × 1 byte) so the validation worktree won't reverse-apply the committed patch. Verdict: content may be fine, artifact must be regenerated as a minimal LF diff.
- **PYTHONPATH shadow needs `__init__.py`**: injecting a stale witness's new modules next to the LIVE repo to re-run its tests (content-validity check for a stale patch) silently fails with `ModuleNotFoundError` unless the shadow tree's package dirs carry `__init__.py` — otherwise `import hermes_cli.cli_content_scrub` resolves the REAL repo package (found later on sys.path? no: package resolution picks the first `hermes_cli` with `__init__.py`, which is the repo's) and the injected submodule never loads. Distinct from the overlay-collection crash pitfall (that one is a `tests/` dir shadowing); here the fix is `touch hermes_cli/__init__.py tests/__init__.py tests/hermes_cli/__init__.py` in the shadow tree.
- **Empty `__init__.py` markers** in new/ trees are omitted by GNU diff — a cosmetic gap, recreatable at merge time.
- **W3 worktree from the wrong ref**: the live repo may sit on a PR branch with unrelated local mods and a DIFFERENT godfile md5 than the wave-2 baseline. Always `git worktree add ... main` (the pristine ref), md5-verify the worktree's godfile against the w2 record BEFORE applying — validating the live working tree gives false failures.
- **Pristine source after apply**: once the patch is applied the worktree's godfile is modified — for byte-fidelity comparisons use `git show HEAD:<godfile>` (read-only git object), not the worktree file.
- **Same-named worktrees across campaigns**: `wt-s5-w3b` exists under godfile/main, godfile/kanban_db, godfile/cli, ... — a bare `git worktree list | grep <name>` matches other campaigns' trees. Confirm removal with the full unique path; never remove/prune a tree you didn't create.
- **Generic artifact filenames collide in the shared wave dir (main.py s2-w3b)**: parallel witnesses share `extraction/w3/` and generic names like `check_fidelity_w3b.py` are a race — a sibling's same-named file silently REPLACED this witness's checker mid-run (signature: the script's output suddenly references another shard's worktree/methods, or a bizarre FileNotFoundError naming a sibling's `wt-s*` path; the checker had passed 15/15 minutes earlier). Shard-suffix EVERY artifact you write into a shared dir (`check_fidelity_s2_w3b.py`, `s2-w3b.json`), verify a file's content is yours before editing it, and never delete a same-named file you didn't create (it is the sibling's evidence). `ls -la` mtimes: an artifact's timestamp between your successful run and your next listing is the overwrite window.
- **Conflicting w2 canonical verdicts → adjudicate with the decisive test + suite audit (main.py s2-w3b)**: w2a picked w1a because w1b breaks the GMI monkeypatch seam; w2b picked w1b on module-scaffolding aesthetics — its adjacent suite never included `test_gmi_provider.py`, which is exactly the test w1b fails (21/22 per w2a). When wave-2 verdicts disagree, the w3 validator must (a) RUN the decisive test(s) the conflict hinges on in the applied worktree (here: `test_gmi_provider.py::test_select_provider_and_model_routes_gmi_to_generic_flow`, which monkeypatches `hermes_cli.main._model_flow_*` and requires the moved code to resolve them lazily at call time) and (b) read each verdict's suite MANIFEST, not its summary: a verdict whose suite omits the decisive test is weaker evidence regardless of how clean its rationale reads. Record both verdicts' suite composition in your JSON.
- **Lazy-import stripping in fidelity checkers (main.py s2-w3b)**: when byte-fidelity means "moved unit verbatim EXCEPT sanctioned `from hermes_cli.main import ...` insertions", strip-then-exact-equal has three traps: (1) constants like `_AUX_TASKS: list[...] = [...]` are `ast.AnnAssign`, not `ast.Assign` — handle both or the member is 'not found'; (2) single-line AND parenthesized multi-line import blocks (`from X import (\n name,\n ...\n )`) must both be stripped — DOTALL for the block; (3) strip the WHOLE line including leading indentation (`^[ \t]*from ... import ...\n` with MULTILINE) — replacing the import text with `\n` leaves indentation-only artifact lines that fail the equality compare. Full working checker pattern: `references/wave3-canonical-patch-validation.md`.
- **Orphaned wave branches**: died lanes leave `gfg/cx-s5-w3b*` refs with NO registered worktrees. Check `git branch --list` AND `git worktree list` before reusing; branches without worktrees are leftovers, not evidence — create a fresh unique-suffixed branch (`-val`) and delete it on cleanup.
- **Wave-3 verbatim-audit false positives (AST-anchor everything, main.py s5-w3a)**: (a) re-export detection via per-line `"from X import" in ln and name in ln` MISSES parenthesized multi-line imports (names sit on continuation lines) — parse module-level `ast.ImportFrom` nodes instead; (b) comment-block adjacency via `src.find(name)` hits the constant's mention in the module DOCSTRING and reports 0 lines — anchor on the AST Assign/FunctionDef node's lineno and scan upward; (c) expected counts (comment-block lengths, line numbers) must be verified against the LIVE source, never copied from prior-witness JSON — w2 claimed the `_TOP_LEVEL_VALUE_FLAGS` block was 9 lines, live and the module both have 8 byte-identical (w2 miscount, not a fidelity issue). Same rule for patch-hygiene counts: w2a reported "3 pyc junk lines" in s2-impl-w1a.patch, the file has 4 (`grep -c 'Binary files'`: 3 header + 1 mid-patch — w2b's "3 at top, 1 mid-patch" was right, s2-w3b copied w2a's 3 into its verdict and the self-verify script caught it). Byte-count the artifact yourself before writing the claim into your verdict. A witness JSON saying CONTRADICTED on detector bugs is a false alarm: fix the detector, re-run, record the corrected audit.
- **Head-drift is EXPECTED in applied-vs-new md5 compares**: when the live head moved since wave 1 (committed, not local mods), the applied godfile differs from w1's `new/` godfile by exactly the documented unrelated insertions — `diff` and COUNT the changed lines (s5-w3a: exactly 3 at line 6879, outside the region); don't read it as byte-fidelity failure. Complement to the wrong-ref pitfall: if the live HEAD's godfile is clean (md5 == `git show HEAD:`), a worktree at that live HEAD SHA is VALID and is the tree the merger will actually patch — verify the base md5 first, then expect the drift delta.
- **Pipe exit-code trap on apply checks**: `git apply --check ... | grep -v warn; echo $?` reports GREP's exit (1 when grep filtered everything), not git's — a "LIVE_CHECK_EXIT=1" scare was grep's, git was 0. Capture git's code before the pipe (no pipe, or `${PIPESTATUS[0]}`).
- **Combined-canonical w3 validation (two disjoint patches, ship-both; tui_server s3-w3b)**: when both w2 verdicts pick DIFFERENT witnesses for DISJOINT clusters, canonical = BOTH patches applied sequentially in one worktree (w1a-then-w1b). The second patch's `--check` output shows a NEGATIVE tail offset (e.g. `Hunk #2 succeeded at 13007 (offset -669 lines)`) = the first patch's deletions — expected, not an error. Verify drift vs EACH sandbox new/ tree: `git diff --no-index` of applied-vs-w1a-new must reduce to exactly (upstream drift lines) + (w1b's removed span, present in w1a-new) + (w1b's tail additions), mirrored for w1b — count hunks and confirm each `@@` context is one of those three classes. Reverse-apply in REVERSE order (last-applied patch first, `-R`). Line math: live − del1 − del2 + add1 + add2 == final `wc -l`. Full recipe: `references/wave3-combined-canonical-validation.md`.
- **Interpreter matching via pyc artifacts + dual-venv trap (tui_server s3-w3b)**: sandbox `new/` trees carry `__pycache__/*.cpython-311-pytest-9.1.1.pyc` — the pyc filename reveals the witnesses' python (3.11); use THAT interpreter. A repo can have two venvs: `.venv` (broken 3.12 — missing certifi → `module 'hermes_cli' has no attribute 'model_switch'` failures) and `venv/` (3.11, working). 2 adjacent tests failed under 3.12 in the applied worktree and reproduced IDENTICALLY on the LIVE repo → environment-driven, NOT a regression; re-run with the witnesses' 3.11 venv (78/78). Baseline-verify any suite failure with the SAME interpreter as the failing run.
- **try/except-embedded module-state names break top-level-only AST finders (extends the AnnAssign trap)**: a constant assigned inside a module-level `try/except` (or `if`) block is NOT in `tree.body` — `node_source()` returns None → false "NOT FOUND". Fix: `ast.walk` for Assign/AnnAssign targets anywhere, then compare the raw slice of the ENCLOSING top-level statement (the whole try block) in live vs module. `_PET_REFERENCE_MAX_BYTES` was this shape; the enclosing try block was verbatim.
- **Per-witness leftover-def scoping in combined validation**: each sandbox `new/server.py` is ONE patch's server and legitimately still defines the OTHER patch's moved names — a no-leftover-defs check against the FULL combined name set produces N false failures (43/43 here). Scope it per witness (w1a's new/server.py checked against w1a's own moved names + its own seam marker); the all-names check only applies to the actually-combined applied tree.
- **Windows worktree dir stuck after `git worktree remove --force` (tui_server s3-w3b)**: remove can de-register the tree (git-hygiene-critical part — `git worktree list` clean) yet fail to delete the physical dir ("Permission denied" / "Device or resource busy"). Do NOT kill the python processes holding handles — many are sibling witnesses' shared-venv processes. `rm -rf` may keep failing; `cmd //c rd /s /q` mangles paths in MSYS; PowerShell `Remove-Item -LiteralPath <native C:/path> -Recurse -Force` finishes the job.

## PR phase / shipped-branch hygiene (run_agent kill closeout, 2026-08-05)
- **A CRLF patch ships as a whole-file rewrite on the PR even when the merger applied it**: the raw w1a patch carried CRLF; the merged worktree's godfile showed `-1,8159 +1,7405` (every line "changed", +8,671/−8,159 on an 8,159-line file) though the real extraction was −760. The w3 witness had produced an LF-normalized canonical (`s2-w3b-canonical-lf.patch`) the merger does NOT prefer. Fix: check `file <worktree>/<godfile>` for CRLF; rebuild the worktree from the LF canonical, re-run the shipped suite (69/69), commit, force-push. Verify the true delta with `git diff --no-index --ignore-cr-at-eol --stat`.
- **`git add -A` sweeps the pytest basetemp into the commit if it lives inside the worktree**: a `.bt-s2lf/` basetemp directory (58 files) got committed with the extraction. Fix: run `--basetemp` OUTSIDE the worktree (e.g. `C:/tmp/tg-campaign/...`), or repair with `git reset --soft HEAD~1 && git rm -r --cached <bt-dir> && git commit`. Diff-hygiene is the kill's quality bar — junk in the diff is a blocker.
- **GitHub's PR-diff endpoint lags force-pushes**: after correcting a branch and force-pushing, `gh pr diff` may still show the OLD (contaminated) file list for minutes. Ground truth is the fork's commit API: `curl -s https://api.github.com/repos/<fork>/commits/<branch>` → `files` count + the file list. Don't judge the PR until the fork commit API agrees.
- **`add_contributor.py` may resolve against the LIVE repo, not the worktree**: it printed "present" but the branch's tree lacked the mapping files → the attribution CI check would fail. After running it, verify with `git ls-files contributors/emails/andrexibiza*` INSIDE the worktree; if absent, `cp` the files from the live repo's `contributors/emails/` into the worktree and commit them explicitly.
- **w3-verified in-body seam fixes can sit as UNCOMMITTED worktree edits**: the time-seam one-line fix (`from gateway.run import time  # keep patch("gateway.run.time") seam (precedent #77752)`) was verified by w3 in its own worktree but existed only as a dirty edit in the merger's worktree — the pushed branch lacked it, and CI failed the monkeypatch-seam test (`test_fresh_turn_resets_idle_clock`: patched `gateway.run.time` bypassed by the mixin's own `import time`). After the merger, gate on `git status --porcelain` being EMPTY before committing; any w3-verified in-body fix must be committed explicitly (commit message citing the precedent PR), then CI re-runs.
- **CI flake triage when the failing test is in a subsystem the PR never touches**: a gateway drain-race test failed on a PR touching only `run_agent.py`. Proof chain: (1) the PR diff has ZERO paths in the failing subsystem (`gh pr diff | grep -cE "^diff --git a/gateway/"` == 0); (2) the exact test passes on the live repo; (3) the same tree passed the test in an earlier run (once-pass-once-fail under load). Then re-trigger: direct job rerun is 403 without admin on the main repo, so push an empty commit (`git commit --allow-empty -m "ci: re-trigger checks (flake, no code change)"`). The empty commit is honest and documented, not noise.
- **`monotonic()` is boot-relative — a shipped regression test asserting "first call allowed" fails on fresh CI containers**: `time.monotonic()` starts near 0 in a fresh container, so `now - last(0.0) < cooldown` rate-limits the FIRST call (returns False) while the long-booted dev machine passes. Fix in the TEST: seed an old baseline per key (`inst._ts = {chat: monotonic() - 1000.0}`) so the assertion is boot-time-independent. Same class as the other test-authoring bugs: verify the live method's semantics first, then fix the test, not the code.
- **Delegation provider resolution gate before dispatching**: a batch can die instantly with "Cannot resolve delegation provider 'nous': Hermes is not logged into Nous Portal" when the configured provider lacks a credential. Diagnose with `hermes auth list` (shows which providers actually have keys), fix with `hermes config set delegation.provider <provider-with-credential>`, verify in config.yaml, THEN dispatch. Restore the pinned primary provider when its login returns — the user's pinned model is the default, not the workaround. Refills after a provider fix carry the prior attempt's surviving evidence (worktree runs that landed before the deaths) so lanes resume, not restart.
- **Billing 402 "Insufficient Balance" ≠ rate-limit 429**: the 429/503 refill doctrine (persist-early, immediate redispatch) does NOT apply to a provider whose credits are exhausted — every lane dies identically (12-20 api_calls, same HTTP 402 text) regardless of retries. Diagnose with `hermes auth list` for the real credential set, switch delegation to a funded provider, and refill ONCE on the working provider. Flag the top-up to the user (credential/billing changes are user-only per the auth boundary) — never silently rotate keys.
- **Per-cluster MIXED canonical → the merger's single-witness pick() BLOCKS (base s2, 2026-08-05)**: when the w2 adjudication splits clusters across witnesses (c2/c3→w1b, c8→w1a) and the w3 verdict says "SHIP CANONICAL UNION AS-IS ... assembled per <w> recipe", the merger returns `s2: BLOCKED — no admissible patch` because its pick() admits exactly one witness per region. Diagnose by reading the w3 verdict's schema keys — a `canonical_union_recipe` / `canonical_merge_recipe_from_w2` field means the region is a UNION, not a pick. Build it manually per the recipe (base s2): (1) apply the primary witness's patch wholesale; (2) copy the specific module from the other witness's `new/` tree; (3) remove the specific block from the godfile (use the exact hunk the recipe names); (4) extend the bottom re-export block with the union names. The w2 witness's idempotent `build_union.py` (guarded mutations, variant-swappable) is the proven assembly tool — run it against the merger's worktree. Verify: py_compile + the full shipped union test set (58 passed). Record the union in the merge manifest as its own region with the recipe quoted.
- **Pre-flight the merger's pick() while w3 is still landing (base, 2026-08-05)**: before the w3 batch completes, import the merger module (set EX_* envs first) and run `pick(region)` per shard against the w2 verdicts already on disk. It catches (a) verdict-schema gaps that would BLOCK a region (the s2 union case surfaced this way — expected w1b, pick returned w1a), (b) w3-file presence so you know which regions still need the batch. Fixes land BEFORE the batch finishes instead of blocking the kill at the merger. Re-run after the batch to confirm all regions resolve.
- **Merger pick() expected-vs-actual audit per region**: after the merger runs, the pre-flight's expected canonicals ARE the contract — a mismatch (pick=w1a where the adjudication table says w1b) means either the schema parser missed a field or the canonical is mixed. Never trust the merger's print alone; check `extraction-merge.json` region-by-region against the w2/w3 verdict files.

## Extraction w2 adjudication (stage 7, cli s1-w2b / s4-w2b recipes)
- **Check coverage FIRST — it is either disjoint or overlapping, and the adjudication differs**:
  - *Disjoint* (cli s1: w1a c2+c3, w1b c10+c11+c18 — zero overlap): per-cluster canonical = the covering witness's patch, validated independently; there is no patch-to-patch comparison to make.
  - *Overlapping / head-to-head* (cli s4: BOTH witnesses did c8+c6 with the same 30 top-level + 10 nested method set): the comparison is direct and decisive. The canonical witness is the one that wins on byte-fidelity + conventions, NOT the first one checked. A cluster skipped by BOTH witnesses with the same module-global-invariant reasoning is double-blind agreement — record the skip as corroborated, not just accepted.
- **Head-to-head decisive criteria (s4 case — all real, all witnessed)**:
  1. **Blank-line separator fidelity** (the #1 differentiator): a witness that strips the trailing blank separator after every moved method produces mixin methods jammed together with ZERO blank lines between them (PEP8 violation, breaks the repo's one-blank-line convention). The faithful witness preserves them and is byte-identical to live. Check: `for each def, gap = lines[prev_def+1:def]; missing if gap[-1] != ""`.
  2. **In-class section comments travel with the cluster**: a witness that leaves the `# ==== Foo methods ====` header orphaned in cli.py mislabels the NEXT (staying) section and usually leaves a double blank at the seam; the faithful witness moves the header into the mixin and leaves a clean seam (single blank, next section follows directly).
  3. **MRO order between NEW mixins is irrelevant** — verify by set-intersection of method names across ALL mixins (existing + new); if empty, either class-line order is fine (keep the canonical witness's).
  4. **Last-method-of-file trailing blank is an EOF artifact, not a fidelity loss**; a comment block that follows a moved method but belongs to the NEXT section (e.g. wake-word header after `_disable_voice_mode`) is correctly left in cli.py — both are extraction false positives, verify before believing a "DIFFERS".
- **Scoped def-block extraction (byte-fidelity script)**: key blocks by `(name, parent)` where parent tracking must treat `class` as a boundary too — a module-level def before the class otherwise becomes the "parent" of every class method. Duplicate nested names across parents (`_panel_box_width` exists 3× in live with different signatures) make name-only matching produce false DIFFERS. Normalize away allowed lazy-import lines (`^\s*from cli import .*$`) before comparing.
- **Adjudicate conventions against the MERGED precedent, not opinion**: find the extraction commit (`git log --all --diff-filter=A -- hermes_cli/cli_commands_mixin.py`) and `git show <commit> -- cli.py` to confirm: one blank line between mixin methods, no section comments inside mixin classes, lazy `from cli import ...` discipline. The witness matching the merged precedent wins.
- **Count defs to verify MANIFEST claims**: `^    def ` = top-level, indented = nested; w1b claimed "41 moved (30+11 nested)" but actual = 40 (30+10) — doc-only miscount, catch it by counting, not trusting.
- **Validate in a fresh worktree at CURRENT HEAD, not the witness's stale one**: `git worktree add --detach <w2-path> HEAD && git apply --check && git apply && pytest <the 2-4 touched test files> --basetemp` with the repo venv python; then `git worktree remove --force` + `git worktree prune`. A witness's own validation worktree may sit on an OLD HEAD (cli s1-w1a's wt was at f40fbcf409 while live had moved on) — useful for its own tests, useless for apply-freshness.
- **Per-witness checklist**: byte-fidelity (extract top-level blocks from live, assert verbatim in mixin AND absent from new cli.py; nested defs are NOT top-level — either diff the enclosing parent block or check the indented `def` inside it; block boundaries can swallow the NEXT section's header comments, so diff the block when containment fails before believing a mismatch); plan fidelity (cluster→module + method list vs shard-plan); module conventions (own import block, `logger = logging.getLogger(__name__)`, moved constants re-exported); tests; `git apply --check`; freshness.
- **Moved module-state + re-export seam**: when module-level state (e.g. `_active_worktree`) moves with a re-export, the staying code's `global X; X = ...` rebind diverges from the mixin's copy. Verify the divergence is unobservable by grepping ALL callers of the reader (if every call passes the state explicitly, fine — cli s1: `_cleanup_worktree(wt_info)` everywhere, no no-arg callers).
- **Verdict JSON self-verify before writing**: enumerate ALL plan clusters (cli s1 = 19; my first pass missed c1) and keep the canonical map 1:1 with the cluster map (grouped keys like `"c4/c6/..."` break strict merger parsers). Cross-check classification/proposed_module vs plan, and that every canonical method name appears in the covering patch/manifest. Match the sibling w2 outputs' schema (e.g. `run-godfile-extraction-w2-witness.v1`) — check an already-shipped `extraction/w2/*.json` first. Write the JSON, then run a throwaway integrity script against it (plan-cluster coverage, key parity, method presence, re-run `git apply --check` as a factual anchor, live-repo-untouched via `git status --short` normalized to bare filenames) — it caught two real defects in one pass.
- *Mixed coverage* (cli s2: c18 by BOTH witnesses, c7 only w1a, c22 only w1b): the overlap cluster is head-to-head, the rest is disjoint — adjudicate the shared cluster on the same head-to-head criteria, then canonical per cluster (c18→w1a, c7→w1a, c22→w1b). When both shared-cluster implementations are VERIFIED and interchangeable (15/19 bodies byte-identical between witnesses; the 4 shim methods differ only in shim placement), tie-break on: (1) orig snapshot freshness (byte-identical to live HEAD beats a stale snapshot), (2) plan-consistent superset (moving the plan-embedded c19 method with the c18 span is benign when c19 proposes the same module), (3) module conventions (top-level cycle-free import beats a 5th lazy shim — verify the imported module doesn't import cli). Always write composition notes for the merger: disjoint cli.py regions compose (c18 spans 5078-5525 & 5885-6163, c22 span 5625-5830 sits between), final class line and import block spelled out, apply mode per patch, and which seam edits are REQUIRED (e.g. the `_reload_skills` registry re-point when the `_skill_commands` global moved). Verify interlock claims read-only via `gh pr view <n> --json number,title,state,isDraft`.
