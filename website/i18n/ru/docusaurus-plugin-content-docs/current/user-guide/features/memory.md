# Постоянная память

Агент Hermes имеет ограниченную, курируемую память, которая сохраняется на протяжении всех сеансов. Это позволяет ему запомнить ваши предпочтения, ваши проекты, ваше окружение и то, чему он научился.

## Как это работает

Память агента составляют два файла:

| Файл | Цель | Лимит символов |
|------|---------|------------|
| **MEMORY.md** | Личные заметки агента — факты об окружающей среде, условности, полученные знания | 2200 символов (~800 токенов) |
| **ПОЛЬЗОВАТЕЛЬ.md** | Профиль пользователя — ваши предпочтения, стиль общения, ожидания | 1375 символов (~500 токенов) |

Оба хранятся в `~/.hermes/memories/` и вводятся в системное приглашение в виде замороженного снимка при запуске сеанса. Агент управляет своей памятью с помощью инструмента `memory` — он может добавлять, заменять или удалять записи.

:::осторожно Один агент на каждый дом Гермеса
Не размещайте два агентских процесса в одном домашнем каталоге Hermes. Запись в память происходит автоматически и загружается обратно в системную подсказку при запуске сеанса, поэтому два автора, живущие в одном доме, будут объединять записи друг друга в состояние, не являющееся автором ни они (ни вы). Память по своей природе ограничена для каждого [профиля](/user-guide/profiles) — дайте второму агенту собственный профиль, а если ему нужна общая память, вместо этого используйте [поставщика внешней памяти](/user-guide/features/memory-providers).
:::

:::информация
Ограничения на количество символов помогают сосредоточиться на памяти. Память **не** автоматически сжимается: когда
запись превысит лимит, инструмент `memory` возвращает ошибку вместо
молча удаляя записи. Затем агент сам освобождает место — консолидируя или
удаление записей в том же ходу перед повторной попыткой (см. [Что происходит, когда память
is Full](#что-происходит-когда-память-полна)). Обратите внимание, что `replace` также связан
по пределу: замена записи на более длинную все равно может привести к переполнению, поэтому новая
контент должен быть сокращен (или удалена другая запись), чтобы соответствовать размеру.
:::

## Как память отображается в системной подсказке

В начале каждого сеанса записи памяти загружаются с диска и отображаются в системном приглашении в виде замороженного блока:

```
══════════════════════════════════════════════
MEMORY (your personal notes) [67% — 1,474/2,200 chars]
══════════════════════════════════════════════
User's project is a Rust web service at ~/code/myapi using Axum + SQLx
§
This machine runs Ubuntu 22.04, has Docker and Podman installed
§
User prefers concise responses, dislikes verbose explanations
```

Формат включает в себя:
- Заголовок, показывающий, какой магазин (ПАМЯТЬ или ПРОФИЛЬ ПОЛЬЗОВАТЕЛЯ)
- Процент использования и количество символов, чтобы агент знал емкость
– Отдельные записи, разделенные разделителями `§` (знак раздела).
- Записи могут быть многострочными.

**Шаблон замороженного снимка:** Вставка системного приглашения фиксируется один раз в начале сеанса и никогда не изменяется в середине сеанса. Это сделано намеренно — кэш префиксов LLM сохраняется для повышения производительности. Когда агент добавляет или удаляет записи в памяти во время сеанса, изменения немедленно сохраняются на диске, но не отображаются в системном приглашении до начала следующего сеанса. Ответы инструмента всегда показывают активное состояние.

## Действия инструмента памяти

Агент использует инструмент `memory` для следующих действий:

- **add** — Добавить новую запись в памяти.
- **replace** — заменить существующую запись обновленным содержимым (использует сопоставление подстроки через `old_text`).
- **удалить** — удалить запись, которая больше не актуальна (используется сопоставление подстроки через `old_text`).

Действие `read` отсутствует — содержимое памяти автоматически вводится в системное приглашение при запуске сеанса. Агент рассматривает свои воспоминания как часть контекста разговора.

### Сопоставление подстроки

Действия `replace` и `remove` используют короткие уникальные сопоставления подстрок — вам не нужен полный текст ввода. Параметр `old_text` просто должен быть уникальной подстрокой, идентифицирующей ровно одну запись:

```python
# If memory contains "User prefers dark mode in all editors"
memory(action="replace", target="memory",
       old_text="dark mode",
       content="User prefers light mode in VS Code, dark mode in terminal")
```

Если подстрока соответствует нескольким записям, возвращается ошибка с запросом более конкретного соответствия.

## Объяснение двух целей

### `memory` — Личные заметки агента

Для получения информации агенту необходимо помнить об окружающей среде, рабочих процессах и извлеченных уроках:

- Факты об окружающей среде (ОС, инструменты, структура проекта)
- Соглашения и конфигурация проекта
- Обнаружены особенности инструмента и обходные пути.
- Записи в дневнике выполненных задач
- Навыки и методы, которые сработали.

### `user` — Профиль пользователя

Для получения информации о личности пользователя, предпочтениях и стиле общения:

- Имя, роль, часовой пояс
- Коммуникационные предпочтения (краткие или подробные, предпочтения формата)
- Любимые раздражения и вещи, которых следует избегать
- Навыки рабочего процесса
- Уровень технических навыков

## Что сохранить, а что пропустить

### Сохраните это (заранее)

Агент сохраняет автоматически — вам не нужно спрашивать. Он спасается, когда узнает:

- **Пользовательские настройки:** «Я предпочитаю TypeScript JavaScript» → сохранить в `user`.
- **Факты о среде:** «На этом сервере работает Debian 12 с PostgreSQL 16» → сохранить в `memory`.
- **Исправления:** «Не используйте `sudo` для команд Docker, пользователь находится в группе Docker» → сохранить в `memory`.
- **Условия:** «В проекте используются табуляции, ширина строки 120 символов, строки документации в стиле Google» → сохранить в `memory`.
- **Завершенная работа:** «Перенос базы данных из MySQL в PostgreSQL 15 января 2026 г.» → сохранить в `memory`
- **Явные запросы:** «Помните, что ротация ключей API происходит ежемесячно» → сохраните в `memory`.

### Пропустить это

- **Тривиальная/очевидная информация:** «Пользователь спросил о Python» — слишком расплывчато, чтобы быть полезным.
- **Факты, которые легко обнаружить заново:** «Python 3.12 поддерживает вложенность f-строк» — можно выполнить поиск в Интернете
– **Дампы необработанных данных:** Большие блоки кода, файлы журналов, таблицы данных — слишком велики для памяти.
- **Эфемеры, специфичные для сеанса:** Временные пути к файлам, одноразовый контекст отладки.
- **Информация уже в контекстных файлах:** содержимое SOUL.md и AGENTS.md.

## Управление емкостью

Память имеет строгие ограничения на количество символов, чтобы ограничить системные подсказки:

| Магазин | Лимит | Типичные записи |
|-------|-------|----------------|
| память | 2200 символов | 8-15 записей |
| пользователь | 1375 символов | 5-10 записей |

### Что происходит, когда память заполнена

При попытке добавить запись, превышающую лимит, инструмент возвращает ошибку:

```json
{
  "success": false,
  "error": "Memory at 2,100/2,200 chars. Adding this entry (250 chars) would exceed the limit. Consolidate now: use 'replace' to merge overlapping entries into shorter ones or 'remove' stale or less important entries (see current_entries below), then retry this add — all in this turn.",
  "current_entries": ["..."],
  "usage": "2,100/2,200"
}
```

Затем агент должен:
1. Прочтите текущие записи (отображаются в ответе об ошибке)
2. Определите записи, которые можно удалить или объединить.
3. Используйте `replace` для объединения связанных записей в более короткие версии.
4. Затем `add` новая запись.

**Рекомендации.** Если объем памяти превышает 80 % (отображается в заголовке системного приглашения), объедините записи перед добавлением новых. Например, объедините три отдельные записи «Проект использует X» в одну запись с подробным описанием проекта.

### Практические примеры хороших записей в памяти

**Компактные, насыщенные информацией записи работают лучше всего:**

```
# Good: Packs multiple related facts
User runs macOS 14 Sonoma, uses Homebrew, has Docker Desktop and Podman. Shell: zsh with oh-my-zsh. Editor: VS Code with Vim keybindings.

# Good: Specific, actionable convention
Project ~/code/api uses Go 1.22, sqlc for DB queries, chi router. Run tests with 'make test'. CI via GitHub Actions.

# Good: Lesson learned with context
The staging server (10.0.1.50) needs SSH port 2222, not 22. Key is at ~/.ssh/staging_ed25519.

# Bad: Too vague
User has a project.

# Bad: Too verbose
On January 5th, 2026, the user asked me to look at their project which is
located at ~/code/api. I discovered it uses Go version 1.22 and...
```

## Предотвращение дублирования

Система памяти автоматически отклоняет точные повторяющиеся записи. Если вы попытаетесь добавить контент, который уже существует, он вернет успех с сообщением «дубликаты не добавлены».

## Сканирование безопасности

Записи памяти сканируются на предмет шаблонов внедрения и эксфильтрации перед принятием, поскольку они вводятся в системное приглашение. Содержимое, соответствующее шаблонам угроз (быстрое внедрение, утечка учетных данных, бэкдоры SSH) или содержащее невидимые символы Юникода, блокируется.

## Поиск сеанса

Помимо MEMORY.md и USER.md, агент может искать свои прошлые разговоры с помощью инструмента `session_search`:

- Все сеансы CLI и обмена сообщениями хранятся в SQLite (`~/.hermes/state.db`) с полнотекстовым поиском FTS5.
- Поисковые запросы возвращают фактические сообщения из БД — без суммирования LLM и усечения.
- Агент может найти вещи, которые он обсуждал несколько недель назад, даже если их нет в его активной памяти.
- Агент также может прокручивать вперед/назад внутри любого найденного сеанса.

```bash
hermes sessions list    # Browse past sessions
```

См. [Инструмент поиска сеанса](/user-guide/sessions#session-search-tool) для получения информации о трех формах вызова (обнаружение/прокрутка/просмотр) и формате ответа.

### session_search против памяти

| Особенность | Постоянная память | Поиск сеанса |
|---------|------------------|----------------|
| **Емкость** | Всего ~1300 токенов | Безлимитно (все сеансы) |
| **Скорость** | Мгновенно (в системной подсказке) | Запрос FTS5 ~20 мс, прокрутка ~1 мс |
| **Стоимость** | Стоимость токена в каждой подсказке | Бесплатно — никаких звонков в LLM |
| **Сценарий использования** | Ключевые факты всегда доступны | Поиск конкретных прошлых разговоров |
| **Управление** | Курируется агентом вручную | Автоматически — все сеансы сохраняются |
| **Стоимость токена** | Фиксировано за сессию (~1300 токенов) | По требованию (поиск при необходимости) |

**Память** предназначена для важных фактов, которые всегда должны быть в контексте. **Поиск сеанса** — это вопрос "мы обсуждали X на прошлой неделе?" запросы, в которых агенту необходимо вспомнить детали прошлых разговоров.

## Учебное путешествие (`/journey`)

Учебный процесс представляет собой временную шкалу всего, чему научился Гермес: сохраненные навыки и записи памяти, отображаемые с течением времени (самые старые вверху, самые новые внизу), с игровым «созвездием», которое повторяет наращивание. Одни и те же графические данные управляют тремя поверхностями:

- **Классический интерфейс командной строки / автономный** — `hermes journey` (псевдонимы: `hermes learning`, `hermes memory-graph`) отображает временную шкалу в терминале. Флаги: `--play` анимирует построение (`--fps` для его настройки), `--width`/`--height` переопределяет размер рендеринга, `--no-color` отключает цвет, а `--json` выгружает необработанные полезные данные графа.
- **TUI** — `/journey` (псевдонимы: `/learning`, `/memory-graph`) открывает временную шкалу в виде наложения.
- **Настольное приложение** — `/journey` открывает панель звездной карты/графика памяти, интерактивное изображение тех же узлов.

Помимо просмотра, в путешествии вы также **подрезаете и исправляете** то, чему научился Гермес:

| Команда | Что он делает |
|---------|--------------|
| `hermes journey list` | Идентификаторы узлов списка — имена навыков и идентификаторы `memory:<source>:<index>` для фрагментов памяти. |
| `hermes journey delete <node> [-y]` | Удалить узел. Навыки **архивируются** (восстанавливаются), фрагменты памяти удаляются. `-y` пропускает подтверждение. |
| `hermes journey edit <node>` | Откройте содержимое узла (`SKILL.md` навыка или фрагмент памяти) в `$EDITOR`. |

Те же подкоманды `list` / `delete <id>` / `edit <id>` работают с командой `/journey` в чате в CLI, а панель рабочего стола предлагает редактировать/удалять узлы напрямую.

## Конфигурация

```yaml
# In ~/.hermes/config.yaml
memory:
  memory_enabled: true
  user_profile_enabled: true
  memory_char_limit: 2200   # ~800 tokens
  user_char_limit: 1375     # ~500 tokens
  write_approval: false     # false = write freely (default) | true = require approval
```

Установка **оба** `memory_enabled` и `user_profile_enabled` на `false` включает
встроенные хранилища полностью отключены: инструмент `memory` удален из схемы и
его блок навигации удален из системной подсказки, поэтому модель никогда не сообщается
об инструменте, который он не может использовать. Внешний поставщик, установленный через `memory.provider`
(Hindsight, Mem0, Honcho, …) не затрагивается и сохраняет свои собственные инструменты — используйте это
когда вам нужен сторонний сервер памяти *вместо* встроенных файлов.
Листинг `memory` под `agent.disabled_toolsets` является более тяжелым переключателем: он скрывает
инструменты внешнего поставщика тоже.

Если только `memory_enabled: false` (профиль пользователя все еще включен), инструмент остается —
он поддерживает хранилище профилей, но системное приглашение заменяет всю память
руководство для более узкого блока, состоящего только из профилей. Схема инструмента объявляет только
Цель `user`, а прямая или поэтапная запись в отключенный `MEMORY.md` отклоняется.
Обратная конфигурация объявляет только `memory` и отклоняет запись `USER.md`.

## Управление записью в память (`write_approval`)

По умолчанию агент свободно экономит память — в том числе в фоновом режиме.
обзор самосовершенствования, который запускается после поворота. Если вы предпочитаете одобрить сохранения
сначала установите `memory.write_approval: true`. Это простые двухпозиционные ворота, применяемые к
**оба** поворота на переднем плане и обзор фона:

| `write_approval` | Поведение |
|------------------|-----------|
| `false` (по умолчанию) | Пишите свободно — ворота выключены (поведение перед воротами). |
| `true` | Требовать одобрения, прежде чем что-либо будет сохранено. В интерактивном интерфейсе командной строки запросы на запись на переднем плане отображаются в строке (записи достаточно малы, чтобы их можно было прочитать полностью). Везде — платформах обмена сообщениями, скриптах и ​​фоновом обзоре самосовершенствования — записи **подготавливаются** для проверки `/memory pending`. |

> Чтобы полностью отключить память (а не просто отключить ее), установите оба `memory_enabled: false` и `user_profile_enabled: false`. Когда оба встроенных хранилища отключены, встроенный инструмент `memory` автоматически скрывается.

Просмотрите поэтапную запись из CLI или любой другой платформы обмена сообщениями:

```
/memory pending             # list staged memory writes (auto ones tagged [auto])
/memory approve <id>        # apply one (or 'all')
/memory reject <id>         # drop one (or 'all')
/memory approval on         # turn the gate on (or 'off') and persist it
```

Это ответ на "агент сохранил обо мне неверное предположение": set
`write_approval: true` и каждое сохранение, особенно фон без подсказки.
one — ждет вашего ответа «да/нет», прежде чем войти в ваш профиль.

## Уведомления о фоновой проверке (`display.memory_notifications`)

После поворота фоновый обзор самосовершенствования может незаметно сохранить память.
или обновить навык. Это цикл обучения Гермеса с учетом согласия: повторяется
исправления и долгосрочные уроки рабочего процесса становятся компактными записями в памяти или
процедурные навыки, а `write_approval` может подготовить эти записи для проверки
прежде чем они повлияют на будущие сеансы. По умолчанию отображается короткое сообщение
`💾 Memory updated` в чате, чтобы вы знали, что это произошло. Контролируйте, насколько болтливы
то есть:

```yaml
display:
  memory_notifications: on    # off | on (default) | verbose
```

| Значение | Поведение |
|-------|-----------|
| `off` | Нет уведомлений в чате. Обзор все еще работает и пишется — просто вы не видите для него строчки. |
| `on` (по умолчанию) | Общая линия, например. `💾 Memory updated`, `💾 Skill 'foo' patched`. |
| `verbose` | Включает компактный предварительный просмотр того, что изменилось, например. `💾 Memory ➕ User prefers terse replies` или `"old" → "new"` фрагмент различия навыков. |

> Это касается только уведомлений чата **шлюза**. Сам обзор и
> записывает в вашу память/навыки, эта настройка не влияет. Установите это
> для каждой платформы через `display.platforms.<platform>.memory_notifications`.

## Выполняем обзор более дешевой модели (`auxiliary.background_review`)

По умолчанию проверка выполняется в вашей **основной модели чата**, воспроизводя
разговор — который уже теплый в кэше подсказок, поэтому это дешевый кэш
читает. На дорогой основной модели можно провести обзор на более дешевой модели.
вместо этого:

```yaml
auxiliary:
  background_review:
    provider: openrouter
    model: google/gemini-3-flash-preview   # auto (default) = main chat model
```

Когда вы указываете на модель, **отличную** от вашей основной, обзор запускается
там по значительно более низкой цене (~ 3–5 раз в тестах). Потому что другой
модель в любом случае не может повторно использовать кэш подсказок вашей основной модели, форк автоматически
воспроизводит компактный **сборник** разговора (недавние повороты дословно +
краткое изложение старых), а не полную стенограмму, сводя к минимуму то, что
записывает в новый кеш. Захват сохраняется: при тестировании захват памяти был
идентичны, а набор навыков почти идентичен обзору основной модели.

Оставьте значение `auto` (или установите свою основную модель), и ничего не изменится —
Обзор продолжает работать на основной модели с полным воспроизведением из теплого кэша.

### Отключение автоматических проверок (`enabled`)

Вилка обзора может сжигать значительную долю общего количества токенов на занятых хостах.
Операторы могут отключить его без обнуления интервалов смещения:

```yaml
auxiliary:
  background_review:
    enabled: true              # false = skip automatic post-turn forks
```

При использовании `enabled: false` автоматические вилки после поворота не появляются; руководство
`/refine` все еще работает.

Использование вилки сохраняется в `session_model_usage` с `task='background_review'`.
и строка завершения записывается в `agent.log`
(`Background review complete: thread=bg-review calls=… in=… out=… result=…`).

## Управление записью навыков (`skills.write_approval`)

Навыки используют одни и те же ворота включения/выключения, но пользовательский интерфейс обзора отличается, потому что
`SKILL.md` слишком велик, чтобы его можно было прочитать в чате:

```yaml
skills:
  write_approval: false     # false = write freely (default) | true = require approval
```

Когда `write_approval: true`, навык записывает (создать/редактировать/патч/записать_файл/
delete) всегда **этап** независимо от происхождения. Вы просматриваете однострочную суть
встроенный, но полная разница остается вне диапазона:

```
/skills pending             # list staged skill writes + a one-line gist each
/skills diff <id>           # full unified diff (best viewed in CLI or dashboard)
/skills approve <id>        # apply it (or 'all')
/skills reject <id>         # drop it (or 'all')
/skills approval on         # turn the gate on (or 'off') and persist it
```

На платформе обмена сообщениями одобрите навык, основываясь на его сути и метаданных, или откройте
`/skills diff` в CLI/панели мониторинга/проиндексированном файле под
`~/.hermes/pending/skills/<id>.json`, когда вы хотите прочитать все изменения.
Полную информацию см. в [Запись навыков агента Gating](/user-guide/features/skills#gating-agent-skill-writes-skillswrite_approval).


## Поставщики внешней памяти

Для более глубокой и постоянной памяти, выходящей за рамки MEMORY.md и USER.md, Hermes поставляется с 8 плагинами внешних поставщиков памяти, включая Honcho, OpenViking, Mem0, Hindsight, Holographic, RetainDB, ByteRover и Supermemory.

Внешние поставщики используют **наряду** встроенную память (никогда не заменяя ее) и добавляют такие возможности, как графики знаний, семантический поиск, автоматическое извлечение фактов и межсессионное моделирование пользователей.

```bash
hermes memory setup      # pick a provider and configure it
hermes memory status     # check what's active
```

Подробную информацию о каждом поставщике, инструкции по настройке и сравнению см. в руководстве [Поставщики памяти](./memory-providers.md).
