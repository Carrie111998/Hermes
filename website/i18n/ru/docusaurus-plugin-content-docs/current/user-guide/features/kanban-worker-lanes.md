# Рабочие дорожки Канбана

**Рабочая полоса** — это класс процессов, в которые диспетчер канбана может направлять задачи. Каждая полоса имеет идентификатор (строку ответственного лица), механизм создания и контракт о том, что она должна делать с задачей после ее создания.

Эта страница является договором. Он существует для двух аудиторий:

- **Операторы** выбирают, какие дорожки подключать к плате (какие профили создавать, каких исполнителей использовать).
- **Авторы плагинов/интеграций**, желающие добавить новую форму дорожки (работник CLI, который обертывает Codex/Claude Code/OpenCode, контейнерный исполнитель проверки, сервис, не принадлежащий Hermes, который извлекает задачи через API).

Если вы пишете сам код работника — агента, который работает *внутри* дорожки — жизненный цикл канбана и справочные сведения автоматически вводятся в системную подсказку работника (блок `KANBAN_GUIDANCE` в [`agent/prompt_builder.py`](https://github.com/NousResearch/hermes-agent/blob/main/agent/prompt_builder.py)).

## Иерархия

```text
Hermes Kanban  =  canonical task lifecycle + audit trail
Worker lane    =  implementation executor for one assigned card
Reviewer       =  human or human-proxy that gates "done"
GitHub PR      =  upstreamable artifact (optional, for code lanes)
```

Гермес Канбан владеет правдой жизненного цикла — `ready` → `running` → `review` / `blocked` / `done` / `archived`. Рабочие полосы выполняют работу, но никогда не признают эту правду; все, что они делают, проходит обратно через ядро ​​канбана через инструменты `kanban_*` (или, для внешних работников, не являющихся сотрудниками Hermes, через API). Рецензенты контролируют переход от «изменения кода написаны» к «задача выполнена».

## Что дает полоса

Чтобы стать рабочей полосой канбана, интеграция должна обеспечивать три вещи:

### 1. Строка правопреемника

Диспетчер сопоставляет `task.assignee` либо с именем профиля Hermes (форма полосы по умолчанию), либо с зарегистрированным негенерируемым идентификатором (форма полосы плагина — см. [Добавление внешней рабочей полосы CLI](#adding-an-external-cli-worker-lane) ниже). Задачи, правопреемник которых не решается, остаются на `ready` с событием `skipped_nonspawnable`, чтобы оператор доски мог их исправить; они не удаляются автоматически и не выполняются в результате произвольного отката.

### 2. Механизм появления

Для полос профиля Hermes `_default_spawn` диспетчера запускает `hermes -p <assignee> chat -q <prompt>` (или эквивалентную форму модуля, если прокладка `hermes` не находится на `$PATH`) внутри закрепленной рабочей области задачи со следующими установленными переменными окружения:

| Переменная | несет |
|---|---|
| `HERMES_KANBAN_TASK` | идентификатор задачи, над которой работает работник |
| `HERMES_KANBAN_DB` | абсолютный путь к файлу SQLite для каждой платы |
| `HERMES_KANBAN_BOARD` | доска пуля |
| `HERMES_KANBAN_WORKSPACES_ROOT` | корень дерева рабочей области доски |
| `HERMES_KANBAN_WORKSPACE` | абсолютный путь к рабочей области *этой* задачи |
| `HERMES_KANBAN_RUN_ID` | идентификатор текущего запуска (для шлюза жизненного цикла) |
| `HERMES_KANBAN_CLAIM_LOCK` | строка блокировки утверждения (`<host>:<pid>:<uuid>`) |
| `HERMES_PROFILE` | имя профиля работника (для указания автора `kanban_comment`) |
| `HERMES_TENANT` | пространство имен арендатора, если оно есть у задачи |

Для дорожек, отличных от Hermes (зарегистрированных через плагин), плагин предоставляет собственный вызываемый объект `spawn_fn`, который получает `task`, `workspace` и `board` и возвращает дополнительный идентификатор pid для обнаружения сбоев.

### 3. Терминатор жизненного цикла

Каждое утверждение должно заканчиваться ровно одним из:

- `kanban_complete(summary=..., metadata=...)` — задача выполнена успешно, статус меняется на `done`.
- `kanban_request_review(summary=..., metadata=..., reviewer=...)` — реализация той же карты завершена и проходит первоклассную проверку; статус изменится на `review`. Диспетчер загружает встроенный навык `sdlc-review`, если `kanban.review_dispatch` не отключен. Рецензент утверждает с помощью `kanban_complete`, возвращает действенную доработку с помощью `kanban_request_changes` или передает подлинное внешнее блокирующее устройство на уровень `kanban_block`.
- `kanban_block(reason=...)` — задача ожидает ввода человеком, статус меняется на `blocked`. Диспетчер возрождается при запуске `kanban_unblock`.
- Рабочий процесс завершается без вызова инструмента. Ядро получает его и выдает `crashed` (PID умер) или `gave_up` (сработал прерыватель последовательного отказа) или `timed_out` (превышено максимальное время выполнения). Это путь неудачи; здоровые работники на этом не заканчиваются.

Ядро канбана обеспечивает завершение каждого запуска только одним из них. Рабочий процесс, который не вызывает ни одного вызова и завершает работу нормально, считается аварийным.

## Результаты и передача проверки

Для задач по изменению кода выберите модель проверки, закодированную графом задачи:

– **Просмотр той же карты**: позвоните по номеру `kanban_request_review(summary=..., metadata=..., reviewer=...)`. Задача входит в `review`, не затрагивая учет повторений блоков. По умолчанию диспетчер заявляет об этом с помощью встроенного навыка `sdlc-review`. Рецензент утверждает с помощью `kanban_complete`, вызывает `kanban_request_changes(reason=...)`, чтобы закрыть выполнение проверки и направить задачу обратно к исходному исполнителю, или блокирует только для реальной внешней эскалации.
– **Предварительно созданная карточка последующей проверки/QA/выпуска:** `kanban_show` содержит список дочерних идентификаторов; проверьте эти карты с помощью `kanban_show(task_id=...)`, прежде чем выбирать действие терминала. Когда дочерний процесс проходит этап последующей проверки/QA/выпуска, позвоните по номеру `kanban_complete` на этапе реализации. Он не может продвигаться по службе, пока этому родителю не исполнится `done`/`archived`. Не запрашивайте дополнительную проверку той же карты и никогда не блокируйте родителя с помощью `review-required:` — ни для выбора цепочек, ни для дублирования нижестоящей полосы.
- **Доски только для людей:** набор `kanban.review_dispatch: false`. Затем задача может оставаться в `review` до тех пор, пока человек не одобрит ее или не использует `reopen-review`/панель мониторинга, чтобы вернуть ее в `ready`/`todo`.

Обе модели проверки несут структурированную передачу управления на самом переходе жизненного цикла. Не размещайте секреты, токены или необработанные персональные данные в `summary` или `metadata`; беговые ряды долговечны.

Внедренный `KANBAN_GUIDANCE` охватывает обе формы графика: `kanban_complete`, цикл просмотра одной и той же карты, и `kanban_block` для настоящих блокировщиков.

## Журналы и контрольный журнал

Диспетчер записывает рабочий поток stdout/stderr для каждой задачи в `<board-root>/logs/<task_id>.log`. Журналы можно проверить на основе метаданных канбана:

– Строки `task_runs` содержат `log_path`, код выхода (если доступен), сводку и метаданные.
- Строки `task_events` содержат все переходы состояний (`promoted`, `claimed`, `heartbeat`, `completed`, `blocked`, `review_requested`, `changes_requested`, `review_reopened`, `gave_up`, `crashed`, `timed_out`, `reclaimed`, `claim_extended`).
- `kanban_show` возвращает оба, поэтому проверяющий (или последующий работник), читающий задачу, получает полную историю без необходимости доступа к информационной панели.

Панель мониторинга отображает историю запусков со сводками, блоками метаданных и значками статуса выхода. Пользователи CLI могут запустить `hermes kanban tail <task_id>`, чтобы следить за происходящим в реальном времени, или `hermes kanban runs <task_id>`, чтобы просмотреть исторический список попыток.

## Существующие формы дорожек

### Полоса профиля Hermes (по умолчанию)

Форма, которую сегодня принимает каждый канбан-работник: исполнителем является имя профиля, диспетчер создает `hermes -p <profile>`, работник автоматически вводит блок системных подсказок `KANBAN_GUIDANCE` и использует инструменты `kanban_*` для завершения выполнения. Никаких настроек, кроме определения профиля.

Когда вы создаете профили для своего парка, выбирайте имена, соответствующие *роли*, к которой вы хотите, чтобы оркестратор направлялся. Оркестратор (если он есть) обнаруживает имена ваших профилей через `hermes profile list` — система не предполагает фиксированного списка (сторона оркестратора контракта является частью внедренного `KANBAN_GUIDANCE`).

### Полоса профиля Orchestrator

Специализация полосы профиля: оркестратор — это профиль Hermes, набор инструментов которого включает `kanban`, но исключает `terminal` / `file` / `code` / `web` для реализации. Его задача — разложить цель высокого уровня на дочерние задачи с помощью `kanban_create` + `kanban_link` и отступить. В навыке оркестратора закодированы правила борьбы с искушениями.

## Добавление внешней рабочей линии CLI

Подключение инструмента CLI, отличного от Hermes (CLI Codex, Claude Code CLI, OpenCode CLI, локального средства запуска моделей кодирования и т. д.) в качестве рабочей дорожки канбана — это *еще не проложенный путь*. Функция создания диспетчера является подключаемой (`spawn_fn` является параметром `dispatch_once`), и плагин может зарегистрировать свой собственный `spawn_fn` для правопреемника, не являющегося представителем Hermes, но окружающая работа по интеграции — упаковка кода выхода CLI в вызовы `kanban_complete` / `kanban_block`, сопоставление соглашений о рабочем пространстве/песочнице CLI с соглашениями диспетчера. `HERMES_KANBAN_WORKSPACE` env, обработка аутентификации и политики для каждого CLI — по-прежнему является работой над проектированием для каждой интеграции.

Если вы планируете добавить полосу CLI, откройте проблему, описывающую конкретный CLI и рабочий процесс, который вы пытаетесь включить. Вышеупомянутый контракт представляет собой ограничения, которым должна удовлетворять любая такая полоса; форма реализации (один плагин для каждого CLI вместо общего плагина CLI-runner, параметризованного конфигурацией) открыта.

Историческая проблема для этого — [#19931](https://github.com/NousResearch/hermes-agent/issues/19931) и закрытый, необъединённый PR, специфичный для Кодекса [#19924](https://github.com/NousResearch/hermes-agent/pull/19924) — они описывают исходное архитектурное предложение, но не нашли отклика.

## Режимы отказа, обрабатываемые диспетчером

Таким образом, авторам дорожек не нужно переопределять их:

- **Устаревший срок жизни заявки** — рабочий процесс, который запрашивает, а затем никогда не контролируется/завершается/блокируется, восстанавливается после `DEFAULT_CLAIM_TTL_SECONDS` (15 минут по умолчанию) — но только в том случае, если рабочий процесс действительно завершился. Живой работник (медленная модель, тратящая более 20 минут на один звонок LLM без инструментов) получает иск *расширенным* вместо убитого; восстанавливается только мертвый PID.
- **Сбойный рабочий** — рабочий процесс, у которого исчез локальный PID хоста, обнаружен `detect_crashed_workers` и получен; задача увеличивает `consecutive_failures` и может автоматически блокироваться при срабатывании выключателя.
- **Повторная попытка на уровне выполнения** — при повторной попытке задачи (после блокировки, после сбоя, после восстановления) исполнитель может использовать параметр `expected_run_id` для завершения инструментов для быстрого сбоя, если его собственный запуск уже был заменен.
- **Максимальное время выполнения для каждой задачи** — `task.max_runtime_seconds` жестко ограниченное время настенных часов за один запуск, независимо от активности PID. Перехватывает действительно зашедшие в тупик рабочие процессы, которые в противном случае расширение live-PID продолжало бы работать.
- **Обнаружение незавершенной задачи** — готовая задача, правопреемник которой ни разу не предъявил претензии в течение `kanban.stranded_threshold_seconds` (по умолчанию 30 минут), отображается в `hermes kanban diagnostics` как предупреждение `stranded_in_ready`. Серьезность возрастает до ошибки в 2 раза выше порогового значения и до критической в ​​6 раз. Перехватывает опечаток исполнителей, удаленных профилей и отключений внешних рабочих пулов в одном сигнале — независимо от личности, без списка разрешенных для каждой доски, который нужно курировать.
- **Взаимная блокировка проверки устаревших версий** — родительский элемент, заблокированный с помощью `review-required:`, в то время как один или несколько прямых дочерних элементов остаются заблокированными зависимостями в `todo`, немедленно вызывает ошибку `review_dependency_deadlock`. Диагностика доступна только для чтения: она предлагает завершить завершенный этап или отсоединить неправильное ребро, но никогда не удаляет пользовательский блок автоматически.
