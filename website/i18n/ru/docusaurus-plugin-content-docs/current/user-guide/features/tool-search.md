# Поиск инструмента

Если у вас есть много серверов MCP или неосновных плагинов, подключенных к
сеанса их схемы JSON могут занимать значительную часть
контекстное окно на каждом шагу — даже если лишь немногие из них актуальны
тому, что на самом деле запросил пользователь.

**Инструмент поиска** — это уровень прогрессивного раскрытия информации Hermes, который позволяет выполнять эту задачу.
проблема. При активации инструменты MCP и плагинов заменяются в
видимый для модели массив инструментов тремя мостовыми инструментами, и модель загружает каждый
схема конкретного инструмента по запросу.

:::info Встроенные инструменты Hermes никогда не откладываются
Инструменты, составляющие основной набор возможностей Hermes (`terminal`,
`read_file`, `write_file`, `patch`, `search_files`, `todo`, `memory`,
`browser_*`, `web_search`, `web_extract`, `clarify`, `execute_code`,
`delegate_task`, `session_search` и остальные
`_HERMES_CORE_TOOLS`) *всегда* загружаются напрямую. Только инструменты MCP и
неосновные плагины имеют право на отсрочку.
:::

## Как это работает

Когда на ходу активируется поиск инструмента, модель видит три новых инструмента в
место отложенных:

```
tool_search(queries, limit?)   — search the deferred-tool catalog (one or more queries)
tool_describe(names)           — load the full schemas for one or more tools
tool_call(name, arguments)     — invoke a deferred tool
```

Типичное взаимодействие выглядит так:

```
Model: tool_search(["create a github issue", "send a slack message"])
  → { results: [ { query: "create a github issue",
                   matches: ["mcp_github_create_issue", ...] },
                 { query: "send a slack message",
                   matches: ["mcp_slack_post_message", ...] } ],
      tools: { mcp_github_create_issue: { description: "...",
                                          required: ["title"], ... },
               mcp_slack_post_message: { ... } } }
Model: tool_describe(["mcp_github_create_issue", "mcp_slack_post_message"])
  → { tools: { mcp_github_create_issue: { parameters: { ... } },
               mcp_slack_post_message: { parameters: { ... } } } }
Model: tool_call("mcp_github_create_issue", { title: "...", body: "..." })
  → { ok: true, issue_number: 42 }
```

Каждый запрос в вызове `tool_search` ищется независимо от
тот же каталог (`limit` применяется для каждого запроса); группы для каждого запроса содержат инструмент
только имена, а общая карта `tools` содержит данные каждого соответствующего инструмента.
описание и имена обязательных параметров один раз. Запросы ограничены, поэтому
«Проблемы» находит `create_issue`. Каждая группа запросов, которая не возвращает совпадений
включает `available_sources` сводку подключенных серверов, поэтому лексический
промах не ошибочно принимается за отсутствующую возможность.
`tool_describe` разрешает каждое запрошенное имя за один вызов; неизвестные имена
сообщаются в `not_found` без сбоев в остальной части пакета.

Когда модель вызывает `tool_call`, Гермес **разворачивает мост** и
отправляет базовый инструмент точно так же, как если бы его вызвала модель
напрямую. Крюки предварительного вызова инструмента, ограждения, запросы на одобрение и
все хуки post-tool-call работают с реальным именем инструмента, а не с
`tool_call`. Лента активности в интерфейсе командной строки и шлюзе также разворачивается, поэтому вы
смотрите базовый инструмент, а не мост.

## Когда он активируется?

Инструмент поиска использует **многоуровневое раскрытие**: наличие *любых* отложенных
Инструмент (MCP/плагин) активирует мост; что такое масштабы с каталожными размерами
какая часть каталога остается видимой, а не откладываются ли схемы.

| Уровень | Состояние | Что видит модель |
| --- | --- | --- |
| **0** | Нет инструментов MCP/плагинов | Каждый инструмент рвется, нет моста. Проходной. |
| **1** | Отложенное размещение в каталоге соответствует бюджету | Bridge + манифест навыков для каждого отложенного инструмента (название + краткое описание, преобразование в имена — только при превышении бюджета). Деградация происходит **на каждом сервере**: когда один слишком большой сервер (Cloudflare) подключается рядом с меньшими (линейными), маленькие серверы сохраняют свои списки инструментов, и только слишком большой сервер сворачивается в сводную строку. |
| **2** | Список инструментов превышает бюджет, даже только имена для каждого сервера (например, только плоская поверхность API Cloudflare: ~ 3300 инструментов, имена которых представляют собой ~ 32 000 токенов) | Простой мост + сводная информация по каждому серверу в одну строку (имя сервера + количество инструментов), чтобы модель знала, какие домены доступны; отдельные инструменты можно обнаружить только через `tool_search`. |

Бюджет листинга составляет `min(threshold_pct% of context, listing_max_tokens)`.
Решение пересматривается каждый раз при построении массива инструментов, поэтому
добавление или удаление серверов MCP в середине сеанса перемещает сеанс между
ярусы на следующей сборке.

## Конфигурация

```yaml
tools:
  tool_search:
    enabled: auto       # auto (default), on, or off
    threshold_pct: 5    # listing budget as a percentage of context
    search_default_limit: 5
    max_search_limit: 25
    listing: auto       # embed a grouped name+description catalog manifest
    listing_max_tokens: 4000
```

| Ключ | По умолчанию | Значение |
| --- | --- | --- |
| `enabled` | `auto` | `auto`/`on` активируются всякий раз, когда существует хотя бы один инструмент с возможностью отсрочки; `off` полностью отключается (все продолжает работать). `auto` в настоящее время является псевдонимом `on` — он зарезервирован для будущего режима, который встраивает схемы, когда они соответствуют контексту, и откладывает только тогда, когда это не так. Закрепите `on` или `off`, если вы хотите, чтобы текущее поведение гарантировалось при всех обновлениях. |
| `threshold_pct` | `5` | Бюджет листинга в процентах от длины контекста активной модели. Диапазон 0–100. |
| `search_default_limit` | `5` | Обращения, возвращаемые для каждого запроса, когда модель вызывает `tool_search` без `limit`. |
| `max_search_limit` | `25` | Жесткая верхняя граница, которую модель может запрашивать через `limit` (для каждого запроса). Диапазон 1–50. |
| `listing` | `auto` | Вставьте манифест в стиле навыков для каждого отложенного инструмента (имя + первое предложение его описания, ≤60 символов, сгруппированных по серверу MCP) в описание моста `tool_search`. `auto` включает его, когда это соответствует бюджету (возвращаясь к только именам, а затем к сводке серверов уровня 2); `on`/`off` принудительно в любом случае. |
| `listing_max_tokens` | `4000` | Абсолютное ограничение на встроенный листинг, независимо от размера контекста. Диапазон 200–60000. Большие каталоги превращаются в сводки только по именам или по каждому серверу, сохраняя полные схемы доступными посредством поиска. |

Ограничения массива для каждого вызова являются внутренними границами безопасности, а не конфигурацией. Чрезмерная крышка
вызовы возвращают ошибку, поэтому модель может повторить попытку с меньшим пакетом.

### Почему существует объявление

Без этого отложенные возможности *невидимы* — показало живое тестирование.
модели, заменяющие видимые основные инструменты (вместо этого запускается `gh` в терминале)
поиска отложенного инструмента GitHub) или объявления возможности
несуществующий вместо вызова `tool_search`. В списке применяются навыки
шаблон для инструментов: каждая возможность всегда доступна для обнаружения по имени,
в то время как полные схемы параметров остаются отложенными. Если модель видит точную
имя инструмента в списке, можно пропустить `tool_search` и сразу перейти к
`tool_describe`, экономлю на поездке туда и обратно.

Вы также можете перевернуть устаревшую логическую форму:

```yaml
tools:
  tool_search: true   # equivalent to {enabled: auto}
```

## Когда НЕ использовать его

Инструмент «Поиск» торгует фиксированной стоимостью жетона за ход (инструмент «три моста»
схемы плюс листинг в каталоге) и как минимум один дополнительный обход туда и обратно.
холодные инструменты (описать → позвонить) для экономии на отложенных схемах.
На уровне 1 листинг сохраняет все возможности видимыми, поэтому обнаружение
Туда-обратно обычно пропадает — модель едет прямо в
`tool_describe`. Живой бенчмаркинг показал соответствие режима листинга
нетерпеливого выполнения задачи погрузки, при этом стоимость меньше, чем голый мост.

Если вам нужно старое поведение «всегда нетерпеливое» для небольшого набора инструментов, установите
`enabled: off`.

## Компромиссы, которые не исчезнут

Они исходят из инварианта целостности кэша подсказок — они присущи
к любому дизайну с прогрессивным раскрытием информации, не специфичному для этой реализации:

- **Одна дополнительная поездка туда и обратно на холодных инструментах.** Первый раз, когда модель нуждается в
  отложенный инструмент, он тратит один или два дополнительных вызова модели, чтобы найти и
  загрузите схему. Экономия токенов на статической стороне реальна, но
  часть выплачивается во время выполнения.
- **Нет преимущества кэширования в отложенных схемах.** Загруженный `tool_describe`
  результат попадает в историю разговоров (поэтому он кэшируется
  последующие ходы), но он никогда не получает выгоды от кэша системных подсказок.
  префикс.
- **Зависимость от качества модели.** Инструмент поиска предполагает, что модель может написать
  разумный поисковый запрос для нужного инструмента. Меньшие модели делают это
  хуже; опубликованные антропные цифры (49% → 74% по Опусу 4 с
  по сравнению с без поиска инструмента) показывают потенциал роста, но также и то, что ~26 пунктов
  точность по-прежнему является ошибкой поиска.
- **Изменение набора инструментов приводит к недействительности кэша.** Добавление или удаление инструмента в середине
  сеанс изменяет описания инструментов моста (которые включают в себя
  количество отложенных инструментов) и каталог, поэтому кэш подсказок
  признан недействительным. Это тот же компромисс, что и при любом редактировании набора инструментов.

## Детали реализации

- **Извлечение:** BM25 по токенизированному имени инструмента, имени источника (MCP
  сервер или набор инструментов плагина, к которому принадлежит инструмент, поэтому поиск `"linear"`
  находит инструменты этого сервера, даже если собственное имя инструмента не несет в себе
  сервис), описание и имена параметров, с помощью Snowball
  стемминг (английский) применяется как к индексу, так и к запросу, поэтому
  морфологические варианты совпадают («проблемы» найдены `create_issue`). водопад
  возврат к буквальному совпадению подстроки имени инструмента при отсутствии запроса
  токен соответствует любому документу (например, поиск `"hub"`, где находится токен
  `github`).
- **Параллельное выполнение разворачивает мост.** Решение принимает пакетный планировщик.
  параллелизм на *основном* инструменте `tool_call`, а не на
  буквальное имя моста — поэтому сервер MCP согласился через
  `supports_parallel_tool_calls: true` сохраняет параллелизм, когда
  инструменты вызываются через мост, а `tool_search`/
  `tool_describe` выполняет пакетный поиск одновременно, как и любой другой инструмент, доступный только для чтения.
- **Каталог не имеет состояния в разные ходы.** Он восстанавливается на основе текущего
  В Tool-defs перечислены все сборки — без сеансового `Map`. Это позволяет избежать
  класс ошибок, при которых сохраненный каталог не синхронизируется с
  живой реестр инструментов.
- **Каталог ограничен наборами инструментов сеанса.** `tool_search`,
  `tool_describe` и `tool_call` видят и вызывают только те инструменты,
  сессия фактически была предоставлена. Субагент, канбан-работник или шлюз
  сеанс, ограниченный подмножеством наборов инструментов, не может использовать мост для
  обнаружить или вызвать инструмент за пределами этого подмножества — отложенный каталог
  отложенный фрагмент собственных включенных/отключенных наборов инструментов сеанса,
  не весь реестр процессов.
- **Нет песочницы JS.** Hermes использует более простой режим «структурированных инструментов».
  (ищите/описывайте/вызовите как простые функции). Код JS-песочницы
  «режим», который предлагают некоторые другие реализации, представляет собой большую площадь поверхности; мы
  пропусти это.
