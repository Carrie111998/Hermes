# Запланированные задачи (Cron)

Планируйте автоматический запуск задач с помощью естественного языка или выражений cron. Hermes предоставляет управление cron с помощью одного инструмента `cronjob` с операциями в стиле действий вместо отдельных инструментов планирования/списка/удаления.

## Что cron теперь может сделать

Задания Cron могут:

- планировать разовые или повторяющиеся задачи
- приостанавливать, возобновлять, редактировать, запускать и удалять задания
- прикреплять к работе ноль, один или несколько навыков
- доставлять результаты обратно в исходный чат, локальные файлы или настроенные целевые платформы.
- запуск новых сеансов агента с обычным статическим списком инструментов
- запуск в **режиме без агента** — сценарий по расписанию, его стандартный вывод доставляется дословно, нулевое участие LLM (см. раздел [режим без агента](#no-agent-mode-script-only-jobs) ниже)

Все это доступно самой компании Hermes через инструмент `cronjob`, поэтому вы можете создавать, приостанавливать, редактировать и удалять задания, задавая простые вопросы — интерфейс командной строки не требуется.

:::совет
**На какой модели выполняется задание cron?** Разрешение во время срабатывания: PIN-код для каждого задания → `cron.model` в `config.yaml` → глобальное значение по умолчанию — `hermes model`.

- **Привязка для каждого задания** — устанавливается *вы* через панель управления, `hermes cron create/edit --model … --provider …`, или путем редактирования `~/.hermes/cron/jobs.json`. После установки он будет действовать до тех пор, пока вы его не измените. Инструмент агента `cronjob` не может устанавливать или изменять модели для каждого задания — выводы вывода принадлежат пользователю.
- **`cron.model` / `cron.model_provider`** — значение по умолчанию для cron-флота: каждое незакрепленное задание выполняется по этой модели, независимо от вашей модели чата. Установите его один раз (`hermes config set cron.model <name>`), и переключение модели чата на `hermes model` или `/model` никогда не затронет ваш парк cron.
- **Глобальное значение по умолчанию** — задание следует за `hermes model`, только если ни одно из вышеперечисленных не установлено. В этом случае Hermes делает **моментальные снимки** поставщика и модели при создании, и если глобальное значение по умолчанию позже меняет задание, **не удается закрыть**: он пропускает выполнение, не выполняет никаких вызовов вывода и предупреждает вас **один раз** — задание остается пропущенным (и молчащим) при последующих тиках, пока вы не начнете действовать или конфигурация не будет восстановлена ​​(#44585). Для повторяющихся или иным образом повторяемых заданий явно закрепите поставщика/модель (`hermes cron edit <job_id> --provider <provider> --model <model>`), чтобы продолжить. Потребленный конечный одноразовый пакет не может быть обновлен; Вместо этого создайте новый одноразовый вариант будущего с явным поставщиком и моделью. Это предотвращает автоматическое наследование переключения на платного поставщика/модель автоматическим заданием. Установка `cron.model` (или контакта для каждого задания) — это преднамеренный способ маршрутизации затрат cron, и защита от дрейфа не включается для оси, на которую он распространяется. Операторы, которые вместо этого хотят, чтобы открепленные задания отслеживали изменение глобального значения по умолчанию, могут [отключить защиту от дрейфа](#letting-unpinned-jobs-track-global-defaults).

`hermes setup --portal` — это вариант с минимальными трудностями для автоматического выполнения, поскольку обновление OAuth происходит автоматически. См. [Nous Portal](/integrations/nous-portal).
:::

:::совет
**Усилия по рассуждению для каждого задания.** Задание может закрепить свой собственный уровень мышления, независимо от закрепления модели: один из `none`, `minimal`, `low`, `medium`, `high`, `xhigh`, `max`, `ultra`. Если он установлен, он переопределяет как глобальный `agent.reasoning_effort`, так и `agent.reasoning_overrides` для каждой модели для выполнения этого задания (`none` отключает мышление). Установите его через `hermes cron create/edit --reasoning-effort high`; передайте пустую строку при редактировании, чтобы очистить пин-код и снова выполните настройку. (Он намеренно не отображается в инструменте агента `cronjob` — конфигурация модели остается на усмотрение пользователя.) Уровни, которые модель не поддерживает, ограничиваются или опускаются поставщиком во время запроса — закрепление `xhigh` на модели, которая ограничивается `high`, выполняется на `high`. Этот вывод не влияет на задания `no_agent` (вызов LLM для настройки отсутствует). Используйте его для запуска тяжелых плановых анализов на `high`, в то время как дешевые повторяющиеся задания выполняются на `minimal`, не затрагивая глобальное значение по умолчанию.
:::

:::предупреждение
Сеансы, запускаемые Cron, не могут рекурсивно создавать дополнительные задания cron. Hermes отключает инструменты управления cron внутри выполнения cron, чтобы предотвратить неконтролируемые циклы планирования.
:::

## Создание запланированных задач

### В чате с `/cron`

```bash
/cron add 30m "Remind me to check the build"
/cron add "every 2h" "Check server status"
/cron add "every 1h" "Summarize new feed items" --skill blogwatcher
/cron add "every 1h" "Use both skills and combine the result" --skill blogwatcher --skill maps
```

### Из автономного интерфейса командной строки

```bash
hermes cron create "every 2h" "Check server status"
hermes cron create "every 1h" "Summarize new feed items" --skill blogwatcher
hermes cron create "every 1h" "Use both skills and combine the result" \
  --skill blogwatcher \
  --skill maps \
  --name "Skill combo"
```

### Через естественный разговор

Спросите Гермеса обычно:

```text
Every morning at 9am, check Hacker News for AI news and send me a summary on Telegram.
```

Hermes будет использовать унифицированный инструмент `cronjob` внутри компании.

## Проверка конфигурации перед отправкой

Прежде чем создавать какой-либо агентский механизм для запланированного запуска, планировщик
проверяет, что конфигурация задания действительно может привести к успешному выполнению:

- разрешается ключ API поставщика (пропускается, если цепочка `fallback_providers`
  настроен, поскольку резервный путь может восстановить отсутствующий первичный ключ),
- готовы прикрепленные навыки (нет отсутствующих необходимых переменных среды,
  команды или файлы учетных данных),
- Целевые платформы доставки известны и для них настроены учетные данные шлюза.
  (Цели `local`/`origin` никогда не проверяются).

Если проверка не удалась, `last_status` задания становится `blocked_config`, ONE.
оповещение доставлено (оно не повторяется каждый тик), и **вызов LLM не осуществляется.
made** — неправильно настроенное задание никогда не тратит токены. Следующий здоровый пробег очищается
состояние блокировки, поэтому в будущем снова будут выдаваться предупреждения о нарушении конфигурации.

Чтобы отключить проверку и восстановить старое поведение (выполнение продолжается и
происходит сбой во время выполнения):

```yaml
cron:
  preflight: false
```

Или: `hermes config set cron.preflight false`

## Разрешение незакрепленным заданиям отслеживать глобальные значения по умолчанию

Защита от дрейфа модели/провайдера включена по умолчанию. Если ваш неприкрепленный cron
вакансии должны сознательно следовать каждой глобальной модели или смене поставщика, отключите
это в `config.yaml`:

```yaml
cron:
  model_drift_guard: false
```

Или используйте команду конфигурации:

```bash
hermes config set cron.model_drift_guard false
```

Это отключает как блок времени выполнения, так и предупреждение, отображаемое при глобальном
Настройки вывода изменяются. Существующие снимки остаются сохраненными, поэтому установка
Возврат к `true` повторно включает защиту без повторного создания заданий.

:::предупреждение
Если защита отключена, автоматические незакрепленные задания немедленно наследуют изменения.
глобальные настройки по умолчанию. Поэтому переход на платного поставщика или модель может привести к трате денег.
при каждом запланированном запуске.
:::

## Задания cron, поддерживаемые навыками

Задание cron может загрузить один или несколько навыков до запуска приглашения.

### Один навык

```python
cronjob(
    action="create",
    skill="blogwatcher",
    prompt="Check the configured feeds and summarize anything new.",
    schedule="0 9 * * *",
    name="Morning feeds",
)
```

### Несколько навыков

Навыки загружаются по порядку. Подсказка становится инструкцией по выполнению задачи, наложенной поверх этих навыков.

```python
cronjob(
    action="create",
    skills=["blogwatcher", "maps"],
    prompt="Look for new local events and interesting nearby places, then combine them into one short brief.",
    schedule="every 6h",
    name="Local brief",
)
```

Это полезно, если вы хотите, чтобы запланированный агент наследовал многократно используемые рабочие процессы, не вставляя полный текст навыка в саму подсказку cron.

## Запуск задания внутри каталога проекта

По умолчанию задания Cron выполняются отдельно от любого репозитория — `AGENTS.md`, `CLAUDE.md` или `.cursorrules` не загружаются, а инструменты терминала/файла/code-exec запускаются из любого рабочего каталога, в котором запущен шлюз. Передайте `--workdir` (CLI) или `workdir=` (вызов инструмента), чтобы изменить это:

```bash
# Standalone CLI (schedule and prompt are positional)
hermes cron create "every 1d at 09:00" \
  "Audit open PRs, summarize CI health, and post to #eng" \
  --workdir /home/me/projects/acme
```

```python
# From a chat, via the cronjob tool
cronjob(
    action="create",
    schedule="every 1d at 09:00",
    workdir="/home/me/projects/acme",
    prompt="Audit open PRs, summarize CI health, and post to #eng",
)
```

Когда установлен `workdir`:

- `AGENTS.md`, `CLAUDE.md` и `.cursorrules` из этого каталога вводятся в системную подсказку (тот же порядок обнаружения, что и в интерактивном интерфейсе командной строки).
- `terminal`, `read_file`, `write_file`, `patch`, `search_files` и `execute_code` используют этот каталог в качестве рабочего каталога.
- Путь должен быть абсолютным существующим каталогом — относительные пути и отсутствующие каталоги отклоняются во время создания/обновления.
– Передайте `--workdir ""` (или `workdir=""` через инструмент) при редактировании, чтобы очистить его и восстановить старое поведение.

:::примечание Сериализация
Задания с `workdir` выполняются последовательно по такту планировщика, а не в параллельном пуле. Это сделано намеренно: работник cron применяет рабочий каталог задания через глобальное состояние терминала процесса, поэтому два задания рабочего каталога, выполняемые одновременно, повредят cwd друг друга. Задания без рабочего каталога по-прежнему выполняются параллельно, как и раньше.
:::

## Редактирование заданий

Вам не нужно удалять и заново создавать задания только для того, чтобы их изменить.

:::tip Ссылка на вакансию
Заполнитель `<job_id>` ниже (и в [Действиях жизненного цикла](#lifecycle-actions)) также принимает имя задания (без учета регистра) — это удобно, если вы помните `morning-digest`, но не шестнадцатеричный идентификатор. Точный идентификатор задания имеет приоритет над совпадениями имен; если ссылка не является идентификатором, а имя соответствует более чем одному заданию, команда отклоняет и печатает идентификаторы кандидатов, чтобы вы могли устранить неоднозначность.
:::

### Чат

```bash
/cron edit <job_id> --schedule "every 4h"
/cron edit <job_id> --prompt "Use the revised task"
/cron edit <job_id> --skill blogwatcher --skill maps
/cron edit <job_id> --remove-skill blogwatcher
/cron edit <job_id> --clear-skills
```

### Автономный интерфейс командной строки

```bash
hermes cron edit <job_id> --schedule "every 4h"
hermes cron edit <job_id> --prompt "Use the revised task"
hermes cron edit <job_id> --skill blogwatcher --skill maps
hermes cron edit <job_id> --add-skill maps
hermes cron edit <job_id> --remove-skill blogwatcher
hermes cron edit <job_id> --clear-skills
```

Примечания:

- повторный `--skill` заменяет прикрепленный к заданию список навыков.
- `--add-skill` добавляется к существующему списку, не заменяя его.
- `--remove-skill` удаляет определенные прикрепленные навыки.
- `--clear-skills` удаляет все прикрепленные навыки

## Действия жизненного цикла

Задания Cron теперь имеют более полный жизненный цикл, чем просто создание/удаление.

### Чат

```bash
/cron list
/cron pause <job_id>
/cron resume <job_id>
/cron run <job_id>
/cron remove <job_id>
```

### Автономный интерфейс командной строки

```bash
hermes cron list
hermes cron pause <job_id_or_name>
hermes cron resume <job_id_or_name>
hermes cron run <job_id_or_name>
hermes cron remove <job_id_or_name>
hermes cron edit <job_id_or_name> [...flags]
hermes cron status
hermes cron tick
```

Что они делают:

- `pause` — сохранить задание, но прекратить его планирование.
- `resume` — повторно включить задание и вычислить следующий будущий запуск.
- `run` — запустить задание на следующем тике планировщика.
- `remove` — удалить полностью
- `edit` — изменить расписание, приглашение, доставку и т. д.

**Поиск по имени.** Все четыре изменяемых глагола (`pause`, `resume`, `run`, `remove`, `edit`), а также инструмент агента `cronjob` теперь принимают задание **имя** (без учета регистра) вместо шестнадцатеричного идентификатора. И агент, и интерфейс командной строки предпочитают точное совпадение идентификаторов, если таковое существует; неоднозначные совпадения имен (несколько вакансий с одинаковым именем) отклоняются при использовании полного списка идентификаторов кандидатов, поэтому вы можете выбрать один явно. Имена не уникальны, поэтому эта защита является несущей — она предотвращает скрытое изменение неправильного задания, когда у двух одинаковые имена.

## Планирование, управляемое агентом (задания cron, которые управляют заданиями cron)

По умолчанию агенты, запускаемые *планировщиком*, не могут использовать инструмент `cronjob` —
запланированное задание не может создавать, редактировать или удалять другие задания. Подпишитесь через
`config.yaml`:

```yaml
cron:
  allow_agent_scheduling: true   # default: false
```

Если эта функция включена, запланированный агент может управлять таблицей cron, как любым чатом.
сеанс: планируйте последующие одиночные снимки из запланированной работы, настраивайте свои собственные
каденции или запустите задание «библиотекаря cron», которое согласует всю таблицу
(перечислить, затем обновить/удалить/создать по мере необходимости). Два свойства сохраняют это в здравом уме:

- **Одна плоская таблица, принадлежащая пользователю.** Задания, созданные с помощью cron, помещаются в
  тот же `jobs.json`, что и любая другая работа без особого права собственности — вы можете
  перечисляйте, редактируйте или удаляйте их точно так же, как если бы вы создали их самостоятельно.
- **Никакой зависшей доставки.** Запуск cron является эфемерным, поэтому `deliver: origin`
  изнутри одного разрешается **во время создания** в собственное создающее задание
  конкретная цель (`platform:chat_id[:thread_id]` или `local`, если создаётся
  работа ни к чему не приводит). Задание, созданное запланированным агентом, никогда не может указывать
  его вывод в сеансе, который больше не существует. Явные цели
  (`local`, `all`, `telegram:<chat_id>`) соблюдаются дословно.

Предпочитать запросы, обновляющие существующие задания (сначала список, затем обновление по идентификатору)
над теми, которые создают новые рабочие места при каждом запуске.

## Как это работает

**Выполнение Cron осуществляется демоном шлюза.** Шлюз проверяет планировщик каждые 60 секунд, выполняя все необходимые задания в изолированных сеансах агента.

```bash
hermes gateway install     # Install as a user service
sudo hermes gateway install --system   # Linux: boot-time system service for servers
hermes gateway             # Or run in foreground

hermes cron list
hermes cron status
```

### Поведение планировщика шлюза

На каждом тике Гермеса:

1. загружает задания с `~/.hermes/cron/jobs.json`
2. сверяет `next_run_at` с текущим временем
3. запускает новый сеанс `AIAgent` для каждого задания
4. при необходимости добавляет в новую сессию один или несколько дополнительных навыков.
5. запускает подсказку до завершения
6. дает окончательный ответ
7. обновления запускают метаданные и следующее запланированное время.

Блокировка файла по адресу `~/.hermes/cron/.tick.lock` предотвращает перекрытие тактов планировщика от двойного запуска одного и того же пакета заданий.

### История выполнения

Hermes записывает каждую заявленную попытку cron в локальном профиле.
`~/.hermes/cron/executions.db` перед отправкой исполнителя или провайдера. Попытки
пройти через `claimed`, `running` и одно неизменяемое терминальное состояние:
`completed`, `failed` или `unknown`. После перезапуска Гермес отмечает заброшенный
пытайтесь выполнить `unknown` только тогда, когда исходный PID и отпечаток запуска процесса подтвердятся.
что его владелец ушел. Неизвестные попытки являются записями аудита и никогда не
автоматический повторный запуск.

Проверьте недавние попытки с помощью `hermes cron runs [job-id] --limit 20` (псевдоним:
`history`). История терминала ограничена; активные попытки никогда не отсекаются.
Ledger включен в быстрое резервное копирование.

### Подталкивание к повторной проверке сбоя

Каждое задание отслеживает `failure_streak` — последовательные неудачные запуски (доставка
неудачи не в счет). Запуск, который завершается неудачно еще до того, как агент вообще достигнет цели —
плохой импорт после полупримененного обновления, клиент провайдера, который невозможно
сконструированный — рассчитывается и выдается оповещение так же, как и при сбое самого агента. Когда
серия *повторяющихся* заданий достигает порога, появляется сообщение об ошибке
при доставке в чат получает подсказку о проверке, сообщающую, что задание не выполнено. N выполнений
подряд и предлагает исправить, приостановить (`hermes cron pause <job>`) или удалить
это. Любое успешное прохождение сбрасывает серию, и `hermes cron list` показывает
полоса рядом с последним запуском неудачного задания. Разовые задания никогда не подталкивают.

```yaml
cron:
  failure_nudge_threshold: 3   # default; 0 disables the nudge
```

### Сбои: подтвердите известный сбой

Повторяющееся задание, которое постоянно завершается сбоем и вызывает *одну и ту же* ошибку, пингует вас каждый раз.
беги. Каждый сбой также регистрируется как долговременный **инцидент**, кодируемый
задание плюс нормализованная подпись текста ошибки в одном и том же профиле
База данных реестра в качестве истории выполнения.

```bash
hermes cron incidents                 # list incidents (newest activity first)
hermes cron incidents --state alerted # filter: detected | alerted | closed
hermes cron incidents ack <id>        # acknowledge — stop re-pinging
```

Признание инцидента отключает пинг сбоя каждого запуска именно для этого
только подпись. Больше ничего не меняется: в истории запусков по-прежнему записываются все
неудача, полоса неудач продолжает отсчитываться, и момент начала работы
в случае сбоя с *другой* ошибкой регистрируется новый инцидент и предупреждается о пожаре
снова. Успешный запуск не затрагивает инциденты — они регистрируются по сигнатурам, а не по
за работу.

Жизненный цикл инцидента: `detected` (записан сбой) → `alerted` (хотя бы один
неудачный пинг достиг доставки) → `closed` (подтверждено; для этого терминал
подпись). Сохраненный текст ошибки секретно редактируется и усекается перед
написано.

Запись всегда включена, и игнорировать ее не стоит ничего — пинг никогда не отключается.
подавляется до тех пор, пока вы явно не `ack`.

### Доставка бот-чата (`bot-chat`)

`bot-chat` передает выходные данные **в канонический сеанс «чата с ботом» профиля как реальное сообщение**. В отличие от любой другой цели, где получателем является человек, читающий канал, получателем здесь является сам бот: он получает выходные данные в виде входящего сообщения, действует на все, что требует действий, и отвечает в своем чате. Используйте его, когда запланированный вывод должен быть *обработан*, а не просто опубликован.

- `bot-chat` (пустой) нацелен на собственный профиль задания.
- `bot-chat:<profile>` нацелен на другой профиль **на той же машине**. Имена проверяются по `hermes profile list` при создании задания; профили на других шлюзах или машинах никогда не могут быть нацелены, поэтому профили с одинаковыми именами на разных машинах однозначны.
- Каждая доставка обходится целевому боту в один полный оборот агента — учитывайте частоту расписания.
- Составляется с другими целями (`bot-chat,telegram`), но никогда не включается в `all`.

### Назначение маршрутизации (`all`)

`all` позволяет отправлять одно задание cron на каждый настроенный вами канал обмена сообщениями без необходимости перечислять их по имени. Эта проблема **решается во время пожара**, поэтому задание, созданное до того, как вы подключили Telegram, подхватит Telegram на следующем такте после установки `TELEGRAM_HOME_CHANNEL`.

Семантика: `all` распространяется на каждую платформу с настроенным домашним каналом. Ноль в порядке; задание просто не создает целевых показателей доставки и регистрируется как сбой доставки в восходящем направлении.

`all` сочиняет с явными целями. `origin,all` осуществляет доставку в исходный чат *плюс* на все остальные подключенные домашние каналы, дублируя их с помощью `(platform, chat_id, thread_id)`.

### Тема cron Telegram (`TELEGRAM_CRON_THREAD_ID`)

Когда включен тематический режим Telegram, корневой DM резервируется как системное лобби — отправленные туда ответы отклоняются с напоминанием о лобби, а `reply_to_message_id` удаляется, поэтому вы не можете ответить на сообщение cron, которое попало в основной чат.

Вместо этого укажите cron на специальную тему форума:

1. В Telegram откройте DM бота и создайте тему, например. `Cron`. Нажмите и удерживайте заголовок темы → **Копировать ссылку**; последнее целое число — это `message_thread_id` темы.
2. Установите `TELEGRAM_CRON_THREAD_ID=<that id>` в свой `.env`.

Это относится только к поставкам cron. `TELEGRAM_HOME_CHANNEL_THREAD_ID` (используется в других местах, например, в уведомлениях о перезапуске) не изменился. Явные цели `deliver="telegram:chat_id:thread_id"` продолжают побеждать переменную env. Ответы на сообщения cron теперь поступают в существующий сеанс темы, поэтому вы можете действовать напрямую.

### Перенос ответа

По умолчанию доставленные выходные данные cron оборачиваются верхним и нижним колонтитулом, чтобы получатель знал, что они получены в результате запланированной задачи:

```
Cronjob Response: Morning feeds
-------------

<agent output here>

Note: The agent cannot see this message, and therefore cannot respond to it.
```

Чтобы доставлять необработанные выходные данные агента без оболочки, установите для `cron.wrap_response` значение `false`:

```yaml
# ~/.hermes/config.yaml
cron:
  wrap_response: false
```

#### Плоское продолжение внутри канала (Slack)

Приведенное выше поведение, предпочтительное для потоков, создает выделенный поток для каждого
доставка. Если вы предпочитаете постоянную работу, найдите **квартиру в канале.
временная шкала** — без цепочки — установите для **непрерывной поверхности** Slack значение `in_channel`:

```yaml
# ~/.hermes/config.yaml
slack:
  cron_continuable_surface: in_channel   # default: thread
  reply_in_thread: false                 # required pairing (see below)
  require_mention: false                 # so a plain reply continues the job
```

В режиме `in_channel` бриф доставляется как обычный канал верхнего уровня.
сообщение (ни одна ветка не открыта), и ваш ответ продолжает работу через
общий сеанс канала. Три настройки работают вместе:

- **`cron_continuable_surface: in_channel`** — пропускает создание потока при доставке.
- **`reply_in_thread: false`** (обязательно) — заставляет бота ответить на ваш ответ
  *плоско* в канале и переключите его на тот же сеанс всего канала, краткий обзор
  был посеян в. Без него продолжение все еще работает, но приходит в
  поток (он безопасно возвращается к продолжению в стиле потока, никогда не удаляется
  ответ — шлюз регистрирует предупреждение при запуске, чтобы вы могли обнаружить несоответствие).
- **`require_mention: false`** (или добавьте канал в `free_response_channels`)
  — чтобы вы могли ответить простым сообщением; в противном случае бот просыпается только тогда, когда вы
  `@` – упоминайте об этом в каждом ответе.

Поскольку продолжением является сеанс **всего канала**, оно является общим: другие
болтовня в канале — и вторая продолжающаяся внутриканальная работа — присоединяйтесь к тому же
катящийся разговор. Это присуще «флету в канале» и является тем же самым
компромисс `reply_in_thread: false` пользователи уже приняли; используйте значение по умолчанию
`thread` появляется, когда вы хотите изолировать отслеживание каждой доставки.

для каждой платформы, устанавливается в конфигурации каждой платформы. Это флаг конфигурации на стороне шлюза.
— `/restart` подхватывает его; переустановка приложения Slack не требуется.

:::примечание 1:1 в личные сообщения
`cron_continuable_surface` — это настройка **канала**. DM 1:1 не имеет
разделение потока и временной шкалы на выбор (DM уже плоский), поэтому ключ

### Тихое подавление

Если окончательный ответ агента содержит `[SILENT]`, доставка полностью подавляется. Вывод по-прежнему сохраняется локально для аудита (в `~/.hermes/cron/output/`), но никакое сообщение не отправляется в цель доставки.

Это полезно для мониторинга заданий, которые должны сообщать только о том, что что-то не так:

```text
Check if nginx is running. If everything is healthy, respond with only [SILENT].
Otherwise, report the issue.
```

Невыполненные задания всегда выполняются независимо от маркера `[SILENT]` — отключить звук можно только при успешных запусках. Для заданий тихого мониторинга предложите агенту ответить только `[SILENT]`, если не о чем сообщить.

## Таймаут скрипта

Предварительные сценарии (подключаемые с помощью параметра `script`) имеют время ожидания по умолчанию 3600 секунд (1 час). Это ограничивает **только сценарий** — задания, основанные на навыках или LLM, выполняются с отдельным бюджетом неактивности и не ограничены этим значением. Если вашим скриптам нужен другой лимит, вы можете его изменить:

```yaml
# ~/.hermes/config.yaml
cron:
  script_timeout_seconds: 1800   # 30 minutes
```

Или установите переменную среды `HERMES_CRON_SCRIPT_TIMEOUT`. Порядок разрешения: env var → config.yaml → 3600s по умолчанию.

Cron также ограничивает очистку сеанса после запуска и ресурсов агента. Это происходит после возврата хода LLM, поэтому оно не связано с тайм-аутом бездействия. Значение по умолчанию — 10 секунд на операцию очистки. Если финализатор хранилища или клиента перестает возвращать результаты, планировщик регистрирует ошибку, снимает защиту в полете задания и позволяет последующим запускам выполнять отправку вместо того, чтобы навсегда пропускать это задание.

```yaml
# ~/.hermes/config.yaml
cron:
  cleanup_timeout_seconds: 10
```

Установите `cleanup_timeout_seconds: 0` только для восстановления устаревшего режима неограниченной очистки.

## Тайм-аут отправки мультимедиа

Когда доставка cron включает в себя мультимедийные вложения (сгенерированный PDF-файл, аудио TTS, экспортированный отчет), отправленные через адаптер живого шлюза, каждая загрузка вложения ограничена тайм-аутом — по умолчанию 300 секунд. Большим файлам на медленных восходящих каналах может потребоваться больше:

```yaml
# ~/.hermes/config.yaml
cron:
  media_send_timeout_seconds: 600   # 10 minutes per attachment
```

Или установите переменную среды `HERMES_CRON_MEDIA_SEND_TIMEOUT`. Порядок разрешения: env var → config.yaml → 300s по умолчанию. Вложение с истекшим сроком действия записывается в статусе выполнения задания как сбой частичной доставки (текст все равно доставляется).

## Тайм-аут доставки чата бота

Доставка `bot-chat` запускает полный оборот агента в чате целевого бота, поэтому ее граница составляет минуты, а не секунды — по умолчанию 600 с:

```yaml
# ~/.hermes/config.yaml
cron:
  bot_chat_delivery_timeout_seconds: 900
```

Срок доставки записывается в `last_delivery_error`; ход бота все еще может завершиться самостоятельно.

## Режим без агента (задания только для сценариев)

Для повторяющихся заданий, которые не требуют рассуждений LLM — классических сторожевых таймеров, предупреждений о диске/памяти, тактовых импульсов, пингов CI — передайте `no_agent=True` во время создания. Планировщик запускает ваш скрипт по расписанию и доставляет его стандартный вывод напрямую, полностью пропуская агент:

```bash
hermes cron create "every 5m" \
  --no-agent \
  --script memory-watchdog.sh \
  --deliver telegram \
  --name "memory-watchdog"
```

Семантика:

- Стандартный вывод сценария (обрезанный) → доставлен дословно в виде сообщения.
- **Пустой стандартный вывод → тихая галочка**, доставка отсутствует. Это сторожевой шаблон: «говори что-нибудь только тогда, когда что-то не так».
- Ненулевой выход или тайм-аут → выдается предупреждение об ошибке, поэтому сломанный сторожевой таймер не может выйти из строя молча.
- `{"wakeAgent": false}` в последней строке → тихая галочка (те же ворота, которые используются в заданиях LLM).
— Никаких токенов, никакой модели, никакого резервного поставщика — задание никогда не затрагивает уровень вывода.

Файлы `.sh`/`.bash` выполняются под именем `bash` из `PATH`, если они доступны, в противном случае — `/bin/bash` (важно для Windows Git Bash). Все остальное выполняется под текущим интерпретатором Python (`sys.executable`). Сценарии должны разрешаться внутри `$HERMES_HOME/scripts/` — относительные имена, абсолютные пути и пути с префиксом `~` принимаются, когда разрешенная цель остается в этом каталоге; пути, уходящие от него, отвергаются. Окружение подпроцесса очищено (`_sanitize_subprocess_env`): учетные данные API поставщика и другие секреты, управляемые Hermes, **не** наследуются сценариями cron.

### Агент настроит их для вас

Схема инструмента `cronjob` предоставляет `no_agent` непосредственно Hermes, поэтому вы можете описать сторожевой таймер в чате и позволить агенту подключить его:

```text
Ping me on Telegram if RAM is over 85%, every 5 minutes.
```

Hermes напишет сценарий проверки на `~/.hermes/scripts/` через `write_file`, а затем вызовет:

```python
cronjob(action="create", schedule="every 5m",
        script="memory-watchdog.sh", no_agent=True,
        deliver="telegram", name="memory-watchdog")
```

Он выбирает `no_agent=True` автоматически, когда содержимое сообщения полностью определяется сценарием (сторожевые таймеры, пороговые оповещения, контрольные сигналы). Тот же инструмент также позволяет агенту приостанавливать, возобновлять, редактировать и удалять задания — поэтому весь жизненный цикл управляется через чат, и никто не затрагивает интерфейс командной строки.

Рабочие примеры см. в [Руководстве по заданиям Cron только для сценариев](/guides/cron-script-only).

## Объединение заданий с помощью `context_from`

Задания Cron выполняются в изолированных сеансах без памяти о предыдущих запусках. Но иногда результаты одной работы — это именно то, что нужно следующей работе. Параметр `context_from` автоматически устанавливает это соединение — приглашение задания B получает самые последние выходные данные задания A, добавляемые в качестве контекста во время выполнения.

```python
# Job 1: Collect raw data
cronjob(
    action="create",
    prompt="Fetch the top 10 AI/ML stories from Hacker News. Save them to ~/.hermes/data/briefs/raw.md in markdown format with title, URL, and score.",
    schedule="0 7 * * *",
    name="AI News Collector",
)

# Job 2: Triage — receives Job 1's output as context
# Get Job 1's ID from: cronjob(action="list")
cronjob(
    action="create",
    prompt="Read ~/.hermes/data/briefs/raw.md. Score each story 1–10 for engagement potential and novelty. Output the top 5 to ~/.hermes/data/briefs/ranked.md.",
    schedule="30 7 * * *",
    context_from="<job1_id>",
    name="AI News Triage",
)

# Job 3: Ship — receives Job 2's output as context
cronjob(
    action="create",
    prompt="Read ~/.hermes/data/briefs/ranked.md. Write 3 tweet drafts (hook + body + hashtags). Deliver to telegram:7976161601.",
    schedule="0 8 * * *",
    context_from="<job2_id>",
    name="AI News Brief",
)
```

**Как это работает:**

- Когда Задание 2 срабатывает, Гермес читает последний вывод Задания 1 из `~/.hermes/cron/output/{job1_id}/*.md`.
- Этот вывод автоматически добавляется к приглашению задания 2.
- Заданию 2 не нужно жестко запрограммировать «прочитать этот файл» — оно получает содержимое в качестве контекста.
- Цепочка может быть любой длины: Работа 1 → Работа 2 → Работа 3 → ...

**Что принимает `context_from`:**

| Формат | Пример |
|--------|---------|
| Идентификатор отдельного задания (строка) | `context_from="a1b2c3d4"` |
| Несколько идентификаторов вакансий (список) | `context_from=["job_a", "job_b"]` |

Выходы объединяются в указанном порядке.

**Непрерывность: сохранение результатов предыдущего выполнения**

Установите `continuity=true`, и задание будет вводить свой *собственный* самый последний вывод в каждый запуск. Повторяющиеся задания обычно начинаются с амнезии — разведчик новостей повторно сообщает одни и те же новости, монитор повторно предупреждает о тех же условиях. При включенной непрерывности задание просыпается и видит то, что оно сообщило в прошлый раз, и может выполнить дедупликацию и продолжить с того места, где оно остановилось:

```python
cronjob(
    action="create",
    prompt="Scan HN and arXiv for new agent-tooling papers. Report only items NOT already covered in your previous run's output.",
    schedule="every 6h",
    continuity=True,
    name="Agent Tooling Scout",
)
```

Первый запуск не имеет предыдущих выходных данных, поэтому приглашение выполняется как есть. При более поздних запусках к предыдущему выводу добавляется кадр непрерывности («избегайте повторения того, что уже было сообщено»). Он свободно комбинируется с вышестоящими заданиями (`context_from=["<other_job_id>"]` плюс `continuity=true`), а `continuity=false` при обновлении отключает его, сохраняя при этом другие записи `context_from`. Внутри флаг хранится как зарезервированная запись `self` в `context_from`.

Из интерфейса командной строки: `hermes cron create "every 6h" "Scan for news" --continuity` и `hermes cron edit <job_id> --continuity` / `--no-continuity`, чтобы переключить его на существующее задание. Тот же переключатель появляется в редакторе cron на панели управления и в диалоговом окне режима бота на рабочем столе.

**Когда использовать:**

- Многоэтапные конвейеры (собрать → фильтровать → форматировать → доставить)
- Зависимые задачи, в которых работа шага N зависит от результатов шага N-1.
- Шаблоны разветвления/разветвления, при которых одно задание объединяет результаты нескольких других.
- Повторяющиеся разведчики/мониторы, которые должны выполнять дедупликацию на основе своего предыдущего отчета (`continuity=true`)

## Восстановление провайдера

Задания Cron наследуют настроенных резервных поставщиков и ротацию пула учетных данных. Если основной ключ API ограничен по скорости или поставщик возвращает ошибку, агент cron может:

- **Вернитесь к альтернативному поставщику**, если у вас есть `fallback_providers` (или устаревший `fallback_model`), настроенный в `config.yaml`.
- **Переход к следующим учетным данным** в вашем [пуле учетных данных](/user-guide/configuration#credential-pool-strategies) для того же поставщика.

Это означает, что задания cron, которые выполняются с высокой частотой или в часы пик, более устойчивы — один ключ с ограниченной скоростью не приведет к сбою на протяжении всего выполнения.

## Пропущенные запланированные пожары (`last_fire_error`)

В размещенных (управляемых cron) развертываниях запланированный пожар передается от планировщика платформы через панель мониторинга на внутренний сервер API шлюза. Если эта окончательная передача не удалась — процесс шлюза не работает или прослушиватель его API-сервера никогда не запускался — выполнение никогда не начинается, поэтому нет ни записи выполнения, ни `last_status` для проверки. Характерная форма: задание срабатывает каждый раз, когда вы запускаете его вручную, но никогда не запускается автоматически.

Эти промахи отмечаются в записи о задании как `last_fire_error` (метка времени + причина) и обнаруживаются:

- Инструмент `cronjob` → `action: "list"` — поле `last_fire_error`
- `hermes cron list` — красная линия `⚠ Missed scheduled fire:` под заданием.
- Просмотр заданий на панели мониторинга.

Штамп всегда отражает **текущее** состояние автопожара: он перезаписывается новыми промахами и автоматически очищается при следующем успешном запуске. Если вы это видите, задание и его расписание в порядке — сторона шлюза пожарного пути требует внимания (чаще всего перезапустите шлюз через его супервизор, чтобы он загрузил полную среду профиля: `hermes gateway restart`).

### Устранение осечки

Когда внешний поставщик планировщика активен (управляемый cron в размещенных развертываниях), шлюз также запускает догоняющую проверку: задание, запланированное время которого прошло, а пожар не был доставлен (и чье льготное окно истекло), запрашивается и выполняется локально, поэтому сбой при передаче пожара стоит минут, а не целого дня. Очистка дедуплицируется против поздних повторных попыток планировщика с помощью того же утверждения хранилища, которое используется для обычных пожаров.

```yaml
cron:
  misfire_grace_minutes: 10   # wait this long for the scheduler's own retries
                              # before catching up locally; 0 disables catch-up
```

Локальные (встроенные тикерные) развертывания в этом не нуждаются — тикер уже подхватывает просроченные задания на следующем такте.

## Форматы расписания

Окончательный ответ агента автоматически доставляется в цель `deliver:` задания — агент больше не отправляет сообщения сам, поэтому содержимое, обращенное к пользователю, просто включается в окончательный ответ. Чтобы доставить **дополнительные или разные** цели, укажите несколько целей `deliver:` в задании cron (через запятую, например `deliver: "telegram,discord"`), а не отправляйте их агенту.

### Относительные задержки (однократные)

```text
30m     → Run once in 30 minutes
2h      → Run once in 2 hours
1d      → Run once in 1 day
```

### Интервалы (повторяющиеся)

```text
every 30m    → Every 30 minutes
every 2h     → Every 2 hours
every 1d     → Every day
```

### Выражения Cron

```text
0 9 * * *       → Daily at 9:00 AM
0 9 * * 1-5     → Weekdays at 9:00 AM
0 */6 * * *     → Every 6 hours
30 8 1 * *      → First of every month at 8:30 AM
0 0 * * 0       → Every Sunday at midnight
```

### Временные метки ISO

```text
2026-03-15T09:00:00    → One-time at March 15, 2026 9:00 AM
```

## Повторить поведение

| Тип расписания | Повтор по умолчанию | Поведение |
|--------------|----------------|----------|
| Одноразовый (`30m`, временная метка) | 1 | Запускается один раз |
| Интервал (`every 2h`) | навсегда | Работает, пока не будет удален |
| Выражение Cron | навсегда | Работает, пока не будет удален |

Вы можете переопределить его:

```python
cronjob(
    action="create",
    prompt="...",
    schedule="every 2h",
    repeat=5,
)
```

## Наборы инструментов, доступные для заданий cron

Cron запускает каждое задание в новом сеансе агента без подключения платформы чата. По умолчанию агент cron получает **набор инструментов, который вы настроили для платформы `cron` в `hermes tools`**, а не CLI по умолчанию и не все на свете.

```bash
hermes tools
# → pick the "cron" platform in the curses UI
# → toggle toolsets on/off just like you would for Telegram/Discord/etc.
```

Более строгий контроль над каждым заданием доступен через поле `enabled_toolsets` на `cronjob.create` (или на существующем задании через `cronjob.update`):

```text
cronjob(action="create", name="weekly-news-summary",
        schedule="every sunday 9am",
        enabled_toolsets=["web", "file"],      # just web + file, no terminal/browser/etc.
        prompt="Summarize this week's AI news: ...")
```

Когда `enabled_toolsets` приступает к выполнению задания, он побеждает; в противном случае побеждает конфигурация cron-платформы `hermes tools`; в противном случае Hermes вернется к встроенным настройкам по умолчанию. Это важно для контроля затрат: использование `browser`, `delegation` в каждой крошечной задаче по получению новостей приводит к раздуванию подсказки схемы инструмента при каждом вызове LLM.

### Полный пропуск агента: `wakeAgent`

Если к вашему заданию cron прикреплен сценарий предварительной проверки (через `script=`), сценарий может решить во время выполнения, следует ли Hermes вообще вызывать агент. Выдайте последнюю строку стандартного вывода формы:

```text
{"wakeAgent": false}
```

…и cron полностью пропускает запуск агента для этого тика. Полезно для частых опросов (каждые 1–5 минут), при которых LLM необходимо разбудить только тогда, когда состояние действительно изменилось — в противном случае вы снова и снова платите за обороты агента с нулевым содержанием.

```python
# pre-check script
import json, sys
latest = fetch_latest_issue_count()
prev = read_state("issue_count")
if latest == prev:
    print(json.dumps({"wakeAgent": False}))   # skip this tick
    sys.exit(0)
write_state("issue_count", latest)
print(json.dumps({"wakeAgent": True, "context": {"new_issues": latest - prev}}))
```

Если `wakeAgent` опущен, значением по умолчанию является `true` (разбудить агент как обычно).

####Рецепты: дешевые ворота заранее

Ворота `wakeAgent` дают вам возможность за 0 долларов решить, должно ли запланированное задание вообще тратить токены LLM. Три шаблона охватывают большинство случаев использования.

**Шлюз изменения файла** — запускается только в том случае, если в отслеживаемом файле появилось новое содержимое с момента последнего успешного тика. Планировщик записывает `last_run_at` каждого задания; сравните его с mtime файла.

```bash
#!/bin/bash
# ~/.hermes/scripts/feed-changed.sh
FEED="$HOME/data/feed.json"
STATE="$HOME/.hermes/scripts/.feed-changed.last"
test -f "$FEED" || { echo '{"wakeAgent": false}'; exit 0; }
mtime=$(stat -c %Y "$FEED")
last=$(cat "$STATE" 2>/dev/null || echo 0)
if [ "$mtime" -le "$last" ]; then
  echo '{"wakeAgent": false}'
else
  echo "$mtime" > "$STATE"
  echo '{"wakeAgent": true}'
fi
```

```text
cronjob(action="create", name="process-feed",
        schedule="every 30m",
        script="feed-changed.sh",
        prompt="A new ~/data/feed.json has landed. Summarize what changed.")
```

**Шлюз внешнего флага** — запускается только тогда, когда какой-либо другой процесс сигнализирует о готовности (например, перехватчик развертывания удаляет файл, задание CI устанавливает значение в вашем хранилище состояний).

```bash
#!/bin/bash
# ~/.hermes/scripts/flag-ready.sh
if test -f /tmp/new-data-ready; then
  rm -f /tmp/new-data-ready
  echo '{"wakeAgent": true}'
else
  echo '{"wakeAgent": false}'
fi
```

```text
cronjob(action="create", name="nightly-analysis",
        schedule="0 9 * * *",
        script="flag-ready.sh",
        prompt="Run the nightly analysis over today's batch.")
```

**Ворота подсчета SQL** — запускаются только тогда, когда в вашей собственной базе данных есть новые строки для обработки. Сценарий также может передавать счетчик агенту через `context`, чтобы агент знал, сколько он просматривает, без повторного запроса.

```python
#!/usr/bin/env python
# ~/.hermes/scripts/new-rows.py
import json, sqlite3
conn = sqlite3.connect("/home/me/data/app.db")
n = conn.execute(
    "SELECT COUNT(*) FROM messages WHERE ts > strftime('%s','now','-2 hours')"
).fetchone()[0]
if n < 1:
    print(json.dumps({"wakeAgent": False}))
else:
    print(json.dumps({"wakeAgent": True, "context": {"new_rows": n}}))
```

```text
cronjob(action="create", name="summarize-new-msgs",
        schedule="every 2h",
        script="new-rows.py",
        prompt="Summarize the new messages from the last 2 hours.")
```

Тот же шаблон работает для любого источника данных, который вы можете запросить из сценария — Postgres, HTTP API, вашего собственного хранилища состояний — без включения оценщика SQL в подсистему cron.

:::совет
Собственная `~/.hermes/state.db` компании Hermes — это внутренняя схема, которая меняется между выпусками. Не запрашивайте его из предварительно запущенного шлюза — вместо этого укажите на свою собственную базу данных или канал.
:::

Кредит: этот набор рецептов был вызван исследованием @iankar8 в [#2654](https://github.com/NousResearch/hermes-agent/pull/2654), в котором предлагалось добавить триггеры sql/file/command в качестве параллельного механизма. Ворота `script` + `wakeAgent` уже охватывают все три случая по цене 0 долларов, поэтому вместо этого работа попала в документацию.

### Объединение заданий: `context_from`

Задание cron может использовать самые последние успешные выходные данные одного или нескольких других заданий, перечислив их имена (или идентификаторы) в `context_from`:

```text
cronjob(action="create", name="daily-digest",
        schedule="every day 7am",
        context_from=["ai-news-fetch", "github-prs-fetch"],
        prompt="Write the daily digest using the outputs above.")
```

Результаты последних завершенных заданий, на которые имеются ссылки, вставляются над приглашением в качестве контекста для этого запуска. Каждая восходящая запись должна представлять собой действительный идентификатор или имя задания (см. `cronjob action="list"`). Примечание: цепочка считывает *самые последние завершенные* выходные данные — она не ожидает выполнения вышестоящих заданий, выполняющихся в тот же такт.

## Хранилище заданий

Задания хранятся в `~/.hermes/cron/jobs.json`. Результаты выполнения заданий сохраняются в `~/.hermes/cron/output/{job_id}/{timestamp}.md`.

Определения заданий представляют собой простой JSON на диске: они сохраняются при `hermes update`, перезапуске шлюза и перезагрузке компьютера. Задание, выполнение которого во время перезапуска находилось в середине, помечается в журнале выполнения как `unknown` — оно не повторяется автоматически, но следующий запланированный тик задания срабатывает нормально. Подробности см. в разделе [История выполнения](#execution-history).

:::совет
Попросите агента управлять заданиями с помощью инструмента `cronjob`, `hermes cron edit` или `/cron`, а не путем исправления `jobs.json` напрямую. Прямое редактирование может завершиться неудачно, если [безопасность записи файла](../security.md#file-write-safety) блокирует путь (например, если установлен `HERMES_WRITE_SAFE_ROOT`), а нижний колонтитул [file-mutation verifier](../configuration.md#file-mutation-verifier) ​​является достоверным сигналом о том, что ничего не было сохранено.
:::

Задания могут хранить `model` и `provider` как `null`. Если эти поля опущены, Hermes разрешает их во время выполнения из глобальной конфигурации. Они появляются в записи о задании только в том случае, если установлено переопределение для каждого задания.

В хранилище используется атомарная запись файлов, поэтому при прерванной записи не остается частично записанного файла задания.

## Самостоятельные подсказки по-прежнему имеют значение

:::предупреждение Важно
Задания Cron выполняются в совершенно новом сеансе агента. Приглашение должно содержать все, что нужно агенту, чего еще не предусмотрено прикрепленными навыками.
:::

**ПЛОХО:** `"Check on that server issue"`

**ХОРОШО:** `"SSH into server 192.168.1.100 as user 'deploy', check if nginx is running with 'systemctl status nginx', and verify https://example.com returns HTTP 200."`

## Безопасность

Запросы запланированных задач сканируются на предмет шаблонов внедрения подсказок и кражи учетных данных во время создания и обновления. Запросы, содержащие невидимые трюки Unicode, попытки бэкдора SSH или очевидные полезные данные для раскрытия секретов, блокируются.
