# Учебное пособие по Канбану

Пошаговое описание четырех вариантов использования системы Hermes Kanban с открытой в браузере информационной панелью. Если вы еще не прочитали [Обзор Канбана](./kanban), начните с него — это предполагает, что вы знаете, что такое задача, запуск, ответственный и диспетчер.

## Настройка

```bash
hermes kanban init           # optional; first `hermes kanban <anything>` auto-inits
hermes dashboard             # opens http://127.0.0.1:9119 in your browser
# click Kanban in the left nav
```

Приборная панель — самое удобное место для **вас** наблюдения за системой. Работники-агенты, которых создает диспетчер, никогда не видят панель мониторинга или интерфейс командной строки — они управляют доской через специальный `kanban_*` [набор инструментов](./kanban#how-workers-interact-with-the-board) (`kanban_show`, `kanban_list`, `kanban_complete`, `kanban_block`, `kanban_heartbeat`, `kanban_comment`, `kanban_attach`, `kanban_attach_url`, `kanban_attachments`, `kanban_create`, `kanban_link`, `kanban_unblock`). Все три поверхности — панель мониторинга, интерфейс командной строки, рабочие инструменты — проходят через одну и ту же базу данных SQLite для каждой платы (`~/.hermes/kanban.db` для платы по умолчанию, `~/.hermes/kanban/boards/<slug>/kanban.db` для любой доски, которую вы создадите позже), поэтому каждая плата единообразна независимо от того, с какой стороны забора произошло изменение.

В этом уроке повсюду используется плата `default`. Если вам нужно несколько изолированных очередей (по одной на проект/репозиторий/домен), см. раздел [Доски (мультипроект)](./kanban#boards-multi-project) в обзоре — одни и те же потоки CLI/панели мониторинга/работников применяются к каждой доске, и работники физически не могут видеть задачи на других досках.

На протяжении всего руководства **блоки кода с меткой `bash` — это команды, которые *вы* выполняете.** Блоки кода с меткой `# worker tool calls` — это то, что порожденная модель работника выдает в виде вызовов инструментов. Они показаны здесь для того, чтобы вы могли видеть цикл от начала до конца, а не потому, что вы когда-либо запускали их самостоятельно.

## Обзор платы

![Обзор доски Канбан](/img/kanban-tutorial/01-board-overview.png)

Шесть столбцов, слева направо:

- **Триаж** — сырые идеи. По умолчанию диспетчер автоматически запускает **декомпозер** для задач здесь: встроенный декомпозер использует `auxiliary.kanban_decomposer`, считывает список вашего профиля + описания и создает график дочерних задач, направляемых наиболее подходящим специалистам. Исходная задача сохраняется как родительская, поэтому ее ответственный (`kanban.orchestrator_profile` или активный профиль по умолчанию, если он не установлен) снова просыпается, чтобы оценить завершение, когда все завершится. Переверните табличку **Оркестрация: Авто/Ручной** в верхней части страницы канбана, чтобы переключать режимы. В ручном режиме нажмите **⚗ Разложить** на карточке или запустите `hermes kanban decompose <id>` / `/kanban decompose <id>`. Для отдельных задач, которые не требуют разветвления, **✨ Specify** выполняет однократное переписывание спецификации (цель, подход, критерии приемки) и повышает ее до `todo`. Настройте модели под `auxiliary.kanban_decomposer` и `auxiliary.triage_specifier` в `config.yaml`. См. раздел [Автоматическая и ручная оркестровка](./kanban#auto-vs-manual-orchestration) в основном руководстве по Канбану.
- **Todo** — создано, но ожидает зависимостей или еще не назначено.
- **Готов** — назначен и ждет заявки от диспетчера.
- **В процессе** — рабочий активно выполняет задачу. Если включен параметр «Дорожки по профилю» (по умолчанию), этот столбец группируется по исполнителям, поэтому вы можете сразу увидеть, что делает каждый работник.
- **Заблокировано** — работник запросил вмешательство человека или сработал автоматический выключатель.
- **Done** — завершено.

Верхняя панель содержит фильтры для поиска, арендатора и правопреемника, а также переключатель `Lanes by profile` и кнопку `Nudge dispatcher`, которая запускает один такт отправки прямо сейчас, вместо ожидания следующего интервала демона. При нажатии на любую карту открывается ее ящик справа.

## История 1. Индивидуальный разработчик выпускает новую функцию

Вы создаете функцию. Классический процесс: спроектируйте схему, реализуйте API, напишите тесты. Три задачи с родительскими и дочерними зависимостями.

```bash
SCHEMA=$(hermes kanban create "Design auth schema" \
    --assignee backend-dev --tenant auth-project --priority 2 \
    --body "Design the user/session/token schema for the auth module." \
    --json | jq -r .id)

API=$(hermes kanban create "Implement auth API endpoints" \
    --assignee backend-dev --tenant auth-project --priority 2 \
    --parent $SCHEMA \
    --body "POST /register, POST /login, POST /refresh, POST /logout." \
    --json | jq -r .id)

hermes kanban create "Write auth integration tests" \
    --assignee qa-dev --tenant auth-project --priority 2 \
    --parent $API \
    --body "Cover happy path, wrong password, expired token, concurrent refresh."
```

Поскольку родительским элементом `API` является `SCHEMA`, а родительским элементом `tests` является `API`, только `SCHEMA` начинается с `ready`. Двое других сидят в `todo`, пока их родители не закончат. Это механизм продвижения зависимостей, выполняющий свою работу — ни один другой работник не возьмется за написание тестов, пока не будет API для тестирования.

При следующем такте диспетчера (по умолчанию 60 секунд или сразу же, если вы нажмете **Сдвинуть диспетчера**) профиль `backend-dev` появляется как рабочий с `HERMES_KANBAN_TASK=$SCHEMA` в его среде. Вот как выглядит цикл вызова инструмента работника изнутри агента:

```python
# worker tool calls — NOT commands you run
kanban_show()
# → returns title, body, worker_context, parents, prior attempts, comments

# (worker reads worker_context, uses terminal/file tools to design the schema,
#  write migrations, run its own checks, commit — the real work happens here)

kanban_heartbeat(note="schema drafted, writing migrations now")

kanban_complete(
    summary="users(id, email, pw_hash), sessions(id, user_id, jti, expires_at); "
            "refresh tokens stored as sessions with type='refresh'",
    metadata={
        "changed_files": ["migrations/001_users.sql", "migrations/002_sessions.sql"],
        "decisions": ["bcrypt for hashing", "JWT for session tokens",
                      "7-day refresh, 15-min access"],
    },
)
```

`kanban_show` по умолчанию устанавливает для `task_id` значение `$HERMES_KANBAN_TASK`, поэтому работнику не нужно знать свой собственный идентификатор. `kanban_complete` записывает сводку и метаданные в текущую строку `task_runs`, закрывает выполнение и передает задачу `done` — и все это за один атомарный переход через `kanban_db`.

Когда `SCHEMA` достигает `done`, механизм зависимостей автоматически повышает `API` до `ready`. Работник API, когда он поднимет трубку, вызовет `kanban_show()` и увидит сводку и метаданные `SCHEMA`, прикрепленные к родительской передаче, поэтому он знает решения по схеме, не перечитывая длинный проектный документ.

Щелкните выполненное задание схемы на доске, и в ящике появится все:

![Solo dev — завершенный ящик задач схемы](/img/kanban-tutorial/03-drawer-schema-task.png)

Раздел «История запусков» внизу является ключевым дополнением. Одна попытка: результат `completed`, исполнитель `@backend-dev`, длительность, метка времени и полная сводка передачи. Большой двоичный объект метаданных (`changed_files`, `decisions`) также сохраняется при выполнении и доступен любому нижестоящему рабочему процессу, который читает этого родительского объекта.

Вы можете просмотреть те же данные со своего терминала в любое время — эти команды **вы** просматриваете доску, а не работника:

```bash
hermes kanban show $SCHEMA
hermes kanban runs $SCHEMA
# #  OUTCOME       PROFILE       ELAPSED  STARTED
# 1  completed     backend-dev        0s  2026-04-27 19:34
#     → users(id, email, pw_hash), sessions(id, user_id, jti, expires_at); refresh tokens ...
```

## История 2 — Фарм флота

У вас трое работников (переводчик, транскриптор, копирайтер) и куча самостоятельных задач. Вы хотите, чтобы все три работали параллельно и добились видимого прогресса. Это самый простой вариант использования канбана, для которого оптимизирован первоначальный дизайн.

Создайте работу:

```bash
for lang in Spanish French German; do
    hermes kanban create "Translate homepage to $lang" \
        --assignee translator --tenant content-ops
done
for i in 1 2 3 4 5; do
    hermes kanban create "Transcribe Q3 customer call #$i" \
        --assignee transcriber --tenant content-ops
done
for sku in 1001 1002 1003 1004; do
    hermes kanban create "Generate product description: SKU-$sku" \
        --assignee copywriter --tenant content-ops
done
```

Запустите шлюз и уходите — на нем размещен встроенный диспетчер.
который решает задачи всех трех профилей специалистов одновременно
канбан.дб:

```bash
hermes gateway start
```

Теперь отфильтруйте доску по `content-ops` (или просто найдите «Расшифровать»), и вы получите следующее:

![Просмотр парка отфильтрован для расшифровки задач](/img/kanban-tutorial/07-fleet-transcribes.png)

Две расшифровки завершены, одна выполняется, две готовы и ждут следующего тика диспетчера. Столбец «В работе» сгруппирован по профилям (по умолчанию «Дорожки по профилю»), поэтому вы можете видеть активную задачу каждого работника, не просматривая смешанный список. Диспетчер переведет следующую готовую задачу на выполнение сразу после завершения текущей. Поскольку три демона работают над тремя пулами правопреемников параллельно, вся очередь контента опустошается без дальнейшего участия человека.

**Все, что говорилось в Истории 1 о структурированной передаче обслуживания, по-прежнему применимо и здесь.** Сотрудник-переводчик, завершающий вызов, выдает `kanban_complete(summary="translated 4 pages, style matched existing marketing voice", metadata={"duration_seconds": 720, "tokens_used": 2100})` — полезно для аналитики и для любой последующей задачи, которая зависит от этой.

## История 3. Ролевой конвейер с повтором

Именно здесь Канбан зарабатывает себе на жизнь благодаря плоскому списку TODO. ПМ пишет спецификацию. Это реализует инженер. Рецензент отклоняет первую попытку. Инженер пытается еще раз внести изменения. Рецензент одобряет.

Представление информационной панели, отфильтрованное по `auth-project`:

![Представление конвейера для многоролевой функции](/img/kanban-tutorial/08-pipeline-auth.png)

На снимке экрана используется **заранее созданная модель нисходящей карты**: у карты реализации есть специальный дочерний рецензент. В этой модели инженер должен вызвать `kanban_complete`, когда реализация будет готова, чтобы дочерний проверяющий мог покинуть `todo`. Никогда не блокируйте родительскую реализацию только для того, чтобы запросить проверку.

Для рабочих процессов, в которых реализация и проверка принадлежат одной и той же карте, вместо этого используйте жизненный цикл первоклассной проверки. Полная реализация → проверка → изменения → повторная проверка хореографии:

```python
# --- Engineer: first implementation attempt ---
kanban_show()
# (write code, run tests, prepare the candidate)
kanban_request_review(
    summary="implemented reset flow; candidate is ready for review",
    metadata={"changed_files": ["auth/reset.py"], "tests_run": 8},
    reviewer="reviewer",
)
# → the same card enters review; the implementation run closes as
#   outcome='review_requested'

# --- Reviewer: request concrete changes ---
kanban_show()
# (inspect the handoff and candidate)
kanban_request_changes(
    reason="Add password-strength validation and make reset tokens single-use."
)
# → the review run closes as outcome='changes_requested'; the card returns
#   to backend-dev in ready/todo without touching block-loop accounting

# --- Engineer: second implementation attempt ---
kanban_show()  # prior review evidence is in worker_context
# (apply feedback and re-run tests)
kanban_request_review(
    summary="added zxcvbn validation and single-use reset tokens",
    metadata={
        "changed_files": [
            "auth/reset.py",
            "auth/tests/test_reset.py",
            "migrations/003_single_use_reset_tokens.sql",
        ],
        "tests_run": 11,
        "review_iteration": 2,
    },
    reviewer="reviewer",
)

# --- Reviewer: approve ---
kanban_complete(summary="review passed; acceptance criteria verified")
# → done
```

В журнале выполнения задачи теперь записано `review_requested → changes_requested → review_requested → completed`. У каждой попытки есть свой участник, сводка, метаданные и результат, поэтому второй инженер точно видит, что отклонил проверяющий, а окончательное утверждение остается проверяемым. `kanban_block` зарезервировано для реальной внешней эскалации (отсутствует доступ, решение по продукту, недоступная инфраструктура), а не для обычной обратной связи.

Если вы намеренно используете модель нисходящей карты, показанную на снимке экрана, рецензент открывает `Review password reset PR` после завершения родительской реализации:

![Вид рецензента на конвейер](/img/kanban-tutorial/09-drawer-pipeline-review.png)

`worker_context` карточки рецензента включает завершенную передачу реализации. Это отдельный рабочий процесс с картами; не объединяйте ее с той же картой `kanban_request_review`, иначе вы дублируете полосу обзора.

## История 4. Автоматический выключатель и аварийное восстановление

Настоящие работники терпят неудачу. Отсутствуют учетные данные, убийства OOM, временные сетевые ошибки. У диспетчера есть две линии защиты: **автоматический выключатель**, который автоматически блокируется после N последовательных сбоев, чтобы плата не зависала навсегда, и **обнаружение сбоев**, который восстанавливает задачу, рабочий PID которой исчез до истечения срока ее TTL.

### Автоматический выключатель — постоянная неисправность

Задача развертывания, которая не может создать своего рабочего, поскольку `AWS_ACCESS_KEY_ID` не установлен в среде профиля:

```bash
hermes kanban create "Deploy to staging (missing creds)" \
    --assignee deploy-bot --tenant ops \
    --max-retries 3
```

Диспетчер пытается породить работника. Не удалось создать спаун (`RuntimeError: AWS_ACCESS_KEY_ID not set`). Диспетчер освобождает заявку, увеличивает счетчик неудач и пытается повторить попытку в следующем такте. Поскольку в этом примере устанавливается `--max-retries 3`, схема отключается после трёх последовательных сбоев: задача переходит к `blocked` с результатом `gave_up`. Если вы опустите флаг, Hermes будет использовать `kanban.failure_limit` (по умолчанию: 2). Больше никаких повторных попыток, пока человек не разблокирует его.

Нажмите на заблокированную задачу:

![Выключатель — 2 spawn_failed + 1 Give_up](/img/kanban-tutorial/11-drawer-gave-up.png)

Три запуска, все с одной и той же ошибкой в поле `error`. Первые два — `spawn_failed` (повторные), третий — `gave_up` (терминал). В приведенном выше журнале событий показана полная последовательность: `created → claimed → spawn_failed → claimed → spawn_failed → claimed → gave_up`.

На терминале:

```bash
hermes kanban runs t_ef5d
# #   OUTCOME        PROFILE        ELAPSED  STARTED
# 1   spawn_failed   deploy-bot          0s  2026-04-27 19:34
#       ! AWS_ACCESS_KEY_ID not set in deploy-bot env
# 2   spawn_failed   deploy-bot          0s  2026-04-27 19:34
#       ! AWS_ACCESS_KEY_ID not set in deploy-bot env
# 3   gave_up        deploy-bot          0s  2026-04-27 19:34
#       ! AWS_ACCESS_KEY_ID not set in deploy-bot env
```

Если Telegram / Discord / Slack подключены, при событии `gave_up` срабатывает уведомление шлюза, поэтому вы узнаете об отключении без необходимости проверять плату.

### Аварийное восстановление — рабочий погиб во время полета

Иногда порождение завершается успешно, но рабочий процесс позже завершается — segfault, OOM, `systemctl stop`. Диспетчер опрашивает `kill(pid, 0)` и обнаруживает неработающий идентификатор pid; требование отменяется, задача возвращается к `ready`, а следующий тик передает ее новому работнику.

Примером начальных данных является миграция, для которой не хватало памяти:

```bash
# Worker claims, starts scanning 2.4M rows, OOM kills it at ~2.3M
# Dispatcher detects dead pid, releases claim, increments attempt counter
# Retry with a chunked strategy succeeds
```

В ящике отображается полная история двух попыток:

![Сбой и восстановление — 1 сбой + 1 завершено](/img/kanban-tutorial/06-drawer-crash-recovery.png)

Запуск 1 — `crashed`, с ошибкой `OOM kill at row 2.3M (process 99999 gone)`. Запуск 2 — `completed` с `"strategy": "chunked with LIMIT + WHERE id > last_id"` в метаданных. Повторяющий рабочий процесс увидел сбой первого запуска в его контексте и выбрал более безопасную стратегию; метаданные делают очевидным для будущего наблюдателя (или автора вскрытия) то, что изменилось.

## Структурированная передача управления — почему `summary` и `metadata` важны

В каждой истории выше рабочие звонили в конце на номер `kanban_complete(summary=..., metadata=...)`. Это не украшение — это основной канал передачи управления между этапами рабочего процесса.

Когда работник задачи B создается и вызывает `kanban_show()`, `worker_context`, который он получает, включает в себя:

– **Предыдущие попытки** B (предыдущие запуски: результат, сводка, ошибка, метаданные), чтобы повторяющий рабочий процесс не повторял неудачный путь.
- **Результаты родительской задачи** – для каждого родительского задания отображается сводка и метаданные последнего завершенного выполнения, чтобы сотрудники нижестоящего уровня могли видеть, почему и как была выполнена работа вышестоящего уровня.

Это заменяет танец «копаться в комментариях и результатах работы», который преследует плоские системы канбана. Менеджер по проекту записывает критерии приемки в метаданные спецификации, а работник инженера видит их структурно в родительской передаче. Инженер записывает, какие тесты он провел и сколько из них было пройдено, и сотрудник рецензента держит этот список на руках, прежде чем открыть разницу.

Защита массового закрытия существует, поскольку эти данные относятся к каждому запуску. `hermes kanban complete a b c --summary X` (вам, из CLI) отказывают — копировать одно и то же резюме на три задачи почти всегда неправильно. Массовое закрытие без флагов передачи по-прежнему работает в обычном случае «Я выполнил кучу административных задач». Поверхность инструмента вообще не представляет объемного варианта; По той же причине `kanban_complete` всегда выполняет одну задачу одновременно.

## Отслеживание выполненной карты — исправление CI через родительскую ссылку

Карточка реализации истории 1 — `done`. Через два часа произошел сбой CI в объединенной ветке. Не открывайте повторно готовую карту — завершенные карты уходят в историю, и их передача продолжается. Создайте карту исправления, указав готовую карту в качестве **родительского**:

```bash
hermes kanban create "Fix CI: test_backoff_jitter flakes on 3.11" \
    --assignee backend-dev \
    --parent t_impl \
    --workspace worktree --branch wt/ci-fix-backoff \
    --body "CI run #4812 failed after t_impl completed.
FAILED tests/test_retry.py::test_backoff_jitter - TimeoutError
Acceptance: tests/test_retry.py green on 3.11 and 3.12."
```

Три вещи делают эту работу эффективной:

- **Немедленная отправка.** Поскольку родительским элементом уже является `done`, дочерний элемент создается прямо в `ready` — диспетчер может запросить его на следующем такте. (Дочерний элемент все еще открытого родителя будет ждать в `todo`.)
- **Унаследованный контекст.** Контекст работника исправления включает раздел *Результаты родительской задачи*, содержащий сводку о завершении `t_impl` и метаданные — измененные файлы и решения, записанные исходным работником, — поэтому он знает, почему код имеет такую форму, прежде чем прочитать его строку.
- **Свежие доказательства в теле.** Журнал CI не существовал на момент завершения `t_impl`, поэтому он не может находиться в передаче родительской функции — он помещается в тело новой карты вместе с явными критериями приемлемости.

Предпочитайте новое рабочее дерево/ветвь для карты исправления. Проверка исходной ветки дает рабочему репозиторию *состояние*, но не дает никакого *обоснования* — это несет родительская передача. Один и тот же профиль правопреемника обычно прав: профиль, написавший код, обладает навыками его исправления.

## Следующие шаги

- [Обзор Канбана](./kanban) — полная модель данных, словарь событий и справочник по CLI.
- `hermes kanban --help` — каждая подкоманда, каждый флаг.
- `hermes kanban watch --kinds completed,gave_up,timed_out` — прямая трансляция событий терминала по всей доске.
