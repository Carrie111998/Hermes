# Делегирование субагента

Инструмент `delegate_task` порождает дочерние экземпляры AIAgent с изолированным контекстом, унаследованным доступом к инструменту и собственными терминальными сеансами. Каждый ребенок получает новый разговор и работает самостоятельно — только его итоговое содержание входит в контекст родителя.

Вызовы моделей верхнего уровня выполняются автоматически в фоновом режиме. Hermes немедленно возвращает дескриптор, чтобы разговор мог продолжиться, а затем отправляет результат обратно в виде нового сообщения. Субагент оркестратора ожидает своих собственных исполнителей, чтобы он мог синтезировать их результаты перед возвращением.

## Одна задача

```python
delegate_task(
    goal="Debug why tests fail",
    context="Error: assertion in test_foo.py line 42"
)
```

## Параллельная партия

По умолчанию до 3 одновременных субагентов (настраиваемые, без жесткого потолка):

```python
delegate_task(tasks=[
    {"goal": "Research topic A", "context": "Focus on recent primary sources"},
    {"goal": "Research topic B", "context": "Compare the leading explanations"},
    {"goal": "Fix the build", "context": "Project root: /home/user/project"}
])
```

## Как работает контекст субагента

:::Внимание Критическое: Субагенты ничего не знают
Субагенты начинают с **совершенно нового разговора**. Они ничего не знают об истории разговоров родителя, предыдущих вызовах инструментов или о чем-либо, что обсуждалось перед делегированием. Единственный контекст субагента исходит из полей `goal` и `context`, которые родительский агент заполняет при вызове `delegate_task`.
:::

Единственное исключение: если у родителя есть разрешенный каталог рабочей области, в системное приглашение каждого субагента встраиваются **файлы контекста проекта** этого рабочего пространства (`.hermes.md` > цепочка AGENTS.md > CLAUDE.md > `.cursorrules` — те же ограничения обнаружения, приоритета и размера, что и в системном приглашении основного агента; SOUL.md исключен). Субагенты, работающие в репо, действуют в соответствии с собственными соглашениями репо, не открывая их заново.

Это означает, что родительский агент должен передать в вызове **все**, что нужно субагенту:

```python
# BAD - subagent has no idea what "the error" is
delegate_task(goal="Fix the error")

# GOOD - subagent has all context it needs
delegate_task(
    goal="Fix the TypeError in api/handlers.py",
    context="""The file api/handlers.py has a TypeError on line 47:
    'NoneType' object has no attribute 'get'.
    The function process_request() receives a dict from parse_body(),
    but parse_body() returns None when Content-Type is missing.
    The project is at /home/user/myproject and uses Python 3.11."""
)
```

Субагент получает целенаправленное системное приглашение, созданное на основе вашей цели и контекста, которое дает ему указание выполнить задачу и предоставить структурированное описание того, что он сделал, что он нашел, любых измененных файлов и любых возникших проблем.

## Практические примеры

### Параллельные исследования

Исследуйте несколько тем одновременно и собирайте резюме:

```python
delegate_task(tasks=[
    {
        "goal": "Research the current state of WebAssembly in 2025",
        "context": "Focus on: browser support, non-browser runtimes, language support"
    },
    {
        "goal": "Research the current state of RISC-V adoption in 2025",
        "context": "Focus on: server chips, embedded systems, software ecosystem"
    },
    {
        "goal": "Research quantum computing progress in 2025",
        "context": "Focus on: error correction breakthroughs, practical applications, key players"
    }
])
```

### Проверка кода + исправление

Делегируйте рабочий процесс проверки и исправления в новый контекст:

```python
delegate_task(
    goal="Review the authentication module for security issues and fix any found",
    context="""Project at /home/user/webapp.
    Auth module files: src/auth/login.py, src/auth/jwt.py, src/auth/middleware.py.
    The project uses Flask, PyJWT, and bcrypt.
    Focus on: SQL injection, JWT validation, password handling, session management.
    Fix any issues found and run the test suite (pytest tests/auth/)."""
)
```

### Многофайловый рефакторинг

Делегируйте большую задачу рефакторинга, которая заполнила бы родительский контекст:

```python
delegate_task(
    goal="Refactor all Python files in src/ to replace print() with proper logging",
    context="""Project at /home/user/myproject.
    Use the 'logging' module with logger = logging.getLogger(__name__).
    Replace print() calls with appropriate log levels:
    - print(f"Error: ...") -> logger.error(...)
    - print(f"Warning: ...") -> logger.warning(...)
    - print(f"Debug: ...") -> logger.debug(...)
    - Other prints -> logger.info(...)
    Don't change print() in test files or CLI output.
    Run pytest after to verify nothing broke."""
)
```

## Подробности пакетного режима

Когда агент верхнего уровня предоставляет массив `tasks`, Hermes возвращает один фоновый дескриптор, запускает подагенты параллельно и публикует один консолидированный результат после завершения работы каждого дочернего элемента. Субагент оркестратора ожидает своего пакета в текущем ходу, чтобы синтезировать результаты.

– **Максимальный параллелизм:** 3 задачи по умолчанию (настраивается через `delegation.max_concurrent_children` или переменную окружения `DELEGATION_MAX_CONCURRENT_CHILDREN`; этаж 1, без жесткого потолка). Пакеты, превышающие лимит, возвращают ошибку инструмента, а не автоматически усекаются.
- **Пул потоков:** использует `ThreadPoolExecutor` с настроенным ограничением параллелизма в качестве максимального числа рабочих процессов.
- **Отображение хода выполнения.** В режиме CLI в виде дерева отображаются вызовы инструментов от каждого субагента в режиме реального времени со строками завершения каждой задачи. В режиме шлюза прогресс группируется и передается обратному вызову родительского процесса.
- **Упорядочение результатов.** Результаты сортируются по индексу задачи, чтобы соответствовать порядку ввода, независимо от порядка завершения.
- **Отмена:** Последующие сообщения не отменяют фоновый пакет верхнего уровня. `/stop` или закрытие/сброс сеанса-владельца отменяет его активные дочерние элементы. Дочерние элементы синхронного оркестратора по-прежнему следуют состоянию прерывания своего родителя.

Синхронное делегирование одной задачи от оркестратора выполняется напрямую, без дополнительных затрат на пул потоков.

### Надежные фоновые завершения

Когда фоновое делегирование завершается, Hermes сохраняет событие завершения в
`state.db` активного профиля перед публикацией его в обычном обновлении
очередь. Если Гермес перезапустится после завершения, но до доставки, ожидающий
событие восстанавливается и маршрутизируется через те же проверки владения. Конкуренция
потребители используют долгосрочное требование, поэтому только тот потребитель, который успешно принимает
синтетический поворот подтверждает доставку; неудачные попытки снять претензию на
повторите попытку.

Это не возобновляет выполнение дочернего процесса после сбоя. Делегация, владелец которой
процесс исчезает, пока он еще работает, записывается как `unknown`, потому что
Гермес не может доказать, имели ли место его внешние побочные эффекты. В ожидании и
доставляемые записи ограничены и локальны по профилю.

### Уведомления о дочерних фоновых процессах

Фоновые процессы, которые запускает субагент (например, `npm ci` с
`notify_on_complete`) технически проложить маршрут их завершения и схему наблюдения
уведомления в **родительском** разговоре, потому что все, что переживает
ребенку нужен прочный потребитель. По умолчанию эти уведомления
**подавлено** в родительском чате — результат консолидированного делегирования дочернего элемента
это конечный результат, и в середине разговора «процесс завершен» от стены от
внутренние построения ребенка – это шум. Подавленные события регистрируются на уровне отладки.
с идентификатором сеанса процесса и идентификатором задачи субагента, чтобы они оставались диагностируемыми.

Сам результат делегирования никогда не подавляется. Чтобы восстановить доставку
уведомления дочерних процессов (каждое содержит надпись «Запущено субагентом…»
строка авторства):

```yaml
delegation:
  surface_child_process_notifications: true   # default: false
```

## Переопределение модели

Вы можете настроить другую модель для субагентов через `config.yaml` — это полезно для делегирования простых задач более дешевым/быстрым моделям:

```yaml
# In ~/.hermes/config.yaml
delegation:
  model: "google/gemini-flash-2.0"    # Cheaper model for subagents
  provider: "openrouter"              # Optional: route subagents to a different provider
```

Если этот параметр опущен, субагенты используют ту же модель, что и родительский.

### Стратегия затрат: планировщик границ, недорогие рабочие

Разложение проблемы на четко определенные подзадачи требует принятия решений на пограничном уровне; выполнение подзадачи, которая уже имеет четкую цель, полный контекст и выходной контракт, обычно не имеет. В то же время дочерние элементы находятся там, куда идут токены — параллельная партия субагентов обычно сжигает большую часть общего количества токенов цикла, поэтому рабочая модель — это то место, где фактически живут затраты. Привязка `delegation.model` к недорогой модели, в то время как основной сеанс остается на пограничной модели, позволяет сохранить качество планирования там, где это важно, и сократить расходы там, где объемы:

```yaml
# ~/.hermes/config.yaml
model:
  default: "your-frontier-model"     # parent (planner) stays on the frontier model
delegation:
  model: "your-inexpensive-model"    # all delegate_task children run on this
  provider: "openrouter"             # optional: route children to a different provider
```

Порядок разрешения: `delegation.base_url` (прямая конечная точка) имеет приоритет, затем `delegation.provider` (полный пакет учетных данных, разрешенный через систему поставщика среды выполнения), и если ни один из них не установлен, дети наследуют родительского поставщика и учетные данные; `delegation.model` применяется во всех случаях, и когда он пуст, дети наследуют модель родителя.

Обратите внимание, что этот вывод является глобальным: `delegate_task` не имеет параметра модели для каждой задачи, поэтому каждый дочерний элемент в пакете выполняется по настроенной модели делегирования. Для подзадач, чувствительных к качеству, которым требуется более надежная модель, либо оставьте `delegation.model` отключенным для этого сеанса, либо передайте задачу [доске канбана](kanban.md#per-task-model-override), которая поддерживает переопределение модели для каждой задачи.

## Команда `/review`

`/review` порождает независимый фоновый субагент с полными привилегиями, единственная задача которого — проверять работу, которую только что произвел ваш разговор — PR, различия, код, документацию, дизайн. Он работает на любой поверхности: CLI, TUI, настольном приложении и любой платформе обмена сообщениями шлюза.

```
/review                       # review whatever the last 10 messages presented
/review focus on security     # add extra instructions for the reviewer
```

Что происходит:

1. Последние 10 сообщений пользователя/помощника сохраняются в качестве начального доказательства рецензента (вывод инструмента и системные сообщения исключаются).
2. Субагент рецензента отправляется по той же фоновой шине делегирования, что и `delegate_task` — он получает полный набор инструментов обычного субагента (терминал, Интернет, файлы, браузер...), поэтому он фактически открывает PR, читает различия и запускает код, а не судит по отрывку.
3. Рецензент наследует рабочий контекст основного агента: любые навыки, которые основной агент загрузил (предварительно загруженные при запуске или через `skill_view` во время сеанса), называются в его брифинге с инструкцией загрузить их и оценить работу в соответствии с их соглашениями. Как и любой субагент, его системное приглашение также включает файлы контекста проекта рабочей области (AGENTS.md / CLAUDE.md / .cursorrules) в качестве соглашений о привязке.
4. По завершении его полная проверка снова входит в тот же сеанс, что и обычное завершение фонового субагента — ваш основной агент видит его и может действовать в соответствии с ним (исправить выводы, отправить последующие действия, ответить вам).

Канонический процесс: ваш главный агент открывает PR, вы набираете `/review`, а вторая пара глаз изучает его, пока вы продолжаете работать; отзыв возвращается в чат, адресованный агенту, создавшему PR.

### Обзор модели

By default the reviewer runs on your main model. Чтобы закрепить специальную модель для обзора, установите `auxiliary.review` в `config.yaml`:

```yaml
auxiliary:
  review:
    provider: openrouter               # or nous, anthropic, a direct base_url, ...
    model: anthropic/claude-opus-4.6   # a strong reviewer model
```

Учетные данные разрешаются точно так же, как контакт `delegation.provider` (полный пакет поставщика среды выполнения: base_url, ключ API, api_mode). `provider: auto` с пустым `model` означает «наследовать модель основного агента» — значение по умолчанию.

`/review` намеренно отделен от `/refine`: `/refine` просматривает разговор, чтобы обновить память и навыки, `/review` просматривает *рабочий продукт*, созданный в результате разговора.

## Доступ к унаследованному инструменту

`delegate_task` не принимает параметр `toolsets`, ориентированный на модель. Каждый субагент наследует включенные наборы инструментов родительского агента, поэтому модель не может предоставить дочернему агенту возможности, которых нет у родителя. Настройте родительские инструменты перед началом разговора, если делегированная работа требует дополнительных возможностей.

Определенные инструменты блокируются для субагентов, даже если они есть у родителя:
- `delegate_task` — заблокирован для конечных субагентов (по умолчанию). Сохраняется для дочерних элементов `role="orchestrator"`, ограниченных `max_spawn_depth` — см. [Ограничение глубины и вложенная оркестровка](#глубина-предел-и-вложенная оркестровка) ниже.
- `clarify` — субагенты не могут взаимодействовать с пользователем
- `memory` — запись в общую постоянную память не производится.
- `send_message` — no cross-platform side effects
- `cronjob` — дополнительная работа от имени родителя не планируется.

Обе роли сохраняют `execute_code` (программный вызов инструментов), поэтому дети могут выполнять механическую работу в пакетном режиме.

## Макс. итераций

У каждого субагента есть лимит итераций (по умолчанию: 50), который определяет, сколько циклов вызова инструмента может потребоваться:

```python
delegate_task(
    goal="Quick file check",
    context="Check if /etc/nginx/nginx.conf exists and print its first 10 lines",
    max_iterations=10  # Simple task, don't need many turns
)
```

## Дочерний тайм-аут

По умолчанию на субагентах **тайм-аут настенных часов** отсутствует. Дети терпят неудачу только из-за того, что они на самом деле делают — ошибок API, ошибок инструментов или превышения бюджета итерации — и никогда из-за секундомера на уровне делегирования. В более ранних выпусках было жесткое ограничение (300-е, позднее 600-е), которое продолжало убивать законно занятых детей в середине задачи: глубокие проверки кода, крупные исследовательские разветвления и медленные модели рассуждения обычно требуют более 10 минут, при этом все время обеспечивая устойчивый прогресс.

По-настоящему зависшие дочерние элементы по-прежнему обнаруживаются: монитор сердцебиения перестает обновлять активность родителя, когда дочерний элемент не достигает прогресса (нет вызовов API, нет запуска инструмента и нет меток времени активности), позволяя шлюзу срабатывать по тайм-ауту бездействия на действительно заклиненном рабочем процессе. Ожидание модели в реальном времени по-прежнему считается прогрессом — субагенты обновляют часы активности во время ожидания поставщика, поэтому медленное локальное завершение или завершение с длительным предварительным заполнением не рассматривается как остановленное.

Если вам все равно нужно жесткое ограничение (например, контроль затрат на автоматическое делегирование, управляемое cron), выберите настройку по количеству установок:

```yaml
delegation:
  child_timeout_seconds: 0     # default: 0 = no timeout
  # child_timeout_seconds: 1800  # opt-in hard cap (floor 30s)
```

Положительное значение устанавливает жесткий предел настенных часов для каждого дочернего элемента; `0` или отрицательное значение отключает его.

Когда срабатывает настроенное ограничение, дочерний результат имеет структурированный тайм-аут.
метаданные рядом с сообщением об ошибке, чтобы родители и перехватчики могли различить
убийство секундомера от других сбоев без разбора текста: `timeout_seconds`
(настроенная крышка), `timed_out_after_seconds` (настоящие настенные часы) и
`timeout_phase` (`before_first_llm_call`, когда ребенок так и не достиг своего
первый запрос, `after_llm_calls` в противном случае). Все трое включены `null`
ошибки, не связанные с тайм-аутом.

:::tip Диагностический дамп при тайм-ауте нулевого вызова
При настройке жесткого ограничения, если у субагента истекает время выполнения **нулевых** вызовов API (обычно из-за недоступности поставщика, сбоя аутентификации или отклонения схемы инструмента), `delegate_task` записывает структурированную диагностику в `~/.hermes/logs/subagent-timeout-<session>-<timestamp>.log`, содержащую снимок конфигурации субагента, трассировку разрешения учетных данных, любые ранние сообщения об ошибках и трассировки стека для **всех** активных потоков (а не только собственных дочерних) — дочерний элемент припаркован в ожидании вложенный вспомогательный поток неотличим от медленного провайдера без полной картины.
:::

## Обнаружение остановок для фоновых субагентов

За фоновыми делегациями (`delegate_task(background=true)`) наблюдает

## Мониторинг работающих подагентов (`/agents`)

TUI предоставляет наложение `/agents` (псевдоним `/tasks`), которое превращает рекурсивное разветвление `delegate_task` в первоклассную поверхность аудита:

- Живое древовидное представление запущенных и недавно завершенных субагентов, сгруппированных по родительскому элементу.
- Стоимость каждого филиала, токен и объединение файлов.
- Элементы управления убийством и паузой — отмените работу конкретного субагента в процессе работы, не прерывая его братьев и сестер.
- Последующий обзор: просматривайте пошаговую историю каждого субагента даже после того, как он вернулся к родительскому агенту.

Классический интерфейс командной строки просто печатает `/agents` как текстовую сводку; TUI — это то место, где сияет накладка. См. [TUI — команды слэша](/user-guide/tui#slash-commands).

В классическом интерфейсе командной строки и на каждой платформе шлюза (Telegram, Discord, Slack...)
`/agents` также перечисляет **фоновые делегирования с живой активностью каждого ребенка**,
взято непосредственно у каждого работающего дочернего элемента:

```
Background delegations: 1 running
- deleg_ab12cd34 · running · research the delegation stall monitor
  - child 1: 4 api calls · in web_search · active 12s ago
  - child 2: 7 api calls · between turns · active 3s ago
```

Делегация, которую монитор киоска пометил, показывает как
`stalling · no progress 450s — interrupting`, и давно тихий, но здоровый
дети показывают свое тихое время, чтобы вы могли отличить «медленно» от «застрявшего»
взгляд.

## Управление работающим субагентом

Прерывание ребенка сводит на нет его работу в полете; часто вы просто хотите перенаправить его.

### От родительского агента (обращённого к модели)

Родительский агент управляет своими собственными запущенными дочерними элементами с помощью того же инструмента `delegate_task`, с помощью которого он их породил, — без отдельного инструмента управления:

```json
{"action": "list"}
{"action": "steer", "subagent_id": "sa-0-1a2b3c4d", "message": "focus on pricing instead"}
{"action": "stop",  "subagent_id": "sa-0-1a2b3c4d"}
```

- **`list`** возвращает живые дочерние элементы беседы: `subagent_id`, цель, статус, `running_seconds`, `accepting_steer` и путь к активной расшифровке. Идентификаторы также возвращаются в ответе на отправку появления как `subagent_ids`.
- **`steer`** ставит в очередь коррекцию курса работающего дочернего элемента, не останавливая его (семантика доставки ниже).
- **`stop`** завершает дочерний элемент раньше на границе следующей итерации; частичный результат по-прежнему повторно входит в разговор как обычное сообщение о завершении.

Действия управления выполняются синхронно поочередно (никогда не в фоновом режиме), ограничены собственным деревом появления вызывающего абонента — диалог никогда не может видеть или контролировать дочерние элементы другого сеанса — и никогда не используют лимит появления субагента за ход, поэтому `stop` продолжает работать даже после достижения ограничения.

### Из TUI/шлюза (с сеансовым доступом)

`steer_subagent(subagent_id, text)` в `tools/delegate_tool.py` является зеркалом на стороне перенаправления `interrupt_subagent()`: он помещает текст в очередь в живой дочерний элемент с помощью того же механизма, что и [`/steer`](/reference/slash-commands) — текст добавляется к последнему результату дочернего инструмента на границе следующей итерации, текущий вызов инструмента никогда не прерывается, и дочерний элемент видит его как внеполосного пользователя сообщение. Программные хосты достигают его через RPC-шлюз `subagent.steer` в области сеанса, который находится рядом с `subagent.interrupt`:

```json
{"method": "subagent.steer", "params": {"session_id": "owning-ui-session", "subagent_id": "sa-0-1a2b3c4d", "text": "focus on pricing instead"}}
```

Идентификаторы субагентов берутся из `delegation.status` (или `list_active_subagents()`) — из того же места, где их получает `subagent.interrupt`. Шлюз принимает управление только из того живого сеанса пользовательского интерфейса/шлюза, который породил дочерний элемент. Отсутствующий, посторонний, неоднозначный или устаревший/переработанный идентификатор сеанса отклоняется; знание глобального идентификатора субагента не является авторитетом. Прямые вызовы в процессе намеренно сохраняют вспомогательный контракт с незаданной областью действия.

**В очереди не доставляется, но это никогда не является синтетическим успехом.** Ответ `"queued"` означает, что текст был принят до границы завершения дочернего элемента, не обязательно, что дочерний элемент его видел. Принятие и завершение синхронизируются: либо дочерний элемент все еще может потреблять текст, либо его точный текст передается в результат как `pending_steer`. Вызовы после закрытия возвращают `"rejected"`. Если ребенок принял подсказку, но уже дал окончательный ответ, запись о завершении, которую получает родитель, сохраняет его как `missed_steer` с примечанием, добавленным к сводке:

```
[steer did not land — the subagent finished before it could be delivered: focus on pricing instead]
```

Таким образом, родитель (или оператор, управляющий им) может отличить управляемого ребенка от ребенка, который выполнил старые инструкции, и повторно выдать указание в качестве продолжения, вместо того, чтобы верить, что оно приземлилось.

## Живые стенограммы

При каждой отправке `delegate_task` также создается один **доступный только для добавления, удобочитаемый журнал для каждой задачи**, поэтому вы (или родительский агент) можете наблюдать за работой субагента в режиме реального времени, а не ждать сводной сводки:

```
<hermes_home>/cache/delegation/live/<delegation_id>/task-<n>.log
```

Ответ на отправку включает пути как `live_transcripts`, а файлы создаются заранее во время отправки, поэтому это работает немедленно:

```bash
tail -f ~/.hermes/cache/delegation/live/deleg_ab12cd34/task-0.log
```

Каждая строка имеет временную метку и показывает текст помощника ребенка, фрагменты размышлений, вызовы инструментов (`-> tool_name({args})`), результаты работы инструментов и маркер конечного состояния. `manifest.json` в том же каталоге описывает пакет (цели, количество задач, статус каждой задачи). Журналы сохраняются после завершения — они служат полной операционной записью наряду со сводкой — а каталоги старше 7 дней автоматически удаляются при новых рассылках. Поскольку они находятся под адресом `cache/delegation`, их также можно прочитать из серверных частей удаленного терминала (Docker/Modal/SSH).

## Ограничение глубины и вложенная оркестровка

По умолчанию делегирование является **плоским**: родительский элемент (глубина 0) порождает дочерние элементы (глубина 1), и эти дочерние элементы не могут делегировать дальше. Это предотвращает неконтролируемое рекурсивное делегирование.

Для многоэтапных рабочих процессов (исследование → синтез или параллельная оркестровка подзадач) родитель может создавать дочерние элементы **оркестратора**, которые *могут* делегировать своих собственных работников:

```python
delegate_task(
    goal="Survey three code review approaches and recommend one",
    role="orchestrator",  # Allows this child to spawn its own workers
    context="...",
)
```

- `role="leaf"` (по умолчанию): дочерний элемент не может дальше делегировать — идентично поведению с фиксированным делегированием.
- `role="orchestrator"`: дочерний элемент сохраняет набор инструментов `delegation`. Закрыто `delegation.max_spawn_depth` (по умолчанию **1** = ровное, поэтому `role="orchestrator"` по умолчанию не используется). Увеличьте значение `max_spawn_depth` до 2, чтобы позволить дочерним элементам оркестратора создавать внуков листьев; 3+ для более глубоких деревьев. Верхнего потолка нет — практический предел — стоимость.
- `delegation.orchestrator_enabled: false`: глобальный переключатель уничтожения, который заставляет каждого дочернего элемента выполнять `leaf` независимо от параметра `role`.

**Предупреждение о стоимости:** При использовании `max_spawn_depth: 3` и `max_concurrent_children: 3` дерево может достигать 3×3×3 = 27 одновременных конечных агентов. Каждый дополнительный уровень увеличивает расходы — намеренно поднимите `max_spawn_depth`.

## Срок службы и долговечность

:::предупреждение. Долговечность фонового завершения не является долговечным выполнением.
Вызовы `delegate_task` верхнего уровня, ориентированные на модель, выполняются автоматически в фоновом режиме, когда сеанс поддерживает последующую доставку. Hermes немедленно возвращает дескриптор, и результат повторно вводится в диалог после завершения дочернего процесса или пакета. Субагенты-оркестраторы ждут своих исполнителей на текущем ходу, поскольку они должны синтезировать эти результаты перед возвратом. Конечные точки запроса/ответа без сохранения состояния возвращаются к синхронному выполнению, когда они не могут позже доставить отдельный результат.

- Обычные последующие сообщения не отменяют фоновых дочерних сообщений. `/stop` отменяет выполнение фонового делегирования, а закрытие или сброс сеанса-владельца отменяет его активные дочерние элементы.
- Явное закрытие/сброс сеанса прерывает фоновые дочерние элементы этого сеанса. Закрытие средства просмотра TUI сеанса, принадлежащего шлюзу, не прекращает работу шлюза.
- Перезапуск процесса Hermes **не** возобновляет работающий дочерний процесс. Его попытка становится `unknown`, поскольку Гермес не может доказать, какие именно побочные эффекты произошли.
- Дочерний процесс, который завершился до перезапуска, но результат которого не был доставлен, восстанавливается и направляется обратно через обычные проверки владеющего сеанса.
- Отмененные дочерние элементы возвращают структурированный результат (`status="interrupted"`, `exit_reason="interrupted"`), но поскольку родительский элемент тоже был прерван, этот результат часто никогда не превращается в видимый пользователю ответ.

Для **долговременного выполнения**, которое должно пережить закрытие сеанса или перезапуск процесса, используйте:

- `cronjob` (action=`create`) — планирует отдельный запуск агента; невосприимчив к прерываниям родительского хода.
- `terminal(background=True, notify_on_complete=True)` — долго выполняющиеся команды оболочки, которые продолжают выполняться, пока агент выполняет другие действия.
:::

## Ключевые свойства

- Каждый субагент получает свой **собственный терминальный сеанс** (отдельный от родительского).
- Субагенты наследуют включенные наборы инструментов родительского объекта; модель не может выбрать или расширить их за один звонок
- **Вложенное делегирование разрешено** — дальше делегировать могут только дочерние элементы `role="orchestrator"`, и только тогда, когда `max_spawn_depth` повышается со значения по умолчанию, равного 1 (плоское). Отключите глобально с помощью `orchestrator_enabled: false`.
- Конечные субагенты **не могут** вызывать: `delegate_task`, `clarify`, `memory`, `send_message`, `cronjob`. Субагенты оркестратора сохраняют `delegate_task`, но сохраняют остальные блоки. Обе роли сохраняют `execute_code` (программный вызов инструментов), поэтому дети могут пакетно выполнять механическую работу вместо того, чтобы сжигать итерации рассуждений.
- **Отмена следует за владением** — `/stop` или закрытие/сброс сеанса владения отменяет его фоновые дочерние элементы; синхронные потомки оркестраторов следуют состоянию прерывания своего родителя
- Только окончательная сводка входит в контекст родительского объекта, что обеспечивает эффективное использование токенов.
- Субагенты наследуют родительский **ключ API, конфигурацию поставщика и пул учетных данных** (включение ротации ключей при ограничениях скорости).

## Изоляция рабочего дерева

По умолчанию субагенты используют общий рабочий каталог родительского объекта — подходит для исследований.
и тяжелая работа по чтению, но параллельные дети, редактирующие один и тот же репозиторий, могут столкнуться.
Установите `delegation.worktree_isolation: true`, чтобы предоставить каждому дочернему элементу свой собственный git.
рабочее дерево, ответвление от текущего репозитория `HEAD` (вдохновленного кодом Muse Code).
`--subagent-worktree-isolation`):

```yaml
delegation:
  worktree_isolation: true   # default: false
```

При включенной изоляции:

- Каждый дочерний элемент запускает свой терминал в `<repo>/.worktrees/subagent-<id>` на своем
  собственная ветка `hermes-subagent/subagent-<id>`, и ее сообщение о цели сообщает ей:
  работать и совершать там.
- Касса родителя остается нетронутой; дети не могут бить друг друга
  правки.
- Когда дочерний элемент завершает работу, его запись результата получает поле отчета `worktree`.
  `path`, `branch`, `commits` (впереди базы) и `dirty`. Родитель
  проверяет или объединяет каждую ветку (`git log <branch>`, `git merge <branch>`).
- Рабочее дерево остается без **коммитов, чистое дерево автоматически обрезается**
  (`pruned: true`); все, что сохраняет работу, сохраняется.
- Обрезка требует доказательств. Если проверка git не удалась или завершение
  сами ошибки — рабочее дерево и ветка сохраняются, а запись переносится
  Тогда `inspection_failed: true` плюс `note` — `commits`/`dirty`
  значения по умолчанию, а не измерения, поэтому проверяйте рабочее дерево, а не предполагайте
  ребенок ничего не произвел.

Область применения: по согласию, только для git и только для локального терминала. В не-git
в каталоге docker/ssh/modal или в случае сбоя создания рабочего дерева,
настройки незаметно деградируют до сегодняшнего поведения в общем рабочем пространстве — никогда
ошибка.

## Делегирование против выполнения_кода

| Фактор | делегат_задача | код_выполнения |
|--------|--------------|-------------|
| **Рассуждение** | Полный цикл рассуждений LLM | Просто выполнение кода Python |
| **Контекст** | Свежий изолированный разговор | Никаких разговоров, только сценарий |
| **Доступ к инструментам** | Все неблокируемые инструменты с рассуждениями | 7 инструментов через RPC, без рассуждений |
| **Параллелизм** | 3 одновременных субагента по умолчанию (настраиваемые) | Одиночный сценарий |
| **Лучший вариант** | Сложные задачи, требующие решения | Механические многоступенчатые трубопроводы |
| **Стоимость токена** | Высшее (полный цикл LLM) | Нижний (возвращается только стандартный вывод) |
| **Взаимодействие с пользователем** | Нет (субагенты не могут уточнить) | Нет |

**Правило**. Используйте `delegate_task`, если подзадача требует рассуждений, суждений или многоэтапного решения проблемы. Используйте `execute_code`, если вам нужна механическая обработка данных или сценарии рабочих процессов.

```yaml
  provider: "openrouter"                             # Optional built-in provider
  api_mode: anthropic_messages                       # optional; auto-detected from base_url for anthropic_messages endpoints

# Or use a direct custom endpoint instead of provider:
delegation:
  model: "qwen2.5-coder"
  base_url: "http://localhost:1234/v1"
  api_key: "local-key"
  # api_mode: "anthropic_messages"  # Optional. Wire protocol override for base_url ("chat_completions", "codex_responses", or "anthropic_messages"). Empty = auto-detect from URL (e.g. /anthropic suffix). Set explicitly for endpoints the heuristic can't classify (Azure AI Foundry, MiniMax, Zhipu GLM, LiteLLM proxies, …).
```

Когда `base_url` указывает на конечную точку, совместимую с Anthropic — например, путь, заканчивающийся на `/anthropic`, маршрут Azure Foundry Claude или прокси-сервер MiniMax `/anthropic` — `api_mode` автоматически определяется как `anthropic_messages`, поэтому субагент использует правильный формат передачи без каких-либо настроек. Установите `api_mode` явно, если предположение автоматического обнаружения неверно (редко).
