# Веб-панель Hermes

Веб-панель представляет собой пользовательский интерфейс на основе браузера для управления установкой агента Hermes. Вместо редактирования файлов YAML или запуска команд CLI вы можете настраивать параметры, управлять ключами API и отслеживать сеансы из чистого веб-интерфейса.

:::совет
Аутентификация в режиме хостинга использует Nous Portal OAuth; если вы также хотите, чтобы панель мониторинга взаимодействовала с реальным сервером, `hermes setup --portal` также подключает модель и шлюз инструментов. См. [Nous Portal](/integrations/nous-portal).
:::

## Быстрый старт

```bash
hermes dashboard
```

При этом запускается локальный веб-сервер и в вашем браузере открывается `http://127.0.0.1:9119`. Панель управления полностью работает на вашем компьютере — никакие данные не покидают локальный хост.

### Опции

| Флаг | По умолчанию | Описание |
|------|---------|-------------|
| `--port` | `9119` | Порт для запуска веб-сервера |
| `--host` | `127.0.0.1` | Привязать адрес |
| `--no-open` | — | Не открывать браузер автоматически |
| `--insecure` | выключен | **Устарело/не работает.** Ранее аутентификация обходилася при привязке без обратной связи; он больше не отключает аутентификацию — для публичной привязки всегда требуется поставщик аутентификации (пароль или OAuth) |
| `--isolated` | выключен | При запуске из именованного профиля (`worker dashboard`) запускайте выделенный сервер для каждого профиля вместо маршрутизации на панель управления компьютера |

```bash
# Custom port
hermes dashboard --port 8080

# Bind to all interfaces (use with caution on shared networks)
hermes dashboard --host 0.0.0.0

# Start without opening browser
hermes dashboard --no-open
```

## Управление несколькими профилями

Панель управления представляет собой поверхность управления **на уровне компьютера**: один сервер управляет
каждый [профиль](../profiles.md) на компьютере. Переключатель профилей в
боковая панель (видимая, если существует более одного профиля) решает, какой из них
профилируйте страницы управления для чтения и записи — Конфигурация, Ключи API, Навыки,
За ним следуют MCP, «Модели» и вкладка «Чат». Хотя профиль, отличный от
выбран собственный профиль панели управления, желтый баннер называет управляемый профиль
поэтому цель записи никогда не бывает двусмысленной.

Выделенный фрагмент находится в URL-адресе (`?profile=<name>`), поэтому глубокие ссылки типа
`http://127.0.0.1:9119/skills?profile=worker` приземлился с помощью переключателя
предварительно выбраны и сохраняются при обновлении.

Запуск дашборда из псевдонима профиля направляет на машину
приборная панель вместо запуска второго сервера:

```bash
worker dashboard
# → already running: opens the browser at ?profile=worker
# → not running:     starts the machine dashboard with "worker" preselected
```

Передайте `--isolated`, чтобы отказаться и запустить выделенный сервер, ограниченный этой возможностью.
профиль (поведение до объединения — полезно, если вы намеренно раскрываете
информационные панели разных профилей с разной авторизацией).

Вкладка **Чат** также следует за переключателем: чат с ограниченной областью порождает свой PTY.
ребенок с `HERMES_HOME` выбранного профиля, поэтому разговор ведется
с моделью этого профиля, навыками, памятью и историей сеансов. Переключение
Profiles запускает новый сеанс терминала.

Что остается в каждом профиле и *не* поглощается коммутатором: шлюз
процессы (управляйте ими через `hermes -p <name> gateway …`), каждый профиль
базу данных сеансов и планировщики cron (страница Cron уже объединяет
по профилям с собственным фильтром).

## Предварительные условия

При установке по умолчанию `hermes-agent` не поставляется стек HTTP или помощник PTY — это необязательные дополнения. Для **веб-панели** требуются FastAPI и Uvicorn (дополнительно `web`). Вкладка **Чат** также требует `ptyprocess` для создания встроенного TUI за псевдотерминалом (дополнительно `pty` в POSIX). Установите оба с помощью:

```bash
cd ~/.hermes/hermes-agent && uv pip install -e ".[web,pty]"
```

Дополнительный элемент `web` использует FastAPI/Uvicorn; `pty` извлекает `ptyprocess` (POSIX) или `pywinpty` (родной Windows — обратите внимание, что сам встроенный TUI по-прежнему требует WSL). `cd ~/.hermes/hermes-agent && uv pip install -e ".[all]"` включает в себя обе дополнительные функции и является самым простым способом, если вам также нужен обмен сообщениями, голосовая связь и т. д.

Когда вы запустите `hermes dashboard` без зависимостей, он сообщит вам, что нужно установить. Если интерфейс еще не создан и доступен `npm`, он создается автоматически при первом запуске.

Вкладка «Чат» является частью каждого запуска `hermes dashboard` — встроенная панель чата браузера (запускающая TUI через PTY/WebSocket) всегда доступна, без необходимости установки дополнительных флагов.

### Статус

На целевой странице показан обзор вашей установки в реальном времени:

- **Версия агента** и дата выпуска.
- **Состояние шлюза** — работает/остановлен, PID, подключенные платформы и их состояние.
- **Активные сеансы** — количество активных сеансов за последние 5 минут.
- **Последние сеансы** — список из 20 последних сеансов с указанием модели, количества сообщений, использования токенов и предварительного просмотра разговора.

Страница статуса автоматически обновляется каждые 5 секунд.

#### Баннер о нехватке ресурсов

Когда хосту не хватает памяти или диска, вверху появляется баннер.
панель мониторинга (получаемая тем же опросом статуса — никаких дополнительных запросов):

- **"Вашему агенту почти не хватает памяти, и он может перезагрузиться"** — система доступна
  Память упала до *повышенного* (< 128 МБ или < 15%) или *критического* уровня.
  (< 64 МБ или < 5%), по данным 30-секундного контрольного сигнала шлюза.
- **"Ваш агент неожиданно перезапустился, скорее всего, потому, что у него закончились
  Memory"** — в журнале жизненного цикла зафиксирован нечистый выход в память
  давление на предыдущую загрузку (подозрение на убийство OOM).
- **Предупреждения о диске** — том, содержащий `~/.hermes`, почти заполнен.
  (*повышено* ниже 512 МБ свободного места, *критическое* ниже 256 МБ свободного места).

Одновременно отображается только самое серьезное активное предупреждение (критический диск > память).
критический > перезапуск OOM > диск повышен > память повышена). Увольнения
ограничено текущей загрузкой шлюза: отклонение предупреждения приводит к следующему
активный, перезапуск шлюза или повторное открытие эскалации (повышенный → критический)
это, и устаревшее сердцебиение не отображает ничего, кроме ложного предупреждения.

### Чат

Вкладка **Чат** встраивает полный TUI Hermes (тот же интерфейс, что и в `hermes --tui`) непосредственно в браузер. Все, что вы можете делать в TUI терминала — команды с косой чертой, выбор модели, карточки вызова инструментов, потоковая передача уценки, запросы уточнения/sudo/утверждения, оформление тем оформления — здесь работает идентично, поскольку панель мониторинга запускает настоящий двоичный файл TUI и визуализирует его выходные данные ANSI через [xterm.js](https://xtermjs.org/) с помощью средства рендеринга WebGL для идеального попиксельного макета ячеек.

**Как это работает:**

- `/api/pty` открывает WebSocket, аутентифицированный с помощью токена сеанса панели мониторинга.
- Сервер создает `hermes --tui` за псевдотерминалом POSIX.
- Нажатия клавиш переходят в PTY; Выходные потоки ANSI возвращаются в браузер.
- средство рендеринга WebGL xterm.js рисует каждую ячейку в сетке целых пикселей; отслеживание мыши (SGR 1006), широкие символы (Unicode 11) и глифы в виде прямоугольников — все они визуализируются изначально.
- При изменении размера окна браузера изменяется размер TUI с помощью дополнения `@xterm/addon-fit`.

**Возобновите существующий сеанс:** на вкладке **Сеансы** нажмите значок воспроизведения (▶) рядом с любым сеансом. Это переходит к `/chat?resume=<id>` и запускает TUI с `--resume`, загружая полную историю.

**Переключатель сеансов (правая панель):** на вкладке «Чат» имеется собственный список разговоров в стиле ChatGPT, расположенный на тонкой правой панели рядом с терминалом, поэтому вы можете переключаться между разговорами, не покидая страницу. На направляющей располагается средство выбора модели сверху, а список сеансов — непосредственно под ним; терминал занимает большую часть экрана. В списке показаны ваши самые последние сеансы для активного профиля — заголовок (возврат к предварительному просмотру сообщения), относительное время последней активности, количество сообщений и исходный канал для сеансов без CLI. Щелкните любую строку, чтобы возобновить ее (терминал возобновится с историей этого разговора); активный сеанс выделяется. **Новый чат** запускает новый сеанс, а элемент управления обновлением повторно извлекает список. При переключении рельс доступен только для чтения — удаление, переименование, экспорт и массовая очистка по-прежнему доступны на вкладке **Сеансы**. На узких экранах он складывается в выдвижную панель.

**Предварительные требования:**

- Node.js (те же требования, что и `hermes --tui`; пакет TUI создается при первом запуске)
- `ptyprocess` — устанавливается с помощью дополнения `pty` (`cd ~/.hermes/hermes-agent && uv pip install -e ".[web,pty]"` или `[all]` охватывает оба)
- Ядро POSIX (Linux, macOS или WSL2).  Для панели терминала `/chat` специально требуется POSIX PTY — собственный Windows Python не имеет эквивалента, поэтому при установке собственной Windows остальная часть информационной панели (сеансы, задания, метрики, редактор конфигурации) работает, но на вкладке `/chat` будет отображаться баннер с предложением использовать WSL2 для этой функции.

Закройте вкладку браузера, и PTY будет очищен на сервере. Повторное открытие порождает новую сессию.

Чтобы указать [Hermes Desktop](#connecting-hermes-desktop-to-a-remote-backend) на панель мониторинга, работающую на другом компьютере, а не на собственную встроенную серверную часть, см. раздел удаленной серверной части ниже.

### Подключение Hermes Desktop к удаленному серверу

Hermes Desktop обычно запускает собственный локальный бэкэнд, но его также можно подключить к панели управления, работающей на удаленном компьютере (виртуальной машине, домашней лаборатории и т. д.) через **Настройки → Шлюзы → Удаленный шлюз**. Это наиболее распространенный источник отчетов «Рабочий стол сообщает, что серверная часть готова, но чат никогда не работает», поскольку проверка готовности рабочего стола проверяет меньше, чем на самом деле требуется для подключения к живому чату.

:::info Предварительное условие: на удаленном хосте должен быть запущен `hermes dashboard`.
«Удаленный серверный» рабочий стол подключается к **является** процессу `hermes dashboard`, работающему на удаленном компьютере — том же сервере, который описан на этой странице. Прежде чем выполнять какие-либо шаги, описанные ниже, он должен быть доступен и доступен; Рабочий стол к нему привязывается, он у вас его не запускает. Оставьте его работать под `systemd`/`tmux`/и т. д. поэтому он выдерживает выход из системы и перезагружается. **шлюз** (Telegram/Discord/Slack/и т. д.) — это *отдельный* длительный процесс — запустите его независимо, если вы полагаетесь на каналы обмена сообщениями; это не то, к чему подключается настольное приложение.
:::

Проверка готовности удаленной серверной части Desktop достигает только `GET /api/status`, которая является общедоступной конечной точкой — она отвечает, как только на хосте запускается *любая* панель мониторинга. Соединение с живым чатом представляет собой **отдельный** WebSocket для `/api/ws` (и `/api/pty`), и этот сокет закрывается еще двумя проверками, которых никогда не касается зонд состояния:

1. **Вы должны пройти аутентификацию.** Когда панель мониторинга привязана к адресу без обратной связи, она задействует шлюз аутентификации. Защитите его с помощью имени пользователя и пароля (входит в комплект [поставщик имени пользователя и пароля](#usernamepassword-provider-no-oauth-idp)); Desktop входит в систему один раз и повторно использует полученный сеанс для WebSocket с помощью одноразового билета. Без настроенного поставщика панель мониторинга без обратной связи **не закрывается при запуске**.
2. **Хост привязки должен разрешать клиент и соответствовать заголовку Host.** Привязка обратной связи (`127.0.0.1`) принимает только клиентов обратной связи, поэтому удаленный компьютер отклоняется на уровне сокета независимо от учетных данных. Привяжите адрес без обратной связи (`--host 0.0.0.0`), чтобы защита однорангового IP-адреса пропускала удаленного клиента. Удаленный URL-адрес, который вы вводите в Desktop, должен попасть на панель мониторинга через тот же хост, к которому он привязан — защита перепривязки DNS требует, чтобы заголовок Host совпадал.

#### Удаленная настройка панели управления

Установите имя пользователя и пароль, затем запустите панель мониторинга, привязанную к доступному адресу. Для услуги `systemd`:

```ini
[Service]
EnvironmentFile=%h/.hermes/.env
ExecStart=/path/to/venv/bin/python -m hermes_cli.main dashboard \
    --host 0.0.0.0 --port 9119 --no-open
```

с `~/.hermes/.env`, содержащим:

```bash
HERMES_DASHBOARD_BASIC_AUTH_USERNAME=admin
HERMES_DASHBOARD_BASIC_AUTH_PASSWORD=choose-a-strong-password
HERMES_DASHBOARD_BASIC_AUTH_SECRET=<32+ random bytes; openssl rand -base64 32>
```

Затем на рабочем столе введите **Удаленный URL-адрес** (например, `http://VM_IP:9119`) и **Войдите**, используя это имя пользователя и пароль. Полную информацию о конфигурации см. в разделе [поставщик имени пользователя и пароля](#usernamepassword-provider-no-oauth-idp).

:::tip Убедитесь, что шлюз включен, прежде чем повторить попытку рабочего стола.
На любом компьютере убедитесь, что панель мониторинга объявляет поставщика имени пользователя и пароля:

```bash
curl -s http://VM_IP:9119/api/status | jq '.auth_required, .auth_providers'
# true
# ["basic"]
```

- `auth_required: true` и `"basic"` в списке поставщиков → процесс **Вход** в Desktop будет работать.
- `auth_required: false` → привязка петлевая, или шлюз не сработал. Привязка к адресу без обратной связи.
- `auth_required: true`, но нет поставщика `"basic"` → переменные среды имени пользователя и пароля не загружаются. Сначала исправьте их.
:::

Если `/api/status` показывает, что шлюз включен с провайдером `"basic"`, а рабочий стол *все еще* не может подключиться после входа в систему, проблема связана с базовой настройкой — возьмите новый `desktop.log` (Настройки → Шлюзы → Открыть журналы), а также журналы панели мониторинга из того же окна повтора и найдите код закрытия `/api/ws` (4403 = чат WS отклонен защитой запроса, например, Host/peer несоответствие 4401 = билет WS не прошел аутентификацию).

### Конфигурация

Редактор на основе форм для `config.yaml`. Все более 150 полей конфигурации автоматически обнаруживаются из `DEFAULT_CONFIG` и организованы по категориям с вкладками:

![Страница администрирования конфигурации — фильтры разделов слева, автоматически обнаруживаемые поля справа](/img/dashboard/admin-config.png)


- **модель** — модель по умолчанию, поставщик, базовый URL, настройки обоснования.
- **терминал** — бэкэнд (локальный/docker/ssh/модальный), тайм-аут, настройки оболочки
- **display** — скин, ход работы инструмента, отображение возобновления, настройки счетчика.
- **агент** — максимальное количество итераций, тайм-аут шлюза, уровень обслуживания.
- **делегирование** — ограничения субагента, усилия по обоснованию
- **память** — выбор провайдера, настройки внедрения контекста
- **approvals** — режим одобрения опасных команд (умный/ручной/выкл.)
- И еще — каждый раздел config.yaml имеет соответствующие поля формы.

Поля с известными допустимыми значениями (серверная часть терминала, обложка, режим утверждения и т. д.) отображаются как раскрывающиеся списки. Логические значения отображаются как переключатели. Все остальное — ввод текста.

**Действия:**

- **Сохранить** — немедленно записывает изменения в `config.yaml`.
- **Восстановить значения по умолчанию** — возвращает все поля к значениям по умолчанию (не сохраняется, пока вы не нажмете «Сохранить»).
- **Экспорт** — загружает текущую конфигурацию в формате JSON.
- **Импорт** — загружает файл конфигурации JSON для замены текущих значений.

:::совет
Изменения конфигурации вступят в силу при следующем сеансе агента или перезапуске шлюза. Веб-панель редактирует тот же файл `config.yaml`, из которого считывают `hermes config set` и шлюз.
:::

### API-ключи

Управляйте файлом `.env`, в котором хранятся ключи API и учетные данные. Ключи сгруппированы по категориям:

- **Поставщики LLM** — OpenRouter, Anthropic, OpenAI, DeepSeek и т. д.
- **Ключи API инструментов** — Browserbase, Firecrawl, Tavily, ElevenLabs и т. д.

На каждой клавише указано:
- Установлено ли оно в данный момент (с отредактированным предварительным просмотром значения)
- Описание, для чего это нужно.
- Ссылка на страницу регистрации/ключевого доступа провайдера.
- Поле ввода для установки или обновления значения.
- Кнопка удаления, чтобы удалить его.

Расширенные/редко используемые клавиши по умолчанию скрыты за переключателем.

### сеансов

Просмотрите и проверьте все сеансы агента. В каждой строке отображается заголовок сеанса, значок исходной платформы (CLI, Telegram, Discord, Slack, cron), название модели, количество сообщений, количество вызовов инструментов и время, когда оно было активно. Сеансы в реальном времени отмечаются пульсирующим значком.

- **Фильтр** — вкладки **Чаты / Автоматизация / Все** охватывают список: *Чаты* (по умолчанию) отображают человеческие разговоры и скрывают шум автоматизации (cron, инструмент, сеансы API, ACP); *Автоматизация* показывает только их; *Все* показывает все. Раскрывающийся список точного источника сужается до одного канала (например, только Telegram). Поиск учитывает активный фильтр.
- **Поиск** — полнотекстовый поиск по всему содержимому сообщения с помощью FTS5. Результаты показывают выделенные фрагменты и автоматически прокручиваются до первого соответствующего сообщения при раскрытии.
- **Статистика** — сводная панель показывает общее количество сеансов, количество активных в магазине, количество заархивированных сообщений, общее количество сообщений и разбивку по источникам.
- **Развернуть** — щелкните сеанс, чтобы загрузить полную историю сообщений. Сообщения имеют цветовую кодировку в зависимости от роли (пользователь, помощник, система, инструмент) и отображаются в формате Markdown с подсветкой синтаксиса.
- **Вызовы инструментов** — в сообщениях помощника с вызовами инструментов отображаются сворачиваемые блоки с именем функции и аргументами JSON.
- **Переименовать** — установить или удалить встроенный заголовок сеанса (значок карандаша).
- **Экспорт** — загрузить сессию (метаданные + полную историю сообщений) в формате JSON (значок загрузки).
- **Удалить** — кнопка «Удалить старые сеансы» в заголовке удаляет завершенные сеансы старше N дней.
- **Удалить** — удалить сеанс и историю его сообщений со значком корзины.

### Журналы

Просматривайте файлы журнала агента, шлюза и ошибок с помощью фильтрации и отслеживания в реальном времени.

- **Файл** — переключение между файлами журнала `agent`, `errors` и `gateway`.
- **Уровень** — фильтрация по уровню журнала: ВСЕ, ОТЛАДКА, ИНФОРМАЦИЯ, ПРЕДУПРЕЖДЕНИЕ или ОШИБКА.
- **Компонент** — фильтровать по исходному компоненту: все, шлюз, агент, инструменты, интерфейс командной строки или cron.
- **Линии** — выберите количество отображаемых строк (50, 100, 200 или 500).
- **Автообновление** — включение динамического отслеживания, которое проверяет наличие новых строк журнала каждые 5 секунд.
- **Цветовая кодировка** — строки журнала окрашены в зависимости от серьезности (красный — для ошибок, желтый — для предупреждений, тусклый — для отладки).

### Аналитика

Аналитика использования и затрат рассчитывается на основе истории сеансов. Выберите период времени (7, 30 или 90 дней), чтобы увидеть:

- **Сводные карточки** — общее количество токенов (вход/выход), процент попаданий в кэш, общая расчетная или фактическая стоимость, а также общее количество сеансов со средним значением за день.
- **Дневная диаграмма токенов** — гистограмма, показывающая использование входных и выходных токенов за день, с подсказками при наведении, показывающими разбивку и стоимость.
- **Таблица с разбивкой по дням** – дата, количество сеансов, входные токены, выходные токены, частота попадания в кеш и стоимость за каждый день.
- **Разбивка по моделям** — таблица, показывающая каждую используемую модель, количество ее сеансов, использование токенов и ориентировочную стоимость.

### Крон

Создавайте запланированные задания cron, которые запускают запросы агента по регулярному расписанию, и управляйте ими.

- **Создать** — введите имя (необязательно), приглашение, выражение cron (например, `0 9 * * *`) и цель доставки (локально, Telegram, Discord, Slack или электронная почта).
- **Список заданий** — для каждого задания отображается его имя, предварительный просмотр приглашения, выражение расписания, значок состояния (включено/приостановлено/ошибка), цель доставки, время последнего выполнения и время следующего выполнения.
- **Пауза/Возобновить** — переключение задания между активным и приостановленным состояниями.
- **Редактировать** — откройте предварительно заполненное модальное окно, чтобы изменить приглашение, расписание, имя или цель выполнения задания.
- **Триггер сейчас** — немедленное выполнение задания вне обычного расписания.
- **Удалить** — окончательно удалить задание cron.

### Профили

Создавайте и управляйте [профилями](../profiles.md) — изолированными экземплярами Hermes со своей собственной конфигурацией, навыками и сеансами.

- **Карточки профиля** — на каждой указаны модель/провайдер, количество навыков, состояние шлюза, описание и значки (активный, по умолчанию, псевдоним).
- **Создать** — имя + дополнительные навыки клонирования по умолчанию/клонировать все/без объединенных навыков, описание и модель; специальная страница Profile Builder (`/profiles/new`) предлагает полный набор (модель, MCP, навыки)
- **Управление навыками и инструментами** — переход на страницу «Навыки», привязанную к этому профилю (устанавливает переключатель профиля на боковой панели).
- **Установить как активный** — меняет фиксированное значение по умолчанию, которое будет выбрано **будущими запусками CLI/шлюза** (так же, как `hermes profile use`). Это *не* меняет то, чем управляет панель управления — это работа переключателя профилей.
- **Редактировать модель/описание/ДУШУ** — встроенные редакторы пишут в этот профиль
- **Переименовать/Удалить** — только именованные профили.

### МКП

Управляйте серверами [MCP](./mcp) без CLI. Тот самый `mcp_servers`
блок в `config.yaml`, из которого `hermes mcp` читает.

**Ваши серверы MCP:**

- **Добавить** — зарегистрировать сервер HTTP/SSE (URL) или сервер stdio (команда + аргументы) с дополнительными переменными среды `KEY=VALUE` для серверов stdio.
- **Включить/выключить** — включить или выключить сервер, не удаляя его. Отключенный сервер остается в конфигурации, поэтому вы можете включить его позже. Вступает в силу при следующем перезапуске шлюза.

- Значения окружения в форме секрета отредактированы в виде списка.

**Каталог:** просмотрите одобренные Nous серверы MCP (входящий в комплект `optional-mcps/`
каталог) и установить любой из них одним щелчком мыши. Записи, которым нужны ключи API
запросить их в строке; значения переходят в `.env`. Это тот самый каталог
`hermes mcp catalog` / `hermes mcp install` использование.

### Система

Консолидированная панель администрирования для операций всей установки:

- **Хост** — статистика системы в реальном времени: ОС/ядро, архитектура, имя хоста, версии Python и Hermes, количество ядер ЦП + загрузка, память, использование диска в доме Hermes, время безотказной работы и средняя нагрузка. (ЦП/память/диск при установке поступает из `psutil`; поля идентификаторов отображаются всегда.) Версия Hermes показывает **значок статуса обновления** (обновлено / N отстает) и кнопку **Проверить наличие обновлений**. Если обновление доступно при установке git, кнопка **Обновить сейчас** открывает диалоговое окно подтверждения, показывающее, сколько коммитов вы сделаете, перед запуском `hermes update` в фоновом режиме. При установке Docker/Nix панель мониторинга не может применить обновление на месте, поэтому вместо этого отображается правильная внеполосная команда.
- **Nous Portal** — статус входа, активный поставщик логических выводов и таблица маршрутизации Tool Gateway (какие инструменты запускаются через портал, а не локально) со ссылкой для управления вашей подпиской. Зеркало `hermes portal` только для чтения.
- **Куратор навыков** — фоновый статус обслуживания навыков (активен/приостановлен, интервал, последний запуск) с паузой/возобновлением и кнопкой запуска сейчас. Зеркала `hermes curator`.
- **Шлюз** — запуск, остановка и перезапуск шлюза обмена сообщениями с актуальным статусом (работает/остановлен, PID, состояние).
- **Память** — выберите поставщика внешней памяти (или только встроенную) и сбросьте встроенные хранилища `MEMORY.md`/`USER.md`.
- **Пул учетных данных** — добавляйте и удаляйте меняющиеся ключи API, через которые агент выполняет циклический перебор (для каждого поставщика). Ключи в списке редактируются; необработанное значение достигает только агента.
- **Операции** – запуск `doctor`, аудит безопасности, создание резервной копии, восстановление из архива резервной копии, обновление навыков, отображение разбивки по размеру системного запроса, создание дампа поддержки или перенос конфигурации для устаревших настроек. Каждое из них порождает фоновое действие, журнал которого транслируется на страницу.
- **Контрольные точки** — посмотрите размер теневого хранилища `/rollback` и обрежьте его.
- **Перехватчики оболочки** — список настроенных перехватчиков с указанием их согласия и статуса исполняемого файла, **создание** перехватчика (событие, команда, средство сопоставления, таймаут, с согласием на получение согласия) и удаление одного из них. Перехватчики запускают произвольные команды, поэтому форма создания содержит предупреждение системы безопасности, а перехватчик срабатывает только после получения согласия.

:::предупреждение безопасности
Веб-панель считывает и записывает ваш файл `.env`, который содержит ключи и секреты API. По умолчанию он привязывается к `127.0.0.1` — доступен только с вашего локального компьютера, вход в систему не требуется. Привязка к любому адресу без обратной связи (включая `0.0.0.0`) задействует [шлюз аутентификации](#authentication-gated-mode): сервер отказывается запускаться до тех пор, пока не будет настроен поставщик аутентификации (имя пользователя/пароль или OAuth).
:::

## `/reload` Команда косой черты

PR информационной панели также добавляет косую черту `/reload` в интерактивный интерфейс командной строки. После изменения ключей API через веб-панель (или путем непосредственного редактирования `.env`) используйте `/reload` в активном сеансе CLI, чтобы принять изменения без перезапуска:

```
You → /reload
  Reloaded .env (3 var(s) updated)
```

При этом `~/.hermes/.env` пересчитывается в среду работающего процесса. Полезно, если вы добавили новый ключ провайдера через панель управления и хотите немедленно его использовать.

## Аутентификация (закрытый режим)

Когда панель мониторинга привязана к общедоступному адресу или адресу без шлейфа (любому, кроме `127.0.0.1` / `localhost`), агент Hermes задействует шлюз аутентификации. Каждый запрос должен содержать проверенный файл cookie сеанса, иначе он будет перенаправлен на страницу входа. В комплект поставки входят три поставщика:

- **[Имя пользователя/пароль](#usernamepassword-provider-no-oauth-idp)** — самый простой способ поставить аутентификацию на локальной/локальной панели управления/панели домашней лаборатории. Нет внешнего поставщика удостоверений. **Используйте его только в доверенной сети или через VPN — не для публичного доступа в Интернет.**
- **[OAuth (Nous Portal)](#default-provider-nous-research)** — для размещенных развертываний и любой информационной панели, доступной через общедоступный Интернет, а также рекомендуемый путь для [подключения к удаленному рабочему столу Hermes](#connecting-hermes-desktop-to-a-remote-backend). Каждый вход в систему проверяется по вашей учетной записи Nous, поэтому этот провайдер подходит для использования с выходом в Интернет.
- **[Self-hosted OIDC](#self-hosted-oidc-provider)** — для подключения собственного поставщика удостоверений через стандартный OpenID Connect (Keycloak, Auth0, Okta, Google, GitHub через мост OIDC и т. д.). Портал Ноус не задействован; подходит для публичного доступа в Интернет при наличии совместимого сервера OIDC.

Принадлежащие оператору информационные панели, привязанные к шлейфу, не затрагиваются — ни аутентификации, ни страницы входа.

### Когда ворота задействуются

| Флаги | Ворота авторизации | Вариант использования |
|-------|-----------|----------|
| `hermes dashboard` (по умолчанию — привязывается к `127.0.0.1`) | ВЫКЛ | Местное развитие |
| `hermes dashboard --host 0.0.0.0` | **ВКЛ** | Удаленный/производственный — защита с помощью поставщика имени пользователя/пароля или OAuth |

Шлюз включен тогда и только тогда, когда хост привязки не `127.0.0.1`, `::1` или `localhost`. Привязка к `0.0.0.0` (или любому адресу RFC1918/LAN) задействует шлюз. Устаревший флаг `--insecure` **больше не отключает его** — он принят для обратной совместимости, но игнорируется с предупреждением.

:::danger `--insecure` неактивен — он не отключает аутентификацию
После ужесточения безопасности в июне 2026 года `--insecure` больше не обходит аутентификацию информационной панели: привязка без обратной связи всегда требует поставщика аутентификации (поставщика имени пользователя и пароля или OAuth). Если вам нужна панель управления без авторизации, привяжите ее к `127.0.0.1` и подключитесь к ней через SSH-туннель или Tailscale.
:::

### Семантика отказоустойчивости

Если ворота сработают, но **нет** `DashboardAuthProvider` зарегистрирован (нет плагина Nous или специального плагина), `hermes dashboard` откажется привязываться с явным сообщением об ошибке. Не существует резервного варианта «запретить по умолчанию, но принять все» — неправильно настроенная закрытая панель мониторинга никогда не запускается.

Когда вы запускаете `hermes dashboard --host 0.0.0.0` **в интерактивном режиме** (настоящий терминал) и ни один провайдер еще не настроен, Hermes не просто терпит неудачу — он предлагает настроить его на месте: выберите **имя пользователя и пароль** (записывает `dashboard.basic_auth` в `config.yaml`, и вы работаете через несколько секунд) или **OAuth** (указывает на `hermes dashboard register`). Неинтерактивные вызывающие программы — Docker/s6, CI, конвейерные запуски — пропускают приглашение и нажимают на ошибку закрытия при сбое, описанную выше, поэтому автоматическое развертывание по-прежнему никогда не запускается без аутентификации.

### Поставщик по умолчанию: Nous Research

Входящий в комплект плагин `plugins/dashboard_auth/nous` **всегда установлен** и загружается автоматически. Он автоматически регистрирует `DashboardAuthProvider` с именем `nous` при настройке идентификатора клиента.

Поскольку каждый вход в систему проверяется на портале Nous и защищается вашей учетной записью Nous, **провайдер Nous подходит для предоставления панели управления общедоступному Интернету.**

#### Регистрация панели управления

Чтобы использовать провайдера Nous, вам понадобится идентификатор клиента OAuth (форма `agent:{id}`). Есть два способа получить его:

- **CLI — `hermes dashboard register`.** Запустите его на хосте, где находится панель мониторинга. Он разрешает ваш существующий логин Nous (сначала запустите `hermes setup`, если вы не вошли в систему), регистрирует автономный клиент OAuth на портале и записывает `HERMES_DASHBOARD_OAUTH_CLIENT_ID` в `~/.hermes/.env` для вас. Необязательные флаги: `--name` (удобочитаемая метка, в противном случае создается автоматически) и `--redirect-uri` (публичный URL-адрес обратного вызова HTTPS для хоста, подключенного к Интернету).

  ```bash
  hermes dashboard register
  # ✓ Registered dashboard "swift_falcon"
  # …writes HERMES_DASHBOARD_OAUTH_CLIENT_ID to ~/.hermes/.env
  ```

- **Графический интерфейс — страница локальных информационных панелей.** Откройте [`/local-dashboards`](https://portal.nousresearch.com/local-dashboards) на портале Nous, чтобы зарегистрировать, присвоить имя, управлять и отозвать локальные информационные панели из браузера. Скопируйте полученный идентификатор клиента `agent:{id}` в `HERMES_DASHBOARD_OAUTH_CLIENT_ID` (env) или `dashboard.oauth.client_id` (config.yaml). Здесь также можно отозвать панель мониторинга, зарегистрированную через CLI.

#### Конфигурация

Плагин считывает данные с двух поверхностей, причем переменная среды выигрывает, если она не пуста:

**`config.yaml`** — каноническая поверхность:

```yaml
dashboard:
  oauth:
    client_id: agent:01HXYZ…             # required to engage the gate
```

**Переменные среды** — переопределения операторов:

| Конверт вар | Переопределения | Формат | Предоставлено |
|---------|-----------|--------|----------------|
| `HERMES_DASHBOARD_OAUTH_CLIENT_ID` | `dashboard.oauth.client_id` | `agent:{instance_id}` | `hermes dashboard register` |

В соответствии с соглашением об агенте Hermes (`~/.hermes/.env` предназначено только для ключей/секретов API), **`config.yaml` — рекомендуемое место для установки этих значений** для локальной разработки, локальной среды и любого развертывания, которым вы управляете напрямую. Путь к переменной среды существует, поэтому секретная инъекция хост-платформы может отправлять `client_id` для каждого развертывания без необходимости редактирования `config.yaml` внутри образа — это его основная цель.

Пустые значения среды считаются неустановленными, поэтому подготовленный, но не заполненный секрет платформы не может случайно затенить действительную запись `config.yaml`.

Если ни один из источников не предоставляет client_id, плагин сообщает конкретную причину, а ошибка привязки с завершением сбоя на панели управления сообщает вам, что именно нужно исправить:

```
Refusing to bind dashboard to 0.0.0.0 — the auth gate engages on
non-loopback binds, but no auth providers are registered.

Bundled providers reported these issues:
  • nous: HERMES_DASHBOARD_OAUTH_CLIENT_ID is not set (and
    dashboard.oauth.client_id in config.yaml is empty). …

Configure an auth provider before exposing the dashboard:
  • Password: set dashboard.basic_auth.username + password_hash in config.yaml
  • OAuth: run `hermes dashboard register` (Nous Portal) or install a
    DashboardAuthProvider plugin.
There is no unauthenticated public-bind option — to keep it local, bind
127.0.0.1 and tunnel in (SSH / Tailscale).
```

#### Рабочий пример: Nous Research

От установки Hermes, вошедшей в систему, до информационной панели Nous-gated за три шага.

**1. Войдите в систему и зарегистрируйте панель управления.** `hermes dashboard register` использует существующую учетную запись Nous для подготовки клиента OAuth и записывает `HERMES_DASHBOARD_OAUTH_CLIENT_ID` в `~/.hermes/.env` для вас:

```bash
hermes setup            # if you're not already logged into Nous Portal
hermes dashboard register
# ✓ Registered dashboard "swift_falcon"
# …writes HERMES_DASHBOARD_OAUTH_CLIENT_ID to ~/.hermes/.env
```

**2. Запустите панель мониторинга по доступному адресу.** Привязка без обратной связи задействует шлюз OAuth, а только что написанный `client_id` активирует провайдера `nous`:

```bash
hermes dashboard --host 0.0.0.0 --port 9119 --no-open
```

**3. Войдите в систему.** Откройте `http://<host>:9119/`, вы будете перенаправлены на `/login`. Нажмите **Войти через Nous Research** → выполните аутентификацию на портале → вернитесь на панель аутентификации. Проверьте ворота с любой машины:

```bash
curl -s http://<host>:9119/api/status | jq '.auth_required, .auth_providers'
# true
# ["nous"]
```

`GET /api/auth/me` затем возвращает проверенный сеанс (`provider: nous`). Для хоста с выходом в Интернет зарегистрируйтесь с помощью `--redirect-uri https://hermes.example.com/auth/callback` и установите `HERMES_DASHBOARD_PUBLIC_URL`, чтобы обратный вызов OAuth разрешался на ваш общедоступный URL-адрес (см. [Переопределение общедоступного URL-адреса](#public-url-override)).

### Поставщик имени пользователя и пароля (без OAuth IDP)

Если вы не хотите подключать поставщика удостоверений OAuth (автономное развертывание «просто введите пароль на мою панель управления»), входящий в комплект плагин `plugins/dashboard_auth/basic` регистрирует `DashboardAuthProvider` с именем `basic`, который проверяет подлинность с помощью **имени пользователя и пароля** вместо перенаправления OAuth.

Он подключается к тому же шлюзу, что и поставщик OAuth: шлюз использует привязку без обратной связи, страница входа отображает форму учетных данных для этого поставщика (вместо кнопки «Войти с помощью X»), и все, что происходит после входа в систему — файлы cookie сеанса, прозрачное обновление, билеты WS, выход из системы, журнал аудита — идентично пути OAuth. Сессии представляют собой токены без сохранения состояния, подписанные HMAC, которые провайдер создает сам, поэтому здесь **нет ни базы данных, ни внешнего IDP**. Для хеширования паролей используется стандартная библиотека `scrypt` (без сторонних зависимостей).

:::предупреждение Используйте это только в доверенных сетях, а не в общедоступном Интернете.
Поставщик имени пользователя и пароля предназначен для локальных, локальных или домашних информационных панелей в **доверенной сети** или для доступа только через **VPN**. Он защищает единые общие учетные данные без какого-либо внешнего поставщика удостоверений, MFA или учетных записей отдельных пользователей, поэтому он **не подходит для предоставления панели управления непосредственно общедоступному Интернету**. Для информационной панели с выходом в Интернет используйте вместо этого [поставщика Nous Research](#default-provider-nous-research) (или своего собственного [автономного OIDC](#self-hosted-oidc-provider)/[custom OAuth](#custom-providers) провайдера).
:::

#### Конфигурация

Как и провайдер Nous, он читает из `config.yaml` (канонический), причем переменные среды выигрывают, если они установлены непустыми. Он активируется только тогда, когда настроены `username` плюс либо `password_hash` (предпочтительно), либо `password` — в противном случае он не работает, поэтому пользователи OAuth и операторы обратной связи не затрагиваются.

**`config.yaml`:**

```yaml
dashboard:
  basic_auth:
    username: admin
    # Preferred — no plaintext at rest. Compute with:
    #   python -c "from plugins.dashboard_auth.basic import hash_password; print(hash_password('PW'))"
    password_hash: "scrypt$16384$8$1$…$…"
    # ...or a plaintext password (hashed in-memory at load; less safe at rest):
    # password: "s3cret"
    secret: "<32+ random bytes, base64 or hex>"  # token-signing key
    session_ttl_seconds: 43200                    # optional; access-token lifetime (default 12h)
```

**Переопределения среды:**

| Конверт вар | Переопределения | Заметки |
|---------|-----------|-------|
| `HERMES_DASHBOARD_BASIC_AUTH_USERNAME` | `dashboard.basic_auth.username` | требуется для активации |
| `HERMES_DASHBOARD_BASIC_AUTH_PASSWORD_HASH` | `dashboard.basic_auth.password_hash` | предпочтительный (без открытого текста) |
| `HERMES_DASHBOARD_BASIC_AUTH_PASSWORD` | `dashboard.basic_auth.password` | открытый текст; **побеждает конфигурацию `password_hash`**, поэтому вы можете вращать ее через env |
| `HERMES_DASHBOARD_BASIC_AUTH_SECRET` | `dashboard.basic_auth.secret` | ключ для подписи токена |
| `HERMES_DASHBOARD_BASIC_AUTH_TTL_SECONDS` | `dashboard.basic_auth.session_ttl_seconds` | срок действия токена доступа |

:::предупреждение Установите явный `secret` для стабильных сеансов.
Если `secret` пуст, генерируется случайный ключ подписи для каждого процесса. Это нормально для одного процесса, но это означает, что **каждый сеанс становится недействительным при перезапуске** и сеансы **не охватывают несколько рабочих**. Установите явный `secret` для развертываний с возможностью перезапуска или нескольких рабочих мест.
:::

Конечная точка `/auth/password-login` имеет ограничение по скорости для каждого IP-адреса клиента (по умолчанию 10 попыток в минуту → HTTP 429) и возвращает один общий `401 Invalid credentials` как для неизвестных пользователей, так и для неправильных паролей, поэтому ее нельзя использовать в качестве оракула для перечисления имен пользователей.

#### Рабочий пример: имя пользователя/пароль

От ничего до защищенной паролем информационной панели в надежной сети за три шага.

**1. Установите учетные данные в `~/.hermes/.env`.** Хешируйте пароль, чтобы никакой открытый текст не оставался в состоянии покоя, и установите стабильный секрет подписи, чтобы сеансы выдерживали перезапуск:

```bash
# Compute a scrypt hash of your chosen password:
HASH=$(python -c "from plugins.dashboard_auth.basic import hash_password; print(hash_password('choose-a-strong-password'))")

cat >> ~/.hermes/.env <<EOF
HERMES_DASHBOARD_BASIC_AUTH_USERNAME=admin
HERMES_DASHBOARD_BASIC_AUTH_PASSWORD_HASH=$HASH
HERMES_DASHBOARD_BASIC_AUTH_SECRET=$(openssl rand -base64 32)
EOF
chmod 600 ~/.hermes/.env
```

**2. Запустите панель мониторинга по доступному адресу.** Привязка без обратной связи задействует шлюз, а имя пользователя + хэш активирует провайдера `basic`:

```bash
hermes dashboard --host 0.0.0.0 --port 9119 --no-open
```

**3. Войдите в систему.** Откройте `http://<host>:9119/`, вы будете перенаправлены на `/login` — **форму учетных данных** (а не кнопку «Войти с помощью X»). Введите `admin` / свой пароль → перейдите на панель управления с аутентификацией. Проверьте ворота с любой машины:

```bash
curl -s http://<host>:9119/api/status | jq '.auth_required, .auth_providers'
# true
# ["basic"]
```

`GET /api/auth/me` затем возвращает проверенный сеанс (`provider: basic`). Держите это за VPN — см. предупреждение выше; для публичного хоста вместо этого используйте поставщика [Nous Research](#default-provider-nous-research) или [self-hosted OIDC](#self-hosted-oidc-provider).

#### Создание собственного поставщика паролей

`basic` — это всего лишь одна реализация точки расширения. Любой плагин может зарегистрировать поставщика паролей: установите `supports_password = True` в вашем подклассе `DashboardAuthProvider` и реализуйте `complete_password_login(*, username, password) -> Session` (поднимите `InvalidCredentialsError` в случае отклонения, `ProviderError`, если ваше резервное хранилище не работает). Методы OAuth `start_login`/`complete_login` можно оставить как заглушки `NotImplementedError` для поставщика, использующего только пароль. Это путь к привязке LDAP, базе данных учетных данных или любой другой схеме аутентификации без перенаправления — платформа обрабатывает форму, маршрут, файлы cookie и обновляет их за вас.

### Самостоятельный поставщик OIDC

Если вы используете собственный поставщик удостоверений, встроенный плагин `plugins/dashboard_auth/self_hosted` аутентифицирует панель управления с помощью **стандартного OpenID Connect** — без кода каждого IDP и без использования Nous Portal. Он проверен и работает с любым совместимым сервером OIDC:

> **Authentik · Keycloak · Zitadel · Authelia · Auth0 · Okta · Google · …**

Как и провайдер Nous, он автоматически загружается и регистрируется только после настройки, поэтому для панелей мониторинга обратной связи он не используется.

#### Конфигурация

Настройте **эмитент** и **client_id** (публичный клиент PKCE — без секрета клиента). Плагин извлекает `authorization_endpoint`, `token_endpoint` и `jwks_uri` IDP из `{issuer}/.well-known/openid-configuration`, поэтому вам никогда не придется жестко запрограммировать URL-адреса конечных точек.

**`config.yaml`** — каноническая поверхность:

```yaml
dashboard:
  oauth:
    provider: self-hosted
    self_hosted:
      issuer: https://auth.example.com/application/o/hermes/   # required
      client_id: hermes-dashboard                              # required
      scopes: "openid profile email"                           # optional (this is the default)
```

**Переменные среды** — переопределения операторов (env выигрывает у `config.yaml`, если установлено непустое значение; пустое значение считается неустановленным):

| Конверт вар | Переопределения | Заметки |
|---------|-----------|-------|
| `HERMES_DASHBOARD_OIDC_ISSUER` | `dashboard.oauth.self_hosted.issuer` | URL эмитента OIDC — обязательно |
| `HERMES_DASHBOARD_OIDC_CLIENT_ID` | `dashboard.oauth.self_hosted.client_id` | Публичный идентификатор клиента — обязательно |
| `HERMES_DASHBOARD_OIDC_SCOPES` | `dashboard.oauth.self_hosted.scopes` | По умолчанию `openid profile email` |

В своем IDP зарегистрируйте **публичное** приложение/клиент с кодом авторизации + грантом PKCE (S256) и добавьте обратный вызов панели мониторинга в качестве разрешенного URI перенаправления. Обратный вызов — `<dashboard public URL>/auth/callback` (см. [Переопределение общедоступного URL-адреса](#public-url-override), чтобы узнать, как панель мониторинга получает свой общедоступный URL-адрес за прокси-сервером).

#### Что он проверяет

Поставщик проверяет **ID-токен** OpenID Connect (RS256/ES256) на соответствие обнаруженному `jwks_uri`, при этом утверждения `iss` и `aud` закрепляются за настроенными вами `issuer` и `client_id`. Стандартные заявки OIDC сопоставляются с сеансом информационной панели:

| Поле сеанса | Претензия(и) |
|---------------|----------|
| `user_id` | `sub` (обязательно) |
| `email` | `email` |
| `display_name` | `name` → `preferred_username` → `nickname` → `email` |
| `org_id` | `org_id` / `organization`, еще присоединился к `groups` |

Токен идентификатора — это то, что устанавливает идентичность — токен доступа считается непрозрачным (спецификация OIDC не требует, чтобы он был JWT). URL-адреса конечных точек должны быть HTTPS (обратная связь `http://` разрешена для IDP локальных разработчиков), а объявленный в документе обнаружения `issuer` должен совпадать с настроенным вами (разница в косой черте допускается). Токены обновления, когда IDP выдает их, используются для автоматической повторной аутентификации посредством стандартного гранта `refresh_token`; выход из системы вызывает RFC 7009 `revocation_endpoint` IDP при объявлении.

> **Конфиденциальные клиенты** (с `client_secret`) пока не поддерживаются — настройте общедоступный клиент + PKCE, который является типичным выбором для панели управления с браузером.

#### Рабочий пример: Keycloak

[Keycloak](https://www.keycloak.org/) — один из самых простых автономных серверов OIDC, способных выдержать локальное тестирование. Он работает как один контейнер в режиме разработки (база данных в памяти) и обеспечивает обнаружение OIDC по учебникам. Это пошаговое руководство поможет вам с нуля перейти к рабочему входу в панель управления за несколько минут.

**1. Запустите Keycloak с предварительно настроенной областью.** Сохраните экспорт этой области как `realm-hermes.json` — он определяет область `hermes`, **публичный клиент PKCE** (`hermes-dashboard`) и тестового пользователя, все они импортируются при загрузке, поэтому в пользовательском интерфейсе администратора не на что нажимать:

```json
{
  "realm": "hermes",
  "enabled": true,
  "clients": [
    {
      "clientId": "hermes-dashboard",
      "name": "Hermes Agent Dashboard",
      "enabled": true,
      "publicClient": true,
      "standardFlowEnabled": true,
      "protocol": "openid-connect",
      "redirectUris": ["http://localhost:9119/auth/callback"],
      "webOrigins": ["http://localhost:9119"],
      "attributes": { "pkce.code.challenge.method": "S256" }
    }
  ],
  "users": [
    {
      "username": "testuser",
      "enabled": true,
      "emailVerified": true,
      "email": "testuser@example.com",
      "firstName": "Test",
      "lastName": "User",
      "credentials": [
        { "type": "password", "value": "testpassword", "temporary": false }
      ]
    }
  ]
}
```

Запустите его (Keycloak 26+), смонтировав этот файл в каталог импорта:

```bash
docker run --rm -p 8080:8080 \
  -e KC_BOOTSTRAP_ADMIN_USERNAME=admin \
  -e KC_BOOTSTRAP_ADMIN_PASSWORD=admin \
  -v "$PWD/realm-hermes.json:/opt/keycloak/data/import/realm-hermes.json:ro" \
  quay.io/keycloak/keycloak:26.0 \
  start-dev --import-realm
```

Как только это произойдет, сфера объявляет стандартное обнаружение OIDC по адресу
`http://localhost:8080/realms/hermes/.well-known/openid-configuration` (эмитент
`http://localhost:8080/realms/hermes`). Консоль администратора находится по адресу
`http://localhost:8080/` (`admin` / `admin`).

**2. Наведите на него панель управления.** Самостоятельный плагин разрешает эмитент обратной связи `http://` (HTTPS требуется для любого эмитента без обратной связи), поэтому локальный Keycloak работает как есть:

```bash
export HERMES_DASHBOARD_OIDC_ISSUER="http://localhost:8080/realms/hermes"
export HERMES_DASHBOARD_OIDC_CLIENT_ID="hermes-dashboard"
export HERMES_DASHBOARD_PUBLIC_URL="http://localhost:9119"
hermes dashboard --host 0.0.0.0 --port 9119 --no-open
```

`HERMES_DASHBOARD_PUBLIC_URL` сообщает информационной панели, что его обратный вызов OAuth
`http://localhost:9119/auth/callback` — URI перенаправления, зарегистрированный в области.
выше. Привязка к `0.0.0.0` (привязка без обратной связи) – это то, что
задействует шлюз OAuth.

**3. Войдите в систему.** Откройте `http://localhost:9119/`, вы будете перенаправлены на `/login`. Нажмите **Войти с помощью локального OIDC** → выполните аутентификацию в Keycloak как `testuser` / `testpassword` → вернитесь на аутентифицированную панель управления. На боковой панели отображается `Logged in as Test User via self-hosted`, а `GET /api/auth/me` возвращает проверенный сеанс (`provider: self-hosted`, `email: testuser@example.com`).

> Если вы привязываетесь или просматриваете другой хост/порт, добавьте этот источник
> `…/auth/callback` к **Действительным URI перенаправления** клиента в Keycloak
> Консоль администратора (Клиенты → hermes-dashboard → Настройки). Та же схема работает
> для Authentik, Zitadel, Authelia и других серверов OIDC — только эмитент
> URL-адрес и пользовательский интерфейс регистрации клиента различаются.

### Переопределение общедоступного URL-адреса

По умолчанию панель управления восстанавливает URL-адрес обратного вызова OAuth из запроса — `X-Forwarded-Host` + `X-Forwarded-Proto` + `X-Forwarded-Prefix` (когда uvicorn настроен с `proxy_headers=True`, который `start_server` включает под шлюзом). Это работает «из коробки» с обратным прокси-сервером, который правильно устанавливает все три заголовка.

Для развертываний за обратными прокси-серверами, которые не обеспечивают надежную пересылку этих заголовков (ручные настройки nginx, локальные входы, развертывания в пользовательском домене с частичными цепочками прокси), установите для `dashboard.public_url` (или `HERMES_DASHBOARD_PUBLIC_URL`) **полный общедоступный URL-адрес**, по которому доступна панель мониторинга:

```yaml
dashboard:
  public_url: "https://dashboard.example.com/hermes"
```

Если этот параметр установлен, URL-адрес обратного вызова OAuth становится `<public_url>/auth/callback` дословно — `X-Forwarded-Prefix` игнорируется в этом пути кода, поскольку оператор явно объявил общедоступный URL-адрес. Это сделано намеренно: размещение префикса сверху привело бы к двойному префиксу в обычном случае, когда префикс уже встроен в `public_url`.

Имя хоста в `public_url` также принимается как **точное** HTTP `Host` и
Значение WebSocket `Origin`. Это поддерживает обратный прокси, который сохраняет
имя хоста, обращенное к браузеру, при пересылке на панель управления, привязанную к
`127.0.0.1`. Подстановочные знаки и совпадения суффиксов не допускаются, поэтому хост злоумышленника
например `dashboard.example.com.evil.test`, остается отклоненным при повторной привязке DNS
охранник.

Объявление `public_url` без шлейфа всегда задействует шлюз аутентификации панели управления,
даже когда бэкэнд привязан к петле. Настройте пароль или поставщика OAuth
первый; без него Гермес не закрывается при запуске. Это предотвращает местный SPA
токен сеанса не станет механизмом удаленной аутентификации через
прокси. Uvicorn также позволяет в этом режиме обрабатывать доверенные прокси-заголовки.
локальный терминатор TLS может предоставить `X-Forwarded-Proto: https` для безопасных файлов cookie.

```bash
# Backend remains reachable only on this machine.
hermes dashboard --host 127.0.0.1 --port 9119 --no-open
```

Направьте обратный прокси-сервер TLS на `http://127.0.0.1:9119` и используйте
то же внешнее происхождение в `dashboard.public_url`.

Tailscale Serve — один из примеров такой формы развертывания: он может завершить работу
HTTPS только для хвостовой сети на имени хоста `https://<machine>.<tailnet>.ts.net`, в то время как
проксирование на панель обратной связи. Используйте этот точный источник HTTPS как
`dashboard.public_url`. Он по-прежнему рассматривается как браузер без обратной связи.
origin и, следовательно, требует поставщика аутентификации информационной панели; это не требует
сделать услугу доступной из общедоступного Интернета.

Тот же приоритет, что и у других настроек информационной панели — env выигрывает у `config.yaml`:

| Поверхность | Переопределить путь | Когда использовать |
|---------|---------------|-------------|
| `dashboard.public_url` в `config.yaml` | `HERMES_DASHBOARD_PUBLIC_URL` | Локальная разработка/локальная версия (каноническая) |
| `HERMES_DASHBOARD_PUBLIC_URL` переменная окружения | — | Секреты хостинг-платформы / CI |
| (не установлено) | — | По умолчанию — восстановление из заголовков `X-Forwarded-*` |

При проверке отклоняются значения без схемы `http://` / `https://`, без хоста или содержащие кавычки, углы, пробелы или управляющие символы. Неверное значение незаметно попадает в реконструкцию заголовка, поэтому поток входа в систему продолжает работать, а не отправляет пользователя на враждебный URL-адрес.

> **Примечание.** `public_url` переопределяет только URL обратного вызова OAuth. Флаг cookie `Secure` по-прежнему контролируется `request.url.scheme` (X-Forwarded-Proto в разделе proxy_headers), поэтому `http://` `public_url` при общедоступном развертывании, завершенном по TLS, будет создавать незащищенные файлы cookie. Это пулемет оператора — пара `public_url` с правильным завершением TLS в восходящем направлении.

### Поток OAuth

Поставщик реализует [контракт OAuth Nous Portal v1](https://github.com/NousResearch/nous-account-service/blob/main/docs/agent-dashboard-oauth-contract.md) — предоставление кода авторизации с помощью PKCE (S256):

1. Пользователь обращается к `/` без файла cookie сеанса → шлюз перенаправляется на `/login`.
2. На странице входа отображается кнопка «Продолжить исследование Nous» → `/auth/login?provider=nous`.
3. Сервер сохраняет состояние PKCE в кратковременном файле cookie и перенаправляет пользователя на `https://portal.nousresearch.com/oauth/authorize?…`.
4. Пользователь проходит аутентификацию на портале и попадает на адрес `/auth/callback?code=…&state=…`.
5. Сервер обменивает код на токен доступа по адресу `POST /api/oauth/token`, сверяет подпись JWT с JWKS портала (`/.well-known/jwks.json`) и устанавливает файл cookie `hermes_session_at`.
6. Пользователь перенаправляется на `/` (или на исходный путь глубокой ссылки через параметр запроса `next=`).

Токены доступа имеют срок жизни 15 минут. **В контракте версии 1 нет токена обновления** — по истечении срока действия токена оболочка выборки SPA обнаруживает конверт 401 и выполняет полностраничный переход обратно к `/login` для повторного запуска потока.

### Набор файлов cookie

| Имя | Пожизненная | Заметки |
|------|----------|-------|
| `hermes_session_at` | Срок жизни токена (15 минут) | HttpOnly, SameSite=Lax, Secure-when-HTTPS |
| `hermes_session_pkce` | 10 мин | HttpOnly; содержит подсказку верификатора PKCE + поставщика во время передачи туда и обратно. SameSite=None + Secure over HTTPS (должен выдерживать межсайтовую цепочку перенаправления IDP — Chromium удаляет файлы cookie SameSite=Lax, установленные на 302 в межсайтовой цепочке); SameSite=Слабость при обратной связи по HTTP |
| `hermes_session_rt` | не используется в v1 | Зарезервировано для прямой совместимости; не записывается, если `refresh_token` пуст |

Все трое — `Path=/`. Файлы cookie сеанса: `SameSite=Lax`; файл cookie PKCE имеет значение `SameSite=None`, если он установлен через HTTPS (см. таблицу). Флаг `Secure` устанавливается, когда панель управления доступна через HTTPS (обнаруживается с помощью схемы URL-адреса запроса — учитывается `X-Forwarded-Proto` от восходящего терминатора TLS под `proxy_headers=True`).

### Выход

Виджет боковой панели показывает `Logged in as <user_id…> via nous` со значком выхода из системы. При нажатии на нее выполняется POST `/auth/logout`, который очищает все файлы cookie аутентификации панели управления и перенаправляет обратно на `/login`.

### Журнал аудита

Каждый запуск входа, успех, неудача и ошибка проверки сеанса записываются в виде строки JSON в `$HERMES_HOME/logs/dashboard-auth.log`. Чувствительные поля (`access_token`, `refresh_token`, `code`, `code_verifier`, `state`, `Authorization` заголовок) редактируются перед записью в журнал.

### Пользовательские поставщики

Чтобы подключить провайдера OAuth, отличного от Nous (например, Google, GitHub, собственный OIDC), создайте плагин, который регистрирует `DashboardAuthProvider`:

```python
# ~/.hermes/plugins/dashboard-auth-myidp/__init__.py
from hermes_cli.dashboard_auth import DashboardAuthProvider, Session, LoginStart

class MyIdPProvider(DashboardAuthProvider):
    name = "myidp"
    display_name = "My Identity Provider"

    def start_login(self, *, redirect_uri): ...
    def complete_login(self, *, code, state, code_verifier, redirect_uri): ...
    def verify_session(self, *, access_token): ...
    def refresh_session(self, *, refresh_token): ...
    def revoke_session(self, *, refresh_token): ...

def register(ctx):
    ctx.register_dashboard_auth_provider(MyIdPProvider())
```

На странице входа перечислены все зарегистрированные поставщики; можно объединить несколько поставщиков, и пользователь выбирает одного по адресу `/login`.

### Неинтерактивная аутентификация (токен на предъявителя)

Помимо интерактивного входа в систему (файлы cookie сеанса + обновление), `DashboardAuthProvider` ABC поддерживает **неинтерактивную возможность межсервисного взаимодействия** через `supports_token = True` + `verify_token(token=...)`. Когда поставщик соглашается, входящий `Authorization: Bearer <token>` проверяется, и в случае успеха к запросу (`request.state.token_principal`) прикрепляется `TokenPrincipal` для конечных точек, которые поставщик помечает как авторизуемые по токену — без файлов cookie, без перенаправления, без обновления.

Первым потребителем в комплекте является поставщик **слива** (`plugins/dashboard_auth/drain`): `nous-account-service` предоставляет секрет каждого агента через `HERMES_DASHBOARD_DRAIN_SECRET`, а поставщик проверяет входящие токены-носители по нему с помощью сравнения в постоянном времени, регистрируя `/api/gateway/drain` как аутентифицируемый по токену. Он **не закрывается** — слабый/короткий секрет (< 256 бит) отклоняется при регистрации, и конечная точка остается отключенной; это не работает, когда переменная env не установлена. Поведенческие ручки (`scope`, `min_secret_chars`) находятся под `dashboard.drain_auth` в `config.yaml`.

Пользовательские поставщики могут реализовать `supports_token`/`verify_token` таким же образом, чтобы предоставить свои собственные конечные точки с машинной аутентификацией.

## Подключение Hermes Desktop к удаленному серверу

Hermes Desktop может управлять серверной частью Hermes, работающей на другом компьютере (VPS, домашнем сервере, Mini за Tailscale). В приложении это находится в разделе **Настройки → Шлюзы → Удаленный шлюз**, где запрашивается **Удаленный URL-адрес** и способ **Входа**. (Информацию о самом настольном приложении — установка, настройки, чат — см. на странице [Hermes Desktop](/user-guide/desktop).)

Вы защищаете удаленную панель мониторинга с помощью одного из встроенных поставщиков аутентификации, а настольное приложение входит в систему с использованием того, который рекламирует серверная часть. Для серверной части, доступной за пределами вашего собственного компьютера (VPS, общедоступный хостинг, любой доступ к Интернету), рекомендуемым поставщиком является **OAuth (Nous Portal)** (зарегистрируйте его с помощью [`hermes dashboard register`](#registering-a-dashboard) и войдите в систему с помощью *Войдите с помощью Nous Research*). Объединенный [поставщик имени пользователя и пароля](#usernamepassword-provider-no-oauth-idp) – самый быстрый вариант, когда серверная часть находится в доверенной локальной сети или доступна только через VPN, но **не подходит для прямого доступа в общедоступный Интернет**. Привязка информационной панели к адресу без обратной связи задействует шлюз аутентификации; после входа в систему Desktop автоматически повторно использует сеанс для чата WebSocket — токен для копирования или вставки отсутствует.

В приведенном ниже рецепте используется путь имени пользователя и пароля, поскольку он быстрее всего подключается к доверенной сети; путь OAuth см. в разделе [Поставщик по умолчанию: Nous Research](#default-provider-nous-research).

### На серверной стороне (удаленная машина)

```bash
# 1. Set the dashboard login credentials in ~/.hermes/.env (secrets file, 0600).
cat >> ~/.hermes/.env <<'EOF'
HERMES_DASHBOARD_BASIC_AUTH_USERNAME=admin
HERMES_DASHBOARD_BASIC_AUTH_PASSWORD=choose-a-strong-password
# Recommended: a stable signing secret so sessions survive restarts.
HERMES_DASHBOARD_BASIC_AUTH_SECRET=$(openssl rand -base64 32)
EOF
chmod 600 ~/.hermes/.env

# 2. Run the dashboard bound to a reachable address. The non-loopback bind
#    engages the auth gate; the username/password provider handles login.
hermes dashboard --no-open --host 0.0.0.0 --port 9119
```

Предпочитаете отсутствие открытого текста в состоянии покоя? Вместо этого используйте `HERMES_DASHBOARD_BASIC_AUTH_PASSWORD_HASH` с хэшем сценария — полную информацию см. в разделе [Поставщик имени пользователя и пароля](#usernamepassword-provider-no-oauth-idp).

Если вы запускаете панель мониторинга как службу systemd, `~/.hermes/.env` выбирается автоматически, когда на устройстве есть `EnvironmentFile=%h/.hermes/.env`, поэтому учетные данные находятся в среде при загрузке.

:::предупреждение
Панель мониторинга считывает и записывает ваш `.env` (ключи API, секреты) и может запускать команды агента. Показанная здесь настройка **имя пользователя и пароль** предназначена для доверенной сети — никогда не открывайте защищенную паролем панель управления непосредственно в открытом Интернете. Поместите его за VPN. [Tailscale](https://tailscale.com/) — это чистый вариант: привяжите его к IP-адресу Tailscale (`--host <tailscale-ip>`) и используйте `http://<tailscale-ip>:9119` в качестве удаленного URL-адреса. Только устройства в вашей хвостовой сети могут получить к нему доступ. Чтобы получить доступ к серверной части через общедоступный Интернет, используйте вместо этого поставщика **OAuth (Nous Portal)**.
:::

### На рабочем столе Hermes

**Настройки → Шлюзы → Удаленный шлюз:**

- **Удаленный URL-адрес** — `http://<backend-host>:9119` (префиксы пути, такие как `/hermes`, поддерживаются, если вы используете обратный прокси-сервер).
- **Войти** — приложение определяет шлюз имени пользователя и пароля и отображает кнопку **Войти**; щелкните по нему и введите учетные данные из шага 1
- **Сохранить и переподключить** — переключает оболочку рабочего стола на удаленный сервер.

Сеанс обновляется автоматически и сохраняется при перезапуске, если на серверной стороне установлен `HERMES_DASHBOARD_BASIC_AUTH_SECRET`.

### Переопределение переменной среды

Вместо настройки в приложении вы можете указать рабочему столу на серверную часть с помощью переменной env перед его запуском. Если установлен `HERMES_DESKTOP_REMOTE_URL`, он переопределяет сохраненный URL-адрес в приложении (на панели настроек шлюза отображается значок «переопределение среды» и редактирование отключается); вы по-прежнему **войдите** под своим именем пользователя и паролем с панели.

| Конверт вар | Значение |
|---------|-------|
| `HERMES_DESKTOP_REMOTE_URL` | `http://<backend-host>:9119` |

### Устранение неполадок

- **"Удаленный шлюз не завершен"** — вы не ввели удаленный URL-адрес.
- **Сбой входа в систему с ошибкой 401 / «Неверные учетные данные»** — имя пользователя или пароль не соответствуют `HERMES_DASHBOARD_BASIC_AUTH_USERNAME` / `HERMES_DASHBOARD_BASIC_AUTH_PASSWORD` серверной части. Серверная часть возвращает одну и ту же общую ошибку для неизвестного пользователя и неправильного пароля, поэтому проверьте оба варианта. Подтвердите шлюз с помощью `curl -s http://<host>:9119/api/status | jq '.auth_required, .auth_providers'` — он должен сообщить `true` и включить `"basic"`.
- **Нет кнопки «Войти» — вместо этого запрашивается токен сеанса** — поставщик имени пользователя и пароля не активен (`/api/status` не будет отображать `"basic"`). Убедитесь, что имя пользователя и пароль (или хэш пароля) заданы и процесс панели мониторинга загрузил их.
- **Выход при каждой перезагрузке** — установите для `HERMES_DASHBOARD_BASIC_AUTH_SECRET` стабильное значение; в противном случае ключ подписи создается повторно при каждой загрузке.
- **Соединение отклонено/время ожидания** — серверная часть привязана к `127.0.0.1` (по умолчанию) вместо доступного адреса, или брандмауэр/VPN блокирует порт. Привяжитесь к `0.0.0.0` или IP-адресу Tailscale и откройте порт для доверенной сети.

## КОРС

Веб-сервер ограничивает CORS только источниками локального хоста:

- `http://localhost:9119` / `http://127.0.0.1:9119` (производство)
- `http://localhost:3000` / `http://127.0.0.1:3000`
- `http://localhost:5173` / `http://127.0.0.1:5173` (сервер разработки Vite)

Если вы запускаете сервер на специальном порту, этот источник добавляется автоматически.

## Развитие

Если вы вносите вклад в интерфейс веб-панели:

```bash
# Terminal 1: start the backend API
hermes dashboard --no-open

# Terminal 2: start the Vite dev server with HMR
cd web/
npm install
npm run dev
```

Сервер разработки Vite по адресу `http://localhost:5173` передает `/api` запросы к серверной части FastAPI по адресу `http://127.0.0.1:9119`.

Интерфейс построен с использованием React 19, TypeScript, Tailwind CSS v4 и компонентов в стиле shadcn/ui. Производство формирует выходные данные в `hermes_cli/web_dist/`, который сервер FastAPI служит статическим SPA.

## Автоматическая сборка при обновлении

Когда вы запускаете `hermes update`, веб-интерфейс автоматически перестраивается, если `npm` доступен. Это позволяет синхронизировать панель мониторинга с обновлениями кода. Если `npm` не установлен, обновление пропускает сборку внешнего интерфейса, а `hermes dashboard` создаст его при первом запуске.
