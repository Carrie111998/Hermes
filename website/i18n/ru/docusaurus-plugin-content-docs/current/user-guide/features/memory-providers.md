# Поставщики памяти

Агент Hermes поставляется с 8 плагинами внешнего поставщика памяти, которые предоставляют агенту постоянные межсессионные знания, выходящие за рамки встроенных MEMORY.md и USER.md. Одновременно может быть активен только **один** внешний провайдер — рядом с ним всегда активна встроенная память.

## Быстрый старт

```bash
hermes memory setup      # interactive picker + configuration
hermes memory status     # check what's active
hermes memory off        # disable external provider
```

Вы также можете выбрать поставщика активной памяти через `hermes plugins` → Плагины поставщика → Поставщик памяти.

Или установите вручную в `~/.hermes/config.yaml`:

```yaml
memory:
  provider: openviking   # or honcho, mem0, hindsight, holographic, retaindb, byterover, supermemory
```

## Как это работает

Когда поставщик памяти активен, Hermes автоматически:

1. **Вводит контекст провайдера** в системное приглашение (то, что знает провайдер)
2. **Предварительная выборка соответствующих воспоминаний** перед каждым ходом (фоновый, неблокирующийся)
3. **Синхронизирует разговор** с поставщиком услуг после каждого ответа.
4. **Извлекает воспоминания по окончании сеанса** (для провайдеров, которые это поддерживают)
5. **Отражает запись во встроенную память** внешнему поставщику.
6. **Добавляет инструменты, специфичные для провайдера**, чтобы агент мог искать, хранить воспоминания и управлять ими.

Встроенная память (MEMORY.md/USER.md) продолжает работать точно так же, как и раньше. Внешний поставщик является аддитивным.

## Доступные провайдеры

### Хончо

Межсессионное моделирование пользователей на основе искусственного интеллекта с диалектическими рассуждениями, внедрением контекста на уровне сеанса, семантическим поиском и постоянными выводами. Базовый контекст теперь включает в себя сводку сеанса наряду с представлением пользователей и карточками партнеров, что дает агенту представление о том, что уже обсуждалось.

| | |
|---|---|
| **Лучший вариант** | Мультиагентные системы с межсессионным контекстом, согласованием пользовательского агента |
| **Требуется** | `pip install honcho-ai` + [ключ API](https://app.honcho.dev) или автономный экземпляр |
| **Хранение данных** | Honcho Cloud или самостоятельное размещение |
| **Стоимость** | Высококачественные цены (облако) / бесплатно (автономное размещение) |

**Инструменты (5):** `honcho_profile` (чтение/обновление карты узла), `honcho_search` (семантический поиск), `honcho_context` (контекст сеанса — сводка, представление, карта, сообщения), `honcho_reasoning` (синтезированный LLM), `honcho_conclude` (создание/удаление заключений)

**Архитектура:** Двухуровневое внедрение контекста — базовый уровень (сводка сеанса + представление + карточка партнера, обновлено `contextCadence`) плюс диалектическое дополнение (рассуждения LLM, обновлено `dialecticCadence`). Диалектика автоматически выбирает подсказки холодного запуска (общие факты о пользователе) или теплые подсказки (контекст на уровне сеанса) в зависимости от того, существует ли базовый контекст.

**Три ортогональные ручки настройки** независимо контролируют стоимость и глубину:

- `contextCadence` — как часто обновляется базовый уровень (частота вызовов API)
- `dialecticCadence` — как часто срабатывает диалектика LLM (частота вызова LLM)
- `dialecticDepth` — сколько проходов `.chat()` за диалектический вызов (1–3, глубина рассуждения)

Автоматически внедряемая диалектика также масштабирует уровень рассуждения в зависимости от длины запроса (более длинный запрос → более глубокое рассуждение, ограничено `reasoningLevelCap`); см. [Уровень адаптивного рассуждения к запросу](./honcho.md#query-adaptive-reasoning-level).

**Мастер настройки:**
```bash
hermes memory setup        # select "honcho" — runs the Honcho-specific post-setup
```

Устаревшая команда `hermes honcho setup` по-прежнему работает (теперь она перенаправляется на `hermes memory setup`), но регистрируется только после того, как Honcho выбран в качестве активного поставщика памяти.

**Безголовые/удаленные машины:** для облачной аутентификации на компьютере без браузера (SSH, удаленная виртуальная машина) выберите **устройство** в приглашении мастера авторизации. CLI печатает короткий код и ссылку для проверки; откройте ссылку в браузере на любом другом компьютере, подтвердите и настройка будет завершена — копирование и вставка ключа API не требуется. Мастер автоматически выбирает этот параметр по умолчанию, когда не обнаруживает пригодный для использования локальный браузер.

**Конфигурация:** `$HERMES_HOME/honcho.json` (локальная в профиле) или `~/.honcho/config.json` (глобальная). Порядок разрешения: `$HERMES_HOME/honcho.json` > `~/.hermes/honcho.json` > `~/.honcho/config.json`. См. [ссылку на конфигурацию] (https://github.com/NousResearch/hermes-agent/blob/main/plugins/memory/honcho/README.md) и [руководство по интеграции Honcho] (https://docs.honcho.dev/v3/guides/integrations/hermes).

Если вы ранее использовали `hermes honcho setup`, ваша конфигурация и все данные на стороне сервера не повреждены. Просто повторно включите его с помощью мастера настройки или вручную настройте `memory.provider: honcho` для повторной активации через новую систему.

**Многоранговая настройка:**

Honcho моделирует разговоры как обмен сообщениями между одноранговыми узлами — один пользовательский одноранговый узел плюс один AI-одноранговый узел для каждого профиля Hermes, и все они используют одно рабочее пространство. Рабочее пространство — это общая среда: одноранговый узел пользователя является глобальным для всех профилей, каждый одноранговый узел AI имеет свою собственную личность. Каждый партнер ИИ создает независимое представление/карту на основе собственных наблюдений, поэтому профиль `coder` остается ориентированным на код, а профиль `writer` остается редакционным для одного и того же пользователя.

Отображение:

| Концепция | Что это такое |
|---------|-----------|
| **Рабочая область** | Общая среда. Все профили Hermes в одном рабочем пространстве видят одну и ту же личность пользователя. |
| **Узел пользователя** (`peerName`) | Человек. Доступно для всех профилей в рабочей области. |
| **АИ** (`aiPeer`) | По одному на каждый профиль Hermes. Ключ хоста `hermes` → по умолчанию; `hermes.<profile>` для других. |
| **Наблюдение** | Для каждого узла переключается контроль того, что Honcho моделирует на основе чьих сообщений. `directional` (по умолчанию, все четыре включены) или `unified` (пул с одним наблюдателем). |

### Новый профиль, новый коллега Honcho

```bash
hermes profile create coder --clone
```

`--clone` создает блок хоста `hermes.coder` в `honcho.json` с `aiPeer: "coder"`, общим `workspace`, унаследованным `peerName`, `recallMode`, `writeFrequency`, `observation` и т. д. Партнер AI активно создается в Honcho, поэтому он существует до первого сообщения.

### Существующие профили, заполнение высокопоставленными узлами

```bash
hermes honcho sync
```

Сканирует каждый профиль Hermes, создает блоки хостов для любого профиля без него, наследует настройки из блока по умолчанию `hermes` и с готовностью создает новые узлы AI. Идемпотент — пропускает профили, у которых уже есть блок хостов.

### Наблюдение по каждому профилю

Каждый блок хоста может независимо переопределить конфигурацию наблюдения. Пример: профиль, ориентированный на код, в котором партнер ИИ наблюдает за пользователем, но не моделирует себя:

```json
"hermes.coder": {
  "aiPeer": "coder",
  "observation": {
    "user": { "observeMe": true, "observeOthers": true },
    "ai":   { "observeMe": false, "observeOthers": true }
  }
}
```

**Переключатели наблюдения (один набор для каждого узла):**

| Переключить | Эффект |
|--------|--------|
| `observeMe` | Honcho строит представление этого узла на основе своих сообщений |
| `observeOthers` | Этот узел наблюдает за сообщениями другого узла (поддерживает рассуждения между узлами) |

Предустановки через `observationMode`:

- **`"directional"`** (по умолчанию) — включены все четыре флага. Полное взаимное наблюдение; обеспечивает перекрестную диалектику.
- **`"unified"`** — пользователь `observeMe: true`, AI `observeOthers: true`, остальное false. Пул одного наблюдателя; ИИ моделирует пользователя, но не себя, пользователь моделирует только себя.

Переключатели на стороне сервера, установленные через [панель управления Honcho](https://app.honcho.dev), имеют преимущество над локальными настройками по умолчанию — синхронизируются обратно при инициализации сеанса.

См. [страницу Honcho](./honcho.md#observation-direction-vs-unified) для получения полной информации о наблюдениях.

### Сопоставление идентификаторов шлюза

Приведенная выше одноранговая модель охватывает сеансы CLI, TUI и рабочего стола, где каждый разговор заканчивается `peerName`. [Шлюз](../../developer-guide/gateway-internals.md) добавляет вторую ось: пользователи приходят с собственными для платформы идентификаторами среды выполнения (UID Telegram, Discord Snowflake, пользователь Slack), а три ключа определяют, к какому узлу соответствует каждый идентификатор.

| Ключ | Эффект |
|-----|--------|
| `pinUserPeer: true` | Каждый пользователь шлюза, не являющийся агентом, сворачивается до `peerName`. Пин-код проверяется первым, поэтому он переопределяет все псевдонимы — выбирайте его только в том случае, если ни одному идентификатору на стороне пользователя не нужен собственный одноранговый узел |
| `userPeerAliases` | Сопоставляет определенные идентификаторы среды выполнения с одноранговыми узлами (`{"7654321": "alice"}`). Дом для маршрутизации различных идентификаторов, включая агентов, каждый из которых имеет свой собственный узел |
| `runtimePeerPrefix` | Пространствам имен любой несопоставленный идентификатор среды выполнения (`telegram_7654321`), чтобы платформы с идентификаторами одинаковой формы не конфликтовали |

Вне шлюза эти ключи ничего не делают. `hermes memory setup` запрашивает их только тогда, когда обнаруживает подключенную платформу шлюза. См. [страницу Honcho](./honcho.md#gateway-identity-mapping) для получения информации о лестнице преобразователя и процессе настройки.

### ОпенВикинг

Контекстная база данных от Volcengine (ByteDance) с иерархией знаний в стиле файловой системы, многоуровневым поиском и автоматическим разделением памяти на 6 категорий.

| | |
|---|---|
| **Лучший вариант** | Автономное управление знаниями со структурированным просмотром |
| **Требуется** | OpenViking инициализирован, проверен и запущен |
| **Хранение данных** | Самостоятельное размещение (локальное или облачное) |
| **Стоимость** | Бесплатно (с открытым исходным кодом, AGPL-3.0) |

**Инструменты (6):** `viking_search` (семантический поиск), `viking_read` (многоуровневый: абстрактный/обзор/полный), `viking_browse` (навигация по файловой системе), `viking_remember` (сохранение фактов), `viking_forget` (удаление файла памяти по точному `viking://` URI), `viking_add_resource` (загрузка URL-адресов/документов)

**Настройка:**
```bash
# Prepare OpenViking first
openviking-server init
openviking-server doctor
openviking-server

# Then configure Hermes
hermes memory setup    # select "openviking"
# Or manually:
hermes config set memory.provider openviking
```

`hermes memory setup` может повторно использовать или копировать значения соединения из
`~/.openviking/ovcli.conf`. При ручной настройке используется файл `.env` активного профиля;
для профиля по умолчанию — `~/.hermes/.env`, а для именованных профилей используйте
`~/.hermes/profiles/<profile>/.env`.

```text
OPENVIKING_ENDPOINT=http://127.0.0.1:1933
# OPENVIKING_API_KEY=...
# OPENVIKING_ACCOUNT=default
# OPENVIKING_USER=default
# OPENVIKING_AGENT=hermes
```

Настройки сервера OpenViking находятся в `ov.conf` (`--config`,
`OPENVIKING_CONFIG_FILE` или `~/.openviking/ov.conf`). Значения клиентского подключения
живу в `ovcli.conf` (`OPENVIKING_CLI_CONFIG_FILE` или
`~/.openviking/ovcli.conf`).

**Основные особенности:**
- Многоуровневая загрузка контекста: L0 (~100 токенов) → L1 (~2 тыс.) → L2 (полный)
- Автоматическое извлечение памяти при фиксации сеанса (профиль, настройки, сущности, события, случаи, шаблоны)
- `viking://` Схема URI для иерархического просмотра знаний.

`OPENVIKING_ACCOUNT` и `OPENVIKING_USER` используются для локального/доверенного режима.
`OPENVIKING_AGENT` — это идентификатор узла Hermes в OpenViking для одноранговой памяти.
Гермес отправляет `User-Agent: openviking-memory-hermes/<version>` на OpenViking
запросы. Этот стандартный идентификатор жгута не содержит идентификатора пользователя и
не добавляет отдельный запрос.

### Мем0

Извлечение фактов LLM на стороне сервера с семантическим поиском, переранжированием и автоматической дедупликацией. Три режима подключения: **Платформа** (облако Mem0), **автономная панель управления** (сервер Mem0, который вы запускаете через Docker) и **OSS** (Mem0 в процессе работы с вашим собственным хранилищем LLM + вектор).

| | |
|---|---|
| **Лучший вариант** | Автоматическое управление памятью — Mem0 автоматически обрабатывает извлечение |
| **Требуется** | `pip install mem0ai` + ключ API (платформа), работающий сервер Mem0 (автономная панель мониторинга) или LLM + векторное хранилище (OSS) |
| **Хранение данных** | Облако Mem0 (платформа), ваш собственный сервер Mem0 (локальная панель управления) или внутрипроцессный (OSS) |
| **Стоимость** | Цены на Mem0 (платформа) / бесплатно (локальное размещение или OSS) |

**Инструменты (4):** `mem0_search` (семантический поиск; опциональное переранжирование в режиме платформы, по умолчанию отключено), `mem0_add` (сохранение дословных фактов), `mem0_update` (обновление по идентификатору), `mem0_delete` (удаление по идентификатору)

**Настройка (платформа):**
```bash
hermes memory setup    # select "mem0" → "Platform"
# Or manually:
hermes config set memory.provider mem0
echo "MEM0_API_KEY=your-key" >> ~/.hermes/.env
```

**Настройка (OSS):**
```bash
hermes memory setup    # select "mem0" → "Open Source (self-hosted)"
# Or via flags:
hermes memory setup mem0 --mode oss --oss-llm openai --oss-llm-key sk-... --oss-vector qdrant
```

Предварительный просмотр без записи файлов:
```bash
hermes memory setup mem0 --mode oss --oss-llm-key sk-... --dry-run
```

**Настройка (личная панель мониторинга):** подключитесь к серверу Mem0, который вы запускаете через Docker (REST API панели управления):

```bash
hermes memory setup    # select "mem0" → "Self-hosted server"
# Or via flags:
hermes memory setup mem0 --mode selfhosted --host http://localhost:8888 --api-key your-admin-api-key
```

Или настройте вручную — либо как переменные окружения:

```bash
echo "MEM0_HOST=http://localhost:8888" >> ~/.hermes/.env
echo "MEM0_API_KEY=your-admin-api-key" >> ~/.hermes/.env
```

или в `mem0.json`:

```json
{ "host": "http://localhost:8888", "api_key": "your-admin-api-key" }
```

Плагин аутентифицируется с помощью `X-API-Key` и использует маршруты сервера `/search`/`/memories`. `api_key` не является обязательным (опустите только для серверов `AUTH_DISABLED`). Не устанавливайте `mode: oss` — он имеет приоритет над `host`.

**Конфигурация:** `$HERMES_HOME/mem0.json` (настройки поведения). Только секрет `MEM0_API_KEY` принадлежит `~/.hermes/.env`.

| Ключ | По умолчанию | Описание |
|-----|---------|-------------|
| `mode` | `platform` | `platform` (облако Mem0) или `oss` (самоуправляемый, в процессе) |
| `host` | — | URL-адрес локального сервера Mem0 (панель управления Docker). Маршруты через HTTP с помощью `X-API-Key`; не сочетать с `mode: oss` |
| `user_id` | `hermes-user` | Идентификатор пользователя |
| `agent_id` | `hermes` | Идентификатор агента |
| `rerank` | `false` | Изменить рейтинг результатов поиска по релевантности (только в режиме платформы) |

**Поставщики, поддерживающие OSS:**

| Компонент | Провайдеры |
|-----------|-----------|
| LLM | опенай, оллама |
| Встраиватель | опенай, оллама |
| Векторный магазин | qdrant (локальный/серверный), pgvector |

**Переключение режимов**: повторно запустите `hermes memory setup mem0 --mode <platform|selfhosted|oss>` или отредактируйте `mem0.json` напрямую.

### Оглядываясь назад

Долговременная память с графом знаний, разрешением сущностей и поиском с использованием нескольких стратегий. Автоматически сохраняет все ходы разговора (включая вызовы инструментов) с отслеживанием документов на уровне сеанса.

| **Стоимость** | Оглядываясь назад на цены (облако) или бесплатно (локально) |

**Инструменты:** `hindsight_retain` (хранилище с извлечением сущностей), `hindsight_recall` (многостратегический поиск), `hindsight_reflect` (синтез между памятью).

**Интерфейс локального режима:** `hindsight-embed -p hermes ui start`

**Конфигурация:** `$HERMES_HOME/hindsight/config.json`

### Голографический

Локальное хранилище фактов SQLite с полнотекстовым поиском FTS5, оценкой доверия и HRR (голографическими сокращенными представлениями) для композиционных алгебраических запросов.

| | |
|---|---|
| **Лучший вариант** | Локальная память с расширенным извлечением, без внешних зависимостей |
| **Требуется** | Ничего (SQLite всегда доступен). NumPy необязательно для алгебры HRR. |
| **Хранение данных** | Локальный SQLite |
| **Стоимость** | Бесплатно |

**Инструменты:** `fact_store` (9 действий: добавить, найти, проверить, связать, обосновать, противоречить, обновить, удалить, составить список), `fact_feedback` (полезный/бесполезный рейтинг, который тренирует показатели доверия)

**Настройка:**
```bash
hermes memory setup    # select "holographic"
# Or manually:
hermes config set memory.provider holographic
```

**Конфигурация:** `config.yaml` под `plugins.hermes-memory-store`

| Ключ | По умолчанию | Описание |
|-----|---------|-------------|
| `db_path` | `$HERMES_HOME/memory_store.db` | Путь к базе данных SQLite |
| `auto_extract` | `false` | Автоматическое извлечение фактов в конце сеанса |
| `default_trust` | `0.5` | Оценка доверия по умолчанию (0,0–1,0) |

**Уникальные возможности:**
- `probe` — алгебраический вызов конкретной сущности (все факты о человеке/вещи)

- Оценка доверия с асимметричной обратной связью (+0,05 полезно / -0,10 бесполезно)

### Суперпамять

Семантическая долговременная память с вызовом профиля, семантическим поиском, инструментами явной памяти и приемом разговоров в конце сеанса через API графа Supermemory.

| | |
|---|---|

| **Требуется** | `pip install supermemory` + [ключ облачного API](http://app.supermemory.ai/integrations?connect=hermes) или [автономный сервер](https://supermemory.ai/docs/self-hosting/overview) |
| **Хранение данных** | Supermemory Cloud или самостоятельное размещение |
| **Стоимость** | Цены на Supermemory (облако) / бесплатно (автономное размещение) |

**Инструменты:** `supermemory_store` (сохранение явных воспоминаний), `supermemory_search` (поиск семантического сходства), `supermemory_forget` (забыть по идентификатору или запросу наилучшего соответствия), `supermemory_profile` (постоянный профиль + недавний контекст)

**Настройка:**
```bash
hermes memory setup    # select "supermemory"
# Or manually:
hermes config set memory.provider supermemory
echo 'SUPERMEMORY_API_KEY=***' >> ~/.hermes/.env
```

Самостоятельная установка:

```bash
npx supermemory local
```

Прежде чем запускать `hermes memory setup`, установите `base_url` в
`$HERMES_HOME/supermemory.json`:

```json
{
  "base_url": "http://localhost:6767"
}
```

Затем запустите `hermes memory setup` и введите ключ API, напечатанный локальным
сервер. Настройка конечной точки в первую очередь обеспечивает также настройку проверки соединения.
остается локальным.

**Конфигурация:** `$HERMES_HOME/supermemory.json`

| Ключ | По умолчанию | Описание |
|-----|---------|-------------|
| `base_url` | `https://api.supermemory.ai` | Конечная точка API для размещенной или локальной памяти Supermemory. Имеет приоритет над `SUPERMEMORY_BASE_URL`. |
| `container_tag` | `hermes` | Тег контейнера, используемый для поиска и записи. Поддерживает шаблон `{identity}` для тегов на уровне профиля. |
| `auto_recall` | `true` | Внедрить соответствующий контекст памяти перед ходом |
| `auto_capture` | `true` | Хранить очищенные повороты помощника пользователя после каждого ответа |
| `max_recall_results` | `10` | Макс вспомнил элементы для форматирования в контексте |
| `profile_frequency` | `50` | Включайте факты профиля при первом ходу и каждые N ходов |
| `capture_mode` | `all` | По умолчанию пропускать крошечные или тривиальные повороты |
| `search_mode` | `hybrid` | Режим поиска: `hybrid`, `memories` или `documents` |
| `api_timeout` | `5.0` | Тайм-аут для SDK и запросов на прием |

**Переменные среды:** `SUPERMEMORY_API_KEY` (обязательный), `SUPERMEMORY_BASE_URL` (резервный вариант совместимости, если `base_url` не настроен), `SUPERMEMORY_CONTAINER_TAG` (переопределяет конфигурацию).

Базовый приоритет URL: `supermemory.json` → `SUPERMEMORY_BASE_URL` → `https://api.supermemory.ai`. Операции SDK, проверки настройки/статуса и прием разговоров — все они используют разрешенную конечную точку.

**Основные особенности:**
- Автоматическое ограничение контекста — удаляет вызванные воспоминания из захваченных ходов, чтобы предотвратить рекурсивное загрязнение памяти.
- Захват всего сеанса — весь разговор отправляется один раз на границах сеанса.
- Захват разговоров в конце сеанса (в `/v4/conversations`) для более подробного профиля + построение графиков в Supermemory.
- Сквозная самостоятельная маршрутизация — запросы SDK, зондирования и приема разговоров используют одну и ту же настроенную конечную точку.
- Факты профиля вводятся при первом повороте и через настраиваемые промежутки времени.
- **Контейнеры на уровне профиля** — используйте `{identity}` в `container_tag` (например, `hermes-{identity}` → `hermes-coder`) для изоляции воспоминаний по профилю Hermes.
- **Режим нескольких контейнеров** — включите `enable_custom_container_tags` со списком `custom_containers`, чтобы агент мог читать/записывать в именованных контейнерах. Автоматические операции остаются в основном контейнере.

<details>
<summary>Пример нескольких контейнеров</summary>

```json
{
  "container_tag": "hermes",
  "enable_custom_container_tags": true,
  "custom_containers": ["project-alpha", "shared-knowledge"],
  "custom_container_instructions": "Use project-alpha for coding context."
}
```

</details>

## Изоляция профиля

Данные каждого провайдера изолированы для каждого [профиля](/user-guide/profiles):

- **Локальные поставщики хранилища** (Holographic, ByteRover) используют пути `$HERMES_HOME/`, которые различаются в зависимости от профиля.
- **Поставщики файлов конфигурации** (Honcho, Mem0, Hindsight, Supermemory) хранят конфигурацию в `$HERMES_HOME/`, поэтому каждый профиль имеет свои собственные учетные данные.
- **Облачные поставщики** (RetainDB) автоматически получают названия проектов на уровне профиля.
- **Поставщики переменных среды** (OpenViking) настраиваются через файл `.env` каждого профиля.
