# Руководство по Windows (WSL2)

Hermes Agent теперь поддерживает **и нативную Windows, и WSL2**. Эта страница описывает именно путь через WSL2; для нативной установки через PowerShell откройте отдельное **[руководство по нативной установке Windows](./windows-native.md)**.

**Когда стоит выбрать WSL2 вместо нативной установки:**
- вам нужна встроенная терминальная вкладка веб-панели (`/chat`) — эта панель требует POSIX PTY и доступна только в WSL2
- вы разрабатываете ПО в POSIX-среде и хотите, чтобы сессии Hermes работали в той же файловой системе и использовали те же пути, что и инструменты разработки
- у вас уже есть WSL2, и вам не хочется поддерживать ещё одну отдельную установку

**Когда нативная Windows вполне подходит (или даже лучше):**
- для интерактивного чата, шлюза (Telegram/Discord и т. п.), планировщика cron, браузерного инструмента, MCP-серверов и большинства возможностей Hermes нативная Windows тоже работает нормально
- вы не хотите при каждом обращении к файлу или открытии URL определять, используется Windows или WSL

При работе с WSL2 взаимодействуют две изолированные среды: хост Windows и виртуальная машина Linux под управлением WSL. Большинство затруднений возникает, когда пользователь не учитывает, в какой из этих сред выполняется команда.

В этом руководстве рассмотрены особенности такого взаимодействия, важные для Hermes: установка WSL2, обмен файлами между Windows и Linux, сетевое подключение в обоих направлениях и наиболее распространённые проблемы.

## Зачем WSL2, а не нативная Windows

При нативной установке Hermes работает непосредственно в Windows: использует PowerShell, Windows Terminal и другие терминалы Windows, пути вида `C:\Users\…` и процессы Windows. Для выполнения команд оболочки Hermes запускает Git Bash. Такой подход позволяет совместить POSIX-инструменты с Windows без полной переработки каждого инструмента.

WSL2 запускает полноценное Linux-ядро в лёгкой виртуальной машине, поэтому Hermes внутри него по сути ведёт себя так же, как на Ubuntu. Это ценно, когда вам нужна настоящая POSIX-среда: `fork`, `/tmp`, UNIX sockets, семантика сигналов, терминалы на базе PTY, `bash`/`zsh` и инструменты вроде `rg`, `git`, `ffmpeg`, которые работают именно так, как вы привыкли на Linux.

Практические следствия WSL2:

- CLI Hermes, шлюз, сессии, память, навыки и среды выполнения инструментов находятся внутри виртуальной машины Linux
- Приложения Windows, включая браузеры, настольные приложения и Chrome с профилем, в котором выполнен вход, работают за её пределами
- Каждый раз, когда вам нужно, чтобы они взаимодействовали — поделиться файлами, открыть URL, управлять Chrome, достучаться до локального сервера моделей, дать телефону доступ к шлюзу Hermes — вы пересекаете границу. Именно о таких границах и идёт речь в этом руководстве

## Установите WSL2

Откройте PowerShell или профиль PowerShell в Windows Terminal от имени администратора и выполните:

```powershell
wsl --install
```

В актуальной версии Windows 10 22H2 или Windows 11 эта команда устанавливает ядро WSL2, компонент Virtual Machine Platform и дистрибутив Ubuntu по умолчанию. После установки перезагрузите компьютер. Затем Ubuntu запросит имя пользователя и пароль для Linux. Это **новая учётная запись Linux**, не связанная с учётной записью Windows.

Проверьте, что у вас именно WSL2, а не устаревший WSL1:

```powershell
wsl --list --verbose
```

В списке должна отображаться `VERSION  2`. Если для какого-либо дистрибутива указана `VERSION  1`, преобразуйте его в WSL2:

```powershell
wsl --set-version Ubuntu 2
wsl --set-default-version 2
```

Hermes не работает надёжно на WSL1 — там системные вызовы Linux транслируются на лету, и часть поведения (procfs, сигналы, сеть) заметно отличается от настоящего Linux.

### Выбор дистрибутива

Ubuntu LTS — та версия, на которой мы тестируем. Debian тоже подходит. Arch и NixOS работают у тех, кому они нужны, но однострочный установщик предполагает Debian-подобный `apt` — для установки через Nix см. [руководство по настройке Nix](/getting-started/nix-setup).

### Включите systemd (рекомендуется)

Шлюз Hermes и любые долгоживущие процессы удобнее запускать под systemd. В современных сборках WSL включите его один раз внутри дистрибутива:

```bash
sudo tee /etc/wsl.conf >/dev/null <<'EOF'
[boot]
systemd=true

[interop]
enabled=true
appendWindowsPath=true

[automount]
options = "metadata,umask=22,fmask=11"
EOF
```

Затем из PowerShell:

```powershell
wsl --shutdown
```

Снова откройте терминал WSL. Команда `ps -p 1 -o comm=` должна показать `systemd`.

Опция `metadata` выше важна: без неё файлы на `/mnt/c/...` не могут хранить настоящие биты прав доступа Linux, и из-за этого ломаются вещи вроде `chmod +x` для скриптов на путях Windows.

### Установите Hermes внутри WSL

Как только у вас открыта оболочка WSL2:

```bash
curl -fsSL https://hermes-agent.nousresearch.com/install.sh | bash
source ~/.bashrc
hermes
```

Установщик воспринимает WSL2 как обычный Linux — ничего специфичного для WSL делать не нужно. Полная схема установки описана в [Установке](/getting-started/installation).

## Файловая система: как пересекать границу Windows ↔ WSL2

Вот здесь чаще всего и случается путаница. У вас есть **две файловые системы**, и то, куда вы положите файлы, влияет на производительность, корректность и на то, какие инструменты вообще их увидят.

### Два направления

| Направление | Вид изнутри | Что использовать |
|---|---|---|
| Диск Windows, видимый из WSL | `C:\Users\you\Documents` | `/mnt/c/Users/you/Documents` |
| Диск WSL, видимый из Windows | `/home/you/code` | `\\wsl$\Ubuntu\home\you\code` (или `\\wsl.localhost\Ubuntu\...` на новых сборках) |

Оба варианта реальны и рабочие, но это **не одна и та же файловая система** — под капотом их связывает сетевой протокол 9P. У этого есть серьёзные последствия по скорости и семантике.

### Где хранить Hermes и проекты

**Практическое правило: всё Linux-подобное держите внутри файловой системы Linux.**

- Установка Hermes (`~/.hermes/`) — на стороне Linux. Установщик уже делает именно так.
- Git-репозитории, с которыми вы работаете из WSL, — на стороне Linux (`~/code/...`, `~/projects/...`).
- Модели, датасеты, venv — тоже на стороне Linux.

Что вы выигрываете, если следуете этому правилу:

- **Быстрый I/O.** Операции над `/mnt/c/...` идут через 9P и могут быть в 10–100 раз медленнее, чем на нативном ext4. `git status` на репозитории с 10k файлов, который под `~/code` кажется мгновенным, под `/mnt/c` легко превращается в 15+ секунд.
- **Корректные права.** Права доступа Linux на `/mnt/c` эмулируются приблизительно. Проблемы вроде `bad permissions` у SSH-ключа или незаметно не сработавшего `chmod +x` встречаются постоянно.
- **Надёжные наблюдатели за файлами.** inotify через 9P работает нестабильно — серверы разработки и тест-раннеры часто пропускают изменения на `/mnt/c`.
- **Без сюрпризов с чувствительностью к регистру.** Windows-пути обычно не чувствительны к регистру; Linux — чувствителен. Проекты с `Readme.md` и `README.md` ведут себя по-разному в зависимости от стороны.

Храните файлы в `/mnt/c` только тогда, когда к ним требуется прямой доступ из Windows, например для открытия в графическом приложении или запуска Chrome DevTools MCP с текущим каталогом, доступным Windows.

### Как переносить файлы туда и обратно

**Из Windows в WSL:** проще всего открыть Explorer и ввести `\\wsl.localhost\Ubuntu` в адресную строку. Дальше можно перетаскивать файлы в `\home\<you>\...`. Или из PowerShell:

```powershell
wsl cp /mnt/c/Users/you/Downloads/file.pdf ~/incoming/
```

**Из WSL в Windows:** скопируйте файл в `/mnt/c/Users/<you>/...`, и он сразу появится в Windows Explorer:

```bash
cp ~/reports/output.pdf /mnt/c/Users/you/Desktop/
```

**Открыть файл из WSL в Windows-приложении** (графический редактор, браузер и т. п.): используйте `explorer.exe` или `wslview`:

```bash
sudo apt install wslu     # once — gives you wslview, wslpath, wslopen, etc.
wslview ~/reports/output.pdf    # opens with the Windows default handler
explorer.exe .                  # opens the current WSL dir in Windows Explorer
```

**Конвертировать пути между двумя мирами:**

```bash
wslpath -w ~/code/project        # → \\wsl.localhost\Ubuntu\home\you\code\project
wslpath -u 'C:\Users\you'        # → /mnt/c/Users/you
```

### Переносы строк, BOM и git

Если вы редактируете файлы на стороне Windows в Windows-редакторе, они могут получить `CRLF`-переносы строк. Когда `bash` или Python на стороне Linux читает такие файлы, скрипты оболочки ломаются с `bad interpreter: /bin/bash^M`, а Python может споткнуться о `.env` с BOM.

Чтобы избежать этих проблем, настройте Git внутри WSL, а не в Windows:

```bash
git config --global core.autocrlf input
git config --global core.eol lf
```

Если файлы уже с CRLF:

```bash
sudo apt install dos2unix
dos2unix path/to/script.sh
```

### Что лучше: клонировать внутри WSL или на `/mnt/c`?

Клонируйте репозиторий внутри WSL, если только у вас нет конкретной причины поступить иначе. Обычный рабочий процесс Hermes, включая `hermes chat`, поиск по репозиторию через `rg`, наблюдение за файлами и работу фонового шлюза, будет значительно быстрее и надёжнее в `~/code/myrepo`, чем в `/mnt/c/Users/you/myrepo`.

Единственное исключение — **MCP-мосты, которые запускают исполняемые файлы Windows**. Если вы используете `chrome-devtools-mcp` через `cmd.exe` (см. [руководство MCP: WSL → Windows Chrome](/guides/use-mcp-with-hermes#wsl2-bridge-hermes-in-wsl-to-windows-chrome)), Windows может выдать предупреждение `UNC`, если текущая директория Hermes находится в `~`. В этом случае запускайте Hermes из `/mnt/c/`, чтобы Windows-процесс видел текущий каталог с буквой диска.

## Сеть: WSL ↔ Windows

WSL2 работает в компактной виртуальной машине с собственным сетевым стеком. Поэтому `localhost` внутри WSL — **не то же самое**, что `localhost` в Windows. Для каждого сервиса необходимо определить направление трафика и выбрать подходящий способ подключения.

Чаще всего встречаются два сценария.

### Сценарий 1: Hermes в WSL подключается к службе в Windows

Самый частый случай: у вас на Windows запущен **Ollama, LM Studio или llama-server**, а Hermes внутри WSL должен к нему обращаться.

Подробная инструкция находится в руководстве по провайдерам: **[Сеть WSL2 для локальных моделей →](/integrations/providers#wsl2-networking-windows-users)**

Коротко:

- **Windows 11 22H2+**: включите зеркальный режим сети (`networkingMode=mirrored` в `%USERPROFILE%\.wslconfig`, затем выполните `wsl --shutdown`). После этого `localhost` работает в обоих направлениях.
- **Windows 10 и более старые сборки**: используйте IP хоста Windows (шлюз по умолчанию в виртуальной сети WSL) и убедитесь, что сервер на Windows слушает `0.0.0.0`, а не только `127.0.0.1`. Обычно ещё нужно правило брандмауэра на порт.

По ссылке выше приведена подробная таблица с адресами привязки для Ollama, LM Studio, vLLM и SGLang, командами настройки брандмауэра, средствами работы с динамическим IP-адресом и обходным решением для брандмауэра Hyper-V. Здесь эти сведения не дублируются.

### Сценарий 2: приложение в Windows или локальной сети подключается к Hermes в WSL

Это обратное направление, и про него обычно говорят меньше, но оно нужно для:

- использования веб-панели Hermes из браузера Windows;
- использования **API-сервера, совместимого с OpenAI** (который предоставляет `hermes gateway`, если `API_SERVER_ENABLED=true`) из инструмента на стороне Windows. См. [страницу API Server](/user-guide/features/api-server);
- тестирования **шлюза сообщений** (Telegram, Discord и т. п.), когда платформа отправляет запросы на локальный URL вебхука. В этом случае обычно лучше использовать туннель `cloudflared` или `ngrok`, а не настраивать прямой проброс портов.

#### Подсценарий 2a: на самом хосте Windows

В **Windows 11 22H2+ с включённым зеркальным режимом** дополнительная настройка не требуется. Процесс WSL, который прослушивает `0.0.0.0:8080` или `127.0.0.1:8080`, доступен из браузера Windows по адресу `http://localhost:8080`. WSL автоматически перенаправляет подключение на хост.

В **режиме NAT** (Windows 10 и ранние версии Windows 11) стандартное перенаправление localhost в WSL2 обычно связывает Linux-адрес `127.0.0.1` с `localhost` в Windows. Поэтому служба Hermes, запущенная с `--host 127.0.0.1`, обычно доступна в Windows по адресу `http://localhost:PORT`. Если подключиться не удаётся:

- явно привяжитесь к `0.0.0.0` внутри WSL;
- узнайте IP WSL VM через `ip -4 addr show eth0 | grep inet` и обращайтесь к нему из Windows.

#### Подсценарий 2b: с другого устройства в вашей локальной сети (телефон, планшет, другой ПК)

Это наиболее сложный сценарий. Трафик проходит по цепочке **устройство в локальной сети → хост Windows → виртуальная машина WSL**, поэтому необходимо настроить оба перехода:

1. **Привяжитесь ко всем интерфейсам внутри WSL.** Процесс, слушающий `127.0.0.1`, никогда не будет доступен снаружи VM. Используйте `0.0.0.0`.

2. **Настройте проброс порта Windows → виртуальная машина WSL.** В зеркальном режиме это происходит автоматически. В режиме NAT каждый порт необходимо настроить вручную в PowerShell от имени администратора:

   ```powershell
   # Получите текущий IP WSL VM (он меняется при каждом перезапуске WSL в NAT-режиме)
   $wslIp = (wsl hostname -I).Trim().Split(' ')[0]

   # Пробросьте порт Windows 8080 → WSL:8080
   netsh interface portproxy add v4tov4 `
     listenaddress=0.0.0.0 listenport=8080 `
     connectaddress=$wslIp connectport=8080

   # Разрешите его в брандмауэре Windows
   New-NetFirewallRule -DisplayName "Hermes WSL 8080" `
     -Direction Inbound -Protocol TCP -LocalPort 8080 -Action Allow
   ```

   Удалить правило потом можно так: `netsh interface portproxy delete v4tov4 listenaddress=0.0.0.0 listenport=8080`.

3. **На устройстве в локальной сети откройте `http://<windows-lan-ip>:8080`.**

Поскольку IP-адрес виртуальной машины WSL в режиме NAT меняется после каждого `wsl --shutdown`, однократно созданное правило действует только до следующего перезапуска WSL. Для постоянной настройки используйте зеркальный режим или перенесите команду `portproxy` в скрипт, запускаемый при входе в Windows.

Для вебхуков облачных платформ обмена сообщениями, включая Telegram `setWebhook` и события Slack, не настраивайте проброс портов вручную. Используйте туннель `cloudflared` или `ngrok`. См. [руководство по вебхукам](/user-guide/messaging/webhooks).

## Как обеспечить постоянную работу служб Hermes в Windows

[Шлюз инструментов](/user-guide/features/tool-gateway) Hermes и API-сервер должны работать постоянно. В WSL2 это можно настроить несколькими способами.

### Ярлык на рабочем столе для быстрого запуска Hermes

Чтобы запускать интерактивную оболочку Hermes двойным щелчком, создайте в Windows ярлык, который сразу открывает Hermes в WSL:

1. Щёлкните правой кнопкой мыши по рабочему столу Windows и выберите **Создать > Ярлык**.
2. В поле «Объект» укажите имя вашего дистрибутива (замените `Ubuntu`, если нужно):

   ```text
   wt.exe -w 0 -p "Ubuntu" wsl.exe -d Ubuntu --cd ~ -- bash -ic "hermes"
   ```

3. Назовите ярлык понятно, например `Hermes`.

Ярлык откроет Windows Terminal, запустит выбранный дистрибутив WSL, перейдёт в домашний каталог Linux и запустит Hermes. Если команда `hermes` ещё недоступна через `PATH`, один раз откройте WSL вручную и выполните `source ~/.bashrc` либо замените команду на `uv run hermes` внутри рабочей копии репозитория.

Дополнительная настройка:

- **Собственный значок:** откройте **Свойства > Сменить значок** и укажите файл `.ico`, например значок Hermes из репозитория.
- **Закрепление:** когда ярлык заработает, закрепите его в меню «Пуск» или на панели задач, чтобы не искать его снова.

### Внутри WSL с systemd (рекомендуется)

Если вы включили systemd по инструкции выше, `hermes gateway` и API-сервер работают так же, как на любом Linux. Используйте мастер настройки шлюза:

```bash
hermes gateway setup
```

Он предложит установить пользовательский systemd-юнит, чтобы шлюз стартовал автоматически вместе с WSL.

### Чтобы сам WSL запускался при входе в Windows

Виртуальная машина WSL работает только при наличии активных процессов. Чтобы шлюз оставался доступным без открытого окна терминала, настройте запуск процесса WSL при входе в Windows через Планировщик заданий:

- **Триггер:** при входе в систему (ваш пользователь)
- **Действие:** Запустить программу
  - Программа: `C:\Windows\System32\wsl.exe`
  - Аргументы: `-d Ubuntu --exec /bin/sh -c "sleep infinity"`

Такой процесс не позволит виртуальной машине завершить работу, поэтому шлюз под управлением systemd останется доступным. В Windows 11 поддерживаются и более новые способы автоматического запуска WSL, но `sleep infinity` остаётся наиболее переносимым вариантом.

## Прямой доступ к GPU (локальные модели)

WSL2 поддерживает прямой доступ к GPU NVIDIA начиная с версии ядра WSL 5.10.43. Установите обычный драйвер NVIDIA в Windows. Драйвер NVIDIA для Linux внутри WSL устанавливать не нужно. После этого `nvidia-smi` внутри WSL обнаружит GPU, а CUDA, `torch`, `vllm`, `sglang` и `llama-server` смогут использовать его напрямую.

Поддержка AMD ROCm и Intel Arc в WSL2 продолжает развиваться и не входит в тестовую матрицу Hermes. Она может работать с актуальными драйверами, но пока мы не можем рекомендовать проверенную конфигурацию.

Если вы запускаете **сервер локальной модели нативно в Windows** (Ollama for Windows, LM Studio), и он уже использует GPU через драйвер Windows, прямой доступ к GPU через WSL вам не нужен вовсе — просто следуйте Сценарию 1 и обращайтесь к нему по сети из WSL.

## Типовые проблемы

**Ошибка `Connection refused` при подключении к Ollama или LM Studio, запущенным в Windows.**
См. [раздел о сети WSL2](/integrations/providers#wsl2-networking-windows-users). Обычно сервер принимает подключения только на `127.0.0.1`; настройте прослушивание на `0.0.0.0` (для Ollama: `OLLAMA_HOST=0.0.0.0`) и проверьте наличие правила брандмауэра.

**Команды `git status` и `hermes chat` выполняются очень медленно.**
Скорее всего, проект лежит под `/mnt/c/...`. Перенесите его в `~/code/...` (на стороне Linux). Разница по скорости обычно на порядок.

**`bad interpreter: /bin/bash^M` у скриптов.**
Причина в переносах строк CRLF, добавленных редактором Windows. Выполните `dos2unix script.sh` и задайте `core.autocrlf input` в конфигурации Git внутри WSL.

**Предупреждение "UNC paths are not supported" от исполняемых файлов Windows, запущенных через MCP.**
Текущий каталог Hermes находится внутри файловой системы Linux, а `cmd.exe` на Windows не знает, что с ним делать. Запускайте Hermes из `/mnt/c/...` в этой сессии либо используйте обёртку, которая перед вызовом исполняемого файла Windows делает `cd` в путь, доступный Windows.

**После сна или гибернации системные часы отстают.**
Часы WSL2 могут отставать на несколько минут после пробуждения хоста, что нарушает работу сертификатов и OAuth. Синхронизируйте часы командой:

```bash
sudo hwclock -s
```

Или установите `ntpdate` и запускайте его при входе в систему.

**После включения зеркального режима или подключения к VPN перестаёт работать DNS.**
В зеркальном режиме WSL использует сетевые настройки хоста. Если разрешение DNS-имён в Windows нарушено из-за раздельного туннелирования VPN или корпоративного DNS-сервера, проблема возникает и в WSL. В качестве обходного решения отключите автоматическое создание `resolv.conf`: задайте `generateResolvConf=false` в `/etc/wsl.conf`, а затем укажите нужные DNS-серверы в `/etc/resolv.conf`.

**`hermes` не найден после установки.**
Установщик добавляет `~/.local/bin` в PATH через `~/.bashrc`. Чтобы это заработало в текущей сессии, выполните `source ~/.bashrc` (или откройте новый терминал).

**Windows Defender тормозит WSL-файлы.**
Defender сканирует файлы через мост 9P при обращении из Windows, из-за чего работа с `/mnt/c` замедляется ещё сильнее. Если вы работаете с файлами WSL только внутри WSL, это несущественно. Если вы часто открываете `\\wsl$\...` средствами Windows, рассмотрите возможность исключить путь дистрибутива WSL из сканирования в реальном времени.

**Заканчивается диск.**
WSL2 хранит диск виртуальной машины в виде разреженного VHDX-файла в `%LOCALAPPDATA%\Packages\...`. Файл увеличивается по мере использования, но не уменьшается автоматически после удаления данных. Чтобы освободить место, выполните `wsl --shutdown`, а затем в PowerShell от имени администратора запустите `Optimize-VHD -Path <path-to-ext4.vhdx> -Mode Full` (требуются средства управления Hyper-V) либо воспользуйтесь более простым способом через `diskpart`, описанным в документации WSL.
