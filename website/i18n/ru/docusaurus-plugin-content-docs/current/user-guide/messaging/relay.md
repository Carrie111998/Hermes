# Реле Гермеса (разъем)

:::предупреждение Экспериментальное
Реле **экспериментальное**. Контракт проводной связи, схема аутентификации и конфигурация
могут измениться без цикла устаревания во время проверки системы.
:::

Hermes Relay — это не чат-платформа, а **система соединений**, которая
позволяет вашему шлюзу работать с одной или несколькими реальными платформами обмена сообщениями (Discord,
Telegram, Slack, WhatsApp, …) **без каких-либо учетных данных платформы**. А
отдельный сервис, *коннектор*, владеет токенами и сокетами платформенного бота.
Ваш шлюз осуществляет соединение **out** с соединителем через один аутентифицированный
WebSocket получает дескриптор возможностей при рукопожатии, а затем обменивается
нормализованные события сообщений (входящие) и действия (исходящие) через этот сокет.

Ключевые свойства:

- **Сеть только для исходящего трафика.** Шлюз никогда не открывает входящий порт.
  Входящие сообщения отправляются обратно по тому же WebSocket, который набрал шлюз, поэтому
  реле работает за NAT и на хостах без общедоступного IP-адреса.
- **На шлюзе нет секретов платформы.** Токены бота находятся на соединителе.
  URL-адреса мультимедиа платформы с аутентификацией повторно размещаются на стороне коннектора, поэтому платформа
  учетные данные никогда не пересекают провод.
- **Независимость от платформы.** Шлюз узнает, что может делать фронтальная платформа.
  (ограничения на длину сообщений, диалект уценки, поддержка редактирования/потоков/потоковой передачи и
  точный набор поддерживаемых операций) из дескриптора рукопожатия, а не
  из жестко запрограммированной логики платформы.

Формальный интерфейс шлюза ⇄ находится в репозитории по адресу
`docs/relay-connector-contract.md`.

## Когда использовать реле

Ретрансляция предназначена для развертываний, в которых служба размещенного или общего соединителя управляет
сторона платформы — например, мультитенантный хостинг, где один общий бот
защищает агенты многих пользователей или настройки, в которых вам не нужны токены ботов на
шлюзовая машина. Если вы запускаете собственных ботов напрямую, используйте собственную платформу.
адаптеры ([Telegram](/user-guide/messaging/telegram),
Вместо этого [Discord](/user-guide/messaging/discord) и т. д.

## Регистрация

Самостоятельный шлюз проверяет подлинность соединителя с помощью каждого шлюза.
секрет. `hermes gateway enroll` активирует **одноразовый токен регистрации**
(создается соединителем, когда маршрут вашего клиента подготовлен и доставлен
с конфигурацией вашего шлюза) для этого секрета:

```bash
hermes gateway enroll \
  --token <enrollment-token> \
  --connector-url wss://connector.example.com/relay
```

Что он делает:

1. Разрешает новый токен доступа к Nous Portal из вашего существующего входа в систему.
   (`~/.hermes/auth.json`) — это доказывает, какой Nous org (клиентом) вы владеете. Если
   `gateway.idp.token_url` настроен, вместо него используется собственный IdP (
   путь с воздушным зазором/автономный IdP, Nous Portal не задействован): с
   `client_id`/`client_secret` настроен на выполнение общего протокола OAuth2.
   предоставление клиентских учетных данных; если ни один из них не настроен, URL-адрес рассматривается как
   конечная точка окружающего токена (обычный GET, телом ответа которого является токен —
   шаблон сервера метаданных, например. Домино'с `$DOMINO_API_PROXY/access-token`).
   Настройка только одного из двух учетных данных является ошибкой.
2. Отправляет токен регистрации и идентификатор шлюза на разъем соединителя.
   Конечная точка `/relay/enroll` через TLS.
3. Коннектор проверяет токен (подпись, одноразовое использование, соответствие арендатора),
   создает секрет для каждого шлюза плюс ключ доставки для каждого арендатора и возвращает их
   один раз.
4. Сохраняет учетные данные в `~/.hermes/.env`:
   `GATEWAY_RELAY_ID`, `GATEWAY_RELAY_SECRET`, `GATEWAY_RELAY_DELIVERY_KEY`
   (плюс `GATEWAY_RELAY_URL` / `GATEWAY_RELAY_WAKE_URL` при наличии).

После этого перезапустите шлюз, чтобы загрузить новую среду.

Флаги:

| Флаг | Описание |
|------|-------------|
| `--token` | Одноразовый токен регистрации. Также настраивается через `GATEWAY_RELAY_ENROLL_TOKEN`. |
| `--connector-url` | Базовый URL-адрес соединителя или реле (`wss://…/relay` или `https://…`). Также можно установить через `GATEWAY_RELAY_URL` или `gateway.relay_url` в `config.yaml`. |
| `--gateway-id` | Стабильный идентификатор для этого экземпляра шлюза (используется для детализации аварийного отключения). По умолчанию `gw-<hostname>`. |
| `--wake-url` | Необязательный доступный URL-адрес, который использует соединитель (GET без полезной нагрузки), чтобы разбудить этот шлюз, когда буферизованная работа поступает, пока он простаивает. Сохранился как `GATEWAY_RELAY_WAKE_URL`. Без него шлюз по-прежнему будет истощать буферизованные сообщения при каждом следующем повторном подключении. |

:::note Управляемые установки
`hermes gateway enroll` отказывается запускаться в управляемых/хостовых установках — там
хостинговая платформа предоставляет секрет ретрансляции непосредственно в контейнер
окружающая среда.
:::

## Конфигурация

Реле активируется, когда настроен URL-адрес ретранслятора соединителя — нет
отдельный флаг функции. Развертывания, в которых он не установлен, не затрагиваются.

| Настройка | Где | Значение |
|---------|-------|---------|
| `GATEWAY_RELAY_URL` | окружение (`~/.hermes/.env`) | URL-адрес WebSocket ретранслятора соединителя. Присутствие включает ретрансляционную платформу. |
| `gateway.relay_url` | `config.yaml` | То же, что и выше, форма файла конфигурации (env имеет приоритет). |
| `GATEWAY_RELAY_ID` | окружение | Идентификатор этого экземпляра шлюза (написан `enroll`). |
| `GATEWAY_RELAY_SECRET` | окружение | Секрет каждого шлюза, проверяющий подлинность обновления WebSocket (написан `enroll`). |
| `GATEWAY_RELAY_DELIVERY_KEY` | окружение | Ключ доставки для каждого клиента (написан `enroll`; сохранен для прямой совместимости). |
| `GATEWAY_RELAY_WAKE_URL` / `gateway.relay_wake_url` | окр./`config.yaml` | Дополнительная цель пробуждения для простаивающих/приостановленных шлюзов. |
| `GATEWAY_RELAY_PLATFORMS` | окружение | Список платформ, разделенных запятыми, с которыми этот шлюз работает через одно соединение (например, `discord,telegram`). Обычно отмечается развертыванием/оркестратором. |
| `GATEWAY_RELAY_BOT_IDS` | окружение | JSON-карта идентификаторов ботов для каждой платформы, например. `{"discord": {"botId": "…"}}`. В паре с `GATEWAY_RELAY_PLATFORMS`. |
| `gateway.idp.token_url` | `config.yaml` | Если этот параметр установлен, регистрация/подготовка аутентифицируется по вашему собственному IdP вместо Nous Portal: учетные данные клиента OAuth2, если также установлены `gateway.idp.client_id`/`client_secret`; в противном случае конечная точка окружающего токена (обычный GET, возвращающий токен, необработанный или `{"access_token": …}`). |

## Поддерживаемые возможности

То, что на самом деле работает через релейное соединение, согласовывается при рукопожатии:
соединитель объявляет список `supported_ops`, а шлюз использует только
операцию, которую явно объявляет соединитель (более старые соединители возвращаются к
устаревший набор `send`/`edit`/`typing`/`follow_up`). Флаги возможностей каждой платформы
(потоковая передача на основе редактирования, потоки, черновая потоковая передача, диалект уценки, сообщение
предел длины) также берутся из дескриптора рукопожатия. При условии этого
переговоры, реле поддерживает:

- **Текстовые сообщения и потоковая передача** — отправки, ответы и прогрессивный режим.
  потоковая передача на основе редактирования, когда фронтальная платформа поддерживает редактирование сообщений;
  в противном случае выходные данные уменьшаются до одного сообщения на сегмент.
- **Медиа в обоих направлениях** — исходящие изображения, голос, аудио, видео и
  документы загружаются в соединитель (или на них ссылается общедоступный URL-адрес) и
  доставляется через собственную полосу загрузки каждой платформы с подписями.
  Входящие вложения локализуются в файлах агента; авторизованный
  URL-адреса платформы повторно размещаются на стороне соединителя, поэтому учетные данные платформы никогда не
  дойти до шлюза. Размер повторного хостинга мультимедиа ограничен 25 МБ и истекает (~ 1 час).
- **Встроенные интерактивные подсказки** – одобрения, подтверждения и пояснения.
  вопросы отображаются с помощью **собственных элементов управления платформы** (кнопки Discord,
  Встроенные клавиатуры Telegram, действия Slack Block Kit, кнопка/список WhatsApp
  сообщения) вместо резервных номеров с нумерованным текстом. Нажатия кнопок возвращаются как
  аутентифицированные быстрые ответы от фактического пользователя, щелкающего мышью, поэтому
  Шлюзы авторизации шлюза применяются точно так же, как и к напечатанному ответу. Подскажите
  срок действия принудительно устанавливается на стороне шлюза.
- **Reaction ack lifecycle** — реакции бота на статус обработки.
  (👀по ходу работы, ✅/❌по завершению) работа над эстафетой. Реакции
  максимальные усилия: неудачная реакция никогда не приводит к неудаче.
- **Жизненный цикл потока** — создание потоков передачи и переименование потоков.
  (включая семантические переименования под названием LLM) посредством абстрактной платформы
  `thread_create` / `thread_rename` операций с защитой, не допускающей затирания, поэтому
  Ручное переименование человека побеждает. Доступность зависит от платформы (например.
  Slack-потоки нельзя переименовывать; В WhatsApp нет тем).
- **Индикаторы ввода** — шлюз завершает ввод (и прекращение ввода) через
  разъем во время обработки.
- **Метаданные чата** — запросы `get_chat_info` передаются через прокси на коннектор.
  когда рекламируется.
- **Буферизованная доставка и пробуждение** — когда шлюз простаивает или отключается,
  коннектор надежно буферизует входящие сообщения и воспроизводит их по порядку
  повторное подключение (подтверждение, без потерь и дублирования). Если URL-адрес пробуждения зарегистрирован,
  коннектор тыкает его, когда на спящий шлюз поступает буферизованная работа.

Поддерживается многоплатформенное взаимодействие: один шлюз может работать с несколькими платформами.
(например, Discord *и* Telegram) через одно ретрансляционное соединение, причем каждый
исходящее сообщение, помеченное для целевой платформы.

## Устранение неполадок

**При регистрации произошла ошибка 401** — коннектору не удалось подтвердить вашу личность.
жетон. Повторно войдите в систему с помощью `hermes auth add nous` (или `hermes setup`) и повторите попытку.

**Ошибка регистрации: 403** — токен регистрации недействителен, срок его действия истек,
уже используется или принадлежит другому арендатору. Токены регистрации
одноразовый; запросите новый у того, кто предоставил ваш маршрут клиента.

**"Не удалось связаться с соединителем"** — проверьте URL-адрес соединителя. Вы можете вставить
либо URL-адрес набора `wss://…/relay`, либо базовый URL-адрес `https://…`; карты CLI
между ними автоматически.

**`enroll` отказывается запускаться** — вы используете управляемую/хостинговую установку, где
Секрет ретрансляции предоставляется хостинговой платформой. Самостоятельная регистрация возможна только
для самостоятельных шлюзов.

**Платформа ретрансляции отображается как отключенная после того, как она ранее работала** — WebSocket
закрытие с кодом 4401 *после* успешного рукопожатия означает секрет шлюза
был отозван (например, экземпляр был деинициализирован). Шлюз намеренно
прекращает повторное подключение и сообщает о том, что реле отключено, вместо того, чтобы повторять попытку. А 4401
*до* любое успешное рукопожатие рассматривается как временное
еще не предоставленная гонка и повторил попытку в обычном режиме.

**После регистрации ничего не изменилось** — на шлюзе отображается `GATEWAY_RELAY_*`
запуск. Перезапустите его (`hermes gateway restart`).

**Функция (кнопки, мультимедиа, потоки…) автоматически деградирует до обычного текста** —
коннектор для вашей платформы не объявил эту операцию в своем рукопожатии
`supported_ops`. Шлюз намеренно возвращается к текстовому поведению.
вместо отправки операции, которую соединитель не может обработать.
