# Вебхуки

Получайте события от внешних сервисов (GitHub, GitLab, JIRA, Stripe и т. д.) и автоматически запускайте триггерный агент Hermes. Адаптер веб-перехватчика запускает HTTP-сервер, который принимает запросы POST, проверяет подписи HMAC, преобразует полезные данные в запросы агента и направляет ответы обратно к источнику или на другую настроенную платформу.

Агент обрабатывает событие и может отреагировать, публикуя комментарии к PR, отправляя сообщения в Telegram/Discord или записывая результат.

## Быстрый старт

1. Включите через `hermes gateway setup` или переменные среды.
2. Определите маршруты в `config.yaml` **или** создайте их динамически с помощью `hermes webhook subscribe`.
3. Направьте свою услугу на `http://your-server:8644/webhooks/<route-name>`.

## Настройка

Есть два способа включить адаптер веб-перехватчика.

### Через мастер настройки

```bash
hermes gateway setup
```

Следуйте инструкциям, чтобы включить веб-перехватчики, установить порт и глобальный секрет HMAC.

### Через переменные среды

Добавьте в `~/.hermes/.env`:

```bash
WEBHOOK_ENABLED=true
WEBHOOK_PORT=8644        # default
WEBHOOK_SECRET=your-global-secret
```

### Проверьте сервер

Как только шлюз заработает:

```bash
curl http://localhost:8644/health
```

Ожидаемый ответ:

```json
{"status": "ok", "platform": "webhook"}
```

## Настройка маршрутов {#configuring-routes}

Маршруты определяют, как обрабатываются различные источники веб-перехватчиков. Каждый маршрут представляет собой именованную запись под `platforms.webhook.extra.routes` в вашем `config.yaml`.

### Свойства маршрута

| Недвижимость | Требуется | Описание |
|----------|----------|-------------|
| `events` | Нет | Список типов событий, которые можно принять (например, `["pull_request"]`). Если пусто, принимаются все события. Тип события считывается из `X-GitHub-Event`, `X-GitLab-Event` или `event_type` в полезных данных. |
| `secret` | **Да** | Секрет HMAC для проверки подписи. Возвращается к глобальному `secret`, если он не установлен на маршруте. Установите значение `"INSECURE_NO_AUTH"` только для тестирования (пропускает проверку). |
| `profile` | Нет | Профилю разрешено выполнять этот маршрут, если `gateway.multiplex_profiles` включен. Опустите его для маршрута только для профиля по умолчанию; задайте имя профиля (например, `coder`), чтобы привязать маршрут и его секрет к `/p/coder/webhooks/<route>`. |
| `prompt` | Нет | Строка шаблона с доступом к полезной нагрузке в виде точечной записи (например, `{pull_request.title}`). Если этот параметр опущен, в командную строку выгружается вся полезная нагрузка JSON. Поля полезных данных не являются доверенными — см. [Аутентифицированный не означает доверенный](#authenticated-does-not-mean-trusted). |
| `filters` | Нет | Декларативные фильтры полезной нагрузки оцениваются после фильтрации аутентификации/тела/событий и перед работой агента или прямой доставки. При отсутствии совпадений возвращается `{"status":"ignored","reason":"filter"}` с HTTP 200. |
| `script` | Нет | Сценарий фильтрации/преобразования под `~/.hermes/scripts/`. Полезная нагрузка веб-перехватчика передается в формате JSON на стандартный ввод. Стандартный вывод объекта JSON заменяет полезную нагрузку перед созданием шаблона; текстовый стандартный вывод отображается как `script_output`; пустой стандартный вывод, `[SILENT]` или ненулевой код выхода игнорируют веб-перехватчик. |
| `skills` | Нет | Список названий навыков, которые нужно загрузить для запуска агента. |
| `toolsets` | Нет | Список ключей набора инструментов (например, `["terminal", "file", "web"]`), которые **заменяют** набор инструментов веб-перехватчика на уровне платформы для запусков, инициируемых только этим маршрутом. Только редактирование конфигурации вручную — невозможно настроить через `hermes webhook subscribe`, поэтому подписки, созданные агентом, не могут самостоятельно предоставлять инструменты с повышенными правами. Имена проверяются так же, как и записи `platform_toolsets` (неизвестные имена или имена, ограниченные платформой, удаляются). См. [Наборы инструментов для каждого маршрута](#per-route-toolsets). |
| `deliver` | Нет | Куда отправить ответ: `github_comment`, `telegram`, `discord`, `slack`, `signal`, `sms`, `whatsapp`, `matrix`, `mattermost`, `homeassistant`, `email`, `dingtalk`, `feishu`, `wecom`, `weixin`, `bluebubbles`, `qqbot` или `log` (по умолчанию). |
| `deliver_extra` | Нет | Дополнительная конфигурация доставки — ключи зависят от типа `deliver` (например, `repo`, `pr_number`, `chat_id`). Значения поддерживают те же шаблоны `{dot.notation}`, что и `prompt`. |
| `deliver_only` | Нет | Если `true`, полностью пропустите агента — визуализированный шаблон `prompt` станет буквальным сообщением, которое будет доставлено. Нулевая стоимость LLM, доставка за доли секунды. Варианты использования см. в разделе [Режим прямой доставки](#direct-delivery-mode). Требуется, чтобы `deliver` был реальной целью (а не `log`). |

### Полный пример

```yaml
platforms:
  webhook:
    enabled: true
    extra:
      port: 8644
      secret: "global-fallback-secret"
      routes:
        github-pr:
          events: ["pull_request"]
          secret: "github-webhook-secret"
          prompt: |
            Review this pull request:
            Repository: {repository.full_name}
            PR #{number}: {pull_request.title}
            Author: {pull_request.user.login}
            URL: {pull_request.html_url}
            Diff URL: {pull_request.diff_url}
            Action: {action}
          skills: ["github-code-review"]
          deliver: "github_comment"
          deliver_extra:
            repo: "{repository.full_name}"
            pr_number: "{number}"
        deploy-notify:
          events: ["push"]
          secret: "deploy-secret"
          prompt: "New push to {repository.full_name} branch {ref}: {head_commit.message}"
          filters:
            - field: "ref"
              equals: "refs/heads/main"
          deliver: "telegram"
```

### Фильтры полезной нагрузки

Используйте `filters`, когда поставщик отправляет широкий поток событий, но только некоторые полезные данные должны разбудить агента или инициировать доставку `deliver_only`. Фильтры запускаются после проверки подписи, анализа тела и `events`, но перед отрисовкой подсказки, идемпотентностью, отправкой агента или прямой доставкой.

```yaml
platforms:
  webhook:
    extra:
      routes:
        todoist:
          events: ["item:updated"]
          secret: "todoist-secret"
          filters:
            - field: "payload.labels"
              contains: "hermes"
            - any:
                - field: "payload.priority"
                  equals: 4
                - field: "payload.project_id"
                  in_file: "~/.hermes/data/todoist/watchlist.json"
          prompt: "Todoist task changed: {payload.content}"
```

Поддерживаемые операторы:

- `exists: true|false`
- `missing: true`
- `equals` / `not_equals`
- `contains` для строк, списков и ключей dict.
- `in` для встроенных списков.
- `in_file` для массивов JSON, объектов JSON (используются ключи) или текстовых файлов, разделенных новой строкой.
- `regex`
- Группы `all`, `any` и `not`.

Пути к полям используют точечную запись. `payload.foo` считывает из объекта `payload` верхнего уровня, если он существует, или из тела корневого веб-перехватчика для плоских полезных данных. `event`/`event_type` соответствует разрешенному типу события, а `headers.<Name>` считывает заголовки запроса.

### Фильтры и преобразования скриптов

Используйте `script`, когда декларативных фильтров недостаточно. Скрипты должны находиться под `~/.hermes/scripts/` для активного профиля; там разрешаются относительные пути, и обход пути за пределами этого каталога блокируется. Скрипты `.sh` и `.bash` запускаются с помощью bash, а все остальные расширения запускаются с помощью текущего интерпретатора Python.

Полезная нагрузка маршрута отправляется на стандартный ввод в формате JSON:

```python
# ~/.hermes/scripts/todoist-hermes-label.py
import json
import sys

payload = json.load(sys.stdin)
labels = payload.get("payload", {}).get("labels", [])
if "hermes" not in labels:
    print("[SILENT]")
    raise SystemExit(0)

payload["body"] = payload["payload"]["content"]
print(json.dumps(payload))
```

Результаты скрипта:

— Стандартный вывод объекта JSON заменяет полезную нагрузку, используемую `prompt` и `deliver_extra`.
— Текстовый стандартный вывод, отличный от JSON, добавляется в полезные данные как `script_output`.
– Пустой стандартный вывод, точное значение `[SILENT]`, `{"__hermes_ignore__": true}`, тайм-аут, отсутствующий скрипт или ненулевой код выхода возвращает HTTP 200 с `{"status":"ignored","reason":"script"}`.

### Шаблоны подсказок

В подсказках используется точечная нотация для доступа к вложенным полям в полезной нагрузке веб-перехватчика:

- `{pull_request.title}` превращается в `payload["pull_request"]["title"]`
- `{repository.full_name}` превращается в `payload["repository"]["full_name"]`
- `{__raw__}` — специальный токен, который выводит **всю полезную нагрузку** в виде JSON с отступом (обрезанным до 4000 символов). Полезно для мониторинга оповещений или общих веб-перехватчиков, когда агенту требуется полный контекст.
- Отсутствующие ключи остаются в виде буквальной строки `{key}` (без ошибок).
- Вложенные словари и списки сериализуются в формате JSON и усекаются до 2000 символов.

Вы можете смешивать `{__raw__}` с обычными переменными шаблона:

```yaml
prompt: "PR #{pull_request.number} by {pull_request.user.login}: {__raw__}"
```

Если для маршрута не настроен шаблон `prompt`, вся полезная нагрузка выгружается в виде JSON с отступом (обрезанным до 4000 символов).

Те же шаблоны точечной записи работают со значениями `deliver_extra`.

### Доставка тем форума

При доставке ответов через вебхук в Telegram вы можете настроить таргетинг на определенную тему форума, включив `message_thread_id` (или `thread_id`) в `deliver_extra`:

```yaml
webhooks:
  routes:
    alerts:
      events: ["alert"]
      prompt: "Alert: {__raw__}"
      deliver: "telegram"
      deliver_extra:
        chat_id: "-1001234567890"
        message_thread_id: "42"
```

Если `chat_id` не указан в `deliver_extra`, доставка возвращается на домашний канал, настроенный для целевой платформы.

## PR-обзор GitHub (шаг за шагом) {#github-pr-review}

В этом пошаговом руководстве настраивается автоматическая проверка кода для каждого запроса на включение.

### 1. Создайте вебхук в GitHub.

1. Перейдите в свой репозиторий → **Настройки** → **Вебхуки** → **Добавить вебхук**.
2. Установите для **URL полезной нагрузки** значение `http://your-server:8644/webhooks/github-pr`.
3. Установите для **Тип контента** значение `application/json`.
4. Установите **Secret** в соответствии с конфигурацией вашего маршрута (например, `github-webhook-secret`).
5. В разделе **Какие события?** выберите **Разрешить мне выбирать отдельные события** и установите флажок **Запросы на извлечение**.
6. Нажмите **Добавить вебхук**.

### 2. Добавляем конфигурацию маршрута

Добавьте маршрут `github-pr` к вашему `~/.hermes/config.yaml`, как показано в примере выше.

### 3. Убедитесь, что `gh` CLI аутентифицирован.

Тип доставки `github_comment` использует интерфейс командной строки GitHub для публикации комментариев:

```bash
gh auth login
```

### 4. Проверьте это

Откройте запрос на включение в репозиторий. Вебхук срабатывает, Hermes обрабатывает событие и публикует комментарий к PR.

## Настройка GitLab Webhook {#gitlab-webhook-setup}

Веб-хуки GitLab работают аналогично, но используют другой механизм аутентификации. GitLab отправляет секрет в виде обычного заголовка `X-Gitlab-Token` (точное соответствие строки, а не HMAC).

### 1. Создайте вебхук в GitLab

1. Перейдите в свой проект → **Настройки** → **Вебхуки**.
2. Установите **URL** на `http://your-server:8644/webhooks/gitlab-mr`.
3. Введите свой **Секретный токен**.
4. Выберите **События запроса на слияние** (и любые другие события, которые вы хотите).
5. Нажмите **Добавить вебхук**.

### 2. Добавляем конфигурацию маршрута

```yaml
platforms:
  webhook:
    enabled: true
    extra:
      routes:
        gitlab-mr:
          events: ["merge_request"]
          secret: "your-gitlab-secret-token"
          prompt: |
            Review this merge request:
            Project: {project.path_with_namespace}
            MR !{object_attributes.iid}: {object_attributes.title}
            Author: {object_attributes.last_commit.author.name}
            URL: {object_attributes.url}
            Action: {object_attributes.action}
          deliver: "log"
```

## Варианты доставки {#delivery-options}

Поле `deliver` определяет, куда направляется ответ агента после обработки события веб-перехватчика.

| Тип доставки | Описание |

| `telegram` | Направляет ответ в Telegram. Использует домашний канал или укажите `chat_id` в `deliver_extra`. |
| `discord` | Направляет ответ в Discord. Использует домашний канал или укажите `chat_id` в `deliver_extra`. |
| `slack` | Направляет ответ в Slack. Использует домашний канал или укажите `chat_id` в `deliver_extra`. |
| `signal` | Направляет ответ в Signal. Использует домашний канал или укажите `chat_id` в `deliver_extra`. |
| `sms` | Направляет ответ на SMS через Twilio. Использует домашний канал или укажите `chat_id` в `deliver_extra`. |
| `whatsapp` | Направляет ответ в WhatsApp. Использует домашний канал или укажите `chat_id` в `deliver_extra`. |
| `matrix` | Направляет ответ в Matrix. Использует домашний канал или укажите `chat_id` в `deliver_extra`. |
| `mattermost` | Направляет ответ на Mattermost. Использует домашний канал или укажите `chat_id` в `deliver_extra`. |
| `homeassistant` | Направляет ответ Home Assistant. Использует домашний канал или укажите `chat_id` в `deliver_extra`. |
| `email` | Направляет ответ на электронную почту. Использует домашний канал или укажите `chat_id` в `deliver_extra`. |
| `dingtalk` | Направляет ответ на DingTalk. Использует домашний канал или укажите `chat_id` в `deliver_extra`. |

Для кросс-платформенной доставки целевая платформа также должна быть включена и подключена к шлюзу. Если в `deliver_extra` не указан `chat_id`, ответ отправляется на настроенный домашний канал этой платформы.

## Режим прямой доставки {#direct-delivery-mode}

По умолчанию каждый веб-перехватчик POST запускает запуск агента — полезные данные становятся приглашением, агент обрабатывает их и доставляет ответ агента. Это стоит токенов LLM на каждом мероприятии.

Для случаев, когда вы просто хотите **отправить простое уведомление** — без рассуждений, без цикла агента, просто доставить сообщение — установите `deliver_only: true` в маршруте. Отрисованный шаблон `prompt` становится буквальным телом сообщения, и адаптер отправляет его непосредственно в настроенную цель доставки.

### Когда использовать прямую доставку

- **External Service Push** — веб-хук Supabase/Firebase срабатывает при изменении базы данных → мгновенно уведомляет пользователя в Telegram.
- **Оповещения мониторинга** — веб-хук оповещений Datadog/Grafana → отправить на канал Discord
- **Межагентские проверки** — агент А уведомляет пользователя агента Б о завершении длительной задачи.
- **Завершение фонового задания** — задание Cron завершается → отправьте результат в Slack.

Преимущества:

- **Ноль токенов LLM** — агент никогда не вызывается.
- **Доставка за доли секунды** — один вызов адаптера, без цикла рассуждений.
- **Та же безопасность, что и в режиме агента** — аутентификация HMAC, ограничения скорости, идемпотентности и ограничения размера тела по-прежнему применяются.
- **Синхронный ответ** — POST возвращает `200 OK` в случае успешной доставки или `502`, если цель отклоняет его, чтобы ваша вышестоящая служба могла разумно повторить попытку.

### Пример: отправка Telegram из Supabase

```yaml
platforms:
  webhook:
    enabled: true
    extra:
      port: 8644
      secret: "global-secret"
      routes:
        antenna-matches:
          secret: "antenna-webhook-secret"
          deliver: "telegram"
          deliver_only: true
          prompt: "🎉 New match: {match.user_name} matched with you!"
          deliver_extra:
            chat_id: "{match.telegram_chat_id}"
```

Ваша пограничная функция Supabase подписывает полезную нагрузку с помощью HMAC-SHA256 и POST на `https://your-server:8644/webhooks/antenna-matches`. Адаптер веб-перехватчика проверяет подпись, отображает шаблон из полезных данных, доставляет его в Telegram и возвращает `200 OK`.

### Пример: динамическая подписка через CLI

```bash
hermes webhook subscribe antenna-matches \
  --deliver telegram \
  --deliver-chat-id "123456789" \
  --deliver-only \
  --prompt "🎉 New match: {match.user_name} matched with you!" \
  --description "Antenna match notifications"
```

### Коды ответов

| Статус | Значение |
|--------|---------|
| `200 OK` | Доставлено успешно. Тело: `{"status": "delivered", "route": "...", "target": "...", "delivery_id": "..."}` |
| `200 OK` (статус=дубликат) | Дублирование идентификатора `X-GitHub-Delivery` в течение срока жизни идемпотентности (1 час). Не доставлено повторно. |
| `401 Unauthorized` | Подпись HMAC недействительна или отсутствует. |
| `400 Bad Request` | Неверный формат тела JSON. |
| `404 Not Found` | Неизвестное название маршрута. |
| `413 Payload Too Large` | Тело превысило `max_body_bytes`. |
| `429 Too Many Requests` | Превышен лимит скорости маршрута. |
| `502 Bad Gateway` | Целевой адаптер отклонил сообщение или поднял его. Ошибка регистрируется на стороне сервера; текст ответа представляет собой общий формат `Delivery failed`, чтобы избежать утечки информации о внутренних компонентах адаптера. |

### Ошибки конфигурации

- `deliver_only: true` требует, чтобы `deliver` был реальной целью. `deliver: log` (или отсутствие `deliver`) отклоняется при запуске — адаптер отказывается запускаться, если обнаруживает неправильно настроенный маршрут.
- Поле `skills` игнорируется в режиме прямой доставки (агент не запускается, поэтому не во что внедрять навыки).
- При отрисовке шаблона используется тот же синтаксис `{dot.notation}`, что и в режиме агента, включая токен `{__raw__}`.
- Идемпотентность использует один и тот же заголовок `X-GitHub-Delivery`/`X-Request-ID` — повторные попытки с тем же идентификатором возвращают `status=duplicate` и НЕ выполняют повторную доставку.

## Динамические подписки (CLI) {#dynamic-subscriptions}

Помимо статических маршрутов в `config.yaml`, вы можете динамически создавать подписки веб-перехватчиков с помощью команды `hermes webhook` CLI. Это особенно полезно, когда агенту самому необходимо настроить триггеры, управляемые событиями.

### Создать подписку

```bash
hermes webhook subscribe github-issues \
  --events "issues" \
  --prompt "New issue #{issue.number}: {issue.title}\nBy: {issue.user.login}\n\n{issue.body}" \
  --deliver telegram \
  --deliver-chat-id "-100123456789" \
  --description "Triage new GitHub issues"
```

Это вернет URL-адрес веб-перехватчика и автоматически созданный секрет HMAC. Настройте свой сервис для POST по этому URL-адресу.

### Получение списка подписок

```bash
hermes webhook list
```

### Удалить подписку

```bash
hermes webhook remove github-issues
```

### Проверьте подписку

```bash
hermes webhook test github-issues
hermes webhook test github-issues --payload '{"issue": {"number": 42, "title": "Test"}}'
```

### Как работают динамические подписки

- Подписки хранятся в `~/.hermes/webhook_subscriptions.json`.
- Адаптер веб-перехватчика выполняет горячую перезагрузку этого файла при каждом входящем запросе (с ограничением по времени, незначительные накладные расходы).
- Статические маршруты от `config.yaml` всегда имеют приоритет над динамическими маршрутами с тем же именем.
- Динамические подписки используют тот же формат маршрута и возможности, что и статические маршруты (события, шаблоны подсказок, навыки, доставка).
- Перезапуск шлюза не требуется — подпишитесь, и он сразу же появится в эфире.

### Подписки, управляемые агентом

Агент может создавать подписки с помощью инструмента терминала, руководствуясь навыком `webhook-subscriptions`. Попросите агента «настроить веб-перехватчик для проблем с GitHub», и он выполнит соответствующую команду `hermes webhook subscribe`.

## Наборы инструментов для каждого маршрута {#per-route-toolsets}

Агент Webhook по умолчанию использует намеренно ограниченный набор инструментов (`web_search`, `web_extract`, `vision_analyze`, `clarify`), поскольку полезные данные вебхука могут переносить ненадежный сторонний контент — общедоступный PR-заголовок или комментарий к проблеме никогда не должен иметь возможность внедрить его в ваш терминал.

Для **доверенных** маршрутов — демона мониторинга localhost, отправляющего системные оповещения, внутренней системы CI — вы можете предоставить более широкий набор инструментов только для этого маршрута, не расширяя каждый другой маршрут веб-перехватчика:

```yaml
platforms:
  webhook:
    enabled: true
    extra:
      routes:
        oom-emergency:
          secret: "monitor-secret"
          prompt: "Memory emergency: {detail}. Diagnose with ps/free/py-spy and report."
          toolsets: ["terminal", "file", "code_execution", "web"]
          deliver: "telegram"
```

Для динамических подписок добавьте ключ `toolsets`, отредактировав `~/.hermes/webhook_subscriptions.json` напрямую:

```json
{
  "oom-emergency": {
    "secret": "...",
    "prompt": "...",
    "toolsets": ["terminal", "file", "web"],
    "deliver": "telegram"
  }
}
```

Поведение и безопасность:

- Список маршрутов **заменяет** разрешение набора инструментов веб-перехватчика на уровне платформы для запусков этого маршрута (он не объединяется).
— Имена проверяются по тому же пути, что и конфигурация `platform_toolsets` — неизвестные имена и наборы инструментов, ограниченные платформой, удаляются.
- `hermes webhook subscribe` намеренно **не** принимает флаг набора инструментов. Предоставление инструментов с повышенными правами — это редактирование файла конфигурации вручную, поэтому агент, создающий собственную подписку во время выполнения, не может самостоятельно предоставить `terminal`.
- Предоставляйте повышенные наборы инструментов только тем маршрутам, отправителей которых вы полностью контролируете, с настоящим секретом HMAC. Любой, кто может отправить по этому маршруту действительно подписанные полезные данные, фактически запускает агент с этими инструментами.

## Безопасность {#security}

Адаптер веб-перехватчика включает в себя несколько уровней безопасности:

### Проверка подписи HMAC

Адаптер проверяет входящие подписи веб-перехватчиков, используя соответствующий метод для каждого источника:

- **GitHub**: заголовок `X-Hub-Signature-256` — шестнадцатеричный дайджест HMAC-SHA256 с префиксом `sha256=`.
- **GitLab**: заголовок `X-Gitlab-Token` — совпадение простой секретной строки.
- **Общий (рекомендуется версия 2)**: заголовки `X-Webhook-Signature-V2` + `X-Webhook-Timestamp` — шестнадцатеричный дайджест HMAC-SHA256 для `<timestamp>.<body>`. Временная метка (в секундах Unix) должна находиться в пределах ±300 секунд от часов сервера, что предотвращает повторное воспроизведение захваченных запросов в дальнейшем.
- **Общий (версия 1, устаревшая версия)**: заголовок `X-Webhook-Signature` — только необработанный шестнадцатеричный дайджест HMAC-SHA256 тела. По-прежнему принимается для обратной совместимости, но не имеет защиты от повторного воспроизведения (захваченный запрос воспроизводится бесконечно); шлюз регистрирует предупреждение об устаревании один раз для каждого маршрута. Переключите отправителей на V2.

Если секрет настроен, но распознанный заголовок подписи отсутствует, запрос отклоняется.

### Требуется секрет

У каждого маршрута должен быть секрет — либо установленный непосредственно в маршруте, либо унаследованный от глобального `secret`. Маршруты без секрета приводят к сбою адаптера при запуске с ошибкой. Только для разработки/тестирования вы можете установить секрет `"INSECURE_NO_AUTH"`, чтобы полностью пропустить проверку.

Если включена многопрофильная маршрутизация, поле `profile` маршрута также
привязывает этот секрет к одной цели выполнения. Маршрут без `profile`
только профиль по умолчанию. Запрос, содержащий действительную подпись маршрута, все еще остается
отклоняется, если его префикс `/p/<profile>/` не соответствует привязке маршрута.

`INSECURE_NO_AUTH` принимается только в том случае, если шлюз привязан к узлу обратной связи (`127.0.0.1`, `localhost`, `::1`). Если оно сочетается с привязкой без обратной связи, такой как `0.0.0.0` или IP-адрес локальной сети, адаптер отказывается запускаться — это предотвращает случайное раскрытие неаутентифицированной конечной точки на общедоступном интерфейсе.

### Ограничение скорости

По умолчанию каждый маршрут ограничен **30 запросами в минуту** (фиксированное окно). Настройте это глобально:

```yaml
platforms:
  webhook:
    extra:
      rate_limit: 60  # requests per minute
```

Запросы, превышающие лимит, получают ответ `429 Too Many Requests`.

### Идемпотентность

Идентификаторы доставки (из `X-GitHub-Delivery`, `X-Request-ID` или резервной метки времени) кэшируются на **1 час**. Дубликаты доставки (например, повторные попытки веб-перехватчика) автоматически пропускаются с помощью ответа `200`, что предотвращает повторные запуски агента.

### Ограничения по размеру тела

Полезные данные, превышающие **1 МБ**, отклоняются до прочтения тела сообщения. Настройте это:

```yaml
platforms:
  webhook:
    extra:
      max_body_bytes: 2097152  # 2 MB
```

### Аутентифицированный не означает доверенный

:::предупреждение
**Проверка HMAC подтверждает подлинность _sender_, а не _content_.** Действительная подпись только доказывает, что запрос поступил от стороны, владеющей секретом маршрута (например, GitHub). В нем ничего не говорится о том, кто написал _бизнес-поля_ внутри полезных данных — PR-заголовки, сообщения о фиксации, описания проблем и любой другой исходный текст созданы произвольными третьими лицами и должны рассматриваться как ненадежные.

Это та же модель доверия, которая применяется ко всему, что читает агент: веб-страницы, файлы и выходные данные инструмента являются ненадежными входными данными. Hermes не выполняет — и не может надежно — очищать ненадежный текст с помощью черного списка; формулировка, кодирование и перевод делают это тривиально обойти. **Граница доверия — это поверхность возможностей агента, а не входной канал.** Укрепите ее:

- **Изолированная среда выполнения.** Запускайте шлюз с помощью серверной части терминала Docker или SSH (или на виртуальной машине) при наличии доступа к Интернету, чтобы перехваченный ход не мог коснуться хоста.
- **Охватите набор инструментов.** Отключите `terminal`, `file` и инструменты исходящих действий в сеансах, запускаемых веб-перехватчиком, если маршруту нужно только прочитать и суммировать. Меньшие возможности означают меньший радиус взрыва, если поле полезной нагрузки содержит введенные инструкции.
- **Включите одобрения** для любой разрушительной или исходящей операции, чтобы внедренная инструкция не могла действовать без присмотра.
- **Узкий шаблон.** Предпочитайте конкретный `prompt` с именованными полями (`{pull_request.title}`) вместо `{__raw__}` или пустой шаблон, который выгружает всю полезную нагрузку, чтобы в подсказку попадали только нужные поля.
:::

## Устранение неполадок {#устранение неполадок}

### Вебхук не доходит

– Убедитесь, что порт открыт и доступен из источника веб-перехватчика.
- Проверьте правила брандмауэра — порт `8644` (или настроенный вами порт) должен быть открыт.
– Убедитесь, что URL-путь соответствует: `http://your-server:8644/webhooks/<route-name>`.
– Используйте конечную точку `/health`, чтобы убедиться, что сервер работает.

### Не удалось проверить подпись

– Убедитесь, что секрет в конфигурации вашего маршрута точно соответствует секрету, настроенному в источнике веб-перехватчика.
- Для GitHub секрет основан на HMAC — проверьте `X-Hub-Signature-256`.
- Для GitLab секрет — это простое совпадение токенов — проверьте `X-Gitlab-Token`.
– Проверьте журналы шлюза на наличие предупреждений `Invalid signature`.

### Событие игнорируется

– Убедитесь, что тип события указан в списке `events` вашего маршрута.
– В событиях GitHub используются такие значения, как `pull_request`, `push`, `issues` (значение заголовка `X-GitHub-Event`).
- В событиях GitLab используются такие значения, как `merge_request`, `push` (значение заголовка `X-GitLab-Event`).
- Если `events` пуст или не установлен, принимаются все события.

### Агент не отвечает

- Запустите шлюз на переднем плане, чтобы просмотреть журналы: `hermes gateway run`.
– Убедитесь, что шаблон приглашения отображается правильно.
- Убедитесь, что цель доставки настроена и подключена.

### Повторяющиеся ответы

- Кэш идемпотентности должен предотвратить это — убедитесь, что источник веб-перехватчика отправляет заголовок идентификатора доставки (`X-GitHub-Delivery` или `X-Request-ID`).
- Идентификаторы доставки кэшируются на 1 час.

### `gh` Ошибки CLI (доставка комментариев GitHub)

- Запустите `gh auth login` на узле шлюза.
- Убедитесь, что аутентифицированный пользователь GitHub имеет доступ на запись в репозиторий.
- Убедитесь, что `gh` установлен и находится в PATH.
