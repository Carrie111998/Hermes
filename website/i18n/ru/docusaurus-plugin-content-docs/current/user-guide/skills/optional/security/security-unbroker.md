# анброкер

Найдите, где раскрывается личная информация человека (имя, адреса, телефон, электронная почта, родственники)
брокеров данных и сайтов поиска людей, а затем удалить их – по возможности автоматически, под руководством
человеческие действия только в том случае, если сайт требует CAPTCHA, правительственного удостоверения личности, телефонного звонка или факса. Управляет несколькими
люди независимо. Он **не** побеждает антиботовые системы, **не** действует ни на кого без
записанное согласие и **не** удаляет общедоступные записи (избирателя/собственность/суд) или учетные записи,
человек контролирует.

Интерфейс командной строки Python (`scripts/pdd.py`) имеет детерминированное состояние — конфигурация, досье + согласие,
база данных брокера, многоуровневое планирование, реестр, черновики, отчеты, **отправка электронной почты (SMTP), ссылка для проверки
опрос (IMAP) и очередь автономных действий (`next`)**. Вы (агент) выполняете сканирование и
управление формами с помощью собственных инструментов: `web_extract` и `browser_navigate` для поиска и веб-форм, а также
`cronjob` для повторяющихся повторных сканирований.

## Когда использовать

- «Удалить мои данные (или данные члена моей семьи) с брокеров данных/сайтов поиска людей».
- «Отключить меня», «удалить меня из Spokeo/Whitepages/и т. д.», «очистить после доксинга».
- «Настроить периодический мониторинг конфиденциальности» (брокеры переписывают людей).
- Проверка того, какие брокеры все еще кого-то выставляют и почему.

## Как бежать

Запустите все через инструмент `terminal`. Из каталога этого навыка:

```bash
PDD="python3 scripts/pdd.py"
```

Движок хранит данные под `$PDD_DATA_DIR` (по умолчанию `$HERMES_HOME/unbroker`), записанными
`0600`. Запускать через `terminal`, **не** `execute_code` (эта песочница очищает окружение и редактирует выходные данные, что
перерывы в чтении досье).

## Краткий справочник

| Команда | Цель |
|---|---|
| `$PDD setup --auto` | **Автономная настройка**: определите возможности, выберите наиболее автономную действующую конфигурацию (без вопросов) |
| `$PDD doctor` | Проверка готовности: конфигурация, количество брокеров и какие обновления включены/доступны |
| `$PDD cdp [--check] [--print] [--port N]` | Запустить/обнаружить Chrome оператора через CDP для браузера фазы 2 + веб-почты (специальный профиль отладки; надежный способ отправки веб-почты и очистки шлюзов, привязанных к сеансу) |
| `$PDD intake --full-name "..." [--alias ...] [--email ... --phone ...] [--city --state] [--prior-location "City,ST"] --consent` | Создайте соглашающегося субъекта; фиксирует псевдонимы + несколько адресов электронной почты/телефонов + предыдущие местоположения; принты `subject_id` |
| `$PDD next <subject>` | **Драйвер автономного цикла**: упорядоченные действия агента прямо сейчас + человеческий дайджест + `next_wake_at` |
| `$PDD brokers [--priority crucial]` | Перечислите базу данных брокеров по поиску людей (кураторская и живая) |
| `$PDD refresh-brokers` | Получите последний список поиска людей BADBOOL **и реестр CA Data Broker** (`next` автоматически запрашивает его, когда кэш устаревает) |
| `$PDD registry [--search NAME]` | Охват государственного реестра (загружено ~545 CA; появились порталы VT/OR/TX); полоса DROP/электронная почта, не сканируется |
| `$PDD drop <subject> [--filed]` | **Одноразовый юридический рычаг**: один запрос CA DROP удаляет ВСЕ зарегистрированные брокеры; `--filed` записывает это |
| `$PDD plan <subject> [--priority crucial]` | Уровень каждого брокера + метод + `search_vectors` + точные поля для раскрытия |
| `$PDD plan <subject> --batch` | **Уменьшить представление**: накладывает состояние реестра, группирует брокеров по следующему действию (неотсканировано/найдено/косвенно/заблокировано/в_прогрессе/выполнено), сворачивает кластеры владения, **заказывает `found` кластер-родители-сначала + выдает специальный `parent_playbook`**, печатает `next_actions` |
| `$PDD fanout <subject> [--priority crucial] [--size 5]` | Пакетные брокеры в параллельные субагенты `delegate_task` (автоматически для больших циклов; пакеты по 5–8+ с тайм-аутом) |
| `$PDD record <subject> <broker> <state> [--found true] [--evidence JSON] [--disclosed F --channel C] [--reason "..."]` | Обновить реестр (проверенный конечный автомат); **автоштампы `next_recheck_at`** |
| `$PDD show <subject> <broker>` | Прочитать записанное состояние дела + доказательства + журнал раскрытия (чтобы родитель повторно проверил `found` субагента без повторного получения URL-адреса листинга) |
| `$PDD send-email <subject> <broker> --listing <url> [--kind ccpa_indirect ...]` | Оформить + записать запрос (получатель привязан к собственному адресу брокера). **режим браузера** возвращает полезную нагрузку `compose` для отправки через веб-почту (без пароля); **программный** режим SMTP-отправок |
| `$PDD verify-link <subject> <broker> --text '<body>'` | **режим браузера**: извлеките ссылку для проверки брокера из текста веб-почты, который вы читаете (оценка защиты от фишинга) |

## Пакетная операция (двухэтапная: сканирование всего, затем удаление)

Для всего, что превышает пару брокеров, запустите это как **map → уменьшить → действовать**, а не для каждого брокера:

- **Этап 1 — ОБНАРУЖЕНИЕ (только для чтения, параллельный, идемпотентный).** Сначала просканируйте *каждый* брокер и запишите
  вердикт для каждого (`found` / `not_found` / `indirect_exposure` / `blocked`). У сканирования нет сторон
  эффекты, поэтому можно безопасно распараллеливать и повторять попытки. Получить полную карту воздействия *прежде* действовать — это
  что открывает дедупликацию кластера и определение приоритетов ниже. **По умолчанию: родительские диски `web_extract`.
  зондирует напрямую** — большинство сайтов поиска людей отображают результаты имени/телефона/адреса в виде статического HTML-кода, который
  `web_extract` читается за секунды. Передавайте на `browser_*` только несколько сайтов, поддерживающих только JS, и
  `delegate_task` субагенты только для действительно *рассуждений*-тяжелой работы (крупномасштабные одноимённые/родственные
  неоднозначность). **НЕ передавайте субагенту набора инструментов браузера большой список брокеров для сканирования** - в
  время ожидания в этом поле повторяется (600 секунд, ~5-6 брокеров каждый, без сводки), поскольку навигация в браузере
  тяжелый; в реестре написано, что выживание обошлось в 10 раз дороже родительского `web_extract`. `blocked`
  (DataDome/Cloudflare/`antibot`) также *не* является заданием субагента: запишите `blocked` и повторно поставьте его в очередь
  для прохода скрытого/облачного браузера (Browserbase). Отчеты субагента — это самоотчеты — родительский
  повторно извлекает ключевые URL-адреса, чтобы подтвердить `found`, прежде чем доверять ему (это обоюдоострое: он поймал настоящий
  внесение в список, который родитель ошибочно предположил, было ложным срабатыванием).
- **REDUCE - `$PDD plan <subject> --batch`.** Сворачивает обход сканирования в поэтапный план: группирует по
  следующее действие: **сворачивает кластеры владения** (удаление родительского элемента с удалением дочерних элементов — ОДНО действие,
  не N - например. одно подавление Intelius/PeopleConnect распространяется на Truthfinder/Instant Checkmate/US Search/…),
  и печатает `next_actions`. `phase` — это `discover`, пока ничего не сканируется, иначе — `delete`.
- **Этап 2 – УДАЛЕНИЕ (последовательное, необратимое).** Работа с сокращенными группами **сначала родители**:
  `plan --batch` упорядочивает группу `found` с приоритетом родителей-кластеров (сначала большинство дочерних элементов) и выдает
  `parent_playbook` с индивидуальными упорядоченными шагами для каждого родителя – следуйте этому порядку и этим шагам.
  (полные рецепты в `references/methods.md` → «Кластеры собственности — СНАЧАЛА РОДИТЕЛИ»). Сделайте
  кластерные родители (пропуская охватываемые дочерние элементы), **повторное сканирование дочерних элементов каждого родителя после подтверждения**
  (они обычно выпадают), затем отдельные листинги; отправьте дела `indirect_exposure` как
  CCPA/GDPR удалить электронные письма с личными данными (`send-email --kind ccpa_indirect`) и отложить `blocked` до
  стелс-браузер проходит. Отказ затрагивает CAPTCHA, циклы проверки электронной почты и привязку сеанса — работает
  их **по одному, осторожно** (это противоположность разветвлению), но НЕ останавливайтесь, чтобы спросить
  разрешение на отправку в `autonomy=full`; в `assisted` подтвердите каждый из них. **Обычно предпочитают
  удаление вместо подавления**, когда брокер предлагает оба варианта (Spokeo/BeenVerified), но следуйте инструкциям
  запись `deletion.prefer`: **PeopleConnect является исключением** (`prefer: false`), при котором удаление
  ваши пользовательские данные снимают ваши подавления и не препятствуют повторному включению в общедоступные записи, поэтому вы
  Вместо этого подавляйте и поддерживайте.
- **Слепой отказ – это вариант ПО УМОЛЧАНИЮ, а не запасной вариант.** Отправьте запрос на отказ/удаление на **каждом сайте с
  доступный канал удаления, даже если объявление не было предварительно подтверждено** — он раскрывает только
  собственные идентификаторы субъекта на собственный официальный канал брокера, поэтому это не нарушает
  минимум-раскрытие. Два следствия: (1) управляемый поток, который соответствует адресу электронной почты+роду+имя и сообщает «нет результатов».
  является **более сильным `not_found`**, чем любая очистка: поток отказа дублируется поиском; (2) когда форма
  несовместим с автоматизацией (жесткий CAPTCHA, Cloudflare/DataDome, слайдер для проверки слайдов), **по умолчанию
  указанный брокером адрес электронной почты с запросом прав** (только имя+штат+контактный адрес электронной почты), а не запись `blocked`.
  Политика CAPTCHA: никогда не преодолевайте поведенческие проблемы/проблемы с токенами/слайдерами; ОК, чтобы прочитать статический искаженный текст или
  простая арифметическая CAPTCHA при отказе самого субъекта, но прекратится, если сайт отклонит всю информацию
  отправка после правильного ответа (это дактилоскопия автоматизации). Сторонние/косвенные записи
  являются исключением - все же

подтвердите это, прежде чем действовать. Планы игры для каждого сайта + отсутствие мета-поиска
  список пропуска находится в `references/site-playbooks.md`; полная политика находится в `references/methods.md`.
- **Подавление удаления-очистки-удаления PeopleConnect (постоянное правило).** *Удаление* PeopleConnect удаляет
  подавление и повторный список субъектов по всему партнерскому кластеру. Если «Ваш запрос на удаление
  для PeopleConnect.us is Complete» когда-либо появляется электронное письмо, подавление снято -> **повторно запустить подавление
  и еще раз убедитесь, что** на этапе управления указано «подавлено». Никогда не покидайте этот кластер после завершения удаления.
  (см. `references/brokers/intelius.json`).

Отчеты субагентов представляют собой самоотчеты: родительский орган повторно проверяет ключевые утверждения (список URL-адресов, база совпадений) перед тем, как
запись `found` и перед любым удалением.

## Процедура (автономный цикл)

1. **Настройка (один раз, вопросов нет).** Запускаем `$PDD setup --auto` - он определяет возможности и настраивает
   самая автономная действительная комбинация (программное электронное письмо при наличии `EMAIL_*` кредитов,
   База браузера, если существует его ключ, `age` шифрование, если существует двоичный файл, `autonomy=full`). Тогда
   `$PDD doctor` и покажите оператору вывод готовности **для информации, а не в виде вопроса** -
   приступайте немедленно. Упомяните, что позволит повысить уровень автоматизации (например, учетные данные электронной почты), но не ждите.
2. **Прием + согласие (ОДИН человеческий разговор).** `$PDD intake ...` с `--consent` (и
   `--consent-method`). Без согласия двигатель отказывается планировать или действовать. Соберите все в одном
   пароль — имена/псевдонимы, текущие и предыдущие города, адреса электронной почты, телефоны — чтобы вам никогда не приходилось возвращаться с
   вопросы. Для испытуемых из Калифорнии также прочтите `references/legal/drop.md`: `next` выявит
   `drop_submit` одноразовый, который удаляет сразу у каждого зарегистрированного брокера (~ 545), что является
   одно действие с наибольшим кредитным плечом. Сохраните его, затем `drop <subject> --filed`. Для субъектов, не входящих в CA
   в реестр попадают целевые электронные письма CCPA/GDPR (`registry --search`, затем `send-email`); тот
   В любом случае сайты поиска людей работают напрямую.
3. **Очистка очереди.** Цикл:

   ```
   while true:
     q = $PDD next <subject>
     if q.actions is empty: break
     execute EVERY action in order; record each outcome via $PDD record
   ```

`next` выдает по порядку: `refresh_brokers` (устаревший кэш), `fanout_scan`/`scan_inline` (фаза 1
   сканирование — см. шаг 4), `poll_verification` (подтверждения по электронной почте), `verify_removal` (срок
   повторные проверки), `optout_web_form`/`optout_email_send` (этап 2, в первую очередь родители, с пошаговыми инструкциями),
   `indirect_email_send` и `stealth_rescan`. Работа, выполняемая только человеком, никогда не проявляется как действие.
   накапливается в `q.human_digest`. В `autonomy=full` выполнять действия без паузы; честь
   `confirm_first` в режиме `assisted`.
4. **Сканирование (когда `next` так говорит).** Для `fanout_scan`: запустите `$PDD fanout <subject>` и **создайте один
   Субагент `delegate_task` на `batch`, параллельно передавая готовый `brief`** этого пакета - сделать
   не сканируйте всех брокеров последовательно. Для `scan_inline`: самостоятельно просканируйте нескольких брокеров.
   В любом случае каждый брокер получает **каждую** запись `search_vectors` через `references/methods.md`.
   лестница (`web_extract` → `site:` зонд → `browser_navigate` → `scrapling`), 404 НЕУЧЕТНО
   (не `not_found`), `blocked` записывается, когда установлен `antibot` и скрытый браузер недоступен,
   и субъект против тезки/родственника подтверждается перед записью:
   `$PDD record <subject> <broker> <found|not_found|indirect_exposure|blocked> --found <bool> --evidence '{"listing_urls":[...]}'`.
   Родитель повторно проверяет утверждения ключа `found` от субагентов, прежде чем доверять им.
5. **Отказ от участия (если `next` так говорит).** Действия выполняются по предварительному заказу родителей (в первую очередь с `steps` от каждого).
   собственная запись брокера `optout.playbook` (проверена на местах; родительские элементы кластера, такие как PeopleConnect,
   На Whitepages, BeenVerified, Spokeo есть точные, проверенные рецепты). **Удаление обычно лучше
   подавление**: если действие содержит `prefer_deletion`, завершите полосу УДАЛЕНИЯ записи, а не
   просто процесс скрытия моего списка. Когда вместо этого он содержит `prefer_suppression` (**PeopleConnect** -
   удаление удаляет ваши подавления и не прекращает повторный список), выполните поток подавления и продолжайте
   он сохранился; используйте кнопку «Удалить» только для преднамеренной очистки данных. По методу:
   - **web_form** → диск `optout_url` с `browser_navigate`/`browser_type`/`browser_click`, отправить
     только `disclosure_fields`, сделайте скриншот подтверждения, затем команду записи действия `after`.
     Учебники могут заканчиваться следующим сообщением о праве на удаление `send-email` — сделайте это (полное удаление, а не просто
     подавление листинга).
    - **email** → `$PDD send-email <topic> <broker> --kind <ccpa|gdpr|generic> --to <address>
      --listing <url>` записи + раскрывает за один шаг (получатель привязан к адресам брокера)
      запись заявляет; `next` выбирает тип места жительства — никогда не предъявляйте претензий CCPA/GDPR для тех, кто
      не могу). В режиме **браузера** он возвращает полезную нагрузку `compose`, заблокированную получателем: создайте новый
      сообщение на `compose.to` с `compose.subject`/`compose.body` именно на почте оператора
      через `browser_*` и отправить (без пароля); в **программном** режиме отправляется SMTP. `next` также
      направляет формы, управляемые человеком (phone-callback/gov-ID), через электронное письмо об удалении брокера, когда один
      существует - **спасательная полоса** (проверенный шаблон Whitepages). Только черновик возвращается к
      `render-email` + запись дайджеста.
   - **капча** → программные/управляемые вызовы автоматически очищаются в облачном браузере по умолчанию (продолжите
     как обычно); записано только сложное интерактивное/поведенческое испытание, которое он не может пройти `blocked`

     `$PDD record <subject> <broker> human_task_queued --reason "..."`.

    находит пришедшие ссылки подтверждения через IMAP (оценка защиты от фишинга, состояние автоматического продвижения). В

   keeps advancing with zero human attention.

## Pitfalls

- **Never disclose more than the broker already shows.** Submit only `disclosure_fields`. The engine
  never volunteers SSN/ID numbers; you must not either.
- **No consent, no action.** The engine enforces this; do not work around it to "research" a third party.
- **`send-email` is idempotent + rate-limited.** It refuses to re-send a case already `submitted`
  or beyond (use `--force` only if a genuine re-send is needed), and SMTP sends are paced by
  `email_min_interval_seconds` (default 20s) with retry/backoff. Do not loop it to "make sure" -
  a successful SMTP handoff is not proof of delivery; the due-queue re-scan is the real confirmation.
- **Ledger writes are locked.** Concurrent runs (cron + manual) serialize safely; if you ever see a
  lock timeout, another run is mid-write - let it finish, don't delete the `.lock` by hand.
- **Autonomy ≠ improvisation.** Full autonomy means not *asking* between steps; it does not loosen any
  gate. If a broker demands MORE than the planned `disclosure_fields` mid-flow, stop that case and
  queue it (`human_task_queued --reason`) rather than deciding alone to disclose extra PII.
- **Don't interrupt the run with questions.** Config choices are `setup --auto`'s job; human-only work
  goes to the digest. The only mid-run question that's ever warranted is a missing-identity fact that
  blocks scanning (e.g. no city at all) - and that should have been collected at intake.
- **Use `terminal`, not `execute_code`** for `pdd.py` (secret scrubbing + output redaction break it).
- **Dossiers are plaintext by default** (JSON, `0600` under `HERMES_HOME`). For at-rest encryption run
  `$PDD setup --encryption age` - it generates a local `age` key and encrypts dossiers + ledgers (the
  audit log holds field names only and stays plaintext). It guards casual/backup/commit exposure, not
  a full-`HERMES_HOME` read; set `PDD_AGE_IDENTITY` to a separate volume for real key separation.
  `$PDD doctor` shows whether encryption is *actually* engaged (not just whether `age` is installed).
- **"Hidden from free search" ≠ deleted.** Only mark `confirmed_removed` after verifying the record is
  actually gone; note paid-tier retention in the report.
- **Soft CAPTCHAs clear by default; don't fight the hard ones.** The default cloud browser passes
  managed/soft challenges as normal operation (those brokers stay T1). For a hard interactive one it
  genuinely can't pass, record `blocked` and let the stealth/operator-browser pass take it - never a
  third-party solver service or fingerprint spoofing.
- **Broker pages change.** If a flow breaks, `$PDD record ... blocked` and flag the broker file in
  `references/brokers/` for re-verification instead of guessing.
- **Verify non-field-verified records before submitting.** `confidence: auto` records came from
  parsing BADBOOL (read `optout.notes`/`optout.links`, confirm the real opt-out URL). `confidence:
  documented` records (several people-search sites) carry the correct published opt-out URL but have
  **not** been field-verified (they 403 datacenter IPs), so confirm the live flow via the operator's
  residential browser on first use, then set `last_verified`. Field-verified curated records (no
  `confidence`, e.g. the cluster parents) have checked mechanics and take precedence.
