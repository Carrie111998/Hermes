# 1-3-1 Правило связи

Структурированный формат принятия решений, когда к задаче имеется несколько жизнеспособных подходов и пользователю нужна четкая рекомендация. Дает краткую формулировку проблемы, три варианта с компромиссами и действенный план для рекомендуемого пути.

## Когда использовать

- Пользователь явно запрашивает ответ «1-3-1».
- Пользователь говорит: «дайте мне варианты» или «какой у меня выбор» для технического решения.
- Задача имеет несколько жизнеспособных подходов со значимыми компромиссами (архитектура, инструменты, стратегия миграции).
- Пользователю нужно предложение, которое он может отправить команде или заинтересованному лицу.

НЕ используйте для простых вопросов с одним очевидным ответом, сеансов отладки или задач, подход к которым пользователь уже определил.

## Процедура

1. **Проблема** (одно предложение)
   - Изложите основное решение или желаемый результат в одном кратком предложении.
   - Сосредоточьтесь на том, что*, а не на том, как* — никаких подробностей реализации, названий инструментов или конкретных технологий.
   - Держи крепче. Если вам нужно «и», вы описываете две проблемы.

2. **Варианты** (ровно три)
   - Представьте три различных, жизнеспособных подхода, обозначенных A, B, C.
   - Каждый вариант имеет краткое описание, плюсы и минусы.
   - Варианты должны представлять собой действительно разные стратегии, а не незначительные вариации одного и того же подхода.

3. **Рекомендация** (один вариант)
   - Укажите, какой вариант вы рекомендуете и почему, исходя из контекста и приоритетов пользователя.
   — Будьте прямолинейны — это ваше профессиональное суждение, а не страховка.

4. **Определение готовности**
   - Перечислите конкретные критерии успеха для рекомендуемого варианта.
   - Это конкретные, поддающиеся проверке результаты, а не расплывчатые стремления.
   – Если пользователь выберет другой вариант, измените этот раздел, чтобы он соответствовал.

5. **План реализации**
   - Конкретные шаги по реализации рекомендуемого варианта.
   - Включите конкретные команды, инструменты или действия, где это применимо.
   – Если пользователь выберет другой вариант, измените этот раздел, чтобы он соответствовал.

## Проверка

- В ответе ровно одно проблемное предложение.
- В ответе ровно три варианта (A, B, C) с плюсами и минусами для каждого.
- В ответе имеется единственная рекомендация, в которой выбирается один вариант с обоснованием.
- Определение выполнения и план реализации соответствуют рекомендуемому варианту.
- Если пользователь выбирает другой вариант, рекомендации, DoD и план реализации обновляются соответствующим образом.

## Пример

Пользователь: «Дайте мне 1-3-1 за добавление логики повторов в наш API-клиент».

Агент:

**Проблема:** вызовы API к внешним службам периодически терпят неудачу под нагрузкой и требуют корректной обработки повторных попыток.

**Варианты:**

- **Вариант А: Экспоненциальная задержка с джиттером в общей утилите.**
  Плюсы: Простая, понятная выкройка; единая реализация, используемая всеми вызывающими объектами.
  Минусы: Нет автоматического отключения; вызывающие абоненты по-прежнему блокируются во время повторных попыток.

- **Вариант Б: Повторить попытку библиотеки (стойкость) в качестве декоратора при каждом вызове конечной точки.**
  Плюсы: настраивается для каждой конечной точки; встроенная поддержка автоматических выключателей и ограничений скорости.
  Минусы: Добавляет зависимость; Шаблон декоратора может скрыть поток управления.

- **Вариант C: асинхронная повторная попытка на основе очереди с обработкой недоставленных сообщений.**
  Плюсы: Неблокируется; неудавшиеся вызовы отслеживаются и воспроизводятся; хорошо масштабируется.
  Минусы: Значительное увеличение сложности; требуется серверная часть очереди; излишество для услуг с небольшим объемом.

**Рекомендация:** Вариант А. Объем вызовов не оправдывает инфраструктуру очередей, а общая утилита с экспоненциальной задержкой + джиттер четко покрывает режим сбоя без новых зависимостей.

**Определение готовности:**
- Утилита `api_retry()` обрабатывает временные ошибки HTTP (429, 502, 503, 504).
- Повторные попытки до 3 раз с экспоненциальной задержкой и джиттером.
— Все внешние вызовы API направляются через утилиту повтора.
- Регистрирует каждую повторную попытку с указанием конечной точки и номера попытки.
- Тесты охватывают сценарии исчерпания повторных попыток, немедленный успех и временные сценарии, а затем успех.

**План реализации:**
1. Создайте `utils/api_retry.py` с настраиваемым максимальным количеством повторов, базовой задержкой и кодами состояния повторных попыток.
2. Добавьте джиттер, используя `random.uniform(0, base_delay)`, чтобы избежать грохота стада.
3. Оберните существующие вызовы API в `api_client.py` с помощью утилиты повтора.
4. Добавьте модульные тесты, имитирующие ответы HTTP для каждого сценария повтора.
5. Проверьте работу под нагрузкой с помощью простого стресс-теста на ненадежном макете конечной точки.
