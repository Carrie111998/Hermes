# Режим планирования

Используйте этот навык, когда пользователю нужен план, а не исполнение.

## Основное поведение

Вы планируете только этот ход.

- Не внедряйте код.
- Не редактируйте файлы проекта, кроме файла уценки плана.
— Не запускайте изменяющие команды терминала, не фиксируйте, не отправляйте и не выполняйте внешние действия.
- При необходимости вы можете проверить репозиторий или другой контекст с помощью команд/инструментов, доступных только для чтения.
– Ваш результат – это план уценки, сохраненный в активной рабочей области под `.hermes/plans/`.

## Требования к выводу

Напишите план уценки, который будет конкретным и осуществимым.

Включите, если это уместно:
- Цель
- Текущий контекст/предположения
- Предлагаемый подход
- Пошаговый план
- Файлы могут измениться
- Тесты/проверка
- Риски, компромиссы и открытые вопросы

Если задача связана с кодом, укажите точные пути к файлам, вероятные объекты тестирования и этапы проверки.

## Сохранить местоположение

Сохраните план с помощью `write_file` в папке:
- `.hermes/plans/YYYY-MM-DD_HHMMSS-<slug>.md`

Считайте это относительно активного рабочего каталога/внутренней рабочей области. Файловые инструменты Hermes учитывают серверную часть, поэтому при использовании этого относительного пути план сохраняется в рабочей области на локальных, Docker, ssh, модальных и Daytona серверах.

Если среда выполнения предоставляет конкретный целевой путь, используйте именно этот путь.
Если нет, создайте самостоятельно подходящее имя файла с отметкой времени под `.hermes/plans/`.

## Стиль взаимодействия

- Если запрос достаточно ясен, напишите план напрямую.
– Если `/plan` не сопровождается явной инструкцией, выведите задачу из текущего контекста разговора.
- Если действительно не указано, задайте краткий уточняющий вопрос вместо того, чтобы гадать.
- После сохранения плана кратко ответьте, что вы запланировали, и сохраненный путь.

# Хорошо пишем план

Остальная часть этого навыка — это умение создать *хороший* план реализации — контент, который находится в файле уценки выше.

## Обзор

Напишите комплексные планы реализации, предполагая, что у разработчика нет контекста для кодовой базы и сомнительный вкус. Документируйте все, что им нужно: какие файлы трогать, полный код, команды тестирования, документы для проверки, как проверять. Давайте им небольшие задачи. СУХОЙ. ЯГНИ. ТДД. Частые коммиты.

Предположим, что разработчик — опытный разработчик, но почти ничего не знает о наборе инструментов или проблемной области. Предположим, они не очень хорошо знают хороший дизайн тестов.

**Основной принцип:** Хороший план делает реализацию очевидной. Если кто-то должен догадаться, план неполный.

## Когда помогает полный план реализации

**Всегда используйте перед:**
- Реализация многоэтапных функций.
- Разбор сложных требований.
- Делегирование субагентам посредством субагентной разработки.

**Не пропускайте, если:**
- Функция кажется простой (предположения вызывают ошибки)
- Вы планируете реализовать это самостоятельно (в будущем вам понадобится руководство)
- Работаем самостоятельно (документация имеет значение)

## Мелкая детализация задач

**Каждая задача = 2–5 минут целенаправленной работы.**

Каждый шаг – это одно действие:
- «Написать неудачный тест» — шаг
- «Запустите его, чтобы убедиться в сбое» — шаг
- «Реализуйте минимальный код, чтобы тест прошел» — шаг
— «Запустите тесты и убедитесь, что они пройдены» — шаг
- «Зафиксировать» — шаг

**Слишком большой:**
```markdown
### Task 1: Build authentication system
[50 lines of code across 5 files]
```

**Правильный размер:**
```markdown
### Task 1: Create User model with email field
[10 lines, 1 file]

### Task 2: Add password hash field to User
[8 lines, 1 file]

### Task 3: Create password hashing utility
[15 lines, 1 file]
```

## Структура документа плана

### Заголовок (обязательно)

Каждый план ДОЛЖЕН начинаться с:

```markdown
# [Feature Name] Implementation Plan

> **For Hermes:** Use subagent-driven-development skill to implement this plan task-by-task.

**Goal:** [One sentence describing what this builds]

**Architecture:** [2-3 sentences about approach]

**Tech Stack:** [Key technologies/libraries]

---
```

### Структура задачи

Каждая задача имеет следующий формат:

````markdown
### Task N: [Descriptive Name]

**Objective:** What this task accomplishes (one sentence)

**Files:**
- Create: `exact/path/to/new_file.py`
- Modify: `exact/path/to/existing.py:45-67` (line numbers if known)
- Test: `tests/path/to/test_file.py`

**Step 1: Write failing test**

```python
защита test_special_behavior():
    результат = функция (вход)
    утверждать результат == ожидается
```

**Step 2: Run test to verify failure**

Run: `pytest tests/path/test.py::test_specific_behavior -v`
Expected: FAIL — "function not defined"

**Step 3: Write minimal implementation**

```python
функция определения (вход):
    ожидается возврат
```

**Step 4: Run test to verify pass**

Run: `pytest tests/path/test.py::test_specific_behavior -v`
Expected: PASS

**Step 5: Commit**

```bash
git добавить тесты/путь/test.py src/path/file.py
git commit -m "подвиг: добавить конкретную функцию"
```
````

## Процесс написания

### Шаг 1. Ознакомьтесь с требованиями

Прочтите и поймите:
- Требования к функциям
- Проектная документация или описание пользователя
- Критерии приемки
- Ограничения

### Шаг 2. Изучите кодовую базу

Используйте инструменты Hermes для понимания проекта:

```python
# Understand project structure
search_files("*.py", target="files", path="src/")

# Look at similar features
search_files("similar_pattern", path="src/", file_glob="*.py")

# Check existing tests
search_files("*.py", target="files", path="tests/")

# Read key files
read_file("src/app.py")
```

### Шаг 3: Подход к проектированию

Решите:
- Архитектурный образец
- Организация файлов
- Необходимы зависимости
- Стратегия тестирования

### Шаг 4. Написание задач

Создайте задачи по порядку:
1. Настройка/инфраструктура
2. Основная функциональность (TDD для каждого)
3. Краевые случаи
4. Интеграция
5. Очистка/документирование

### Шаг 5: Добавьте полную информацию

Для каждой задачи укажите:
- **Точные пути к файлам** (не «файл конфигурации», а `src/config/settings.py`)
- **Полные примеры кода** (не «добавить проверку», а сам код).
- **Точные команды** с ожидаемым результатом
– **Этапы проверки**, подтверждающие работоспособность задачи.

### Шаг 6. Просмотрите план

Проверьте:
- [ ] Задачи последовательные и логичные
- [ ] Каждое задание небольшое (2–5 минут).
- [ ] Пути к файлам точны
- [ ] Примеры кода готовы (с возможностью копирования)
- [ ] Команды точны с ожидаемым результатом
- [ ] Нет отсутствующего контекста
- [ ] Применены принципы DRY, YAGNI, TDD

## Принципы

### СУХОЙ (Не повторяйтесь)

**Плохо:** Проверка копирования и вставки в трех местах.
**Хорошо:** Извлеките функцию проверки, используйте везде.

### ЯГНИ (Оно тебе не понадобится)

**Плохо:** Добавьте гибкость для будущих требований.
**Хорошо:** внедряйте только то, что необходимо сейчас.

```python
# Bad — YAGNI violation
class User:
    def __init__(self, name, email):
        self.name = name
        self.email = email
        self.preferences = {}  # Not needed yet!
        self.metadata = {}     # Not needed yet!

# Good — YAGNI
class User:
    def __init__(self, name, email):
        self.name = name
        self.email = email
```

### TDD (разработка через тестирование)

Каждая задача, создающая код, должна включать полный цикл TDD:
1. Напишите проваленный тест
2. Запустите, чтобы убедиться в ошибке
3. Напишите минимальный код
4. Запустите проверку пропуска

Подробности см. в навыке `test-driven-development`.

### Частые коммиты

Коммит после каждой задачи:
```bash
git add [files]
git commit -m "type: description"
```

## Распространенные ошибки

### Неясные задачи

**Плохо:** «Добавить аутентификацию»
**Хорошо:** «Создать модель пользователя с полями электронной почты и пароля_хэша»

### Неполный код

**Плохо:** «Шаг 1. Добавьте функцию проверки»
**Хорошо:** «Шаг 1. Добавьте функцию проверки», после чего следует полный код функции.

### Отсутствует проверка

**Плохо:** «Шаг 3. Проверьте, работает ли это»
**Хорошо:** "Шаг 3. Запустите `pytest tests/test_auth.py -v`, ожидается: 3 пройдено"

### Отсутствуют пути к файлам

**Плохо:** «Создайте файл модели»
**Хорошо:** "Создать: `src/models/user.py`"

## Передача выполнения

После сохранения плана предложите способ выполнения:

**"План завершен и сохранен. Готов к выполнению с использованием разработки под агентом — я буду отправлять новый субагент для каждой задачи с двухэтапной проверкой (соответствие спецификациям, затем качество кода). Продолжить?"**

При выполнении используйте навык `subagent-driven-development`:
- Свежие `delegate_task` для каждой задачи с полным контекстом.
- Проверка соответствия спецификациям после каждой задачи
- Проверка качества кода после прохождения спецификации.
– Продолжайте только после того, как оба отзыва одобрят.

## Помните

```
Bite-sized tasks (2-5 min each)
Exact file paths
Complete code (copy-pasteable)
Exact commands with expected output
Verification steps
DRY, YAGNI, TDD
Frequent commits
```

**Хороший план делает реализацию очевидной.**
