# Систематическая отладка

## Обзор

Случайные исправления тратят время и создают новые ошибки. Быстрые исправления маскируют основные проблемы.

**Основной принцип:** ВСЕГДА находите основную причину, прежде чем пытаться ее исправить. Устранение симптомов - сбой.

**Нарушение буквы этого процесса — нарушение духа отладки.**

## Железный закон

```
NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST
```

Если вы не завершили этап 1, вы не можете предлагать исправления.

## Правило обратной связи

Цикл обратной связи — это работа по отладке. Прежде чем читать код для построения теории, создайте или определите **жесткую** команду, которая может загореться красным при точном симптоме пользователя и зеленым, когда ошибка исправлена. Плотный цикл является быстрым, детерминированным, управляемым агентом и достаточно специфичным, чтобы обнаружить эту ошибку, а не просто «не дает сбоя».

Когда чистое воспроизведение затруднено, потратьте непропорционально много усилий на создание цикла. Угадывание без красной петли — это режим неудачи, для предотвращения которого существует этот навык.

## Когда использовать

Используйте для ЛЮБОЙ технической проблемы:
- Неудачные тесты
- Ошибки в производстве
- Неожиданное поведение
- Проблемы с производительностью
- Ошибки сборки
- Проблемы интеграции

**Используйте это ОСОБЕННО, когда:**
- В условиях нехватки времени (чрезвычайные ситуации делают догадки заманчивыми)
- «Всего одно быстрое решение» кажется очевидным
- Вы уже попробовали несколько исправлений
- Предыдущее исправление не сработало
- Вы не до конца понимаете суть вопроса

**Не пропускайте, если:**
- Проблема кажется простой (простые ошибки тоже имеют коренные причины)
- Вы спешите (спешка гарантирует переделку)
- Кто-то хочет, чтобы это исправили СЕЙЧАС (систематически быстрее, чем трясти)

## Этап 1: Исследование первопричин

**ПЕРЕД попыткой ЛЮБОГО исправления:**

### 1. Внимательно читайте сообщения об ошибках

- Не пропускайте прошлые ошибки или предупреждения.
- Они часто содержат точное решение
- Полностью прочитать трассировку стека
- Обратите внимание на номера строк, пути к файлам, коды ошибок.

**Действие:** Используйте `read_file` для соответствующих исходных файлов. Используйте `search_files`, чтобы найти строку ошибки в базе кода.

### 2. Создайте тесный цикл обратной связи

- Можете ли вы вызвать точный симптом пользователя с помощью одной команды?
- Команда завершается неудачно из-за этой ошибки и выполняется только после ее исправления?
- Достаточно ли быстро, чтобы бегать неоднократно?
- Это детерминировано? Можете ли вы поднять скорость воспроизведения настолько высоко, чтобы можно было отлаживать ненадежные ошибки?
- Если невозможно воспроизвести → собрать больше данных, не гадать.

**Способы создания цикла — попробуйте примерно в следующем порядке:**

1. **Неудачный тест** на стыке, доходящем до ошибки: модульный, интеграционный или сквозной.
2. **HTTP-скрипт/curl** на работающем сервере разработки.
3. **Вызов CLI** с входными данными, сравнивающий stdout/stderr с ожидаемым выходным сигналом.
4. **Скрипт безголового браузера** (Драматург/Кукловод), утверждающий DOM, консоль или сеть.
5. **Воспроизведите захваченную трассировку**: HAR, полезные данные запроса, журнал событий, сообщение очереди или тело веб-перехватчика.
6. **Одноразовый жгут**, который загружает самый маленький полезный фрагмент системы и вызывает сбойный путь.
7. **Петля свойств/нечеткости**, когда ошибка периодически приводит к неправильному выводу в широком пространстве ввода.
8. **Двухсекционный жгут** подходит для `git bisect run`, когда ошибка появилась между двумя известными состояниями.
9. **Дифференциальный цикл**, сравнивающий старую и новую версии, две конфигурации, двух поставщиков или два набора данных.
10. **Сценарий «человек в цикле»** только в крайнем случае: запишите шаги человека и зафиксируйте их результат, чтобы цикл оставался структурированным.

**Затяните петлю, как только она появится:**

- Сделайте это быстрее: настройка кэша, узкая область действия, пропуск несвязанной инициализации.
- Сделайте сигнал более резким: утверждайте точный симптом, а не общий успех.
- Сделайте его более детерминированным: время закрепления, случайность начального числа, изолируйте файловую систему, заморозьте сеть.

Для недетерминированных ошибок ближайшей целью является более высокая скорость воспроизводства, а не совершенство. Запустите триггер 100 раз, распараллелите, добавьте нагрузку, сузьте временные окна или внедрите спящие режимы. 50%-ная чешуйка поддается отладке; 1% хлопьев обычно нет.

**Действие:** Используйте инструмент `terminal` для выполнения жесткого цикла:

```bash
# Run a specific failing test
pytest tests/test_module.py::test_name -v

# Or run a scripted repro
python scripts/repro_bug.py

# Or run a high-repetition flaky repro
for i in {1..100}; do pytest tests/test_flake.py::test_name -q || break; done
```

### 3. Проверьте последние изменения

- Что изменилось, что могло вызвать это?
- Git diff, последние коммиты
- Новые зависимости, изменения конфигурации

**Действие:**

```bash
# Recent commits
git log --oneline -10

# Uncommitted changes
git diff

# Changes in specific file
git log -p --follow src/problematic_file.py | head -100
```

### 4. Сбор доказательств в многокомпонентных системах

**КОГДА система состоит из нескольких компонентов (API → сервис → база данных, CI → сборка → развертывание):**

**ПРЕЖДЕ ЧЕМ предлагать исправления, добавьте диагностические инструменты:**

Для КАЖДОЙ границы компонента:
- Записывать, какие данные поступают в компонент
- Запишите, какие данные выходят из компонента.
- Проверка распространения среды/конфигурации.
- Проверьте состояние на каждом уровне

Бегите один раз, чтобы собрать доказательства, показывающие, ГДЕ он сломался.
ЗАТЕМ проанализируйте доказательства, чтобы определить неисправный компонент.
ЗАТЕМ исследуйте этот конкретный компонент.

### 5. Отслеживание потока данных

**Ошибка WHEN находится глубоко в стеке вызовов:**

- Откуда берется плохая ценность?
- Что вызвало эту функцию с плохим значением?
- Продолжайте отслеживать вверх по течению, пока не найдете источник.
- Устраняйте источник, а не симптом.

**Действие:** Используйте `search_files` для отслеживания ссылок:

```python
# Find where the function is called
search_files("function_name(", path="src/", file_glob="*.py")

# Find where the variable is set
search_files("variable_name\\s*=", path="src/", file_glob="*.py")
```

### Контрольный список завершения этапа 1

- [ ] Сообщения об ошибках полностью прочитаны и поняты.
- [ ] Команда жесткого цикла существует и была запущена хотя бы один раз.
- [ ] Цикл поддерживает красный цвет: он сообщает о точном симптоме пользователя, а не о ближайшем сбое.
- [ ] Цикл детерминирован, или нестабильная ошибка имеет достаточно высокую скорость воспроизведения для отладки.
- [ ] Недавние изменения выявлены и рассмотрены
- [ ] Собранные доказательства (журналы, состояние, поток данных)
- [ ] Проблема связана с конкретным компонентом/кодом
- [ ] Гипотезы об основных причинах могут быть сформулированы и проверены.

**СТОП:** Не переходите к этапу 2, пока не поймете, ПОЧЕМУ это происходит.

## Этап 2: Анализ закономерностей

**Найдите закономерность, прежде чем исправлять:**

### 0. Минимизируйте воспроизведение

Как только петля станет красной, уменьшите воспроизведение до наименьшего сценария, который все еще горит красным. Вырезайте входные данные, вызывающие объекты, конфигурацию, данные и шаги **по одному**, повторно запуская цикл после каждого сокращения. Оставляйте только то, что является несущим на случай отказа.

При завершении удаления любого оставшегося элемента цикл становится зеленым. Минимальное воспроизведение сужает пространство гипотез и часто становится самым чистым регрессионным тестом.

### 1. Найдите рабочие примеры

- Найдите аналогичный рабочий код в той же базе кода.
- Что работает и похоже на то, что сломано?

**Действие:** Используйте `search_files`, чтобы найти сопоставимые шаблоны:

```python
search_files("similar_pattern", path="src/", file_glob="*.py")
```

### 2. Сравнение со ссылками

- При реализации шаблона ПОЛНОСТЬЮ прочтите эталонную реализацию.
- Не бегло бегло читать каждую строчку.
- Полностью понять рисунок перед применением

### 3. Выявите различия

- Чем отличается работающее от сломанного?
- Перечислите все различия, даже самые незначительные.
- Не думайте, что «это не имеет значения».

### 4. Понимание зависимостей

- Какие еще компоненты для этого нужны?
- Какие настройки, конфиг, окружение?
- Какие предположения это делает?

## Этап 3: гипотеза и проверка

**Научный метод:**

### 1. Формируйте ранжированные фальсифицируемые гипотезы

- Выдвигайте 3–5 правдоподобных гипотез, прежде чем проверять какую-либо одну.
- Ранжируйте их по вероятности и дешевизне фальсификации.
- Сформулируйте прогноз, который дает каждая гипотеза: «Если X является причиной, то изменение или наблюдение Y должно привести к тому, что Z произойдет».
- Отбросьте или уточните любую гипотезу, которая не дает проверяемого прогноза.

Если пользователь присутствует, покажите ранжированный список перед тестированием. У них могут быть знания предметной области, которые мгновенно изменят ее рейтинг. Если пользователь AFK, продолжите ранжирование.

### 2. Тестируйте минимально

- Проверьте гипотезу с самым высоким рейтингом с помощью наименьшего возможного зонда.
- Изменяйте одну переменную за раз.
- Не чините несколько вещей одновременно.
- Предпочитайте проверку отладчика/REPL, если она доступна; одна точка останова лучше десяти журналов.
– Если вы добавляете журналы, пометьте каждую временную строку уникальным префиксом, например `[DEBUG-a4f2]`, чтобы очистка выполнялась за один поиск.

### 3. Проверьте, прежде чем продолжить

- Это сработало? → Этап 4
- Не сработало? → Сформировать НОВУЮ гипотезу
- НЕ добавляйте больше исправлений сверху.

### 4. Когда ты не знаешь

- Скажите: «Я не понимаю X»
- Не притворяйся, что знаешь
- Попросить пользователя о помощи
- Исследуйте больше

## Этап 4: Реализация

**Устраняйте причину, а не симптом:**

### 1. Создайте неудачный тестовый пример

- Простейшее возможное воспроизведение
- Автоматический тест, если это возможно.
- ОБЯЗАТЕЛЬНО иметь перед ремонтом
- Используйте навык `test-driven-development`.

### 2. Внедрение одного исправления

- Устранить выявленную основную причину
- ОДНО изменение за раз
- Никаких улучшений «пока я здесь»
- Никакого комплексного рефакторинга

### 3. Проверьте исправление

```bash
# Run the specific regression test
pytest tests/test_module.py::test_regression -v

# Run full suite — no regressions
pytest tests/ -q
```

### 4. Если исправление не работает — правило трех

- **СТОП.**
- Подсчитайте: сколько исправлений вы попробовали?
- Если &lt; 3. Вернитесь к этапу 1, повторите анализ с новой информацией.
- **Если ≥ 3: ОСТАНОВИТЕСЬ и проверьте архитектуру (шаг 5 ниже)**
- НЕ пытайтесь исправить № 4 без обсуждения архитектуры.

### 5. Если не удалось исправить 3+ исправлений: архитектура вопроса

**Шаблон, указывающий на архитектурную проблему:**
- Каждое исправление показывает новое общее состояние/связь в другом месте.
- Для реализации исправлений требуется «массовый рефакторинг».
- Каждое исправление создает новые симптомы в другом месте.

**СТОП и вопросы к основам:**
- Эта закономерность принципиально обоснована?
- Мы «держимся этого по чистой инерции»?
- Должны ли мы реорганизовать архитектуру или продолжать исправлять симптомы?

**Обсудите с пользователем, прежде чем пытаться исправить ситуацию.**

Это НЕ неудачная гипотеза — это неправильная архитектура.

## Красные флажки — ОСТАНОВИТЕСЬ и следуйте процессу

Если вы поймаете себя на мысли:
- «Пока быстрое решение, разберёмся позже»
- «Просто попробуйте изменить X и посмотрите, сработает ли это»
- «Добавить несколько изменений, запустить тесты»
- «Пропустите тест, я проверю вручную»
- «Наверное, это Х, позвольте мне это исправить»
- «Я не совсем понимаю, но это может сработать»
- «Шаблон говорит X, но я адаптирую его по-другому»
- «Вот основные проблемы: [перечисляет исправления без исследования]»
- Предложение решений перед отслеживанием потока данных.
- **"Еще одна попытка исправления" (когда уже пробовали 2+)**
- **Каждое исправление обнаруживает новую проблему в другом месте**

**ВСЕ это означает: СТОП. Вернитесь к этапу 1.**

**Если не удалось исправить более 3 исправлений:** Проверьте архитектуру (этап 4, шаг 5).

## Распространенные рационализации

| Извините | Реальность |
|--------|---------|
| «Проблема проста, не нужен процесс» | У простых проблем тоже есть коренные причины. Процесс быстрый для простых ошибок. |
| «Чрезвычайная ситуация, нет времени на процесс» | Систематическая отладка происходит БЫСТРЕЕ, чем переборка методом догадок и проверок. |
| «Сначала попробуйте, а потом исследуйте» | Первое исправление устанавливает шаблон. Сделайте это с самого начала. |
| «Я напишу тест после подтверждения работы исправления» | Непроверенные исправления не приживаются. Тест сначала это доказывает. |
| «Несколько исправлений одновременно экономят время» | Не могу выделить то, что сработало. Вызывает новые ошибки. |
| «Ссылка слишком длинная, адаптирую шаблон» | Частичное понимание гарантирует ошибки. Прочтите полностью. |
| «Я вижу проблему, позвольте мне ее решить» | Видеть симптомы ≠ понимать первопричину. |
| «Еще одна попытка исправления» (после 2+ неудач) | 3+ неудачи = архитектурная проблема. Ставьте под сомнение шаблон, не исправляйте его снова. |

## Краткий справочник

| Фаза | Ключевые виды деятельности | Критерии успеха |
|-------|---------------|------------------|
| **1. Основная причина** | Чтение ошибок, воспроизведение, проверка изменений, сбор доказательств, отслеживание потока данных | Понять ЧТО и ПОЧЕМУ |
| **2. Узор** | Найдите рабочие примеры, сравните, выявите различия | Знайте, что отличается |
| **3. Гипотеза** | Теория форм, проверяйте минимум, по одной переменной за раз | Подтвержденная или новая гипотеза |
| **4. Реализация** | Создать регрессионный тест, устранить основную причину, проверить | Ошибка устранена, все тесты пройдены |

## Интеграция агента Гермеса

### Инструменты расследования

Используйте эти инструменты Hermes на этапе 1:

- **`search_files`** — Поиск строк ошибок, отслеживание вызовов функций, обнаружение шаблонов.
- **`read_file`** — Чтение исходного кода с номерами строк для точного анализа.
- **`terminal`** — Запуск тестов, проверка истории git, воспроизведение ошибок
- **`web_search`/`web_extract`** — Сообщения об ошибках исследования, библиотечная документация.

### С делегатом_задачи

Для сложной многокомпонентной отладки отправляйте субагенты расследования:

```python
delegate_task(
    goal="Investigate why [specific test/behavior] fails",
    context="""
    Follow systematic-debugging skill:
    1. Read the error message carefully
    2. Reproduce the issue
    3. Trace the data flow to find root cause
    4. Report findings — do NOT fix yet

    Error: [paste full error]
    File: [path to failing code]
    Test command: [exact command]
    """,
    toolsets=['terminal', 'file']
)
```

### С разработкой через тестирование

При исправлении ошибок:
1. Напишите тест, воспроизводящий ошибку (КРАСНЫЙ).
2. Систематически проводите отладку, чтобы найти основную причину.
3. Устраните основную причину (ЗЕЛЕНЫЙ)
4. Тест подтверждает исправление и предотвращает регресс.

## Влияние на реальный мир

Из сеансов отладки:
- Системный подход: 15-30 минут на исправление
- Случайный подход к исправлениям: 2-3 часа возни.
- Процент исправлений с первого раза: 95% против 40%
- Введены новые ошибки: около нуля против обычных.

** Никаких ярлыков. Никаких догадок. Системность всегда побеждает.**
