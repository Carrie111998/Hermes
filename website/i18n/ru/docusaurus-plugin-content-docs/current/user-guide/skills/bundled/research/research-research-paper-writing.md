# Конвейер написания исследовательских работ

Комплексный конвейер для подготовки готовых к публикации исследовательских работ по ML/AI, ориентированных на **NeurIPS, ICML, ICLR, ACL, AAAI и COLM**. Этот навык охватывает полный жизненный цикл исследования: планирование эксперимента, его проведение, мониторинг, анализ, написание статей, обзор, пересмотр и подачу.

Это **не линейный конвейер** — это итеративный цикл. Результаты запускают новые эксперименты. Отзывы вызывают новый анализ. Агент должен управлять этими циклами обратной связи.

## Когда использовать этот навык

Используйте этот навык, когда:
- **Начинаем новую исследовательскую работу** на основе существующей кодовой базы или идеи.
- **Разработка и проведение экспериментов** для обоснования заявлений на бумаге.
- **Написание или редактирование** любого раздела исследовательской работы.
- **Подготовка к подаче** на конкретную конференцию или семинар.
– **Ответы на отзывы** с дополнительными экспериментами или изменениями.
- **Преобразование** документа между форматами конференции.
- **Написание неэмпирических статей** — теоретических, обзорных, контрольных или позиционных статей (см. [Типы статей за пределами эмпирического машинного обучения](#paper-types-beyond-empiical-ml))
- **Проектирование человеческих оценок** для НЛП, HCI или исследований согласованности.
- **Подготовка результатов после приемки** — плакаты, доклады, релизы кода.

## Основная философия

1. **Будьте активны.** Предлагайте полные черновики, а не вопросы. Ученые заняты: создают что-то конкретное, на что они могут отреагировать, а затем повторяют.
2. **Никогда не галлюцинируйте цитаты.** Частота ошибок в цитатах, созданных искусственным интеллектом, составляет ~40 %. Всегда извлекайте программно. Отметьте непроверяемые цитаты как `[CITATION NEEDED]`.
3. **Статья — это история, а не сборник экспериментов.** В каждой статье необходим один четкий вклад, изложенный в одном предложении. Если вы не можете этого сделать, значит, статья не готова.
4. **Эксперименты служат утверждениям.** В каждом эксперименте должно быть явно указано, какое утверждение он поддерживает. Никогда не проводите эксперименты, которые не связаны с повествованием статьи.
5. **Совершайте транзакции как можно раньше, совершайте их часто.** Каждая завершенная партия экспериментов, каждое обновление черновика документа — фиксируйте с описательными сообщениями. Git log — это история экспериментов.

### Проактивность и сотрудничество

**По умолчанию: будьте активны. Сначала черновик, спросите вместе с черновиком.**

| Уровень уверенности | Действие |
|-----------------|--------|
| **Высокий** (чистое репо, очевидный вклад) | Напишите полный проект, доставьте, доработайте отзывы |
| **Средний** (некоторая двусмысленность) | Написать черновик с отмеченными неопределенностями, продолжить |
| **Низкая** (основные неизвестные) | Задайте 1–2 целевых вопроса через `clarify`, а затем напишите |

| Раздел | Проектировать автономно? | Флаг с проектом |
|---------|-------------------|-----------------|
| Аннотация | Да | «Вклад в рамке X — при необходимости откорректируйте» |
| Введение | Да | «Выделенная проблема Y — исправьте, если не прав» |
| Методы | Да | «Включены детали А, Б, С — дополните недостающие детали» |
| Эксперименты | Да | «Выделенные результаты 1, 2, 3 — при необходимости измените порядок» |
| Связанные работы | Да | «Цитированные статьи X, Y, Z — добавьте все, что я пропустил» |

**Блокировать ввод только в том случае, если**: неясно целевое место проведения, множество противоречивых формулировок, результаты кажутся неполными, имеется явный запрос на предварительное рассмотрение.

## Этап 0: Настройка проекта

**Цель**: создать рабочее пространство, понять существующую работу, определить ее вклад.

### Шаг 0.1: Исследуйте репозиторий

```bash
# Understand project structure
ls -la
find . -name "*.py" | head -30
find . -name "*.md" -o -name "*.txt" | xargs grep -l -i "result\|conclusion\|finding"
```

Ищите:
- `README.md` — обзор проекта и претензии
- `results/`, `outputs/`, `experiments/` — имеющиеся данные
- `configs/` — экспериментальные настройки
- `.bib` файлов — существующие цитаты
- Черновики документов или заметок

### Шаг 0.2: Организуйте рабочее пространство

Создайте последовательную структуру рабочего пространства:

```
workspace/
  paper/               # LaTeX source, figures, compiled PDFs
  experiments/         # Experiment runner scripts
  code/                # Core method implementation
  results/             # Raw experiment results (auto-generated)
  tasks/               # Task/benchmark definitions
  human_eval/          # Human evaluation materials (if needed)
```

### Шаг 0.3. Настройка контроля версий

```bash
git init  # if not already
git remote add origin <repo-url>
git checkout -b paper-draft  # or main
```

**Дисциплина Git**: каждая завершенная партия экспериментов фиксируется с описательным сообщением. Пример:
```
Add Monte Carlo constrained results (5 runs, Sonnet 4.6, policy memo task)
Add Haiku baseline comparison: autoreason vs refinement baselines at cheap model tier
```

### Шаг 0.4: Определите вклад

Прежде чем что-либо писать, сформулируйте:
- **Что**: Чему посвящена эта статья?
- **Почему**: Какие доказательства подтверждают это?
- **И что**: почему читателей это должно волновать?

> Предложите ученому: «Насколько я понимаю, основной вклад заключается в следующем: [одно предложение]. Ключевые результаты показывают [Y]. Это та формулировка, которую вы хотите?»

### Шаг 0.5. Создайте список дел

Используйте инструмент `todo` для создания структурированного плана проекта:

```
Research Paper TODO:
- [ ] Define one-sentence contribution
- [ ] Literature review (related work + baselines)
- [ ] Design core experiments
- [ ] Run experiments
- [ ] Analyze results
- [ ] Write first draft
- [ ] Self-review (simulate reviewers)
- [ ] Revise based on review
- [ ] Submission prep
```

Обновляйте это на протяжении всего проекта. Он служит постоянным состоянием между сеансами.

### Шаг 0.6. Оцените бюджет вычислений

Прежде чем проводить эксперименты, оцените общую стоимость и время:

```
Compute Budget Checklist:
- [ ] API costs: (model price per token) × (estimated tokens per run) × (number of runs)
- [ ] GPU hours: (time per experiment) × (number of experiments) × (number of seeds)
- [ ] Human evaluation costs: (annotators) × (hours) × (hourly rate)
- [ ] Total budget ceiling and contingency (add 30-50% for reruns)
```

Отслеживайте фактические расходы по мере проведения экспериментов:
```python
# Simple cost tracker pattern
import json, os
from datetime import datetime

COST_LOG = "results/cost_log.jsonl"

def log_cost(experiment: str, model: str, input_tokens: int, output_tokens: int, cost_usd: float):
    entry = {
        "timestamp": datetime.now().isoformat(),
        "experiment": experiment,
        "model": model,
        "input_tokens": input_tokens,
        "output_tokens": output_tokens,
        "cost_usd": cost_usd,
    }
    with open(COST_LOG, "a") as f:
        f.write(json.dumps(entry) + "\n")
```

**При ограниченном бюджете**: проведите пилотные эксперименты (1–2 начальных этапа, подмножество задач), прежде чем переходить к полной проверке. Используйте более дешевые модели для отладки конвейеров, а затем переключайтесь на целевые модели для финальных запусков.

### Шаг 0.7: Координация нескольких авторов

Большинство статей имеют от 3 до 10 авторов. Наладьте рабочие процессы заранее:

| Рабочий процесс | Инструмент | Когда использовать |
|----------|------|-------------|
| **На обороте** | На основе браузера | Несколько авторов редактируют одновременно, нет опыта работы с git |
| **Git + LaTeX** | `git` с `.gitignore` для дополнительных файлов | Техническим командам необходима отраслевая проверка |
| **На обороте + синхронизация с Git** | Премиум на обороте | Лучшее из обоих — живая совместная работа с историей версий |

**Владелец раздела**. Назначьте каждый раздел одному основному автору. Другие комментируют, но не редактируют напрямую. Предотвращает конфликты слияния и несогласованность стилей.

```
Author Coordination Checklist:
- [ ] Agree on section ownership (who writes what)
- [ ] Set up shared workspace (Overleaf or git repo)
- [ ] Establish notation conventions (before anyone writes)
- [ ] Schedule internal review rounds (not just at the end)
- [ ] Designate one person for final formatting pass
- [ ] Agree on figure style (colors, fonts, sizes) before creating figures
```

**Соглашения LaTeX, которые необходимо согласовать заранее**:
- Макрос `\method{}` для единообразного именования методов.
– Стиль цитирования: использование `\citet{}` и `\citep{}`.
- Математические обозначения: жирный шрифт строчными буквами для векторов, жирный регистр прописными буквами для матриц и т. д.
- Британское и американское правописание

## Этап 1: Обзор литературы

**Цель**: найти похожие работы, определить исходные данные, собрать цитаты.

### Шаг 1.1: Определите исходную бумагу

Начните с статей, на которые уже есть ссылки в кодовой базе:

```bash
# Via terminal:
grep -r "arxiv\|doi\|cite" --include="*.md" --include="*.bib" --include="*.py"
find . -name "*.bib"
```

### Шаг 1.2: Поиск похожих работ

**Загрузите навык `arxiv`** для поиска структурированной бумаги: `skill_view("arxiv")`. Он обеспечивает поиск по arXiv REST API, графики цитирования Semantic Scholar, профили авторов и генерацию BibTeX.

Используйте `web_search` для широкого поиска, `web_extract` для получения конкретных документов:

```
# Via web_search:
web_search("[main technique] + [application domain] site:arxiv.org")
web_search("[baseline method] comparison ICML NeurIPS 2024")

# Via web_extract (for specific papers):
web_extract("https://arxiv.org/abs/2303.17651")
```

Дополнительные поисковые запросы, которые стоит попробовать:

```
Search queries:
- "[main technique] + [application domain]"
- "[baseline method] comparison"
- "[problem name] state-of-the-art"
- Author names from existing citations
```

**Рекомендуется**: установите **Exa MCP** для академического поиска в режиме реального времени:
```bash
claude mcp add exa -- npx -y mcp-remote "https://mcp.exa.ai/mcp"
```

### Шаг 1.2b: Углубляем поиск (сначала в ширину, затем в глубину)

Плоский поиск (один раунд запросов) обычно упускает из виду важную связанную работу. Используйте итерационный шаблон **ширина, затем глубина**, вдохновленный глубокими исследовательскими конвейерами:

```
Iterative Literature Search:

Round 1 (Breadth): 4-6 parallel queries covering different angles
  - "[method] + [domain]"
  - "[problem name] state-of-the-art 2024 2025"
  - "[baseline method] comparison"
  - "[alternative approach] vs [your approach]"
  → Collect papers, extract key concepts and terminology

Round 2 (Depth): Generate follow-up queries from Round 1 learnings
  - New terminology discovered in Round 1 papers
  - Papers cited by the most relevant Round 1 results
  - Contradictory findings that need investigation
  → Collect papers, identify remaining gaps

Round 3 (Targeted): Fill specific gaps
  - Missing baselines identified in Rounds 1-2
  - Concurrent work (last 6 months, same problem)
  - Key negative results or failed approaches
  → Stop when new queries return mostly papers you've already seen
```

**Когда остановиться**: если в ходе раунда возвращается >80 % статей, уже находящихся в вашей коллекции, значит, поиск перегружен. Обычно 2-3 раундов достаточно. Для обзорных работ ожидайте 4-5 раундов.

**Для рабочих процессов на основе агентов**: параллельно делегируйте запросы каждого раунда через `delegate_task`. Соберите результаты, выполните дедупликацию, а затем сгенерируйте запросы следующего раунда на основе объединенных знаний.

### Шаг 1.3. Проверка каждой цитаты

**НИКОГДА не генерируйте BibTeX из памяти. ВСЕГДА извлекайте программно.**

Для каждой цитаты выполните обязательный пятиэтапный процесс:

```
Citation Verification (MANDATORY per citation):
1. SEARCH → Query Semantic Scholar or Exa MCP with specific keywords
2. VERIFY → Confirm paper exists in 2+ sources (Semantic Scholar + arXiv/CrossRef)
3. RETRIEVE → Get BibTeX via DOI content negotiation (programmatically, not from memory)
4. VALIDATE → Confirm the claim you're citing actually appears in the paper
5. ADD → Add verified BibTeX to bibliography
If ANY step fails → mark as [CITATION NEEDED], inform scientist
```

```python
# Fetch BibTeX via DOI
import requests

def doi_to_bibtex(doi: str) -> str:
    response = requests.get(
        f"https://doi.org/{doi}",
        headers={"Accept": "application/x-bibtex"}
    )
    response.raise_for_status()
    return response.text
```

Если вы не можете проверить цитату:

```latex
\cite{PLACEHOLDER_author2024_verify_this}  % TODO: Verify this citation exists
```

**Всегда говорите ученому**: «Я отметил [X] цитаты как заполнители, требующие проверки».

Полную документацию по API и полный класс `CitationManager` см. в [references/citation-workflow.md](https://github.com/NousResearch/hermes-agent/blob/main/skills/research/research-paper-writing/references/citation-workflow.md).

### Шаг 1.4: Организуйте соответствующую работу

Группируйте статьи по методологии, а не по отдельности:

**Хорошо**: «В одном направлении работы используется предположение X [ссылки], тогда как мы используем предположение Y, потому что…»
**Плохо**: «Смит и др. представили X. Джонс и др. представили Y. Мы объединили оба».

## Этап 2: План эксперимента

**Цель**: разработать эксперименты, которые напрямую подтверждают бумажные утверждения. Каждый эксперимент должен отвечать на конкретный вопрос.

### Шаг 2.1. Сопоставьте претензии с экспериментами

Создайте явное сопоставление:

| Заявить | Эксперимент | Ожидаемые доказательства |
|-------|-----------|-------------------|
| «Наш метод превосходит базовые показатели» | Основное сравнение (Таблица 1) | Процент побед, статистическая значимость |
| «Эффект больше для более слабых моделей» | Исследование масштабирования модели | Кривая монотонного улучшения |
| «Конвергенция требует ограничений объема» | Ограниченный против неограниченного | Сравнение скорости сходимости |

**Правило**: если эксперимент не соответствует заявке, не проводите его.

### Шаг 2.2. Проектирование базовых показателей

Прочные базовые показатели — это то, что отличает принятые статьи от отклоненных. Рецензенты спросят: «А сравнивали ли они с X?»

Стандартные базовые категории:
– **Наивный базовый уровень**: самый простой подход.
- **Надежная база**: наиболее известный из существующих методов.
- **Базовые показатели абляции**: ваш метод минус один компонент.
– **Базовые показатели, соответствующие вычислительным ресурсам**: тот же бюджет вычислительных ресурсов, но другое распределение.

### Шаг 2.3: Определите протокол оценки

Прежде чем что-либо запускать, укажите:
– **Метрики**: что вы измеряете, символы направления (чем выше/ниже, тем лучше).
– **Агрегация**: как результаты объединяются по запускам/задачам.
- **Статистические тесты**: какие тесты установят значимость
– **Объемы выборки**: сколько прогонов/проблем/задач.

### Шаг 2.4. Написание сценариев экспериментов

Следуйте этим шаблонам успешных исследовательских процессов:

**Инкрементное сохранение** — сохраняйте результаты после каждого шага для восстановления после сбоя:
```python
# Save after each problem/task
result_path = f"results/{task}/{strategy}/result.json"
if os.path.exists(result_path):
    continue  # Skip already-completed work
# ... run experiment ...
with open(result_path, 'w') as f:
    json.dump(result, f, indent=2)
```

**Сохранение артефактов** — сохраните все промежуточные результаты:
```
results/<experiment>/
  <task>/
    <strategy>/
      final_output.md          # Final result
      history.json             # Full trajectory
      pass_01/                 # Per-iteration artifacts
        version_a.md
        version_b.md
        critic.md
```

**Разделение задач** — разделяйте генерацию, оценку и визуализацию:
```
run_experiment.py              # Core experiment runner
run_baselines.py               # Baseline comparison
run_comparison_judge.py        # Blind evaluation
analyze_results.py             # Statistical analysis
make_charts.py                 # Visualization
```

См. [references/experiment-patterns.md](https://github.com/NousResearch/hermes-agent/blob/main/skills/research/research-paper-writing/references/experiment-patterns.md) для получения полных шаблонов проектирования, мониторинга cron и устранения ошибок.

### Шаг 2.5: Разработайте человеческую оценку (если применимо)

Многие документы по НЛП, HCI и согласованию требуют человеческой оценки в качестве основного или дополнительного доказательства. Разработайте это перед запуском автоматических экспериментов — оценка с участием человека часто занимает больше времени (утверждение IRB, набор аннотаторов).

**Когда необходима человеческая оценка:**
– Автоматизированные показатели не отражают то, что вас волнует (беглость речи, полезность, безопасность).
- Ваш вклад касается человеческих качеств (читабельность, предпочтения, доверие)
- Рецензенты на площадках НЛП (ACL, EMNLP) ожидают, что это будет для задач генерации.

**Ключевые дизайнерские решения:**

| Решение | Опции | Руководство |
|----------|---------|----------|
| **Тип аннотатора** | Эксперт, краудворкер, конечный пользователь | Соответствуйте тому, что требуется для ваших претензий |
| **Масштаб** | Лайкерт (1-5), парное сравнение, рейтинг | Попарный метод более надежен, чем Лайкерт, для выходных данных LLM |
| **Объем выборки** | По аннотаторам и общему количеству элементов | Анализ мощности или минимум 100 элементов, 3+ аннотатора |
| **Показатель соглашения** | Каппа Коэна, альфа Криппендорфа, ICC | Альфа Криппендорфа для >2 аннотаторов; также сообщить о необработанном соглашении |
| **Платформа** | Prolific, MTurk, внутренняя команда | Плодовитый по качеству; MTurk для масштаба; внутренняя экспертиза предметной области |

**Контрольный список рекомендаций по аннотациям:**
```
- [ ] Clear task description with examples (good AND bad)
- [ ] Decision criteria for ambiguous cases
- [ ] At least 2 worked examples per category
- [ ] Attention checks / gold standard items (10-15% of total)
- [ ] Qualification task or screening round
- [ ] Estimated time per item and fair compensation (>= local minimum wage)
- [ ] IRB/ethics review if required by your institution
```

**Требования к отчетности** (рецензенты проверяют все это):
- Количество аннотаторов и их квалификация
- Соглашение между аннотаторами с конкретной метрикой и значением.
- Детали компенсации (сумма, ориентировочная почасовая ставка)
- Описание интерфейса аннотации или скриншот (приложение)
- Общее время аннотации

См. [references/human-evaluation.md](https://github.com/NousResearch/hermes-agent/blob/main/skills/research/research-paper-writing/references/human-evaluation.md) для получения полного руководства, включая статистические тесты для данных оценки человека, схемы краудсорсингового контроля качества и рекомендации IRB.

## Этап 3: Проведение эксперимента и мониторинг

**Цель**: надежно проводить эксперименты, отслеживать ход выполнения и восстанавливаться после сбоев.

### Шаг 3.1. Запуск экспериментов

Используйте `nohup` для длительных экспериментов:

```bash
nohup python run_experiment.py --config config.yaml > logs/experiment_01.log 2>&1 &
echo $!  # Record the PID
```

**Параллельное выполнение**. Запускайте независимые эксперименты одновременно, но помните об ограничениях скорости API. Более 4 одновременных экспериментов с одним и тем же API замедлят работу каждого из них.

### Шаг 3.2. Настройка мониторинга (шаблон Cron)

Для длительных экспериментов настройте периодические проверки статуса. Приглашение cron должно соответствовать следующему шаблону:

```
Monitor Prompt Template:
1. Check if process is still running: ps aux | grep <pattern>
2. Read last 30 lines of log: tail -30 <logfile>
3. Check for completed results: ls <result_dir>
4. If results exist, read and report: cat <result_file>
5. If all done, commit: git add -A && git commit -m "<descriptive message>" && git push
6. Report in structured format (tables with key metrics)
7. Answer the key analytical question for this experiment
```

**Тихий режим**: если с момента последней проверки ничего не изменилось, ответьте `[SILENT]`, чтобы отключить уведомление пользователя. Сообщайте только тогда, когда есть новости.

### Шаг 3.3: Обработка сбоев

Распространенные режимы отказа и восстановление:

| Неудача | Обнаружение | Восстановление |
|---------|-----------|----------|
| Ограничение ставки API / исчерпание кредита | Ошибки 402/429 в логах | Подождите, затем запустите заново (скрипты пропускают завершенную работу) |
| Сбой процесса | PID пропал, результаты неполные | Перезапуск с последней контрольной точки |
| Тайм-аут на сложные задачи | Процесс завис, нет прогресса в журнале | Убить и пропустить, отметить в результатах |
| Неправильный идентификатор модели | Ошибки со ссылкой на название модели | Исправить идентификатор и повторить запуск |

**Ключ**: сценарии всегда должны проверять существующие результаты и пропускать завершенную работу. Это делает повторные запуски безопасными и эффективными.

### Шаг 3.4: Зафиксируйте завершенные результаты

После завершения каждой серии экспериментов:

```bash
git add -A
git commit -m "Add <experiment name>: <key finding in 1 line>"
git push
```

### Шаг 3.5: Ведите журнал экспериментов

Git-коммиты отслеживают то, что произошло, но не **дерево исследований** — решения о том, что попробовать дальше, основанные на том, что вы узнали. Ведите структурированный журнал экспериментов, в котором записано это дерево:

```json
// experiment_journal.jsonl — append one entry per experiment attempt
{
  "id": "exp_003",
  "parent": "exp_001",
  "timestamp": "2025-05-10T14:30:00Z",
  "hypothesis": "Adding scope constraints will fix convergence failure from exp_001",
  "plan": "Re-run autoreason with max_tokens=2000 and fixed structure template",
  "config": {"model": "haiku", "strategy": "autoreason", "max_tokens": 2000},
  "status": "completed",
  "result_path": "results/exp_003/",
  "key_metrics": {"win_rate": 0.85, "convergence_rounds": 3},
  "analysis": "Scope constraints fixed convergence. Win rate jumped from 0.42 to 0.85.",
  "next_steps": ["Try same constraints on Sonnet", "Test without structure template"],
  "figures": ["figures/exp003_convergence.pdf"]
}
```

**Почему журнал, а не просто git?** Git отслеживает изменения файлов. В журнале отслеживаются рассуждения: почему вы попробовали X, что вы узнали и что это означает для следующего эксперимента. При написании статьи это дерево имеет неоценимое значение для раздела «Методы» («мы наблюдали X, что мотивировало Y») и для честного отчета об ошибках.

**Выбор лучшего пути**: когда в журнале отображается ветвящееся дерево (exp_001 → exp_002a, exp_002b, exp_003), определите путь, который лучше всего поддерживает утверждения статьи. Задокументируйте тупиковые ветви в приложении как абляцию или отрицательные результаты.

**Код моментального снимка для каждого эксперимента**: копируйте сценарий эксперимента после каждого запуска:
```bash
cp experiment.py results/exp_003/experiment_snapshot.py
```
Это обеспечивает точное воспроизведение даже после последующих изменений кода.

## Этап 4: Анализ результатов

**Цель**: извлечь результаты, вычислить статистику, определить историю.

### Шаг 4.1: Обобщение результатов

Напишите сценарии анализа, которые:
1. Загрузите все файлы результатов из пакета.
2. Вычисление показателей для каждой задачи и совокупных показателей.
3. Создайте сводные таблицы

```python
# Standard analysis pattern
import json, os
from pathlib import Path

results = {}
for result_file in Path("results/").rglob("result.json"):
    data = json.loads(result_file.read_text())
    strategy = result_file.parent.name
    task = result_file.parent.parent.name
    results.setdefault(strategy, {})[task] = data

# Compute aggregate metrics
for strategy, tasks in results.items():
    scores = [t["score"] for t in tasks.values()]
    print(f"{strategy}: mean={np.mean(scores):.1f}, std={np.std(scores):.1f}")
```

### Шаг 4.2: Статистическая значимость

Всегда вычисляйте:
- **Планы погрешностей**: стандартное отклонение или стандартная ошибка, укажите, какая именно.
- **Доверительные интервалы**: 95 % ДИ для ключевых результатов.
- **Парные тесты**: тест Макнемара для сравнения двух методов.
- **Размеры эффекта**: d или h Коэна для практической значимости.

См. [references/experiment-patterns.md](https://github.com/NousResearch/hermes-agent/blob/main/skills/research/research-paper-writing/references/experiment-patterns.md) для получения полных реализаций теста Макнемара, самозагруженных CI и h Коэна.

### Шаг 4.3: Определите историю

После анализа четко ответьте:
1. **Какой основной вывод?** Сформулируйте его в одном предложении.
2. **Что вас удивило?** Неожиданные результаты часто становятся лучшими статьями.
3. **Что не удалось?** Неудачные эксперименты могут быть наиболее информативными. Честное сообщение о неудачах укрепляет газету.
4. **Какие дополнительные эксперименты необходимы?** Результаты часто вызывают новые вопросы.

#### Обработка отрицательных или нулевых результатов

Если ваша гипотеза неверна или результаты неубедительны, у вас есть три варианта:

| Ситуация | Действие | Место проведения |
|-----------|--------|-----------|
| Гипотеза неверна, но вопрос **почему** информативен | Документ в рамке вокруг анализа причин | NeurIPS, ICML (при строгом анализе) |
| Метод не превосходит базовые показатели, но **открывает что-то новое** | Переосмыслить вклад как понимание/анализ | ICLR (понимание ценностей), материалы семинара |
| Чистый отрицательный результат по популярному заявлению | Напишите это — поле должно знать | Наборы данных и тесты NeurIPS, TMLR, семинары |
| Результаты неубедительны, нет ясной истории | Pivot — проведите различные эксперименты или переосмыслите | Не заставляйте бумагу, которой нет |

**Как написать документ об отрицательных результатах:**
- Руководствуйтесь тем, во что верит сообщество, и почему важно это проверить.
- Опишите свою строгую методологию (должна быть герметичной — рецензенты будут более тщательно проверять)
- Четко представить нулевой результат со статистическими данными.
- Проанализируйте, **почему** ожидаемый результат не был достигнут.
- Обсудить последствия для данной области.

**Площадки, которые явно приветствуют отрицательные результаты**: NeurIPS (наборы данных и контрольные показатели), TMLR, ML Reproducibility Challenge, семинары на крупных конференциях. Некоторые семинары специально требуют отрицательных результатов.

## Итеративное уточнение: выбор стратегии

Любой результат в этом конвейере — черновики документов, сценарии экспериментов, анализ — можно итеративно уточнять. Исследование автопричин дает эмпирические доказательства того, когда каждая стратегия уточнения работает, а когда терпит неудачу. Используйте этот раздел, чтобы выбрать правильный подход.

### Таблица быстрых решений

| Ваша ситуация | Стратегия | Почему |
|---------------|----------|-----|
| Модель среднего уровня + ограниченная задача | **Авторазум** | Сладкое место. Разрыв в оценках поколений самый большой. Базовые линии активно разрушают слабые результаты модели. |
| Модель среднего уровня + открытая задача | **Автообоснование** с добавленными ограничениями области | Добавьте фиксированные факты, структуру или результаты, чтобы ограничить пространство улучшений. |
| Пограничная модель + задача с ограничениями | **Авторазум** | Выигрывает 2/3 ограниченных задач даже на границе. |
| Модель Frontier + неограниченная задача | **Критика и пересмотр** или **один проход** | Авторазум идет последним. Модель самооценивает достаточно хорошо. |
| Конкретное техническое задание (проектирование системы) | **Критика и пересмотр** | Прямой цикл поиска и исправления более эффективен. |
| Задание на заполнение шаблона (одна правильная структура) | **Один проход** или **консервативный** | Минимальное пространство для принятия решений. Итерация не добавляет никакой ценности. |
| Код с тест-кейсами | **Автопричина (вариант кода)** | Структурированный анализ *почему* это не удалось, прежде чем исправлять. Скорость восстановления 62% против 43%. |
| Очень слабая модель (класс Лама 8Б) | **Один проход** | Модель слишком слаба для разных кандидатов. Инвестируйте в качество генерации. |

### Разрыв в оценках поколений

**Основная идея**: ценность Autoreason зависит от разрыва между способностью модели генерировать данные и ее способностью самооценки.

<!-- ascii-guard-ignore -->
```
Model Tier        │ Generation │ Self-Eval │ Gap    │ Autoreason Value
──────────────────┼────────────┼───────────┼────────┼─────────────────
Weak (Llama 8B)   │ Poor       │ Poor      │ Small  │ None — can't generate diverse candidates
Mid (Haiku 3.5)   │ Decent     │ Poor      │ LARGE  │ MAXIMUM — 42/42 perfect Borda
Mid (Gemini Flash)│ Decent     │ Moderate  │ Large  │ High — wins 2/3
Strong (Sonnet 4) │ Good       │ Decent    │ Medium │ Moderate — wins 3/5
Frontier (S4.6)   │ Excellent  │ Good      │ Small  │ Only with constraints
```
<!-- ascii-guard-ignore-end -->

Этот разрыв носит структурный, а не временный характер. По мере снижения затрат сегодняшняя граница завтра становится промежуточным уровнем. Золотая середина движется, но никогда не исчезает.

### Цикл автопричин (сводка)

Каждый проход создает трех кандидатов из свежих изолированных агентов:

1. **Критик** → находит проблемы у действующего президента А (без исправлений)
2. **Автор Б** → пересматривает А на основе критики.
3. **Синтезатор** → объединяет A и B (случайные метки)
4. **Судейская коллегия** → 3 слепых судьи ЦТ ранга A, B, AB по подсчету Борда.
5. **Сходимость** → А выигрывает k=2 последовательных передачи → готово

**Основные параметры:**
- конвергенция k=2 (k=1 преждевременно, k=3 слишком дорого, нет прироста качества)
- Судьи CoT всегда (сходимость в 3 раза быстрее)
- Температура 0,8 авторов, 0,3 судей
- Консервативный тай-брейк: действующий президент выигрывает вничью
- Каждая роль — это новый агент без общего контекста.

### Применение к бумажным черновикам

При доработке самой статьи через автопричину:
- **Предоставьте критику основную информацию**: фактические экспериментальные данные, результаты в формате JSON, статистические данные. Без этого модели галлюцинируют сфабрикованные исследования абляции и подделывают доверительные интервалы.
- **Используйте минимум 3 рабочих судьи**: сломанный анализатор судей не добавляет шума — он полностью нарушает равновесие.
- **Ограничение объема пересмотра**: «Устранить эти конкретные недостатки», а не «улучшить статью».

### Режимы отказа

| Неудача | Обнаружение | Исправить |
|---------|-----------|-----|
| Нет сближения (А никогда не побеждает) | А выигрывает &lt;15% за 20+ передач | Добавьте ограничения области действия к задаче |
| Синтез дрейфа | Количество слов растет безгранично | Ограничить структуру и результат |
| Деградация ниже одного прохода | Базовые показатели оцениваются выше, чем повторные результаты | Переключиться на одиночный проход; модель может быть слишком слабой |
| Переоснащение (код) | Высокий уровень прохождения публичного теста, низкий уровень прохождения частного теста | Используйте структурированный анализ, а не просто проверяйте обратную связь |
| Сломанные судьи | Ошибки синтаксического анализа уменьшают количество панелей ниже 3 | Прежде чем продолжить, исправьте парсер |

См. [references/autoreason-methodology.md](https://github.com/NousResearch/hermes-agent/blob/main/skills/research/research-paper-writing/references/autoreason-methodology.md) для получения полных подсказок, подробностей оценки Borda, руководства по выбору модели, шаблонов проектирования ограничений объема и справки по расчету бюджета.

## Этап 6: Самопроверка и пересмотр

**Цель**: смоделировать процесс проверки перед отправкой. Выявляйте слабые места заранее.

### Шаг 6.1: Моделирование отзывов (шаблон ансамбля)

Создавайте обзоры с разных точек зрения. Ключевой вывод из автоматизированных исследовательских конвейеров (в частности, AI-Scientist от SakanaAI): **комплексное рецензирование с помощью мета-рецензента дает гораздо более выверенную обратную связь, чем одиночный проход рецензирования.**

**Шаг 1. Создайте N независимых отзывов** (N=3–5)

Используйте разные модели или настройки температуры. Каждый рецензент видит только статью, а не другие рецензии. **По умолчанию отрицательная предвзятость** — LLM имеют хорошо задокументированную положительную предвзятость в оценке.

```
You are an expert reviewer for [VENUE]. You are critical and thorough.
If a paper has weaknesses or you are unsure about a claim, flag it clearly
and reflect that in your scores. Do not give the benefit of the doubt.

Review this paper according to the official reviewer guidelines. Evaluate:

1. Soundness (are claims well-supported? are baselines fair and strong?)
2. Clarity (is the paper well-written? could an expert reproduce it?)
3. Significance (does this matter to the community?)
4. Originality (new insights, not just incremental combination?)

Provide your review as structured JSON:
{
  "summary": "2-3 sentence summary",
  "strengths": ["strength 1", "strength 2", ...],
  "weaknesses": ["weakness 1 (most critical)", "weakness 2", ...],
  "questions": ["question for authors 1", ...],
  "missing_references": ["paper that should be cited", ...],
  "soundness": 1-4,
  "presentation": 1-4,
  "contribution": 1-4,
  "overall": 1-10,
  "confidence": 1-5
}
```

**Шаг 2: Мета-обзор (объединение региональных председателей)**

Передайте все N обзоров мета-рецензенту:

```
You are an Area Chair at [VENUE]. You have received [N] independent reviews
of a paper. Your job is to:

1. Identify consensus strengths and weaknesses across reviewers
2. Resolve disagreements by examining the paper directly
3. Produce a meta-review that represents the aggregate judgment
4. Use AVERAGED numerical scores across all reviews

Be conservative: if reviewers disagree on whether a weakness is serious,
treat it as serious until the authors address it.

Reviews:
[review_1]
[review_2]
...
```

**Шаг 3: Цикл размышлений** (по желанию, 2–3 раунда)

Каждый рецензент может уточнить свой обзор после просмотра мета-обзора. Используйте сигнал досрочного завершения: если рецензент отвечает: «Я закончил» (без изменений), прекратите итерацию.

**Выбор модели для рецензирования**. Рецензирование лучше всего проводить с использованием самой надежной доступной модели, даже если вы писали статью, используя более дешевую модель. Модель рецензента следует выбирать независимо от модели письма.

**Калибровка по нескольким кадрам**. Если возможно, включите в качестве примера 1–2 реальных опубликованных обзора с целевой площадки. Это значительно улучшает калибровку оценок. Примеры обзоров см. в [references/reviewer-guidelines.md](https://github.com/NousResearch/hermes-agent/blob/main/skills/research/research-paper-writing/references/reviewer-guidelines.md).

### Шаг 6.1b: Проход визуальной проверки (VLM)

В текстовом обзоре упускается из виду целый класс проблем: качество рисунков, проблемы с версткой, визуальная последовательность. Если у вас есть доступ к модели с возможностью машинного зрения, запустите отдельную **визуальную проверку** скомпилированного PDF-файла:

```
You are reviewing the visual presentation of this research paper PDF.
Check for:
1. Figure quality: Are plots readable? Labels legible? Colors distinguishable?
2. Figure-caption alignment: Does each caption accurately describe its figure?
3. Layout issues: Orphaned section headers, awkward page breaks, figures far from their references
4. Table formatting: Aligned columns, consistent decimal precision, bold for best results
5. Visual consistency: Same color scheme across all figures, consistent font sizes
6. Grayscale readability: Would the figures be understandable if printed in B&W?

For each issue, specify the page number and exact location.
```

Это позволяет выявить проблемы, с которыми не может справиться текстовый обзор: график с неразборчивыми метками осей, рисунок, расположенный на расстоянии трех страниц от первой ссылки, несовместимые цветовые палитры между рисунками 2 и 5 или таблица, ширина которой явно превышает ширину столбца.

### Шаг 6.1c: Получите пропуск проверки

После смоделированных проверок запустите отдельный этап проверки. Это выявляет фактические ошибки, которые рецензенты могут пропустить:

```
Claim Verification Protocol:
1. Extract every factual claim from the paper (numbers, comparisons, trends)
2. For each claim, trace it to the specific experiment/result that supports it
3. Verify the number in the paper matches the actual result file
4. Flag any claim without a traceable source as [VERIFY]
```

Для рабочих процессов с участием агента: делегируйте проверку **новому субагенту**, который получает только бумажный текст и файлы необработанных результатов. Свежий контекст предотвращает предвзятость подтверждения — проверяющий не «помнит», какими должны были быть результаты.

### Шаг 6.2: Приоритизация обратной связи

Собрав отзывы, классифицируйте:

| Приоритет | Действие |
|----------|--------|
| **Критический** (техническая ошибка, отсутствие базовой линии) | Надо исправить. Могут потребоваться новые эксперименты → назад к Фазе 2 |
| **Высокая** (проблема с ясностью, отсутствие абляции) | Должно исправить в этой версии |
| **Средний** (незначительные проблемы с письмом, дополнительные эксперименты) | Исправьте, если позволяет время |
| **Низкий** (стилевые предпочтения, косвенные предложения) | Примечание для будущей работы |

### Шаг 6.3: Цикл пересмотра

По каждой критической/важной проблеме:
1. Определите конкретные разделы, которые были затронуты
2. Напишите исправление
3. Убедитесь, что исправление не нарушает другие претензии.
4. Обновите статью
5. Повторная проверка на предмет беспокойства рецензента.

### Шаг 6.4: Написание опровержения

При ответе на реальные отзывы (после отправки) опровержение — это навык, отличный от навыка редактирования:

**Формат**: По пунктам. По каждому вопросу рецензента:
```
> R1-W1: "The paper lacks comparison with Method X."

We thank the reviewer for this suggestion. We have added a comparison with 
Method X in Table 3 (revised). Our method outperforms X by 3.2pp on [metric] 
(p<0.05). We note that X requires 2x our compute budget.
```

**Правила**:
- Решите все проблемы: рецензенты заметят, если вы пропустите одну из них.
- Лидер с самыми сильными ответами
- Будьте краткими и прямыми: рецензенты прочитали десятки опровержений.
– Включите новые результаты, если вы проводили эксперименты в период опровержения.
- Никогда не защищайтесь и не пренебрегайте даже слабой критикой.
– Используйте `latexdiff` для создания размеченного PDF-файла с изменениями (см. раздел «Профессиональные инструменты LaTeX»).
– Благодарите рецензентов за конкретные, действенные отзывы (а не за общие похвалы).

**Чего НЕ следует делать**: «Мы с уважением не согласны» без доказательств. «Это выходит за рамки» без объяснения причин. Игнорирование слабостей, реагирование только на сильные стороны.

**Цель**: окончательная проверка, форматирование и отправка.

### Шаг 7.1: Контрольный список конференции

На каждом объекте есть обязательные чек-листы. Заполняйте их внимательно: неполные контрольные списки могут привести к отказу от рассмотрения.

См. [references/checklists.md](https://github.com/NousResearch/hermes-agent/blob/main/skills/research/research-paper-writing/references/checklists.md), чтобы узнать:
- Контрольный список NeurIPS из 16 пунктов
- ICML более широкое воздействие + воспроизводимость
- Политика раскрытия информации ICLR LLM
- Раздел обязательных ограничений ACL
- Универсальный контрольный список перед подачей

### Шаг 7.2: Контрольный список анонимизации

Двойное слепое рецензирование означает, что рецензенты не могут знать, кто написал статью. Проверьте ВСЕ из них:

```
Anonymization Checklist:
- [ ] No author names or affiliations anywhere in the PDF
- [ ] No acknowledgments section (add after acceptance)
- [ ] Self-citations written in third person: "Smith et al. [1] showed..." not "We previously showed [1]..."
- [ ] No GitHub/GitLab URLs pointing to your personal repos
- [ ] Use Anonymous GitHub (https://anonymous.4open.science/) for code links
- [ ] No institutional logos or identifiers in figures
- [ ] No file metadata containing author names (check PDF properties)
- [ ] No "our previous work" or "in our earlier paper" phrasing
- [ ] Dataset names don't reveal institution (rename if needed)
- [ ] Supplementary materials don't contain identifying information
```

**Распространенные ошибки**: сообщения о коммитах Git, видимые в дополнительном коде, цифры с водяными знаками из институциональных инструментов, благодарности, оставшиеся от предыдущего черновика, препринт arXiv, опубликованный до периода анонимности.

### Шаг 7.3: Проверка форматирования

```
Pre-Submission Format Check:
- [ ] Page limit respected (excluding references and appendix)
- [ ] All figures are vector (PDF) or high-res raster (600 DPI PNG)
- [ ] All figures readable in grayscale
- [ ] All tables use booktabs
- [ ] References compile correctly (no "?" in citations)
- [ ] No overfull hboxes in critical areas
- [ ] Appendix clearly labeled and separated
- [ ] Required sections present (limitations, broader impact, etc.)
```

### Шаг 7.4: Проверка перед компиляцией

Запустите эти автоматические проверки **перед** попыткой `pdflatex`. Обнаружение ошибок здесь происходит быстрее, чем отладка вывода компилятора.

```bash
# 1. Lint with chktex (catches common LaTeX mistakes)
# Suppress noisy warnings: -n2 (sentence end), -n24 (parens), -n13 (intersentence), -n1 (command terminated)
chktex main.tex -q -n2 -n24 -n13 -n1

# 2. Verify all citations exist in .bib
# Extract \cite{...} from .tex, check each against .bib
python3 -c "
import re
tex = open('main.tex').read()
bib = open('references.bib').read()
cites = set(re.findall(r'\\\\cite[tp]?{([^}]+)}', tex))
for cite_group in cites:
    for cite in cite_group.split(','):
        cite = cite.strip()
        if cite and cite not in bib:
            print(f'WARNING: \\\\cite{{{cite}}} not found in references.bib')
"

# 3. Verify all referenced figures exist on disk
python3 -c "
import re, os
tex = open('main.tex').read()
figs = re.findall(r'\\\\includegraphics(?:\[.*?\])?{([^}]+)}', tex)
for fig in figs:
    if not os.path.exists(fig):
        print(f'WARNING: Figure file not found: {fig}')
"

# 4. Check for duplicate \label definitions
python3 -c "
import re
from collections import Counter
tex = open('main.tex').read()
labels = re.findall(r'\\\\label{([^}]+)}', tex)
dupes = {k: v for k, v in Counter(labels).items() if v > 1}
for label, count in dupes.items():
    print(f'WARNING: Duplicate label: {label} (appears {count} times)')
"
```

Прежде чем продолжить, устраните все предупреждения. Для рабочих процессов на основе агента: верните выходные данные chktex обратно агенту с инструкциями по внесению минимальных исправлений.

### Шаг 7.5: Окончательная компиляция

```bash
# Clean build
rm -f *.aux *.bbl *.blg *.log *.out *.pdf
latexmk -pdf main.tex

# Or manual (triple pdflatex + bibtex for cross-references)
pdflatex -interaction=nonstopmode main.tex
bibtex main
pdflatex -interaction=nonstopmode main.tex
pdflatex -interaction=nonstopmode main.tex

# Verify output exists and has content
ls -la main.pdf
```

**Если компиляция не удалась**: проанализируйте файл `.log` на наличие первой ошибки. Общие исправления:
- «Неопределенная последовательность управления» → отсутствует пакет или опечатка в названии команды.
- «Отсутствует $ вставлен» → математический символ вне математического режима.
- «Файл не найден» → неверный путь к фигуре или отсутствует файл .sty.
- «Цитирование не определено» → запись .bib отсутствует или bibtex не запускается.

### Шаг 7.6: Требования, специфичные для конференции

| Место проведения | Особые требования |
|-------|---------------------|
| **НейриПС** | Бумажный контрольный список в приложении, краткое изложение, если принято |
| **ИКМЛ** | Более широкое заявление о воздействии (после заключения не учитывается при расчете лимита) |

### Шаг 7.7: Повторная отправка конференции и преобразование формата

При преобразовании между площадками **никогда не копируйте преамбулы LaTeX между шаблонами**:

```bash
# 1. Start fresh with target template
cp -r templates/icml2026/ new_submission/

# 2. Copy ONLY content sections (not preamble)
#    - Abstract text, section content, figures, tables, bib entries

# 3. Adjust for page limits
# 4. Add venue-specific required sections
# 5. Update references
```

| Откуда → Куда | Изменение страницы | Ключевые изменения |
|-----------|-------------|-----------------|
| НейрИПС → ICML | 9 → 8 | Вырезать 1 страницу, добавить более широкое воздействие |
| ICML → ICLR | 8 → 9 | Расширьте эксперименты, добавьте раскрытие информации о LLM |
| НейрИПС → ACL | 9 → 8 | Реструктуризация соглашений НЛП, добавление ограничений |
| ICLR → АААИ | 9 → 7 | Значительные сокращения, строгое соблюдение стиля |
| Любой → КОЛМ | варьируется → 9 | Рефрейминг для фокуса на языковой модели |

При обрезке страниц: переместите корректуру в приложение, сократите связанную работу, объедините таблицы, используйте подрисунки.
При расширении: добавьте абляцию, расширьте ограничения, включите дополнительные базовые показатели, добавьте качественные примеры.

**После отклонения**: устраните проблемы рецензента в новой версии, но не включайте раздел «изменения» и не ссылайтесь на предыдущую отправку (слепая рецензия).

```
Camera-Ready Checklist:

- [ ] Add Acknowledgments section (funding, compute grants, helpful reviewers)
- [ ] Add public code/data URL (real GitHub, not anonymous)
```

### Шаг 7.9: стратегия arXiv и препринтов

Публикация сообщений в arXiv является стандартной практикой в машинном обучении, но требует соблюдения сроков и анонимности.

**Дерево временных решений:**

| Ситуация | Рекомендация |
|-----------|----------------|
| Отправка в двойное слепое исследование (NeurIPS, ICML, ACL) | Публикуйте в arXiv **после** срока подачи, а не раньше. Публикация ранее может технически нарушать политику анонимности, хотя меры по обеспечению соблюдения могут различаться. |
| Отправка в ICLR | ICLR явно разрешает публикацию arXiv перед отправкой. Но не указывайте имена авторов в самой заявке. |
| Статья уже на arXiv и отправляется на новое место | Приемлемо в большинстве заведений. НЕ обновляйте версию arXiv во время проверки, внося изменения, относящиеся к обзорам. |
| Мастерская бумаги | arXiv подойдет в любое время — семинары обычно не проводятся двойным слепым методом. |
| Хотите установить приоритет | Публикуйте немедленно, если вас беспокоит скупка информации, но примите компромисс с анонимностью. |

**Выбор категории arXiv** (документы по ML/AI):

| Категория | Код | Лучшее для |
|----------|------|----------|
| Машинное обучение | `cs.LG` | Общие методы машинного обучения |
| Вычисления и язык | `cs.CL` | НЛП, языковые модели |
| Искусственный интеллект | `cs.AI` | Рассуждение, планирование, агенты |
| Компьютерное зрение | `cs.CV` | Модели зрения |
| Информационный поиск | `cs.IR` | Поиск, рекомендации |

**Укажите основные + 1–2 категории из перекрестного списка.** Больше категорий = больше видимости, но добавляйте в перекрестный список только там, где это действительно актуально.

## Этап 8: Результаты после приемки

**Цель**: максимально повысить эффективность принятой вами статьи с помощью презентационных материалов и взаимодействия с сообществом.

### Шаг 8.1: Плакат конференции

Большинство конференций требуют стендовой сессии. Принципы оформления плаката:

| Элемент | Руководство |
|---------|-----------|
| **Размер** | Проверьте требования к месту проведения (обычно 24 x 36 дюймов или A0 книжная/альбомная ориентация) |
| **Содержание** | Название, авторы, вклад в 1 предложение, методическая схема, 2–3 ключевых результата, заключение |
| **Поток** | Слева сверху вниз справа (Z-образец) или столбчатый |
| **Текст** | Название читается с расстояния 3 м, текст — с 1 м. Никаких полных абзацев — только пункты. |
| **Цифры** | Повторно используйте бумажные фигурки в более высоком разрешении. Увеличить ключевой результат. |

**Инструменты**: LaTeX (пакет `beamerposter`), PowerPoint/Keynote, Figma, Canva.

**Производство**: Заказ за 2+ недели до конференции. Плакаты из ткани легче путешествовать. Многие конференции теперь поддерживают виртуальные/цифровые плакаты.

### Шаг 8.2: Выступление на конференции/В центре внимания

Если будет вручена устная презентация или презентация:

| Тип разговора | Продолжительность | Содержание |
|-----------|----------|---------|
| **В центре внимания** | 5 мин | Проблема, подход, один ключевой результат. Репетируйте ровно 5 минут. |
| **Оральный** | 15-20 мин | Полная история: проблема, подход, ключевые результаты, абляция, ограничения. |
| **Выступление на семинаре** | 10-15 мин | Адаптируйтесь в зависимости от аудитории семинара — возможно, потребуется дополнительная информация. |

**Правила оформления слайдов:**
- Одна идея на слайд
- Минимизируйте текст — говорите детали, а не проецируйте их.
- Анимируйте ключевые фигуры, чтобы шаг за шагом добиться понимания
– В конце добавьте слайд с выводами (вклад в одно предложение).
- Подготовьте резервные слайды для ожидаемых вопросов.

### Шаг 8.3: Публикация в блоге/социальные сети

Доступное резюме значительно повышает эффективность:

- **Твиттер/X**: 5–8 твитов. Руководствуйтесь результатом, а не методом. Включите рисунок 1 и ключевой показатель результата.
– **Сообщение в блоге**: 800–1500 слов. Написано для практиков ОД, а не для рецензентов. Откажитесь от формализма, подчеркните интуицию и практический смысл.
- **Страница проекта**: HTML-страница с аннотацией, рисунками, демонстрацией, ссылкой на код, BibTeX. Используйте страницы GitHub.

**Время**: Опубликуйте в течение 1–2 дней после появления статьи о слушаниях или готовности камеры arXiv.

## Семинар и короткие статьи

Документы семинаров и короткие статьи (например, короткие статьи ACL, статьи с результатами) следуют одному и тому же алгоритму, но с разными ограничениями и ожиданиями.

### Документы семинара

| Недвижимость | Мастерская | Основная конференция |
|----------|----------|-----------------|
| **Ограничение количества страниц** | 4-6 страниц (обычно) | 7-9 страниц |
| **Стандарт обзора** | Нижняя планка для полноты | Должно быть полным, тщательным |
| **Процесс проверки** | Обычно одинарный слепой или упрощенный обзор | Двойной слепой, строгий |
| **Что ценно** | Интересные идеи, предварительные результаты, позиции | Полная эмпирическая история с убедительными исходными данными |
| **arXiv** | Публикуйте в любое время | Время имеет значение (см. стратегию arXiv) |
| **Панель вкладов** | Новое направление, интересный отрицательный результат, работа в разработке | Значительный прогресс с убедительными доказательствами |

**Когда лучше ориентироваться на семинар:**
- Идея на ранней стадии, по которой вы хотите получить обратную связь до написания полноценной статьи.
- Отрицательный результат, не оправдывающий 8+ страниц.
- Позиция статьи или мнения по актуальной теме.
- Исследование репликации или отчет о воспроизводимости

### Короткие статьи и выводы ACL

Площадки ACL имеют разные типы подачи заявок:

| Тип | Страницы | Что ожидается |
|------|-------|-----------------|
| **Длинная статья** | 8 | Полное исследование, сильные исходные данные, абляция |
| **Краткая статья** | 4 | Целенаправленный вклад: одно четкое утверждение с доказательствами |
| **Результаты** | 8 | Солидная работа, которая едва не пропустила основную конференцию |

**Стратегия коротких статей**: выберите ОДНО утверждение и тщательно его подтвердите. Не пытайтесь сжать длинную статью в 4 страницы — напишите другую, более целенаправленную статью.

## Типы бумаги, выходящие за рамки эмпирического машинного обучения

Основной поток, описанный выше, нацелен на эмпирические статьи по ОД. Другие типы бумаг требуют другой структуры и стандартов доказательств. Подробные инструкции по каждому типу см. в [references/paper-types.md](https://github.com/NousResearch/hermes-agent/blob/main/skills/research/research-paper-writing/references/paper-types.md).

### Теоретические статьи

**Структура**: Введение → Предварительные сведения (определения, обозначения) → Основные результаты (теоремы) → Наброски доказательства → Обсуждение → Полные доказательства (приложение).

**Ключевые отличия от эмпирических работ:**
- Вклад — это результат теоремы, границы или невозможности, а не экспериментальные числа.
- Раздел «Методы» заменен на «Предварительные результаты» и «Основные результаты».
- Доказательства – это доказательства, а не эксперименты (хотя эмпирическое подтверждение теории приветствуется)
- Эскизы корректуры в основном тексте, полные корректуры в приложении являются стандартной практикой.
- Экспериментальный раздел не является обязательным, но усиливает статью, если подтверждает теоретические предсказания.

**Принципы написания корректуры:**
- Формулируйте теоремы формально со всеми явными предположениями.
- Предоставьте интуицию, прежде чем формальные доказательства («Ключевое понимание...»)
- Эскизы-доказательства должны передавать основную идею на 0,5-1 странице.
– Используйте среду `\begin{proof}...\end{proof}`.
- Пронумеруйте предположения и укажите их в теоремах: «При предположениях 1-3,...»

### Обзорные/учебные материалы

**Структура**: Введение → Таксономия/Организация → Подробное освещение → Открытые проблемы → Заключение.

**Основные отличия:**
- Вклад – это организация, синтез и выявление открытых проблем, а не новые методы.
- Должен быть всеобъемлющим в пределах объема (рецензенты проверят наличие недостающих ссылок)
- Требуется четкая таксономия или организационная структура.
- Ценность возникает из связей между работами, которые не создают отдельные статьи.
- Лучшие площадки: TMLR (опросный трек), JMLR, Foundations and Trends in ML, ACM Computing Surveys.

### Контрольные документы

**Структура**: Введение → Определение задачи → Построение набора данных → Базовая оценка → Анализ → Назначение и ограничения.

**Основные отличия:**
- Вклад сам по себе является эталоном: он должен заполнить реальный пробел в оценке.
- Документация набора данных является обязательной, а не дополнительной (см. Таблицы данных, шаг 5.11).
- Должен продемонстрировать, что контрольный показатель является сложным (базовые показатели не перегружают его)
- Должен продемонстрировать эталонные меры того, что, как вы утверждаете, они измеряют (конструктная валидность)
- Лучшие площадки: наборы данных и тесты NeurIPS, ACL (справочные документы), LREC-COLING.

### Документы с изложением позиции

**Структура**: Введение → Предыстория → Тезис/аргумент → Подтверждающие доказательства → Контраргументы → Последствия.

**Основные отличия:**
- Вклад – это аргумент, а не результат
- Необходимо серьезно относиться к контраргументам.
- Доказательства могут представлять собой эмпирический, теоретический или логический анализ.
- Лучшие места проведения: ICML (позиционный трек), семинары, TMLR.

### Управление состоянием с помощью `memory` и `todo`

**`memory` инструмент** — сохранение ключевых решений (ограничено: ~2200 символов для MEMORY.md):


**`todo` инструмент** — детальное отслеживание прогресса:

```
todo("add", "Design constrained task experiments for Sonnet 4.6")
todo("add", "Run Haiku baseline comparison")
todo("add", "Draft Methods section")
todo("update", id=3, status="in_progress")
todo("update", id=1, status="completed")
```

**Протокол запуска сеанса:**
```
1. todo("list")                           # Check current task list
2. memory("read")                         # Recall key decisions
3. terminal("git log --oneline -10")      # Check recent commits
4. terminal("ps aux | grep python")       # Check running experiments
5. terminal("ls results/ | tail -20")     # Check for new results
6. Report status to user, ask for direction
```

### Мониторинг Cron с помощью `cronjob`

Используйте инструмент `cronjob`, чтобы запланировать периодические проверки эксперимента:

```
cronjob("create", {
  "schedule": "*/30 * * * *",  # Every 30 minutes
  "prompt": "Check experiment status:
    1. ps aux | grep run_experiment
    2. tail -30 logs/experiment_haiku.log
    3. ls results/haiku_baselines/
    4. If complete: read results, compute Borda scores, 
       git add -A && git commit -m 'Add Haiku results' && git push
    5. Report: table of results, key finding, next step
    6. If nothing changed: respond with [SILENT]"
})
```

**Протокол [SILENT]**: если с момента последней проверки ничего не изменилось, ответьте ровно `[SILENT]`. Это подавляет доставку уведомлений пользователю. Сообщайте только о реальных изменениях, о которых стоит знать.

**Отслеживание сроков**:
```
cronjob("create", {
  "schedule": "0 9 * * *",  # Daily at 9am
  "prompt": "NeurIPS 2025 deadline: May 22. Today is {date}. 
    Days remaining: {compute}. 
    Check todo list — are we on track? 
    If <7 days: warn user about remaining tasks."
})
```

### Шаблоны общения

**Когда уведомлять пользователя** (через прямой/окончательный ответ или цель cron `deliver:` для автоматических запусков):
- Экспериментальная партия завершена (с таблицей результатов)
- Неожиданное обнаружение или сбой, требующий принятия решения.
- Черновой раздел готов к рассмотрению.
- Приближение дедлайна с невыполненными задачами

**Когда НЕ уведомлять:**
- Эксперимент еще продолжается, новых результатов нет → `[SILENT]`
- Плановый мониторинг без изменений → `[SILENT]`
- Промежуточные этапы, не требующие внимания

**Формат отчета** — всегда включайте структурированные данные:
```
## Experiment: <name>
Status: Complete / Running / Failed

| Task | Method A | Method B | Method C |
|------|---------|---------|---------|
| Task 1 | 85.2 | 82.1 | **89.4** |

Key finding: <one sentence>
Next step: <what happens next>
```

### Точки принятия решений, требующие участия человека

Используйте `clarify` для целевых вопросов, если вас действительно заблокировали:

| Решение | Когда спрашивать |
|----------|-------------|
| Целевое место | Перед началом работы над статьей (влияет на пределы страниц и рамки) |
| Вклад в создание | Когда существует несколько допустимых кадров |
| Приоритет эксперимента | Когда в списке TODO больше экспериментов, чем позволяет время |
| Готовность подачи | Перед окончательной отправкой |

**НЕ спрашивайте** (проявите инициативу, сделайте выбор, отметьте):
- Выбор слов, порядок разделов
- Какие конкретные результаты выделить
- Полнота цитирования (черновик с тем, что вы найдете, обратите внимание на пробелы)

## Критерии оценки рецензента

Понимание того, что ищут рецензенты, помогает сосредоточить усилия:

| Критерий | Что они проверяют |
|-----------|----------------|
| **Качество** | Техническая надежность, обоснованные претензии, справедливые исходные данные |
| **Ясность** | Четкое письмо, воспроизводимое экспертами, последовательные обозначения |
| **Значимость** | Влияние на сообщество, улучшение понимания |
| **Оригинальность** | Новые идеи (не требует нового метода) |

**Оценка (6-балльная шкала NeurIPS):**
- 6: Strong Accept — новаторский, безупречный
- 5: Accept — технически надежно, сильно влияет
- 4: Пограничное принятие — надежная, ограниченная оценка.
- 3: Пограничный отказ – недостатки перевешивают
- 2: Отклонить — технические недостатки.
- 1: Сильное отклонение — известные результаты или этические проблемы.

См. [references/reviewer-guidelines.md](https://github.com/NousResearch/hermes-agent/blob/main/skills/research/research-paper-writing/references/reviewer-guidelines.md) для получения подробных рекомендаций, общих проблем и стратегий опровержения.

## Распространенные проблемы и решения

| Выпуск | Решение |
|-------|----------|
| Аннотация слишком общая | Удалите первое предложение, если оно может быть добавлено к любому документу по ОД. Начните с вашего конкретного вклада. |
| Введение превышает 1,5 страницы | Разделите фон на связанные работы. Пули с фронтальной загрузкой. |
| В экспериментах отсутствуют явные утверждения | Добавьте: «Этот эксперимент проверяет, является ли [конкретное утверждение]…» перед каждым из них. |
| Рецензенты считают, что за статьей трудно следить | Добавьте указатели, используйте последовательную терминологию, сделайте подписи к рисункам самостоятельными. |
| Отсутствует статистическая значимость | Добавьте планки ошибок, количество прогонов, статистические тесты, доверительные интервалы. |
| Расширение масштабов экспериментов | Каждый эксперимент должен соответствовать конкретному утверждению. Откажитесь от экспериментов, которые этого не делают. |
| Статья отклонена, необходимо отправить ее повторно | См. «Повторная подача на конференцию» на этапе 7. Решите проблемы рецензентов, не ссылаясь на рецензии. |
| Отсутствует более широкое заявление о воздействии | См. шаг 5.10. Большинство площадок требуют этого. «Отсутствие негативного воздействия» почти никогда не вызывает доверия. |
| Человеческую оценку критикуют как слабую | См. шаг 2.5 и [references/human-evaluation.md](https://github.com/NousResearch/hermes-agent/blob/main/skills/research/research-paper-writing/references/human-evaluation.md). Отчет о показателях соглашения, сведениях об аннотаторах, вознаграждении. |
| Рецензенты сомневаются в воспроизводимости | Выпустите код (шаг 7.9), задокументируйте все гиперпараметры, включите начальные значения и детали вычислений. |
| Теоретической статье не хватает интуиции | Перед формальными доказательствами добавляйте эскизы доказательств с пояснениями на простом языке. См. [references/paper-types.md](https://github.com/NousResearch/hermes-agent/blob/main/skills/research/research-paper-writing/references/paper-types.md). |
| Результаты отрицательные/нулевые | См. этап 4.3, посвященный обработке отрицательных результатов. Рассматривайте семинары, TMLR или рефрейминг как анализ. |
