# Проблема GitHub с запросом на извлечение

Превратите проблему GitHub в проверенный и проверенный PR. Этот навык предполагает сквозную дисциплину — проверку предпосылок, проверку дубликатов, исправления на уровне класса и честную отчетность CI; родственный GitHub и навыки разработки имеют собственную механику.

## Когда использовать

- «Исправьте проблему №123 и откройте PR».
— «Реализуйте этот запрос функции GitHub».
- «Перенесите этот баг из задачи в зеленый CI».

Не используйте для проверки существующего запроса на публикацию или ответа на вопрос по коду без запрошенных изменений.

## Процедура

### 1. Прочтите актуальный выпуск — тело И полную ветку.

Используйте `terminal` для запуска `gh issue view <N> --comments`. Тело представляет собой снимок времени подачи документов; самые новые комментарии сохраняют актуальное состояние: частичные исправления уже объединены, новый анализ первопричин, решения специалиста по сопровождению или вопросы, адресованные вам, которые меняют задачу. Также прочитайте инструкции по репозиторию (`AGENTS.md`, документы вклада) с `read_file`. Выполняется, когда известны запрошенное в данный момент поведение, нецели и любые оставшиеся без ответа вопросы цепочки.

### 2. Очистка существующих и дублирующихся работ.

Прежде чем писать что-либо, запустите `gh pr list --search "#<N>" --state all` плюс как минимум два варианта ключевого слова/синонима симптома (`gh pr list --search "<subsystem> <symptom>" --state open`). Популярные проблемы требуют множества независимых исправлений; создание дубликата приводит к потере работы и кредита. Также проверьте, исправила ли это недавняя фиксация: `git log --oneline -20 -- <relevant files>`. Готово, если вы знаете все открытые PR и недавние коммиты, касающиеся этой проблемы, или что их не существует.

### 3. Проверьте предпосылку на соответствие текущему коду и замыслу проекта.

Воспроизведите ошибку или продемонстрируйте отсутствующее поведение в текущей ветке по умолчанию с помощью неудачного теста или приспособления, используя `search_files` и `read_file` для отслеживания пути, о котором сообщается. Тогда проверьте второй вопрос: действительно ли «ошибка» является преднамеренной разработкой? Запустите `git log -p -S "<symbol>"` в коде, который проблема требует изменить, и прочитайте намерение исходного коммита — часто это недостающая ссылка или ограничение. Бросьте вызов устаревшей или ошибочной формулировке проблемы, вместо того, чтобы слепо реализовывать ее. Выполняется, когда основная причина или пробел в функциях продемонстрированы в текущем коде И изменение не противоречит преднамеренному замыслу.

### 4. Определите принятие и риск

Перечислите критерии приемки, интерфейсы, миграции/изменения состояния, совместимость, безопасность/конфиденциальность, развертывание и откат. Сопоставьте каждый критерий с тестом или явной проверкой. Выполняется, если проверка имеет конечный контракт.

### 5. Внедрите наименьшее полное изменение — и исправьте класс

Работайте над изолированной ветвью или рабочим деревом, загружая `systematic-debugging` или `test-driven-development`, когда их требует класс ошибок. Сначала добавьте регрессионные тесты, а затем реализуйте. Когда исправление готово, `search_files` для той же формы ошибки на сайтах вызовов одноуровневых узлов и исправьте весь класс в этом PR — неполное исправление, в результате которого известные одноуровневые элементы выходят из строя, хуже, чем отсутствие. Каждая измененная строка должна указывать на проблему; никакой уборки проезжавшего мимо автомобиля. Это делается, когда целевые тесты пройдены, первоначальный сбой больше не воспроизводится, а дочерние сайты исправляются или явно исключаются.

###6. Докажите укусы регрессионного теста (диверсия)

Временно восстановите старое поведение конкретной тестируемой функции, запустите новый тест и подтвердите, что он НЕ ПРОЙДЕН; затем восстановите исправление и подтвердите, что оно прошло. Регрессионный тест, проходящий с исправлением и без него, ничего не доказывает. Выполняется, когда тест явно не пройден для кода до исправления.

### 7. Запустите контроль качества репозитория, а затем немедленно откройте PR.

Запустите форматтер, lint, проверку типов и каноническую тестовую точку входа репозитория в затронутых областях; используйте `requesting-code-review` для различий. Затем сразу же нажмите и откройте PR — PR — это то, что отправляет CI, а задержка CI — это длинный полюс; не сидите на законченной работе. Загрузите `github-pr-workflow` для механики PR: обычная ветка/коммит, тело, связывающее проблему с проблемой, подходом, тестами, риском и исключениями. Прочтите PR и проверьте SHA головы, базу, заголовок и файлы. Выполняется, когда существует PR с заданным различием и работает CI.

### 8. Будьте честны и замкните петлю.

Просматривайте текущие проверки и журналы ошибок через `gh pr checks` / `gh run view --log-failed`. Отличайте сбои, вызванные вашими различиями, от ранее существовавших базовых сбоев или сбоев инфраструктуры — воспроизводите их в ветке по умолчанию, если не уверены, и повторяйте запуск один раз только для подлинных инфраструктурных сбоев. Никогда не говорите «зеленый», «объединенный» или «выпущенный» без живого подтверждения именно этого состояния. Когда появится PR, прокомментируйте проблему, указав ссылку на PR и однострочное объяснение, чтобы репортер получил прослеживаемое решение. Готово, когда состояние CI, оставшиеся блокировщики и цепочка проблем отражают реальность.

## Подводные камни

- Написание кода перед чтением комментариев к проблемам, поиском повторяющихся PR или чтением текущего кода.
— «Исправление» поведения, которое показывает исходный коммит, является преднамеренным.
- Исправление симптома на одном сайте вызова, в то время как на родственных сайтах сохраняется та же ошибка.
- Доставка регрессионного теста, который также проходит без исправлений.
- Открытие PR с невыполненными тестами или несвязанным оттоком форматирования.
- Утверждение о проблеме доставлено, поскольку существует PR.

## Проверка

- [ ] Прочитана полная тема темы; состояние новейшего комментария отражено в плане.
- [ ] Повторная PR-проверка с номером проблемы + 2 варианта ключевого слова.
- [ ] Помещение воспроизведено по текущему коду; Замысел проекта проверяется через историю git.
- [ ] Регрессионный тест оказался неудачным без исправления.
- [ ] Сайты вызовов братьев и сестер исправлены или явно исключены.
- [ ] Каждая измененная строка указывает на проблему.
- [ ] Состояние CI сообщается только на основе живых свидетельств; выпуск прокомментирован ссылкой на PR.
