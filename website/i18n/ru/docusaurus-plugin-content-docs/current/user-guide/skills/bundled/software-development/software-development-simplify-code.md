# Упрощение кода — параллельная проверка и очистка

Просмотрите свои недавние изменения в коде вместе с четырьмя целенаправленными рецензентами.
параллельно, обобщить полученные результаты и применить исправления, которые стоит применить.

**Это очистка, а не поиск ошибок.** Вы улучшаете качество
код, который уже работает — устранение дублирования, выравнивание ненужного
сложность, сокращение отходов и углубление пластырей. Не ходите на охоту
за корректность ошибок здесь; для этого и нужен `requesting-code-review`.

**Основной принцип:** Четыре узкоспециализированных рецензента превосходят одного широкого рецензента. Каждый
глубоко ищет в базе кода один класс проблем — повторное использование, качество,
эффективность, высота — не рассеивая своего внимания на всех четырех. Они
работать одновременно, поэтому вы платите за задержку одной проверки, а не четырех.

## Когда использовать

Активируйте этот навык, когда пользователь говорит что-либо из:

- «упростить» / «упростить мои изменения» / «упростить эти изменения»
- «проверь мой код» / «проверь мои последние изменения» / «очисти мои изменения»
- «/simplify» (если они переносят привычку Клода Кода)

Дополнительные модификаторы, которые может добавить пользователь — соблюдайте их:

- **Фокус:** «упростить фокус на эффективности» → запускать только средство проверки эффективности.
  (или взвесить агрегацию по отношению к нему). Признанные фокусы: `reuse`,
  `quality` (также принимает `simplification`), `efficiency`, `altitude`.
– **Прогон:** «упростить, но ничего не менять» / «просто сообщить» → запустить
  четыре рецензента, представляют выводы, НИЧЕГО не применяют. Спросите перед подачей заявки.
- **Область действия:** «упростить последнюю фиксацию» / «упростить поэтапное» / «упростить
  src/foo.py" → соответствующим образом сузьте источник различий (см. Этап 1).

НЕ запускайте это автоматически после каждого редактирования и не прикрепляйте его к концу несвязанного файла.
задачи. Это стоит жетонов четырех субагентов — вызывайте его только тогда, когда
явно спрашивает пользователь.

## Процесс

### Этап 1. Определите изменения

Запишите разницу для просмотра. Выберите источник по тому, что запросил пользователь, в
этот порядок по умолчанию:

```bash
# 1. Default: uncommitted working-tree changes (tracked files)
git diff

# 2. If that's empty, include staged changes
git diff HEAD

# 3. Scoped variants the user may request:
git diff --staged                 # "staged changes"
git diff HEAD~1                    # "the last commit"
git diff main...HEAD              # "this branch" / "my PR"
git diff -- src/foo.py            # specific file(s)
```

Если `git diff` и `git diff HEAD` пусты и репозиторий git отсутствует или отсутствует
изменения, вернитесь к файлам, явно названным пользователем или которые были
недавно созданные/отредактированные в этом сеансе. Если вы действительно не можете найти ничего
поменял код, скажи так и хватит — нечего упрощать.

Запишите полный текст различий. Обратите внимание на его размер: если он очень большой (скажем, >2000
измененные строки), предупреждают пользователя о том, что четыре субагента, каждый из которых несет полную разницу
будет перегружен токенами и предложит сократить его объем (для каждого каталога, для каждой фиксации)
прежде чем продолжить.

### Этап 2 — параллельный запуск четырех рецензентов

Используйте `delegate_task` **пакетный режим** — выполните все четыре задания за одно `tasks`
массив, чтобы они работали одновременно. Четыре — подходящее ответвление для этого паттерна;
это укладывается в бюджет `delegation.max_concurrent_children` по любому умолчанию
установить.

**Делегирование недоступно?** Если вы не можете позвонить `delegate_task` в этом
контекст (вы являетесь конечным субагентом, делегирование отключено или бюджет
исчерпан), НЕ пропускайте обзор и не сбрасывайте ракурсы. Проработать все четыре
рецензент последовательно рассматривает себя в этом контексте — тот же поиск
стандарты, тот же формат поиска. Затем четко скажите в своем окончательном резюме, что
это была однопроходная поточная проверка, а не параллельное разветвление, поэтому пользователь
знает, что на самом деле бежало.

Предоставьте **каждому** рецензенту **полные различия** (а не фрагменты — кросс-файл
проблемы скрываются в пробелах), а также абсолютный путь репо, чтобы они могли искать
более широкая кодовая база. Каждый рецензент получает `terminal`, `file` и `search`.
наборы инструментов (чтобы они могли `git`, `read_file` и `search_files`/grep).

Попросите каждого рецензента:
- Найдите доказательства в существующей кодовой базе (не делайте выводы только на основе различий).
- **Примените Chesterton's Fence:** прежде чем отмечать что-либо для удаления, запустите
  `git blame` на линии, чтобы понять, почему он существует. Если вы не можете определить
  первоначальная цель, отметьте ее `confidence: low` — не угадайте.
- Сообщайте о результатах в виде структурированных результатов с указанием конкретных затрат, достоверности,
  и риск:
  ```
  file:line → problem → cost (what's duplicated/wasted/harder to maintain) → suggested fix | confidence: high/medium/low | risk: SAFE/CAREFUL/RISKY
  ```
  Поле **стоимости** заставляет каждое открытие оправдывать себя – открытие, которое
  не могу сформулировать, чего на самом деле стоит проблема, вероятно, гнида.
  - **SAFE** = доказано, что не влияет на поведение (неиспользуемый импорт, закомментирован
    код, сквозные оболочки). Автоматически применять их.
  - **ВНИМАНИЕ** = улучшается без изменения семантики (переименовывает локальную переменную,
    сгладить вложенный тройной код, извлечь помощник). Подайте заявку с тестовой проверкой.
  - **РИСКОВЫЙ** = может изменить поведение или нарушить государственные контракты (N+1
    реструктуризация, переименование публичного API, изменение жизненного цикла памяти). Флаг для
    человеческая проверка — НЕ применяйте автоматически.
- Пропускайте нитки и отбивайте только стиль. Отмечайте только те вещи, которые существенно улучшаются
  код.

Достигните этих четырех целей (отбросьте все, что исключает фокус пользователя):

**Рецензент 1. Повторное использование кода**
> Просмотрите эту разницу на наличие кода, который дублирует функциональность, уже включенную в
> Кодовая база. Поиск служебных модулей, общих помощников и соседних файлов.
> (используйте search_files/grep) для существующих функций, констант или шаблонов
> новый код мог бы вызывать вместо переопределения. Флаг: новые функции
> которые дублируют существующие; проработанная вручную логика, которая существует в существующей утилите
> уже делает (ручное манипулирование строками/путями, пользовательские проверки окружения, специальные
> охранники типов, переработан парсинг). Для каждого назовите существующую вещь, чтобы
> Использование и где оно обитает.

**Рецензент 2. Качество кода**
> Просмотрите эту разницу на наличие проблем с качеством. Ищите: избыточное состояние (значения
> которые дублируют или могут быть получены из существующего состояния; кэши, которые не
> необходимо существовать); разрастание параметров (новые параметры прикреплены там, где функция
> надо было реструктуризировать); копипаста с вариациями (почти дубликат)
> блоки, которые должны иметь общую абстракцию); дырявые абстракции (разоблачающие
> внутренние компоненты, нарушающие существующую границу инкапсуляции); строкотипизированный
> код (необработанные строки, где константа/перечисление/реестр уже существует — проверьте
> канонические реестры перед пометкой); глубоко вложенные условные выражения (троичные
> цепочки, 3+-уровневые пирамиды if/else — сглаживание с защитными предложениями, ранняя версия
> возвращает или таблицу поиска); Шаблоны уклонов, генерируемые искусственным интеллектом (доп.
> комментарии, повторяющие очевидный код, например `// increment counter` выше `count++`;
> ненужные защитные проверки на ноль для уже проверенных входных данных; `as any`
> приведения типов в обход системы типов; шаблоны, несовместимые с остальными
> файл). Для каждого приведите конкретный рефакторинг.

**Рецензент 3. Эффективность**
> Просмотрите эту разницу на наличие проблем с эффективностью. Ищите: ненужную работу
> (избыточные вычисления, повторное чтение файлов, дублирование вызовов API, N+1
> шаблоны доступа); пропущенный параллелизм (независимые операции выполняются последовательно);
> раздувание горячих путей (тяжелая/блокирующая работа при запуске или путях каждого запроса);
> Антишаблоны TOCTOU (предварительная проверка существования перед операцией вместо выполнения
> операция и обработка ошибки); проблемы с памятью (неограниченный рост, отсутствие
> очистка, прослушивание/обработка утечек; долгоживущие обратные вызовы или объекты, созданные как
> замыкания, захватывающие всю включающую область — все, что захватывается
> остается живым до тех пор, пока жив объект, поэтому предпочитайте небольшой класс или
> структура явных полей, которая копирует только то, что ей нужно); слишком широкое чтение
> (загрузка целых файлов вместо фрагмента); тихие сбои (пустой catch
> блоки, игнорируются возвраты ошибок, `except: pass`, `.catch(() => {})` без
> обработка, пробелы в распространении ошибок — они скрывают ошибки и должны быть как минимум
> войдите, прежде чем проглотить). Для каждого из них укажите конкретное решение и объясните, почему оно необходимо.
> быстрее или безопаснее.

**Рецензент 4. Высота**
> Просмотрите эту разницу на наличие изменений, реализованных на неправильной глубине — пластыри
> накладывается поверх общей инфраструктуры вместо исправлений
> Сама инфраструктура. Признаки слишком поверхностного исправления: добавлен особый случай
> общий путь кода для обработки одного вызывающего объекта (ветвь `if (caller == X)`,
> проверка типа, аварийный люк с магическим значением); симптом исправлен при звонке
> сайт, в то время как сайты одноуровневых вызовов сохраняют тот же недостаток; обходной путь, наложенный на
> более ранний обходной путь; добавлена обертка, чтобы не касаться того, что
> действительно нуждается в изменении; конфигурация или флаги, введенные для маршрутизации
> сломанный дефолт вместо исправления дефолта. Для каждого определите
> основной механизм уклонения от изменения и описание более глубокого исправления —
> обобщить общий путь, исправить корневой путь по умолчанию или исправить всю ошибку
> класс — и честно отметьте, когда более глубокое исправление достаточно велико, чтобы
> это должно быть отдельной задачей, а не частью этой очистки. Прочтите
> сначала окружающий код и `git blame`: то, что выглядит как пластырь, на самом деле
> иногда намеренная граница (совместимые прокладки, поэтапные миграции,
> изоляция встроенного кода). Не отмечайте их.

### Этап 3. Обобщение и применение

Подождите, пока все четыре вернутся (пакетный режим возвращает их вместе).

1. **Объедините** результаты в один список, устраняя совпадения рецензентов —
   когда два открытия нацелены на одну и ту же линию или на один и тот же основной механизм,
   сложите их в один.
2. **Откажитесь от ложных срабатываний** — у вас больше всего контекста; тебе не обязательно
   Спорьте с рецензентом, просто молча высказывайте слабые или неправильные предложения.
3. **Разрешить конфликты.** Рецензенты могут не согласиться (Рецензент 1: «Используйте существующие
   util X»; Рецензент 3: «X медленный, встраивайте его»). Порядок разрешения по умолчанию:
   **правильность > заявленная пользователем направленность > читаемость/повторное использование > микропроизводительность.**
   Не применяйте «исправление» производительности, которое ухудшает ясность, если только путь не является действительно правильным.
   жарко. Когда два предложения являются взаимоисключающими и оба оправданы, выберите
   тот, который затрагивает меньше кода, и обратите внимание на альтернативу.
4. **Применяйте в порядке уровня риска:**
   - **SAFE first** (автоматическое применение): неиспользуемый импорт, закомментированный код,
     сквозные оболочки, избыточные утверждения типов. Запустите тесты после.
   - **ВНИМАНИЕ дальше** (применять с проверкой, по одному файлу): переименовывать.
     местные жители, выравнивают тройки, извлекают помощников, объединяют обманутых. Запуск тестов
     после каждого файла. Верните все эти разрывы.
   - **РИСКОВАННЫЙ последний** (пометка для проверки — НЕ применять автоматически): реструктуризация N+1,
     Изменения общедоступного API, исправления параллелизма, изменения в обработке ошибок. Настоящее время
     каждый с описанием риска и статусом покрытия тестированием. Высотные выводы
     обычно попадают сюда — углубление исправления означает прикосновение к общим
     инфраструктуры, поэтому представьте более глубокое исправление и позвольте пользователю решить
     стоит ли делать это сейчас или в качестве продолжения.
   Если пользователь выбрал пробный прогон, представьте все три уровня и ничего не применяйте.
5. **Убедитесь**, что вы ничего не сломали: запустите целевые тесты проекта на
   затронутые файлы (не полный набор) и повторно запустите любой линтер/тип, проверьте
   использует репо. Если исправление нарушает тест, отмените это исправление и сообщите о нем.
6. **Подведите итог** того, что вы изменили: краткий список примененных исправлений, сгруппированных по
   категория рецензента и уровень риска, а также любые выводы, которые вы намеренно пропустили
   и почему. Если вы использовали встроенный режим (без делегирования), сообщите об этом здесь.

## Подводные камни

– **Не расширяйте список более чем на 4.** Больше рецензентов означает больше затрат и больше.
  противоречивые предложения по примирению, а не по улучшению освещения. Четверо
  категории охватывают пространство.
– **Передавайте ВСЮ разницу каждому рецензенту.** Разделение разницы между рецензентами.
  противоречит дизайну — дублирование между файлами и N+1 появляются только с
  полная картина.
- **Рецензенты ищут, а не догадываются.** Повторное использование без указателя на
  существующая утилита («наверное, для этого есть помощник») — это шум. Требовать
  `file:line` доказательства; отказаться от выводов, в которых его нет.
- **Применить ≠ переписать.** Это очистка последних изменений пользователя, а не
  лицензия на рефакторинг всего модуля. Сохраняйте изменения в пределах различий
  коснулся плюс минимальные изменения окружения, необходимые для исправления. Высота
  результаты являются исключением, подтверждающим правило: когда правильное решение
  глубже, чем разница, ПОМЕЧИТЕ ее — не перестраивайте в одностороннем порядке общий
  механизм внутри прохода очистки.
- **Не увлекайтесь поиском ошибок.** Если рецензент обнаруживает подлинную
  правильность ошибки, сообщите об этом на видном месте — но отдельным пунктом «найдена ошибка»
  заметьте, не включены в исправления очистки. Проверка правильности - это другое
  пройти с различными стандартами проверки.
- **Соблюдайте соглашения проекта.** Если в репозитории есть AGENTS.md / CLAUDE.md /
  HERMES.md или конфигурацию линтера, добавьте эти правила в подсказки рецензента, чтобы
  предложения соответствуют стилю дома, а не борются с ним.
- **Большие различия нарушают контекст.** Если разница огромна, перед этим уменьшите ее масштаб.
  делегирование — четыре субагента, каждый из которых несет разницу в 5000 строк, обходятся дорого и
  может обрезаться.
- **Чрезмерное доверие к инструментам мертвого кода.** Флаг `knip`, `ts-prune` и `depcheck`.
  экспорт, который используется динамически (импорт на основе строк, отражение). Всегда
  Grep для имени символа перед удалением — отчет об очистке инструмента не является доказательством.
- **Переименование без проверки публичных контрактов.** Экспорт имен, маршрут API
  пути, имена столбцов БД и ключи конфигурации являются контрактами, даже если имя
  плохо, переименование ломает потребителей. Отмечайте изменения в государственном контракте как РИСКОВЫЕ; никогда
  автоматически переименовывайте их.
- **Удаление «ненужной» обработки ошибок.** Пустой блок catch или игнорируется.
  ошибка может быть преднамеренной — ошибка ожидаема и неопасна в том смысле, что
  контекст. Отметьте это, но не удаляйте; пусть человек решает.
- **Не каждый особый случай помогает.** Совместимые прокладки, поэтапная миграция,
  и слои изоляции вокруг кода производителя выглядят как нарушение высоты, но
  являются преднамеренным дизайном. Перед этим проверьте `git blame` и окружающие его комментарии.

## Похожие

Если ваша установка имеет навык `subagent-driven-development` (необязательно), он
охватывает дополнительный случай: параллельный обзор *во время* реализации, согласно
задача. Этот навык представляет собой отдельный этап очистки *постфактум*. Использование
`requesting-code-review` для шлюза безопасности/качества предварительной фиксации — это
охота за ошибками; это уборка.
