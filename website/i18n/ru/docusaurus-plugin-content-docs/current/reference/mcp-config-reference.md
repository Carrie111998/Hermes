# Справочник по конфигурации MCP

Эта страница представляет собой компактный справочный материал к основной документации MCP.

Концептуальные рекомендации см.:
- [MCP (Протокол контекста модели)](/user-guide/features/mcp)
- [Использовать MCP с Hermes](/guides/use-mcp-with-hermes)

## Форма корневой конфигурации

```yaml
mcp_servers:
  <server_name>:
    command: "..."      # stdio servers
    args: []
    env: {}

    # OR
    url: "..."          # HTTP servers
    headers: {}

    # Optional HTTP/SSE TLS settings:
    ssl_verify: true                # bool or path to a CA bundle (PEM)
    client_cert: "/path/to/cert.pem"  # mTLS client certificate (see below)
    # client_key: "/path/to/key.pem"  # optional, when key lives in a separate file

    enabled: true
    timeout: 120
    connect_timeout: 60
    supports_parallel_tool_calls: false
    tools:
      include: []
      exclude: []
      resources: true
      prompts: true
```

## Ключи сервера

| Ключ | Тип | Применяется к | Значение |
|---|---|---|---|
| `command` | строка | студия | Исполняемый файл для запуска |
| `args` | список | студия | Аргументы в пользу подпроцесса |
| `env` | картографирование | студия | Среда передана в подпроцесс |
| `url` | строка | HTTP | Удаленная конечная точка MCP |
| `headers` | картографирование | HTTP | Заголовки для запросов к удаленному серверу |
| `ssl_verify` | логическое значение или строка | HTTP | TLS-проверка. `true` (по умолчанию) использует системные центры сертификации, `false` отключает проверку (небезопасно) или строковый путь к пользовательскому пакету центров сертификации (PEM) |
| `client_cert` | строка или список | HTTP | Сертификат клиента mTLS. Строка = путь к файлу PEM, содержащему сертификат + ключ. Список `[cert, key]` = отдельные файлы. Список `[cert, key, password]` = зашифрованный ключ |
| `client_key` | строка | HTTP | Путь к закрытому ключу клиента, если `client_cert` — строка и ключ находится в отдельном файле |
| `enabled` | бул | оба | Полностью пропустить сервер, если false |
| `timeout` | номер | оба | Тайм-аут вызова инструмента в секундах (по умолчанию: `300`) |
| `connect_timeout` | номер | оба | Тайм-аут начального соединения в секундах (по умолчанию: `60`) |
| `protocol` | строка | оба | Согласование эпохи протокола: `auto` (по умолчанию — сначала устаревшее рукопожатие `initialize`, возврат к 28 июля 2026 г. `server/discover` зонду без сохранения состояния, когда сервер отклоняет рукопожатие как только современное), `stateless` (сначала зондирование `server/discover`; одна устаревшая повторная попытка) или `legacy` (только рукопожатие, без возврата) |
| `supports_parallel_tool_calls` | бул | оба | Разрешить одновременный запуск инструментов с этого сервера |
| `skip_preflight` | бул | HTTP | Обход отказоустойчивой проверки типа контента для допустимых конечных точек Streamable HTTP, HEAD/GET которых отвечает на тип контента, отличный от MCP (по умолчанию: `false`) |
| `transport` | строка | HTTP | Установите значение `sse`, чтобы использовать транспорт SSE вместо Streamable HTTP |
| `keepalive_interval` | номер | оба | Частота пинга активности в секундах (по умолчанию: `180`, минимальное значение — 5 с). Установите значение ниже TTL сеанса сервера для серверов, которые быстро собирают простаивающие сеансы GC |
| `idle_timeout_seconds` | номер | студия | Необязательная перезапуск сервера stdio после простоя (`0` отключается). Также может жить под отображением `lifecycle:` |
| `max_lifetime_seconds` | номер | студия | Необязательная перезапуск сервера stdio после устаревания (`0` отключается). Также может жить под отображением `lifecycle:` |
| `tools` | картографирование | оба | Политика фильтрации и утилит |
| `auth` | строка | HTTP | Метод аутентификации. Установите значение `oauth`, чтобы включить OAuth 2.1 с PKCE |
| `sampling` | картографирование | оба | Политика запросов LLM, инициируемых сервером (см. руководство MCP) |
| `elicitation` | картографирование | оба | Запросы пользовательского ввода, инициируемые сервером. `enabled` (по умолчанию `true`) и `timeout` в секундах (по умолчанию `300`). Запросы в режиме формы проходят через поверхность утверждения; URL-режим отклонен (см. руководство MCP) |
| `trust` | строка | оба | Уровень доверия: `full` (по умолчанию) или `untrusted`. На сервере `untrusted` каждый вызов инструмента с возможностью записи (любого инструмента без аннотации `readOnlyHint: true`) перед запуском требует одобрения пользователя через стандартную поверхность утверждения. `readOnlyHint` — это *подсказка*, предоставляемая сервером — лживый сервер может в лучшем случае пропустить одобрение инструментов, которые, как он утверждает, доступны только для чтения, и никогда не получить дополнительный доступ — поэтому отметьте любой сервер, который вы не полностью контролируете, как `untrusted`. Нераспознанные значения обрабатываются как `untrusted` (закрытие при отказе) |

## Ссылки на переменные среды

Строковые значения в любом месте записи сервера (`env`, `headers`, `args`, `url`, …) могут ссылаться на переменные среды с помощью `${VAR}` или формы SecretRef в стиле Cursor `${env:VAR}` — оба разрешаются в одну и ту же переменную, поэтому фрагменты MCP, скопированные из конфигураций Cursor/Claude, работают без изменений:

```yaml
mcp_servers:
  github:
    command: "npx"
    args: ["-y", "@modelcontextprotocol/server-github"]
    env:
      GITHUB_PERSONAL_ACCESS_TOKEN: "${env:GITHUB_TOKEN}"   # same as "${GITHUB_TOKEN}"
```

Значения разрешаются из области секрета активного профиля (обратно к среде процесса), поэтому поместите секрет в `~/.hermes/.env`. Неустановленная переменная сохраняет свой буквальный заполнитель.

### Контекстные переменные

Помимо переменных окружения, интерполируются также переменные контекста в стиле курсора (имена чувствительны к регистру):

| Переменная | Разрешается |
|---|---|
| `${userHome}` | Домашний каталог текущего пользователя |
| `${workspaceFolder}` | Корень рабочей области сеанса (cwd терминала сеанса, если он известен, в противном случае — cwd процесса) |
| `${workspaceFolderBasename}` | Базовое имя `${workspaceFolder}` |
| `${pathSeparator}` / `${/}` | Разделитель путей ОС (`os.sep`) |

```yaml
mcp_servers:
  filesystem:
    command: "npx"
    args: ["-y", "@modelcontextprotocol/server-filesystem", "${workspaceFolder}"]
    env:
      CACHE_DIR: "${userHome}${/}.cache${/}mcp"
```

Любая другая ссылка `${...}` попадает в поиск env-var, указанный выше.

## `tools` ключи политики

| Ключ | Тип | Значение |
|---|---|---|
| `include` | строка или список | Белый список инструментов MCP, встроенных в сервер. Записи могут быть точными именами или именами в стиле fnmatch (`*_radar_*`, `get_zones_*`) |
| `exclude` | строка или список | Собственные инструменты MCP сервера в черном списке. Та же семантика точного имени/глоба, что и `include` |
| `resources` | булообразный | Включить/выключить `list_resources` + `read_resource` |
| `prompts` | булообразный | Включить/отключить `list_prompts` + `get_prompt` |

## Фильтрация семантики

### `include`

Если установлен `include`, регистрируются только те собственные серверные инструменты MCP.

```yaml
tools:
  include: [create_issue, list_issues]
```

### `exclude`

Если `exclude` установлен, а `include` — нет, регистрируется каждый собственный серверный инструмент MCP, кроме этих имен.

```yaml
tools:
  exclude: [delete_customer]
```

### Приоритет

Если установлены оба параметра, побеждает `include`.

```yaml
tools:
  include: [create_issue]
  exclude: [create_issue, delete_issue]
```

Результат:
- `create_issue` по-прежнему разрешено
- `delete_issue` игнорируется, поскольку `include` имеет приоритет.

## Политика служебных инструментов

Hermes может зарегистрировать эти оболочки утилит для каждого сервера MCP:

Ресурсы:
- `list_resources`
- `read_resource`

Подсказки:
- `list_prompts`
- `get_prompt`

### Отключить ресурсы

```yaml
tools:
  resources: false
```

### Отключить подсказки

```yaml
tools:
  prompts: false
```

### Регистрация с учетом возможностей

Даже если `resources: true` или `prompts: true`, Hermes регистрирует эти служебные инструменты только в том случае, если сеанс MCP действительно предоставляет соответствующую возможность.

Итак, это нормально:
- вы включаете подсказки
- но утилиты подсказки не появляются
- потому что сервер не поддерживает подсказки

## `enabled: false`

```yaml
mcp_servers:
  legacy:
    url: "https://mcp.legacy.internal"
    enabled: false
```

Поведение:
- нет попыток подключения
- никаких открытий
- нет регистрации инструмента
- конфигурация остается на месте для последующего повторного использования

## Поведение пустого результата

Если фильтрация удаляет все собственные инструменты сервера и не зарегистрировано ни одного служебного инструмента, Hermes не создает пустой набор инструментов среды выполнения MCP для этого сервера.

## Примеры конфигов

### Белый список безопасного GitHub

```yaml
mcp_servers:
  github:
    command: "npx"
    args: ["-y", "@modelcontextprotocol/server-github"]
    env:
      GITHUB_PERSONAL_ACCESS_TOKEN: "***"
    tools:
      include: [list_issues, create_issue, update_issue, search_code]
      resources: false
      prompts: false
```

### Черный список полос

```yaml
mcp_servers:
  stripe:
    url: "https://mcp.stripe.com"
    headers:
      Authorization: "Bearer ***"
    tools:
      exclude: [delete_customer, refund_payment]
```

### Сервер документов только для ресурсов

```yaml
mcp_servers:
  docs:
    url: "https://mcp.docs.example.com"
    tools:
      include: []
      resources: true
      prompts: false
```

### Сертификат клиента TLS (mTLS)

Для серверов HTTP/SSE, которым требуется сертификат клиента, установите `client_cert` (и дополнительно `client_key`):

```yaml
mcp_servers:
  # Combined cert + key in a single PEM file
  internal_api:
    url: "https://mcp.internal.example.com/mcp"
    client_cert: "~/secrets/mcp-client.pem"

  # Separate cert and key files
  partner_api:
    url: "https://mcp.partner.example.com/mcp"
    client_cert: "~/secrets/client.crt"
    client_key: "~/secrets/client.key"

  # Encrypted key with a passphrase (3-element list form)
  bank_api:
    url: "https://mcp.bank.example.com/mcp"
    client_cert: ["~/secrets/client.crt", "~/secrets/client.key", "my-passphrase"]

  # Custom CA bundle (private CA / self-signed server)
  lab_api:
    url: "https://mcp.lab.local/mcp"
    ssl_verify: "~/secrets/lab-ca.pem"
    client_cert: "~/secrets/lab-client.pem"
```

Примечания:
- Пути поддерживают расширение `~`. Отсутствующие файлы быстро выходят из строя во время подключения с сообщением об ошибке на уровне сервера.
- `ssl_verify: false` полностью отключает проверку сертификата сервера. Не используйте это с реальными сервисами.
- Работает как с потоками HTTP, так и с SSE.

После изменения конфигурации MCP перезагрузите серверы с помощью:

```text
/reload-mcp
```

## Именование инструмента

Серверные инструменты MCP становятся:

```text
mcp__<server>__<tool>
```

Примеры:
- `mcp__github__create_issue`
- `mcp__filesystem__read_file`
- `mcp__my_api__query_data`

Служебные инструменты используют тот же шаблон префиксов:
- `mcp__<server>__list_resources`
- `mcp__<server>__read_resource`
- `mcp__<server>__list_prompts`
- `mcp__<server>__get_prompt`

Разделитель в виде двойного подчеркивания (`mcp__…__…`) соответствует соглашению, используемому Claude Code, Codex и OpenCode, и устраняет неоднозначность границы сервера/инструмента, даже если любой из компонентов содержит подчеркивания.

### Очистка имен

Любой символ, который не является буквой, цифрой или подчеркиванием (дефис, точка, пробел и т. д.) как в именах серверов, так и в именах инструментов, перед регистрацией заменяется знаком подчеркивания. Это гарантирует, что имена инструментов являются действительными идентификаторами для API вызова функций LLM.

Например, сервер с именем `my-api`, предоставляющий инструмент под названием `list-items.v2`, становится:

```text
mcp__my_api__list_items_v2
```

Помните об этом при написании фильтров `include` / `exclude` — используйте **оригинальное** имя инструмента MCP (с дефисами и точками), а не очищенную версию.

## аутентификация OAuth 2.1

Для HTTP-серверов, требующих OAuth, установите `auth: oauth` в записи сервера:

```yaml
mcp_servers:
  protected_api:
    url: "https://mcp.example.com/mcp"
    auth: oauth
```

Поведение:
- Hermes использует поток OAuth 2.1 PKCE MCP SDK (обнаружение метаданных, идентификация клиента, обмен токенами и обновление).
- При первом подключении открывается окно браузера для авторизации
- Токены сохраняются в `~/.hermes/mcp-tokens/<server>.json` и повторно используются в разных сеансах.
- Обновление токена происходит автоматически; повторная авторизация происходит только в случае сбоя обновления
- Применяется только к транспорту HTTP/StreamableHTTP (серверы на базе `url`).

### Идентификация клиента: CIMD и DCR

Hermes идентифицирует себя на серверах авторизации с помощью **Документа метаданных идентификатора клиента** (CIMD) — механизма, который в спецификации MCP `2026-07-28` принят вместо динамической регистрации клиента. Документ опубликован на
`https://nousresearch.github.io/hermes-agent/docs/oauth/client-metadata.json`, а этот URL-адрес *является* `client_id` — сервер авторизации извлекает его, чтобы узнать имя, логотип и разрешенные URI перенаправления Hermes. Ничего не регистрируется для каждой установки и ничего не зависит от пользователя.

Окончательный выбор остается за сервером авторизации: SDK отправляет URL-адрес документа как `client_id` только тогда, когда сервер объявляет `client_id_metadata_document_supported: true` в своих метаданных, а в противном случае регистрируется через DCR точно так же, как и раньше. DCR устарел в спецификации MCP, но по-прежнему используется почти на каждом развернутом сервере.

#### Порты обратного вызова

В документе объявлен фиксированный набор URI перенаправления обратной связи, а спецификация требует, чтобы URI перенаправления в запросе авторизации *точно соответствовал* одному из них — поэтому поток CIMD не может использовать случайный высокий порт, который обычно выбирает Hermes. Поэтому Hermes связывает обратный вызов с одним из портов `27890`–`27894`.

Этот вывод необходимо выбрать до того, как станут известны возможности сервера, поскольку URI перенаправления фиксируется в начале потока, в то время как метаданные сервера поступают только в середине процесса. Таким образом, Hermes закрепляет порт для любого потока, который *может* в конечном итоге использовать CIMD, и возвращается к случайному порту для остальных:

- Сервер, к которому Hermes подключался ранее, чьи кэшированные метаданные не рекламируют CIMD, сохраняет случайный порт, который он всегда использовал.
- Сервер, к которому Hermes никогда не обращался, получает закрепленный порт при первом входе в систему, поскольку угадывание - единственный способ использования CIMD.
- Все, что могло бы переместить обратный вызов в другое место, также возвращается: предварительно зарегистрированный `oauth.client_id`, `oauth.client_secret`, пользовательский `oauth.client_name` или `oauth.token_endpoint_auth_method`, переопределение `oauth.redirect_uri` или `oauth.redirect_port`, вход в систему с помощью информационной панели или рабочего стола, существующая регистрация клиента на диске или все пять портов, удерживаемые другими процессами.

Каждый закрепленный порт привязывается, как только он выбран и удерживается до тех пор, пока не произойдет перенаправление браузера, поэтому два одновременных входа в систему — второй профиль или другой сервер в одном процессе — не могут попасть на один и тот же прослушиватель.

#### Когда сервер отклоняет документ

Если сервер получает документ и отклоняет его в конечной точке *token* (`invalid_client`), Hermes регистрирует отказ, записывает его под `~/.hermes/mcp-tokens/<server>.cimd-off` и с этого момента использует DCR для этого сервера.

Сервер, который вообще не может получить или проверить документ, прерывает работу на конечной точке *авторизации*, прежде чем произойдет какое-либо перенаправление. Там нет никакого сигнала, который Гермес мог бы наблюдать, поэтому браузер показывает ошибку недопустимого клиента, и время входа в систему истекает через пять минут. Сообщение о тайм-ауте называет документ и указывает на `cimd: false`. Запуск `hermes mcp login <server>` очищает записанное отклонение, поэтому исправленный документ получает еще один шанс.

#### Дополнительные ключи для каждого сервера

```yaml
mcp_servers:
  protected_api:
    url: "https://mcp.example.com/mcp"
    auth: oauth
    oauth:
      client_metadata_url: "https://example.com/my-cimd.json"  # self-hosted document
      cimd: false                                              # force DCR
      user_agent: "My-MCP-Client/1.0"                          # token-request User-Agent
```

`client_metadata_url` должен быть URL-адресом HTTPS с путем (без исходного источника, без фрагментов, без информации о пользователе, без сегментов `.`/`..`), который возвращает `200` и `Content-Type: application/json` с **без перенаправления** — серверам авторизации запрещено следовать перенаправлениям при его получении. Hermes по-прежнему связывает свой обратный вызов с тем же диапазоном `27890`–`27894`, поэтому самостоятельный документ должен объявить все десять URI обратной связи (`http://127.0.0.1:<port>/callback` и `http://localhost:<port>/callback` для каждого порта), а его `client_id` должен быть собственным URL-адресом.

`user_agent` заменяет значение по умолчанию `User-Agent` библиотеки HTTP **только для запросов токенов-конечных точек** (обмен и обновление кода авторизации) — некоторые серверы авторизации и WAF отклоняют там значение по умолчанию `python-httpx/...`. Это никогда не применяется к трафику MCP или обнаружению OAuth, и никакие другие заголовки запроса токена не могут быть настроены. Пустые или нулевые значения игнорируются.

## Добавить ссылку на Гермес

Поставщики и документация MCP могут предложить кнопку ** «Добавить в Hermes»** одним щелчком мыши, которая открывает настольное приложение Hermes с предварительно заполненной конфигурацией сервера, что отражает схему `cursor://anysphere.cursor-deeplink/mcp/install` Cursor:

```text
hermes://mcp/install?name=NAME&config=BASE64
```

- `name` — имя сервера. Должно соответствовать `^[A-Za-z0-9._-]{1,64}$`.
- `config` — объект конфигурации сервера в формате **JSON в кодировке Base64url** (также принимается стандарт Base64). Декодированный JSON должен быть объектом либо со строковым полем `url` (только `http://`/`https://`), либо со строковым полем `command` и может содержать любой из ключей сервера, описанных выше. Полезные данные размером более 32 КБ отклоняются.

Пример (JavaScript):

```js
const config = { url: 'https://mcp.example.com/mcp' }
const link = `hermes://mcp/install?name=example&config=${btoa(JSON.stringify(config))
  .replace(/\+/g, '-').replace(/\//g, '_').replace(/=+$/, '')}`
```

Открытие ссылки никогда ничего не устанавливает само по себе: настольное приложение отображает диалоговое окно подтверждения с именем сервера и полной, красиво напечатанной конфигурацией (с дополнительным предостережением для серверов на базе `command`, на которых выполняется локальный процесс), и пользователь должен явно подтвердить это. Существующие имена серверов никогда не перезаписываются — пользователю предлагается переименовать или отменить.
