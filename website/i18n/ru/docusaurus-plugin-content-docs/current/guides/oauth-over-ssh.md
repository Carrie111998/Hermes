# OAuth через SSH/удаленные хосты

Некоторые провайдеры Hermes — **Spotify** и **удаленные серверы MCP** (Linear, Sentry, Atlassian, Asana, Figma, …) — используют поток OAuth *loopback redirect*. Сервер аутентификации перенаправляет ваш браузер на `http://127.0.0.1:<port>/callback`, чтобы крошечный HTTP-прослушиватель, запущенный Hermes, мог получить код авторизации.

Это прекрасно работает, когда Hermes и ваш браузер находятся на одном компьютере. Он ломается в тот момент, когда это не так: браузер вашего ноутбука пытается достичь `127.0.0.1` на **вашем ноутбуке**, но прослушиватель привязан к `127.0.0.1` на **удаленном сервере**.

Исправление — однострочная локальная пересылка SSH. Для серверов MCP на интерактивном терминале вы часто можете вместо этого вставить URL-адрес перенаправления обратно (без туннеля).

**xAI Grok OAuth (`xai-oauth`) использует код устройства OAuth**, а не обратный вызов — откройте распечатанный URL-адрес подтверждения в любом браузере и опрашивайте Hermes до одобрения. SSH-туннель не требуется. См. [xAI Grok OAuth](./xai-grok-oauth.md).

## TL;DR

```bash
# On your local machine (laptop), in a separate terminal:
ssh -N -L 43827:127.0.0.1:43827 user@remote-host

# In your existing SSH session on the remote machine:
hermes auth spotify --no-browser
# → Hermes prints an authorize URL. Open it in a browser on your laptop.
# → Your browser redirects to 127.0.0.1:43827/callback, the tunnel forwards
#   the request to the remote listener, login completes.
```

Hermes печатает точный порт, к которому он привязан, в строке `Waiting for callback on ...` — скопируйте его оттуда. Spotify по умолчанию использует порт `43827`.

## Каким провайдерам это нужно

| Провайдер | Шлейфовый порт | Туннель нужен? |
|----------|---------------|----------------|
| Спотифай | `43827` (по умолчанию) | Да, когда Гермес удален |
| Серверы MCP (`auth: oauth`) | автоматически выбирается для каждого сервера | Да, когда Hermes удален (или вставьте URL-адрес перенаправления) |
| `xai-oauth` (Грок СуперГрок) | н/д | Нет — поток кода устройства |
| `anthropic` (Клод Про/Макс) | н/д | Нет — процесс вставки кода |
| `openai-codex` (ChatGPT Plus/Pro) | н/д | Нет — поток кода устройства |
| `minimax`, `nous-portal` | н/д | Нет — поток кода устройства |

Если вашего провайдера нет в таблице, туннель вам не нужен.

## MCP-серверы

Удаленные серверы MCP (Linear, Sentry, Atlassian, Asana, Figma и т. д.) используют один и тот же поток перенаправления обратной связи. Hermes автоматически выбирает свободный порт для каждого сервера и печатает URL-адрес авторизации при запуске потока OAuth — либо при запуске (когда новый сервер появляется в `mcp_servers:`), либо при запуске `hermes mcp login <server>`.

У вас есть два способа завершить его с удаленного хоста:

**Вариант 1 — вставьте URL-адрес перенаправления обратно (настройки не требуется, работает где угодно).** На интерактивном терминале Hermes предложит вам вставить URL-адрес перенаправления вместе с запуском локального прослушивателя. После одобрения в вашем браузере при перенаправлении на `http://127.0.0.1:<port>/callback` будет отображаться ошибка соединения — это ожидаемо. Скопируйте **полный URL-адрес из адресной строки браузера** и вставьте его в командную строку Hermes:

```
  MCP OAuth: authorization required.
  Open this URL in your browser:

    https://mcp.linear.app/authorize?response_type=code&...

  Or paste the redirect URL here (or the ?code=...&state=... portion) and press Enter:
> https://mcp.linear.app/callback?code=abc123&state=xyz
  Got authorization code from paste — completing flow.
```

Также принимается пустая строка запроса `?code=...&state=...`. Это работает для любого сервера MCP с `auth: oauth` и не требует изменений конфигурации SSH.

**Вариант 2 — перенаправление порта SSH (так же, как Spotify).** Hermes печатает точный порт, к которому он привязан, в подсказке SSH-сеанса. Откройте отдельный терминал на своем ноутбуке:

```bash
ssh -N -L <port>:127.0.0.1:<port> user@remote-host
```

Затем откройте URL-адрес авторизации в браузере как обычно; перенаправление проходит через туннели, и слушатель подхватывает его. Используйте это, когда вам нужно, чтобы поток завершился автоматически (например, повторная аутентификация по сценарию, когда вы не можете вставить интерактивно).

**Подводный камень — гонка с перезагрузкой конфигурации в течение 30 секунд.** Если вы отредактируете `~/.hermes/config.yaml`, чтобы добавить сервер OAuth MCP из работающего сеанса Hermes, CLI автоматически перезагрузит соединения MCP с тайм-аутом в 30 секунд. Этого времени недостаточно для завершения интерактивного потока OAuth, и перезагрузка прекратится. Вместо этого используйте `hermes mcp login <server>` из нового терминала — он не имеет такого ограничения и ждет целых 5 минут, пока вы вставите его обратно.

## Почему слушатель не может просто привязать 0.0.0.0

Spotify и большинство серверов MCP OAuth проверяют параметр `redirect_uri` на соответствие белому списку. Оба требуют формы обратной связи (`http://127.0.0.1:<exact-port>/callback`). Привязка прослушивателя к `0.0.0.0` или другому порту приведет к тому, что сервер аутентификации отклонит запрос из-за несоответствия redirect_uri. Туннель SSH сохраняет URI обратной связи нетронутым на всем протяжении.

## Шаг за шагом: одиночный переход по SSH

### 1. Запустите туннель с вашего локального компьютера.

```bash
# Spotify (port 43827)
ssh -N -L 43827:127.0.0.1:43827 user@remote-host
```

`-N` означает «не открывайте удаленную оболочку, просто держите туннель открытым». Оставьте этот терминал включенным на время входа в систему.

### 2. В отдельном сеансе SSH выполните команду auth

```bash
ssh user@remote-host
hermes auth spotify --no-browser
```

Hermes обнаруживает сеанс SSH, пропускает автоматическое открытие браузера и печатает URL-адрес авторизации плюс строку `Waiting for callback on http://127.0.0.1:<port>/callback`.

### 3. Откройте URL-адрес в локальном браузере.

Скопируйте URL-адрес авторизации с удаленного терминала и вставьте его в браузер на своем ноутбуке. Подтвердите экран согласия. Сервер аутентификации перенаправляется на `http://127.0.0.1:<port>/callback`. Ваш браузер попадает в туннель, запрос пересылается удаленному прослушивателю, и Hermes печатает `Login successful!`.

Вы можете снести туннель (Ctrl+C в первом терминале), как только увидите строку успеха.

## Шаг за шагом: через поле перехода

Если вы доберетесь до Гермеса через бастион или прыжковый хост, используйте встроенный в SSH `-J` (ProxyJump):

```bash
ssh -N -L 43827:127.0.0.1:43827 -J jump-user@jump-host user@final-host
```

Это связывает SSH-соединение через хост перехода без помещения порта обратной связи в сам блок перехода. Локальный `127.0.0.1:43827` на вашем ноутбуке подключается напрямую к `127.0.0.1:43827` на конечном удаленном хосте.

Для более старых версий OpenSSH, не поддерживающих `-J`, полная форма выглядит так:

```bash
ssh -N \
    -o "ProxyCommand=ssh -W %h:%p jump-user@jump-host" \
    -L 43827:127.0.0.1:43827 \
    user@final-host
```

## Mosh, tmux, ssh ControlMaster

Туннель является свойством базового соединения SSH. Если вы используете Hermes внутри `tmux` во время сеанса mosh, роуминг mosh не поддерживает пересылку `-L`. Откройте *отдельный* простой сеанс SSH **только** для туннеля `-L` — это соединение должно оставаться активным во время процесса аутентификации. Ваш интерактивный сеанс mosh/tmux может продолжать нормально работать Hermes.

Если вы используете `ssh -o ControlMaster=auto`, переадресация портов в мультиплексном соединении разделяет время жизни ведущего устройства. Перезапустите мастер, если туннель не открывается:

```bash
ssh -O exit user@remote-host
ssh -N -L 43827:127.0.0.1:43827 user@remote-host
```

## Устранение неполадок

### `bind [127.0.0.1]:43827: Address already in use`

Что-то на вашем ноутбуке уже использует этот порт. Либо предыдущий туннель отключился некорректно, либо его тоже прослушивает местный Гермес. Найдите и убейте преступника:

```bash
# macOS / Linux
lsof -iTCP:43827 -sTCP:LISTEN
kill <PID>
```

Затем повторите команду `ssh -L`.

### Время авторизации истекло в ожидании локального обратного вызова

Перенаправление так и не вернулось к удаленному прослушивателю. Убедитесь, что туннель все еще активен (`ssh -N` не отображает выходные данные, поэтому посмотрите на терминал, с которого вы его запустили), убедитесь, что вы использовали порт из последней строки `Waiting for callback on ...` (Hermes может автоматически подключиться, если предпочтительный порт занят), перезапустите туннель, если необходимо, и повторно запустите команду аутентификации.

### Токены попадают не в тот `~/.hermes`

Токены записываются от имени пользователя Linux, который запустил `hermes auth add ...`. Если ваш шлюз/служба systemd работает от имени другого пользователя (например, `root` или выделенного пользователя `hermes`), выполните аутентификацию как **этого** пользователя, чтобы токены попадали в его `~/.hermes/auth.json`. `sudo -u hermes -i` или эквивалент.
