# Собственный вход в систему на рабочем столе (RFC 8252)

Когда приложение Hermes Desktop подключается к **закрытому шлюзу** (хостовому или
самостоятельная панель мониторинга, которая находится за провайдером OAuth), она может войти в систему двумя
способы:

1. **Встроенный вход в систему (RFC 8252)** — приложение открывает **реальный системный браузер**,
   вы подтверждаете согласие в браузере, которому уже доверяете, и приложение получает его токены
   хранит файлы только для владельца в своем каталоге пользовательских данных (необязательно зашифрованном).
   с помощью брелока вашей ОС — Настройки → Шлюз). **Нет встроенного веб-просмотра, нет
   файлы cookie сеанса браузера.** Это значение по умолчанию, когда шлюз
   поддерживает это.
2. **Встроенный вход (устаревший вариант)** — приложение открывает небольшую внутреннюю часть приложения.
   окно браузера и записывает файлы cookie сеанса шлюза. Используется автоматически
   когда шлюз представляет собой более старую сборку, которая не поддерживает встроенный вход.

Вы не выбираете между ними — приложение определяет, что поддерживает шлюз, и
выбирает лучший. На этой странице объясняется, что происходит и почему.

## Почему встроенный вход

Встраивание браузера в собственное приложение для OAuth имеет хорошо известные недостатки:
страница входа не видит существующий сеанс браузера (поэтому вы повторно вводите
учетные данные и повторное выполнение MFA), менеджеры паролей и пароли часто не работают,
и приложение полагается на чтение файла cookie сеанса из частного веб-просмотра. RFC
8252 («OAuth 2.0 для собственных приложений») — это лучшая отраслевая практика, позволяющая избежать
все это: **проведите авторизацию в системном браузере и передайте приложению его
собственные токены.**

В частности, для Hermes встроенный вход означает:

- **Нет встроенного веб-просмотра.** Авторизация происходит в Safari/Chrome/
  Firefox/Edge — что бы вы ни использовали — с вашими логинами, расширениями и
  ключи в целости.
- **Файлы cookie сеанса отсутствуют.** Приложение содержит **токен доступа OAuth** (недолговечный).
  и **токен обновления**, хранящийся как файлы, доступные только владельцу, зашифрованные при хранении с помощью
  ваша связка ключей ОС (Electron `safeStorage`), когда включается связка ключей с подпиской
  Настройки → Шлюз включен. Вызовы REST и билеты WebSocket аутентифицируются.
  с заголовком `Authorization: Bearer`, а не банкой cookie.

## Как это работает

```
Desktop app                Gateway (/auth/native/*)          Nous Portal (IDP)
   │ 1. open loopback 127.0.0.1:<random port>
   │ 2. system browser ─►  /auth/native/authorize
   │    (PKCE challenge)    (starts the normal PKCE login) ─► /oauth/authorize
   │                        ◄──── code ──── /auth/callback ◄──┘
   │                        3. mint one-time gateway code
   │ ◄─ 302 127.0.0.1/cb?code=… ─┘
   │ 4. POST /auth/native/token (code + PKCE verifier)
   │ ◄─ 5. { access_token, refresh_token, expires_at } ───────┘
   │ 6. store in local token store; use Bearer for REST + WS tickets
```

Шлюз **посредник** в потоке: это сервер авторизации *для
настольное приложение* и клиент OAuth *вышестоящему поставщику удостоверений* (Nous
Портал). Это необходимо, поскольку восходящий `client_id` и разрешен
URI перенаправления привязаны к собственному источнику шлюза — настольное приложение не может быть
прямой клиент Портала. Настольные компьютеры по-прежнему получают полную версию RFC 8252.
опыт: собственная пара PKCE, собственное перенаправление обратной связи и принадлежащие ему токены.

**PKCE (RFC 7636)** защищает переход по шлейфу: одноразовый код шлюза
бесполезно без средства проверки кода, которое никогда не покидает приложение. Код
одноразовые и недолговечные.

## Обнаружение возможностей и откат

Рабочий стол считывает общедоступную конечную точку `/api/status` шлюза, которая объявляет
массив `auth_flows`:

| `auth_flows` значение | Значение |
|----|---------|
| `["cookie", "native_pkce"]` | Шлюз поддерживает встроенный вход → приложение использует его |
| `["cookie"]` | Шлюз поддерживает только устаревший поток → приложение использует встроенный веб-просмотр |
| *(поле отсутствует)* | Старый шлюз → приложение использует встроенный веб-просмотр |

Если встроенный вход объявлен, но не удается по локальной причине, например ценная бумага
инструмент блокирует прослушиватель обратной связи, или вы закрываете вкладку браузера — приложение
**автоматически возвращается к встроенному потоку**, чтобы вы по-прежнему могли войти в систему.

## Жизненный цикл токена

- **Токен доступа**: кратковременный (минуты). Отправлено как `Authorization: Bearer`
  при каждом вызове REST и при создании билета WebSocket.
- **Токен обновления**: более продолжительный, вращающийся. Когда токен доступа находится рядом
  по истечении срока действия приложение вызывает `/auth/native/refresh` для ротации обоих токенов, затем
  обновляет свое хранилище токенов.
- **Срок действия терминала**: если токен обновления устарел (истёк срок действия/отозван/
  обнаружено повторное использование), приложение очищает сохраненные токены и запрашивает новый
  войти в систему.
- **Выход**: очищает как сохраненные собственные токены, так и все устаревшие сеансы.
  cookie для этого шлюза.

## Для операторов шлюза

Собственный вход доступен автоматически на любом закрытом шлюзе с
Зарегистрирован поставщик интерактивных сеансов. Никакой настройки не требуется —
Маршруты `/auth/native/*` и реклама `auth_flows` являются частью
Подсистема аутентификации приборной панели. Поставщики OAuth (например, встроенный поставщик **Nous**)
брокер восходящего перенаправления IDP; поставщики паролей (например, прилагаемые
**плагин базовой аутентификации**) поместите системный браузер на `/login` шлюза.
вместо этого используется форма учетных данных — именно это позволяет менеджерам паролей ОС (macOS
пароли и т. д.) автоматически заполняет форму, чего не может сделать ни один встроенный веб-просмотр на рабочем столе.
предложение. Учетные данные только с помощью токена (например, слив) не являются интерактивным входом в систему и не
не рекламировать `native_pkce`.

Соответствующие конечные точки (все общедоступные, загрузочная версия предварительной аутентификации, такая же, как существующая
`/auth/*` Маршруты OAuth):

- `GET /auth/native/authorize` — запускает вход через PKCE через посредника.
- `POST /auth/native/token` — обменивает шлейфовый код + верификатор на токены
- `POST /auth/native/refresh` — ротация токенов из токена обновления приложения.
