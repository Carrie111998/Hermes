# Внутреннее устройство Cron

Подсистема cron обеспечивает выполнение задач по расписанию — от простых одноразовых задержек до повторяющихся заданий cron-выражения с внедрением навыков и кросс-платформенной доставкой.

## Ключевые файлы

| Файл | Цель |
|------|---------|
| `cron/jobs.py` | Модель задания, хранилище, атомарное чтение/запись на `jobs.json` |
| `cron/scheduler.py` | Цикл планировщика — обнаружение выполнения заданий, отслеживание повторений |
| `tools/cronjob_tools.py` | Регистрация и обработка инструмента `cronjob` для работы с моделью |
| `gateway/run.py` | Интеграция шлюза — тиканье cron в длительном цикле |
| `hermes_cli/cron.py` | CLI `hermes cron` подкоманды |

## Модель планирования

Поддерживаются четыре формата расписания:

| Формат | Пример | Поведение |
|--------|---------|----------|
| **Относительная задержка** | `30m`, `2h`, `1d` | Однократный, срабатывает по истечении указанного времени |
| **Интервал** | `every 2h`, `every 30m` | Повторяющиеся пожары через определенные промежутки времени |
| **Выражение Cron** | `0 9 * * *` | Стандартный синтаксис cron из 5 полей (минута, час, день, месяц, день недели) |
| **Временная метка ISO** | `2025-01-15T09:00:00` | Одиночный выстрел, выстрел в точное время |

Поверхность, обращенная к модели, представляет собой один инструмент `cronjob` с операциями в стиле действий: `create`, `list`, `update`, `pause`, `resume`, `run`, `remove`.

## Хранилище заданий

Задания хранятся в `~/.hermes/cron/jobs.json` с семантикой атомарной записи (запись во временный файл, затем переименование). Каждая запись о работе содержит:

```json
{
  "id": "a1b2c3d4e5f6",
  "name": "Daily briefing",
  "prompt": "Summarize today's AI news and funding rounds",
  "schedule": {
    "kind": "cron",
    "expr": "0 9 * * *",
    "display": "0 9 * * *"
  },
  "skills": ["ai-funding-daily-report"],
  "deliver": "telegram:-1001234567890",
  "repeat": {
    "times": null,
    "completed": 42
  },
  "state": "scheduled",
  "enabled": true,
  "next_run_at": "2025-01-16T09:00:00Z",
  "last_run_at": "2025-01-15T09:00:00Z",
  "last_status": "ok",
  "created_at": "2025-01-01T00:00:00Z",
  "model": null,
  "provider": null,
  "script": null
}
```

### Состояния жизненного цикла задания

| Государство | Значение |
|-------|---------|
| `scheduled` | Активен, выстрелит в следующее запланированное время |
| `paused` | Приостановлено — не будет срабатывать, пока не возобновится |
| `completed` | Повторный отсчет исчерпан или произведен одиночный выстрел |
| `running` | Выполняется в данный момент (переходное состояние) |

### Обратная совместимость

Более старые задания могут иметь одно поле `skill` вместо массива `skills`. Планировщик нормализует это во время загрузки — одиночный `skill` повышается до `skills: [skill]`.

## Время выполнения планировщика

### Тиковый цикл

Планировщик запускается периодически (по умолчанию: каждые 60 секунд):

```text
tick()
  1. Acquire scheduler lock (prevents overlapping ticks)
  2. Load all jobs from jobs.json
  3. Filter to due jobs (next_run <= now AND state == "scheduled")
  4. For each due job:
     a. Set state to "running"
     b. Create fresh AIAgent session (no conversation history)
     c. Load attached skills in order (injected as user messages)
     d. Run the job prompt through the agent
     e. Deliver the response to the configured target
     f. Update run_count, compute next_run
     g. If repeat count exhausted → state = "completed"
     h. Otherwise → state = "scheduled"
  5. Write updated jobs back to jobs.json
  6. Release scheduler lock
```

### Интеграция шлюза

В режиме шлюза **триггер** cron (часть, которая решает, *когда* выполнить задание
пожары — «Ось B») выбирается через подключаемый провайдер `CronScheduler`.
шлюз вызывает `resolve_cron_scheduler()` (`cron/scheduler_provider.py`) и запускает
`start()` разрешенного поставщика в выделенном фоновом потоке вместе с
отдельный поток обслуживания шлюза.

Активный провайдер выбирается конфигурационным ключом `cron.provider`:

- **пусто (по умолчанию)** → встроенный `InProcessCronScheduler`, который запускает
  исторический цикл внутри процесса, вызывающий `scheduler.tick()` каждые 60 секунд. Это
  по байтам идентично поведению предварительного поставщика.
- **именованный поставщик** (например, `chronos`, поставщик управляемого cron для
  развертывания с масштабированием до нуля) → обнаружено от `plugins/cron_providers/<name>/` или
  `$HERMES_HOME/plugins/<name>/`.

Если именованный поставщик отсутствует, не загружается или сообщает `is_available() ==
False`, преобразователь возвращается к встроенному с предупреждением — **cron
никогда не остается без триггера.** Встроенный провайдер находится в ядре
(`cron/scheduler_provider.py`), а не в `plugins/`, поэтому резервный вариант не может быть
случайно удалил.

Что *означает* «увольнение» (выполнение задания + доставка) остается неизменным и разделяется всеми
провайдеров — он остается в `scheduler.run_job()`/`scheduler._deliver_result()`.
Поставщик контролирует только триггер, но не выполнение.

В режиме CLI задания cron запускаются только при выполнении команд `hermes cron` или во время активных сеансов CLI.

### Управляемый cron (Chronos) для масштабирования до нуля

На размещенных шлюзах может работать поставщик **Chronos** (`cron.provider: chronos`).
вместо встроенного тикера. Chronos позволяет простаивающему шлюзу **масштабироваться до нуля**
и по-прежнему запускать задания cron: вместо 60-секундного цикла внутри процесса (который
поддерживать процесс активным), он просит инфраструктуру Nous активировать ровно **один
удалось выполнить один выстрел за задание в реальное время следующего пожара**. Во время пожара Ноус
вызывает шлюз обратно через аутентифицированный веб-перехватчик (`POST /api/cron/fire`);
шлюз выполняет задание по тому же пути `run_one_job`, что и встроенный,
затем перевооружает следующий однозарядник. Между пожарами процесс можно полностью остановить —
он просыпается только от настоящего огня, а не от периодического таймера.

Поток (управляемый планировщик предоставляется Nous; агент не имеет
учетные данные планировщика):

```
create/update a cron job
  → Chronos asks Nous to arm a one-shot at the job's next_run_at
      (authenticated with the agent's existing Nous token)
  → at fire time Nous calls the gateway: POST {callback_url}/api/cron/fire
      (authenticated with a short-lived, purpose-scoped Nous-minted JWT)
  → the gateway verifies the token, claims the job (store compare-and-set so
    multi-replica deployments fire at-most-once), runs it, and re-arms the next
    one-shot
```

Конфигурация (все несекретные; на размещенных агентах Nous устанавливает их во время подготовки):

| ключ | смысл |
|---|---|
| `cron.provider` | `chronos` для активации (пусто = встроенный тикер) |
| `cron.chronos.portal_url` | Базовый URL-адрес Nous (постановка на охрану + эмитент пожарного токена) |
| `cron.chronos.callback_url` | собственный общедоступный базовый URL-адрес шлюза для входящих пожаров |
| `cron.chronos.expected_audience` | огненная аудитория этого агента |
| `cron.chronos.nas_jwks_url` | набор ключей для проверки входящего токена пожарной безопасности |

Если Chronos настроен неправильно или агент не вошел в Nous,
`resolve_cron_scheduler()` возвращается к встроенному тиккеру (зарегистрированное предупреждение) —
cron никогда не теряет свой триггер. Повторяющиеся задания перевооружаются после каждого пожара; `repeat`-Н
задания прекращаются полностью, когда счетчик исчерпан (нет потерянных одноразовых заданий). Полный
Контракт агента↔Ноуса проживает в `docs/chronos-managed-cron-contract.md`.

### Свежая изоляция сеанса

Каждое задание cron выполняется в совершенно новом сеансе агента:

- Нет истории разговоров из предыдущих запусков
- Нет памяти о предыдущих запусках cron (постоянная память — MEMORY.md/
  USER.md — загружается, как и любой другой агент, поэтому устойчивые настройки и
  факты переносятся; контекст диалога для каждого запуска — нет)
- Подсказка должна быть автономной — задания cron не могут задавать уточняющие вопросы.
- Набор инструментов `cronjob` отключен (защита рекурсии).

## Вакансии, требующие навыков

Задание cron может прикрепить один или несколько навыков через поле `skills`. Во время выполнения:

1. Навыки загружаются в указанном порядке
2. Содержимое SKILL.md каждого навыка вводится как контекст.
3. Приглашение к заданию добавляется как инструкция к задаче.
4. Агент обрабатывает объединенный контекст навыка + подсказку.

Это позволяет многократно использовать проверенные рабочие процессы без вставки полных инструкций в подсказки cron. Например:

```
Create a daily funding report → attach "ai-funding-daily-report" skill
```

### Задания, поддерживаемые скриптами

Джобс также может прикрепить скрипт Python через поле `script`. Сценарий запускается *перед* каждым поворотом агента, и его стандартный вывод вводится в приглашение в качестве контекста. Это обеспечивает сбор данных и шаблоны обнаружения изменений:

```python
# ~/.hermes/scripts/check_competitors.py
import requests, json
# Fetch competitor release notes, diff against last run
# Print summary to stdout — agent analyzes and reports
```

Тайм-аут сценария по умолчанию составляет 3600 секунд (1 час). `_get_script_timeout()` устраняет ограничение посредством трехуровневой цепочки:

1. **Переопределение на уровне модуля** — `_SCRIPT_TIMEOUT` (для тестов/monkeypatching). Используется только в том случае, если оно отличается от значения по умолчанию.
2. **Переменная среды** — `HERMES_CRON_SCRIPT_TIMEOUT`
3. **Конфигурация** — `cron.script_timeout_seconds` в `config.yaml` (читается через `load_config()`)
4. **По умолчанию** — 3600 секунд (1 час).

Этот таймаут ограничивает **только сценарий предварительного запуска**, а не агента. Задания, основанные на навыках/LLM, выполняются с отдельным бюджетом на основе *бездействия* (`HERMES_CRON_TIMEOUT`, по умолчанию 600 секунд простоя, `0` = неограниченно) — они могут выполняться в течение нескольких часов, пока они продолжают вызывать инструменты или потоковые токены, и прекращаются только после настроенного периода простоя при отсутствии активности. Сценарии отправляются в постоянный пул потоков (не удерживаемый блокировкой), поэтому долго выполняющийся сценарий не блокирует запуск других срочных заданий.

### Восстановление провайдера

`run_job()` передает настроенных пользователем резервных поставщиков и пул учетных данных в экземпляр `AIAgent`:

- **Резервные поставщики** — считывает `fallback_providers` (список) или `fallback_model` (устаревший dict) из `config.yaml`, что соответствует шаблону `_load_fallback_model()` шлюза. Передается как `fallback_model=` в `AIAgent.__init__`, что нормализует оба формата в резервную цепочку.
- **Пул учетных данных** — загружается через `load_pool(provider)` из `agent.credential_pool` с использованием разрешенного имени поставщика среды выполнения. Проходит только в том случае, если у пула есть учетные данные (`pool.has_credentials()`). Включает ротацию ключей одного и того же поставщика при ошибках 429/ограничения скорости.

Это отражает поведение шлюза — без него агенты cron не смогут выполнить ограничения скорости, не пытаясь восстановиться.

## Модель доставки

Результаты заданий Cron могут быть доставлены на любую поддерживаемую платформу.

Простое имя платформы (`slack`, `telegram`, …) доставляется на настроенный **домашний канал** этой платформы. Чтобы указать **конкретный** пункт назначения, добавьте цель после двоеточия: `platform:<target>`. Цель определяется во время запуска (а не при создании задания), поэтому задание может назвать пункт назначения на платформе, которая еще не подключена, и начать доставку, как только оно появится в сети.

Большинство платформ также принимают необязательную тему/тему в качестве третьего сегмента: `platform:<chat_id>:<thread_id>`.

| Цель | Синтаксис | Пример |
|--------|--------|---------|
| Происхождение чата | `origin` | Доставить в чат, где была создана вакансия |
| Локальный файл | `local` | Сохранить в `~/.hermes/cron/output/` |
| Телеграмма | `telegram`, `telegram:<chat_id>`, `telegram:<chat_id>:<thread_id>`, `telegram:@username` | `telegram:-1001234567890:17585` |
| Раздор | `discord`, `discord:#channel`, `discord:<channel_id>`, `discord:<channel_id>:<thread_id>` | `discord:#engineering` |
| слабый | `slack`, `slack:#channel`, `slack:<channel_id>`, `slack:<channel_id>:<thread_ts>` | `slack:#engineering` |
| Матрица | `matrix`, `matrix:<!room_id:server>`, `matrix:<@user:server>` | `matrix:!abc123:example.org` |
| Фейшу | `feishu`, `feishu:<chat_id>`, `feishu:<chat_id>:<thread_id>` | `feishu:oc_abc123def` |
| WhatsApp | `whatsapp`, `whatsapp:<jid>`, `whatsapp:+<E.164>` | `whatsapp:123456@g.us` |
| Сигнал | `signal`, `signal:group:<id>`, `signal:+<E.164>` | `signal:group:aBcD==` |
| СМС | `sms`, `sms:+<E.164>` | `sms:+<E.164 number>` |
| Электронная почта | `email`, `email:<address>` | `email:alerts@example.com` |
| Вэйсинь | `weixin`, `weixin:<wxid>` | `weixin:wxid_abc123` |
| Самое важное | `mattermost` или `mattermost:<channel_id>` | Голое имя доставляет на дом Mattermost |
| Домашний помощник | `homeassistant` или `homeassistant:<conversation>` | Голое имя способствует разговору HA |
| ДинТок | `dingtalk` или `dingtalk:<chat_id>` | Голое имя доставляется на DingTalk |
| ВеКом | `wecom` или `wecom:<chat_id>` | Голое имя доставляет WeCom |
| Синие пузыри | `bluebubbles` или `bluebubbles:<chat_guid>` | Голое имя доставляется в iMessage через BlueBubbles |
| QQ-бот | `qqbot` или `qqbot:<chat_id>` | Голое имя доставляется в QQ (Tencent) через официальный API v2 |
| Чат с ботами | `bot-chat` или `bot-chat:<profile>` | Внедрить в канонический чат-бот локального профиля (бот отвечает) |

Платформы в первой группе имеют явный, проверенный целевой синтаксис — именованные каналы (`#channel`), темы/потоки, идентификаторы комнат/пользователей, идентификаторы групп или номера телефонов. Остальные платформы принимают общую форму `platform:<chat_id>` (значение после двоеточия дословно используется в качестве идентификатора назначения); простое имя платформы всегда доставляется на домашний канал.

**Именованные каналы** (`slack:#engineering`, `discord:#engineering` или понятное имя, например `slack:engineering`) разрешаются по каталогу каналов, который шлюз создает из подключенных адаптеров, поэтому для успешного разрешения имени шлюз должен обнаружить канал; необработанные идентификаторы (`slack:C0123ABCD45`) всегда работают.

Для **тем Telegram** используйте `telegram:<chat_id>:<thread_id>` (например, `telegram:-1001234567890:17585`). Для **Slack threads** третий сегмент — это `thread_ts` родительского сообщения (например, `slack:C0123ABCD45:1700000000.000100`), поэтому он применяется только при ответе на существующее сообщение.

**Бот-чат** (`bot-chat`, `bot-chat:<profile>`) — это локальная псевдоплатформа, а не адаптер шлюза: планировщик обеспечивает доставку, запуская `hermes [-p <profile>] chat --in ~ -c "Bot Chat" --create-if-missing -Q --query-file <tmp>` — ту же полосу, которую используют сообщения между агентами в режиме бота, — поэтому выходные данные поступают как реальный входящий ход в каноническом бот-чате профиля, и бот запускает на нем полную активацию агента (безопасность по альтернативному варианту по конструкции; это командная полоса чата, а не зеркало стенограммы). Голый токен нацелен на собственный профиль задания; именованная форма проверяется на соответствие `~/.hermes/profiles/` при создании снова и снова во время запуска и никогда не разрешается на разных компьютерах. Цели бот-чата исключаются из токена маршрутизации `all` и из предварительной проверки доставки (учетные данные шлюза не используются). Таймаут подпроцесса для каждой доставки составляет `cron.bot_chat_delivery_timeout_seconds` (по умолчанию 600).

### перенос ответа

По умолчанию (`cron.wrap_response: true`) поставки cron обертываются:
- Заголовок, идентифицирующий имя и задачу cron.
- Нижний колонтитул, указывающий, что агент не может видеть доставленное сообщение в разговоре.

Префикс `[SILENT]` в ответе cron полностью подавляет доставку — это полезно для заданий, которым требуется только запись в файлы или выполнение побочных эффектов.

### Изоляция сеанса

Доставки Cron НЕ отражаются в истории сеансов шлюза. Они существуют только в собственном сеансе задания cron. Это предотвращает нарушения чередования сообщений в беседе целевого чата.

## Защита рекурсии

В сеансах Cron отключен набор инструментов `cronjob`. Это предотвращает:
- Запланированное задание по созданию новых заданий cron.
- Рекурсивное планирование, которое может привести к резкому увеличению использования токенов.
- Случайное изменение графика работы внутри задания.

## Блокировка

Планировщик использует межпроцессную блокировку на основе файлов (`fcntl.flock` в Unix, `msvcrt.locking` в Windows), чтобы предотвратить двукратное выполнение одного и того же пакета выполняемых заданий при перекрывающихся тактах — даже между внутрипроцессным тикером шлюза и автономным вызовом `hermes cron`/ручным вызовом `tick()`. Если блокировку невозможно получить, `tick()` немедленно возвращает 0.

## Интерфейс командной строки

Интерфейс командной строки `hermes cron` обеспечивает прямое управление заданиями:

```bash
hermes cron list                    # Show all jobs
hermes cron create                  # Interactive job creation (alias: add)
hermes cron edit <job_id>           # Edit job configuration
hermes cron pause <job_id>          # Pause a running job
hermes cron resume <job_id>         # Resume a paused job
hermes cron run <job_id>            # Trigger immediate execution
hermes cron remove <job_id>         # Delete a job
```
